## What was built on 2026-10-05

**Submission (the optional signed-in route).**
- `src/submit.rs` (new): `submission_security(host, port, tls)` (RFC 8314: port 465 or `tls:
  "implicit"` = TLS from the first byte; any other port = STARTTLS, required; no encryption only with
  STARTTLS off AND the server on this computer - a password never goes unencrypted to another
  computer); `submit(target, from, recipients, message)` over lettre's blocking `SmtpConnection`:
  rustls with the RustCrypto provider (installed once as the process default; lettre's
  `rustls-no-provider` asks for one) and the Mozilla roots plus the settings' extra CA; EHLO;
  STARTTLS; the sign-in `auth::choose_submission` picks from the EHLO AUTH line (PLAIN, else LOGIN
  for a password; XOAUTH2 for a token, only when offered); XOAUTH2's error challenge (Google's way)
  is answered with the empty line so the server's 535 comes back; MAIL / one RCPT per recipient /
  DATA, each recipient's outcome as micromail's `RecipientOutcome` (so the outbox records every route
  alike); the message goes byte for byte (lettre's own CRLF.CRLF is not doubled). `SubmitFailure::
  Waits` (refused sign-in, no usable mechanism, no STARTTLS, TLS cannot be set up) vs `Unreachable`
  (no connection, broken). The secret appears in no result, no log, no file.
- `send.rs`: `SendRoute::Submission` (`{"kind":"submission"}`) = the account's own `smtp` server from
  `account.json` with its user name and kind of secret; `SendSettings::sign_in` (the IMAP secret, never
  saved); `TlsPolicy::Implicit` (`"implicit"`; micromail's routes take it as required STARTTLS);
  `Transport::submit` (the real transport is now `Network`: micromail + lettre); `helo_name` shared
  with micromail's config. A mail that waits for the user (no password in memory, a refused sign-in,
  a setting that cannot work) is NO attempt and due again at once (the next Send / Receive); an
  unreachable server backs off as before; the provider's answers teach the policy list nothing.
- `sending.rs`: `ROUTE_CHOICES` - "Directly" (default), "Through an SMTP server", "Through my
  provider's server (sign in)"; `SendingForm::{submission, route_index, choose_route}`; implicit TLS

- `bin/azmail_send.rs`: `--submission`, `--password-env VAR` (the secret from the environment, never
  the command line), `--tls implicit`.
- `scripts/azmail_smtp_sink.py`: also a submission server - `--auth USER=SECRET`, `--auth-mechs`,
  `--implicit-tls`; AUTH offered only on an encrypted connection when it has a certificate (as Gmail

**`send.rs`** - direct delivery:
- The outbox keeps the message UNSIGNED; every attempt signs it with the key in memory. An account that
  signs but whose key has not come from the keyring yet WAITS (queued, the attempt not counted, due again
  at once) - never sent unsigned. Sent keeps the message as it went out (signed).
- A signed mail is tried directly even where only a SHIPPED default asks for a relay (gmail.com,
  googlemail.com, yahoo.com - those defaults were about unsigned mail from home); a learned refusal still
  holds it back (`PolicyList::holds_back(domain, signed)`).
- Refusals are learned WITH THEIR CAUSE (`RefusalCause` in `send_policy.json`: `home_address` - Spamhaus
  PBL and other home-address lists, Microsoft S3150 / 5.7.606, Yahoo [BL21]; `no_reverse_dns` - Gmail
  5.7.25, Postfix "cannot find your reverse hostname"; `not_authenticated` - 5.7.26 / SPF / DKIM / DMARC)
  and explained in words on the recipient ("example.net refuses mail sent straight from a home Internet
  connection (its answer names a list of home addresses such as Spamhaus PBL): it needs a relay (...)").
- PORT 25: when no exchanger of a domain can even be connected to (no SMTP reply at all), AzMail probes
  big providers' exchangers on port 25 (`gmail-smtp-in.l.google.com:25`,
  `outlook-com.olc.protection.outlook.com:25`, first IPv4 + first IPv6 address, 6 s each). All found in
  DNS and none connectable = this connection blocks port 25: recorded as `port25: {open: false, checked,
  detail}` in `send_policy.json`; every direct mail then waits ("this Internet connection blocks outgoing
  mail on port 25 (many home providers do): the mail waits in the Outbox until it can go through a
  relay") and the probe is repeated after an hour (a laptop on another network). Any server's answer
  records port 25 as open. This is exactly the list the later relay fallback reads.

## How the user tries it with a real account (direct + DKIM)

Requirements: an address at a domain of your OWN (you can edit its DNS), an IMAP mailbox for it (any
hoster), and a connection whose outgoing port 25 is open (AzMail tells you if not).
1. Build: `cargo build --release -p AzMail` (and `--bin azmail-send` for the CLI). Start `target/release/AzMail`.
2. File > Add Account: name, address, the IMAP password (or app password). Incoming: the hoster's IMAP
   server (filled in for known providers). Sending: **Directly**, tick **Sign my mail with DKIM**, keep the
   domain (your address's) and selector (`azmail<yyyymm>`), click **Create a key**. The page shows the record.
3. At your DNS provider add a TXT record: name `<selector>._domainkey` (some providers want the full
   `<selector>._domainkey.<domain>`), value `v=DKIM1; k=rsa; p=...` exactly as shown (zone files: the
   quoted-strings line). Add `_dmarc.<domain>` TXT `v=DMARC1; p=none; rua=mailto:<you>` if there is none.
   Keep SPF ending in `~all`.
4. Finish / Save (the key goes into the system keyring), wait a few minutes, Account Settings > Sending >
   **Check DNS** until it says "published, with this key".
5. Send / Receive once (F9) after each start - it reads the password and the DKIM key from the keyring.
   Then New E-mail, send to a Gmail or Outlook address you can read.
6. Check: Gmail "Show original" must say `DKIM: 'PASS' with domain <your domain>` and `DMARC: 'PASS'`;
   or send to `check-auth@verifier.port25.com` (an automatic report comes back). If the mail stays in the
   Outbox, its reason says why (port 25 blocked, a home-address list, no PTR) and `send_policy.json` in
   the account folder records it - that is the list the relay fallback will use.
CLI alternative: `azmail-send --data <AzMail folder> --account <id> --from you@yourdomain --to x@gmail.com
--direct --dkim-generate /tmp/k.pem` prints the record to publish (a CLI-made key lives in that file).

## How the user tries the signed-in route (submission) with a real account

For an address at a big provider (no domain of your own), or when port 25 is blocked. AzMail signs
in to the provider's outgoing server with the same secret it reads mail with.
1. Make an app password (your normal password does not work over IMAP / SMTP for these):
   - Gmail: turn on 2-Step Verification, then myaccount.google.com/apppasswords (16 letters).
   - iCloud: account.apple.com > Sign-In and Security > App-Specific Passwords.
   - Fastmail: Settings > Privacy & Security > Manage app passwords (give it IMAP + SMTP).
   - Outlook.com / Microsoft 365: passwords are mostly refused; tick "OAuth access token" in the
     wizard and paste an access token (scopes IMAP.AccessAsUser.All and SMTP.Send) - tokens expire
     after about an hour, so this is for trying only.
2. File > Add Account: the address and the app password; the servers fill in (smtp.gmail.com 465,
   smtp.mail.me.com 587, smtp.fastmail.com 465, smtp.office365.com 587; any other domain gets
   `smtp.<domain>` 465 - check it on the Servers page).
3. Sending page: choose **Through my provider's server (sign in)** (Directly stays the default),
   keep "Use STARTTLS" ticked. The note names the server and how it is encrypted (465: from the first
   byte; 587: STARTTLS before the sign-in). DKIM may stay off: the provider signs as its own domain.
4. Finish; Send / Receive once (F9) after each start - it reads the password from the system
   keyring; a mail sent before that waits in the Outbox ("waiting for the password ...") and goes at
   that Send / Receive.
5. New E-mail to an address you can read. A refused sign-in shows the server's words in the mail's
   reason ("smtp.gmail.com port 465 refused the sign-in (535 5.7.8 Username and Password not
   accepted)") and the mail waits - enter the app password again under Account Settings; nothing is
   retried in a loop.
CLI alternative: `AZMAIL_PW=<app password> azmail-send --data <AzMail folder> --account <id> --from
you@gmail.com --to x@example.org --submission --password-env AZMAIL_PW` (the account folder needs
its `account.json`, which the wizard writes).

## Engine gaps seen (not fixed here)

- HTTPBLOCK: `HttpRequestConfig::download_bytes_blocking` exists in azul-layout but is not in
  api.json, so an app Thread cannot get bytes back itself: AzMail's download Thread calls
  `download_bytes` (blocking the worker) and the bytes come back through the request queue on the UI
  thread, which hands them to a second (decode) Thread. Exporting `download_bytes_blocking` (and
  `http_get_blocking`) would let one Thread fetch and decode.
- SCANORDER: `Xml::scan_external_resources` walks with a LIFO stack (siblings come out in reverse
  document order) and scans every text node for `url(` as CSS (a `<style>`'s text is scanned twice:
  as a text node and by the `style` arm), so a resource can be listed twice and a sentence mentioning
  `url(...)` becomes a resource. AzMail de-duplicates and takes the fetch ORDER from the sanitizer.

- FONTREG: no runtime "register a font under a family name": `FontManager::register_named_font` exists,
  but nothing in `CallbackInfo` reaches it, and the DLL swaps the fc_cache on every regenerate_layout
  (`replace_fc_cache` -> `drop_dangling_memory_faces`), which would drop such a face; a runtime list
  re-registered after each swap (like `register_builtin_mock_fonts`) is needed.
- `HttpRequestConfig::download_bytes` / `http_get` run synchronously inside the calling callback on
  desktop (`download_bytes_blocking` then `request::complete`): an app that downloads from a callback
  blocks its UI. Calling them from an azul Thread works (the request queue is a global Mutex).

## micromail notes (micromail untouched)

- `format_dkim_dns_record` publishes `p=` as PKCS#1 RSAPublicKey (what RFC 6376's text says) - OpenDKIM's
  verifier (`d2i_PUBKEY`) reads only SubjectPublicKeyInfo, which is what every provider publishes; AzMail
  writes its own record (SPKI).
- Connection failures come back as `Deferred { reply: None, reason: "could not connect to <host> port
  <port>" }`; a structured "unreachable" status would let a caller tell DNS failures from refused / timed
  out connections without a probe.
