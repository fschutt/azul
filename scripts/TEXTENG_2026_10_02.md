## 1. `line-height: 19px` pitched 19.55px

Root cause: the STRUT. A line box is the union of the text's inline box and
the strut (CSS 2.2 s10.8.1), each put around the baseline by half-leading from
its own ascent A and descent D: A' = A + (lh - A - D)/2. The glyphs took A/D
from their real font; `translate_to_text3_constraints` gave the strut a
synthetic 0.8em / 0.2em. For any font with another split the two boxes sit at
different heights around the same baseline and the union is taller than the
line-height by |(A - D)/2 - 0.3em|: Times (0.891 / 0.216) at 11pt = 0.0375em
= 0.55px exactly. (Same for numbers and `normal` with fonts whose ascent is
below 0.8em, e.g. Helvetica.)

Fix (`layout/src/text3/cache.rs`, `layout/src/solver3/fc.rs`):
- `FontManager::first_available_font_metrics(&FontStack) -> Option<LayoutFontMetrics>`:
  the stack's first face covering U+0020 (CSS Fonts 4 s5.5) through the
  shaper's chain cache; `FontStack::Ref` directly.
- `translate_to_text3_constraints` reads the IFC root's computed
  `StyleProperties` (`get_style_properties_cached`) and takes the strut's
  ascent/descent from that style's first available font (descent exactly as
  `get_item_vertical_metrics` takes a glyph's); 0.8/0.2 only until the face is
  loaded. Its `line_height` is now that same style's (it re-read the cascade:
  a node that declared none came out 1.2em there but `normal` on its runs).
- x-height / cap-height stay approximated (TODO kept).
- `flex_intrinsic_text::text_box_edge_cap_alphabetic_trims_to_the_metrics`
  derived its numbers from the 0.8/0.2 approximation; it now names
  `Azul Mock Mono`, whose real metrics are exactly those.

## 2. `StyleLineHeight` keeps its unit; em / % inherit as the computed length

- css `text.rs`: `#[repr(C, u8)] enum StyleLineHeight { Normal (default), Number(FloatValue),
  Length(PixelValue), Percentage(PercentageValue) }` with `computed(font_px)`
  (em / % -> px length), `is_font_relative_length()`, `resolve_px(font, root
  font, vw, vh) -> Option<f32>` (THE resolution; `None` = normal),
  `interpolate`, Display/Debug/PrintAsCssValue. The parser takes `normal`,
  numbers, percentages and every length (rem, vw, vh, vmin, vmax included) and
  rejects negatives (`-1` used to alias `1px`).
- css `compact_cache.rs`: `CompactLineHeight { Normal, Factor, Px, Uncached }`,
  `encode_line_height_factor` (x1000), `encode_line_height_px` (-px x 100: to
  the hundredth - tenths pitched 14pt lines 18.7px apart), `decode_line_height`;
  `I16_AUTO` = "read the cascade" (viewport units, out of range) instead of
  dropping to `normal` / clamping. `get_line_height` returns `CompactLineHeight`.
- core `compact.rs`: `encode_line_height(lh, font_px, root_px)`; the
  inheritance builder tracks each node's own winning declaration and
  re-encodes it after its font size is resolved, so children copy px;
  viewport-unit line-heights set `uses_viewport_units`.
- core `prop_cache.rs`: `compute_inherited_values` computes an em / %
  line-height against the node's final font size (`compute_font_relative_line_height`),
  and the raw parent-to-child propagation drops such a WINNER
  (`inherits_its_computed_length`) so descendants read the computed length.
- layout `getters.rs`: `get_used_line_height(styled_dom, node, state, font_px,
  viewport) -> text3 LineHeight` is the ONE reader (compact fast path, cascade
  otherwise): `get_style_properties`, `vertical-align: <percentage>`, the empty
  inline box (fc), the editing-host strut (fc) and the empty-editable caret
  (display_list). `get_line_height_value` is gone. The strut and the caret
  read `normalized()` as a factor, so ANY absolute line-height gave them a 1px
  height; `empty_editable_caret_rect` now takes the line-height in px.
- codegen: `FormatAsRustCode` and the `Lower` impl for the enum
  (`lower_types.rs` hand-edited exactly as `gen_codegen_lowering.py` emits a
  tagged enum - regenerate after api.json to confirm a no-op).

## 3. Inline-block inside an inline span

Two bugs, both fixed:
- `collect_inline_span_recursive` looked the nested element up among the IFC
  ROOT's layout children, but the tree builder puts an inline box's children
  under the inline box's own node - so it was never found: the box was
  dropped from the line, never laid out, never positioned. Now it looks among
  the span's own layout children and hands those to nested spans.
- When found, it sized the box from its max-content width alone (no width,
  height, padding, border), took its content height, used a throw-away text
  cache and never mapped it for positioning. Now the span branch calls the
  same `measure_atomic_inline` as the other two branches and maps the shape;
  the driver places a mapped box at the IFC content box + the text3 offset
  whatever its layout parent is (`process_inflow_child`).
- Twins found: the atomic-inline measurement existed THREE times in
  `collect_and_measure_inline_content_impl` / `collect_inline_span_recursive`;
  the anonymous-wrapper copy had drifted (it still resolved the box against
  `constraints.containing_block_size`, the root's own containing block, not
  `atomic_inline_containing_block`). One helper now: `fc::measure_atomic_inline`.

## 4. Formats in the text-edit report; the caret's pending format (D1)

Engine API for RTE (the apps' adoption is RTE's):
- `DocumentTextEdit.runs: TextFormatSpanVec` - ordered, disjoint byte spans of
  `text`, each `TextFormatSpan { start: u32, end: u32, formats: TextFormatSet }`,
  the formats the text carries OVER the block element's own style (a heading's
  bold is the heading's, not reported). Text in no span is plain. A space or
  line break carries the formats its neighbours share. Covers typing after a
  format toggle at a collapsed caret, an inline formatted paste, and typing
  into formatted text. An app can REPLACE a block's runs from `text` + `runs`.
- `TextFormatSet { bold, italic, underline, strikethrough }` (core `events.rs`,
  next to `TextFormat`; `is_empty / has / set / intersection`), `TextFormat::ALL`.
- `CallbackInfo::get_typing_formats(node) -> OptionTextFormatSet` (and
  `LayoutWindow::typing_formats`): the caret's PENDING format - the run under
  the caret with the toggled typing style on top (Ctrl+B in plain text: bold;
  inside bold text: not bold). For toolbar pressed-state (A3.5).
- `LayoutWindow::unsynced_text_edits()` now returns `Vec<DocumentTextEdit>`
  (was a `(node, String, u64)` tuple); two layout tests read the fields.
- Internals: `overlay::inline_content_formats` (walks the items exactly like
  `flatten_inline_content`), `FormatOverrides::formats_over(style, base)`;
  `toggle_text_format` and `typing_formats` share `caret_run_style` +
  `typing_overrides_at`.

How RTE adopts it (AzNotes / AzMail / AzWriter): on `TextChanged`, for each
edit set the block's runs from `edit.text` split at `edit.runs` (formats ->
the model's B/I/U/S flags); delete AzNotes' `Typing` mirror (editor.rs
505-536) and AzMail's flattening `sync_text` (A3.1); toolbar B/I/U pressed
state from `get_typing_formats(host)` (AzWriter's blind flip, A3.5).

## Behaviour changes that may move existing pins

- Line boxes with a system font whose A/D split is not 0.8/0.2 are now
  exactly `line-height` tall (were up to ~0.05em taller); `normal` lines of
  fonts with ascent < 0.8em (Helvetica) lose the strut's excess. Pins built on
  the old values would move by < 1px per line.
- Absolute line-heights are exact to 0.01px (were 0.1px).
- `line-height` without a declaration on the IFC root but declared elsewhere
  in the DOM: the strut's line-height is now `normal` (was 1.2em).
- Atomic inlines in an anonymous IFC wrapper resolve percentages against the
  IFC's content box (was the root's containing block).
- An editable's empty caret / strut with an absolute line-height is that tall
  (was 1px).
