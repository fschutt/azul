# Size budgets for the SHIPPED libazul artifacts, in bytes.
#
# WHY THIS FILE EXISTS: CI already printed artifact sizes in half a dozen
# places - `after local-symbol strip:`, `$before -> $after bytes`, and into the
# release HTML - but nothing ever FAILED on a size regression. Reporting is not
# a ratchet: a change that adds 40 MB to libazul.so lands green and is found
# months later. This file turns the reporting into a gate.
#
# FORMAT:  <target-triple-or-*>  <basename-glob>  <max_bytes>
# The first line whose target AND glob both match wins, so put specific
# targets above `*`. Blank lines and `#` comments are ignored.
#
# PROVENANCE: the first version of this file (0d3b63eb5, 2026-09-05) set every
# number to 1.5x the size the artifact had in the shipped 0.2.0 release, as a
# deliberately loose first ceiling. The first CI run that reached the gate
# (master 34144083957, 2026-09-07) supplied the real numbers, and 1.5x was
# BELOW reality: libazul.so is 52,851,208 bytes against 33,970,016 in 0.2.0,
# a 1.56x growth over the several hundred commits since (widgets, text3,
# the LuaJIT by-reference twins, the pdf/audio/camera surfaces). So:
#   * artifacts with a measured current size are budgeted at ~1.15x of it
#     (the ratchet the first version promised once numbers existed);
#   * cross-compiled targets that have no measurement yet (their builds
#     failed to compile in that run) are budgeted at 1.8x their 0.2.0 size =
#     the observed 1.56x growth times the same 1.15 headroom. Tighten each
#     to 1.15x of its actual size when a run reports it.
# Every line carries the number it was derived from.
#
# RAISING A BUDGET IS A DELIBERATE, REVIEWABLE COMMIT. That is the point: the
# size change shows up in the diff with a reason next to it, instead of
# silently in a release artifact.
