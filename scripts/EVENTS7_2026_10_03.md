## 1. What was built

### 1.1 A pointer event in a VirtualView page bubbles out through its host (brief item 1)

Root cause: both dispatchers - the shells' `dispatch_events_propagated` (dll `common/event.rs`) and the e2e
runner's twin (`layout/src/e2e/runner.rs`) - planned a `Hover` listener's callbacks themselves: a whole dom's
callback map per event, propagation inside `event.target.dom` only. The target of a click on page content is
the deepest node across doms - a node of the CHILD dom - so the page's host and everything around it in the
parent dom never heard it (MEETDRIVE6: a double-click on a drive tile's capacity bar, a `ProgressBar` =
VirtualView, did not open the drive).

- core `events.rs`: `get_event_path(target, parent_of, host_of)` - the propagation path ROOT FIRST across
  the doms that host the target's dom (past a child dom's root it goes on at its host node, like the DOM
  standard's "get the parent" of a shadow root); bounded by a seen-set and `MAX_EVENT_PATH_DOM_HOPS` (16).
  `propagate_event_along(event, path, filters_at)` - capture / target / bubble along such a path
  (`current_target` is the path's node, its own dom); the old `propagate_event` is a wrapper over it (one
  body). `hover_callbacks_along_path(event, filter, styled_dom_of, host_of)` - THE plan of pointer
  listeners, each callback once.
- dll and runner `Hover` arms call `hover_callbacks_along_path` with `layout_results` and
  `VirtualViewManager::host_of_nested_dom` (the ~70-line twins are gone). Side effect of the one plan: a
  node with two callbacks for the same filter ran each of them TWICE (one plan entry per matching filter,
  each expanded to every matching callback); each runs once now.
- `layout/src/context_menu.rs` `nearest_context_menu` walked the same cross-dom chain with its own copy:
  it now walks `get_event_path` (same answers, one walk).

### 1.2 The macOS Edit menu runs its keystroke (brief item 2)

AppKit hands a key equivalent to the main menu BEFORE the view's `keyDown:`; the Edit menu's actions
(`undo:` / `redo:` / `cut:` / `copy:` / `paste:` / `selectAll:`, both views) applied the `SystemChange`
directly (`edit_command`). With the Undo item enabled, Cmd+Z never reached a key handler: the rich-text
editor lost Undo to the engine's text undo; an app's own Cmd+C on a non-editable focus never ran.

- dll common: `PlatformWindow::press_shortcut_keys(keys, site)` - the keystroke a native command stands
  for, pressed through the ordinary key passes (modifiers first, the key last; one pass = the key
  handlers, then the key's default action unless `prevent_default`), then released (another pass). A
  modifier the user already holds stays held; the key itself always comes up (AppKit sends no `keyUp:` for
  a key released while Cmd is held).
- macOS `view_handlers::edit_command` = `press_shortcut_keys(EditCommand::keys())` (primary + Z,
  primary + Shift + Z, primary + X / C / V / A; primary = Cmd, or Ctrl under `LINUX_SHORTCUTS_ON_MACOS`).
  One path for a click on the item and for its key equivalent. Undo / Redo validate as ENABLED on a
  text-editing focus too (the editor may keep a history the engine cannot see). The dead `perform_undo` /
  `perform_redo` (no callers; applied the engine's undo directly) are gone.

### 1.3 The scenario runner's undo keys (brief item 3)

The body of `SystemChange::UndoTextEdit` / `RedoTextEdit` lived in the dll (`undo_text_edit_on` /
`redo_text_edit_on` + `UndoRestore`), so the runner had nothing to call. Ported into layout
(`layout/src/managers/undo_redo.rs`, an `impl LayoutWindow` block at the end of the non-test code):
`undo_text_edit_for_seat` / `redo_text_edit_for_seat` (the bodies) and `undo_text_edit` /
`redo_text_edit` (primary seat, caret put back). The dll's `UndoTextEdit` / `RedoTextEdit` and
`SeatShortcut` Undo / Redo arms call them (its copies deleted); the runner gains the
`DefaultAction::UndoTextEdit` / `RedoTextEdit` arms (primary seat, after the callbacks, vetoable) and the
`SystemChange::UndoTextEdit` / `RedoTextEdit` arms in its pre-filter. Tested with `tap_key` and with a JSON
scenario (`click`, `key_down x`, `key_down z` + primary modifier).

### 1.4 Headless menus close on Escape and on a press outside them, as one chain (brief item 4)

- A window-based menu (`WindowType::Menu`, no `<transient-window>` mailbox) closes itself on the dismissal
  `popup_dismiss_cause` already answered for it (Escape, focus loss) - the close waited for a mailbox it
  never has (common `process_transient_dismissal`).
- The OWNER side: a fresh press in the window that owns menu windows (outside them by construction), or
  an Escape that reached it, dismisses them: `PlatformWindow::dismiss_menu_windows` (default: none -
  native macOS / Win32 menus and the X11 / Wayland grabs dismiss their own; headless closes its menu
  children). The click that leaves a menu does nothing else, as a native menu / X11's grab eats it: the
  press is discarded and its release owed (`CommonWindowState::menu_release_owed`, private).
- A menu child that closes (an item picked, Escape) takes the rest of the chain with it
  (`HeadlessWindow::pump_children`, the headless twin of X11's `dismiss_chain_if_menu`).
- `transient.rs`: `fresh_press` / `fresh_release` / `fresh_escape` - three hand-written copies of "no
  button was down, one is now" / "Escape was not held, it is now" became one predicate each.

### 1.5 Ctrl+B with no selection reaches the app (brief item 5)

What was left after TEXTENG (`DocumentTextEdit.runs`, `get_typing_formats`) and WRITER6 (the rich-text
editor takes the engine's formats) is the toggle itself: the engine's Ctrl/Cmd+B / I / U at a collapsed
caret sets the typing style as the key's DEFAULT action, after the KeyDown callbacks, and told the app
nothing (TEXTENG "left": "an event when the typing style changes"). New: `EventType::TypingStyleChanged`
and `FocusEventFilter::TypingStyleChanged` (appended), dispatched at the editing host after a toggle that
changed something - in the shells' keyboard default-action pass (after the match, like the synthetic
activation click; a `RefreshDom` reply rebuilds) and in the runner's arm. A toolbar reads
`CallbackInfo::get_typing_formats(host)` and shows the pressed B at once. DECISION: a dedicated event, not
a `TextChanged` with no text change (that one means "the text changed": dirty flags and word counts would
misfire).

## 7. Seen, not done (for their owners)

- macOS AppKit quirk, general: a key released while Cmd is held gets no `keyUp:` (NSApplication swallows
  it), so after Cmd+<letter> through `keyDown:` (a combo with no menu item, e.g. Cmd+B) the letter stays in
  `pressed_virtual_keycodes` until it is pressed again. The Edit menu path now releases its key; the
  general fix is a local key-up monitor (GLFW does `addLocalMonitorForEventsMatchingMask:KeyUp` and
  forwards Cmd key-ups) - not done here (risky without a Mac build).
- macOS keyDown maps keycodes POSITIONALLY (`convert_keycode`): on AZERTY Cmd+Z reaches the engine as
  Cmd+W. The Edit menu path is layout-independent now (it presses Z); the keyDown path is not.
- `focusable_under_pointer` (layout `managers/hover.rs`) deliberately walks the target's OWN dom only: a
  click on unfocusable VirtualView content does not focus the host. Kept (documented as intended there);
  worth a user ruling now that events bubble through the host.
- WIDGETS7: the RichTextEditor could take its toolbar's pressed state from `TypingStyleChanged` +
  `get_typing_formats` instead of its `RichTypingStyle` mirror (WRITER6 kept the mirror for inline code,
  which the engine cannot paint: `TextFormat::Code` is still missing - TEXT7 / text3).
- Windows / Wayland: a fallback Menu-type window without a mailbox now also closes itself on Escape /
  focus loss through the shared pass (the comment there always said so); X11 handles both before the pass.
