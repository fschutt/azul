## What was built

`examples/azul-keys` (package `AzKeys`, lib `azkeys`, bin `AzKeys`), registered in the root `Cargo.toml`,
`scripts/workspace_test_members.txt` (`tested: AzKeys`) and `.github/workflows/rust.yml` ("Run AzKeys tests",
dll_tests job, after AzDashboard). 19 source files, ~10 k lines, ~80 unit tests.

Plain model (tested without a window):
- `crypto.rs` - the vault FILE `keys/vaults/<uuid>.azkv`: a JSON envelope. A random 256-bit VAULT KEY seals the
  vault's JSON (XChaCha20-Poly1305, random 192-bit nonce per save); the master password through Argon2id
  (64 MiB, 3 passes, 1 lane, 16-byte salt) gives the PASSWORD KEY that seals the vault key. Associated data:
  the key part binds the id and every KDF parameter + salt; the data part binds the id and the name. A `check`
  value (first 16 bytes of SHA-256 over a label and the vault key) tells a stale keyring key (`WrongKey`) from
  damaged data (`Corrupt`) and commits the data to their key. A save reseals with no password; a new master
  password rewraps the same vault key under a fresh salt (so device unlock keeps working). Cost bounds refuse
  absurd files (<= 1 GiB, <= 64 passes, <= 16 lanes). `SecretKey` wipes on drop, prints `SecretKey(***)`.
- `vault.rs` - items (login, card, secure note, identity, SSH key) with username / password / TOTP / websites /
  notes / tags / favourite / folder / custom fields (hidden or not) / card fields / dates / password history
  (10); search over folded text (never a password, hidden value or card number), scopes, A-Z sections;
  `Debug` shows no secret; `wipe()` overwrites every string on lock.
- `totp.rs` - HOTP (RFC 4226) / TOTP (RFC 6238) with SHA-1 / SHA-256 / SHA-512, base32 (RFC 4648, lenient
  read), otpauth URLs read and written; HOTP URLs refused with a reason.
- `import.rs` - CSV of Chrome / Edge, Firefox, Safari, Bitwarden, 1Password, KeePassXC, LastPass (columns found
  by header name, the `csv` crate), Bitwarden JSON (logins, notes, cards, identities, SSH keys, folders, custom
  fields, password history); encrypted exports refused with what to do; skipped rows reported by row number
  only; `merge` leaves out what the vault already has.
- `generator.rs` + `words.rs` - passwords (sets, avoid-similar, one of each set guaranteed), passphrases (1024
  words = 10 bits each, capitals, a digit), PINs; OS random bytes with rejection sampling (no modulo bias);
  exact entropy for generated secrets, an estimate for typed ones (classes, repeats, runs, a common list).
- `clipboard.rs` (guard: a digest + a label, countdown, 0 = never), `lock.rs` (idle lock; after 3 wrong
  passwords a 30 s wait doubling to 5 min), `audit.rs` (weak / reused / old / no 2FA, a report without secrets),
  `store.rs` (the work on the drive: list, create, unlock with password or keyring key, save with a backup in
  `keys/backups/`, change the master password, put an export), `sample.rs` (the `--sample` vault, password
  `sample`), `session.rs` (the unlocked vault in the window: selection, edit form, copy text, delete, star, wipe).

The window (`app.rs`, `jobs.rs`, `ui.rs`, `ui_item.rs`, `ids.rs` - prefix `__azkeys_`, every name once):
- `NoTitle` + appkit title row; S4 `PimShell` via `.office_shell()` (title row, toolbar ribbon, status bar),
  `ShellThemeScope::body()` (accent Slate), flat / flora x light / dark through the appkit kit.
- Unlock card (vault picker, password + Enter, the wait message, "Use biometrics" / "Unlock from the keyring",
  the sample hint, New vault), new-vault form with a strength bar; empty state when no vault exists.
- Vault: navigation (All / Favourites / One-time codes, the five kinds, tags, with counts), searchable list
  (Avatar initials, subtitle, 2FA mark, star), reading pane: the item (copy / show for every secret, the TOTP
  code with its seconds), the edit form (kind for a new item, card fields, custom fields, tags, notes, Generate,
  Save / Cancel / discard question), the generator panel, the import preview (path / FileDialog / Read, the
  summary, Import N items), the audit (filter by problem, rows open the item, Export report into
  `keys/exports/audit-<date>.txt`).
- Keys: Mod+N new, Mod+L lock, Mod+G generator, Mod+E edit, Mod+S save, Mod+C / Mod+Shift+C / Mod+B copy
  password / code / user name (only when no text field holds the focus or a selection), Delete, Escape,
  Up / Down; the kit's Mod+, / F1.
- Every vault Work runs on an azul `Thread` (`store::run` on a `LocalDrive` at the data root; Argon2id never
  blocks a callback); one save at a time (a change during a save saves again after it); lock and close wait
  for the save on the way; a `CloseGuard` asks before an edited item is lost.
- 1 s timer: clipboard clear at the end of the countdown, idle lock, and a rebuild only while something shows
  seconds (never under an edited item).
- Device unlock (settings > Security): the vault key (base64) goes to the OS keyring with `require_biometry`
  where `get_biometric_kind()` says there is a sensor; if the keychain refuses the binding, it is stored
  without it and read only after `request_biometric_auth` ("prompt" mode); with no biometrics it is a plain
  keyring entry. A stale / missing key clears the setting and falls back to the password.
- Settings: Security (lock after, clipboard clear after, device unlock), Vault (file, KDF, change the master
  password), plus the kit's Appearance / Data / Shortcuts / About.
- stdout markers for scripts: `AZKEYS_DATA`, `_LISTED`, `_CREATED`, `_UNLOCKED`, `_WRONG_PASSWORD`, `_SAVED`,
  `_LOCKED`, `_COPIED`, `_CLIPBOARD_CLEARED`, `_VIEW`, `_SELECTED`, `_ITEM_SAVED`, `_IMPORT_PREVIEW`,
  `_IMPORTED`, `_PASSWORD_CHANGED`, `_WRITTEN`, `_DEVICE_UNLOCK`, `_FAILED` - never a secret.

## Crypto - the choice and why

| Crate | Version | In the lock? | Why |
|---|---|---|---|
| `argon2` | 0.5.3 (no default features; `alloc`, `zeroize`) | NEW (+ `blake2` 0.10.6 NEW; `base64ct` in lock) | Argon2id: memory-hard password KDF (RFC 9106), OWASP's first choice; RustCrypto, same project as the AEAD |
| `chacha20poly1305` | 0.10.1 (`alloc`) | yes (rustls-rustcrypto) | XChaCha20-Poly1305: random 192-bit nonces need no counter across devices sharing the bucket; constant-time in software; zeroizes its key |
| `zeroize` | 1.x | yes | wiping keys, passwords, decrypted bytes, import bytes |
| `getrandom` | 0.2 | yes | OS random source (salts, nonces, vault key, generator) |
| `hmac` 0.12, `sha1` 0.10, `sha2` 0.10 | | yes | TOTP HMACs, the key check value |
| `csv` | 1.4 | yes (AzSheets) | CSV exports |

Not `age`: a large new dependency tree (not in the lock), passphrase mode is scrypt not Argon2id, and its
recipient model fits encrypted backups / exports (a later step, noted) better than a vault key that the
password AND the OS keyring each unlock. KeePass KDBX interop and OpenPGP (rPGP vs Sequoia) are later steps.
The parent handles cargo-vet exemptions for `argon2` and `blake2`.

## Engine gaps seen (not fixed here: engine work, report only)

- The clipboard cannot be read outside a paste, so the guard cannot check that the clipboard still holds the
  secret before clearing it (a later copy elsewhere is cleared too). No "concealed" flag on `ClipboardContent`
  (macOS `org.nspasteboard.ConcealedType`, Windows `ExcludeClipboardContentFromMonitorProcessing`) to keep
  secrets out of clipboard histories - a small engine addition worth doing.
- Keyring secrets cross the FFI as `AzString` and text-field states hold typed passwords: neither can be
  zeroized from the app (the app wipes its own copies).
- No session / screen-lock / sleep event: "lock when the screen locks" is not possible yet (idle lock only).
- Focusing a node by id from a window key handler (Mod+F to the search) needs a NodeHierarchyItemId ->
  NodeId step the app did not find; the shortcut was left out.

## Duplication noted

- AzContacts' hand-written RFC 4180 reader (`examples/azul-contacts/src/csv.rs::parse`) is a twin of the
  `csv` crate AzSheets and AzKeys use; the separator guess (comma / semicolon / tab by the header) now exists
  in both AzContacts and `azkeys::import::separator`. Suggest moving AzContacts onto the crate and sharing the
  guess (azul-pim or appkit).
- The small DOM helpers (`strs`, `text`, `block`, `column`, `row`, `button`, `primary`) are per-app copies in
  AzContacts, AzNotes and now AzKeys - a candidate for azul-appkit's `ui` module.
- base64 comes from `azul_pim::data_uri` (no new twin); base32 (RFC 4648) is new and lives only in `totp.rs`.
