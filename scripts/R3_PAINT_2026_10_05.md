## Per test

### svg_paint x5 (a_filled_path_paints, a_stroked_path_paints_its_outline, fill_and_stroke_are_independent_paints, stroke_comes_through_css_as_well_as_the_attribute, fill_none_paints_nothing)
- Root cause: the test fixture's frame. An inline `<svg>` alone on a line sits on a line box that holds
  the strut of the body's font (CSS 2.2 s10.8). User ruling 2026-10-03 (Chrome is the reference),
  landed as 1adee2882 "a line of only atomic inlines is measured by its line box": the line is the SVG's
  height plus the font's descent and half-leading. The five failing tests render into 8 / 16 px frames
  exactly as large as the SVG, so the root overflowed, the viewport became a scroll frame and its thumb
  (#c1c1c1 = the reported `[193, 193, 193, 255]` centre) covered the frame (64 painted px for
  fill="none", a 4 px stroke cut to 16 px). MAILVIEW saw the same symptom on 2026-09-30 and made svg-alone
  lines box-tall (dd5a38040); the 2026-10-03 ruling reversed that on purpose and names the web's remedy
  ("an icon that wants its box's height alone says `line-height: 0` or `display: block`").
  The 24 / 32 / 48 / 64 px tests did not overflow or sample away from the bar.
- Wrong side: TEST (its frame assumed the pre-ruling line box; Chrome makes the same page scroll).
- Fix: `32c579ef1` - the fixture's style adds `svg { display: block; }`; assertions unchanged.
- Confidence: high (the thumb colour, MAILVIEW's identical diagnosis, the ruling commit).
- File: layout/tests/svg_paint.rs.

### solver3::display_list::svg_mask_memo_tests::a_rebuilt_display_list_reuses_its_unchanged_svg_masks (lib)
- Root cause: the fixture used `crate::xml::parse_xml_to_styled_dom`, the DOCUMENT loader (arena path,
  `open_fast_node` in layout/src/xml/mod.rs). That loader has never built SVG geometry (no
  `SvgNodeData::Path`, no fill layer, no stroke slots, no viewBox / intrinsic size, no absolute shape box;
  `git log -S set_svg_data -- layout/src/xml/mod.rs` is empty). So no `PushImageMaskClip` existed and the
  premise failed before the memo (108450ea2) was reached. Only the TREE loader's DOM builder (core
  `apply_xml_node_attributes`) maps SVG shapes, which is what svg_paint.rs uses.
- Wrong side: TEST (wrong loader for its subject).
- Fix: `08534b7fa` - `parse_xml` + `dom_from_parsed_xml` + `StyledDom::create_from_dom`; assertions unchanged.
- Confidence: high for the premise; the memo assertions then compare `ImageRef`s by id (clones from the
  thread-local memo share it).
- File: layout/src/solver3/display_list.rs (test module `svg_mask_memo_tests` only).

### the_incremental_raster_paints_a_transformed_box_where_the_compositor_does::a_turned_box_is_repainted_turned
- Root cause: the harness rendered with `CpuRenderState::new(..)` and EMPTY transform / opacity maps, so
  both renderers fell back to the matrix baked into the display list. That matrix is computed before the
  solve from the PREVIOUS pass's sizes (window.rs `sync_css_gpu_values`); on a first pass there are none,
  `transform-origin: 50% 50%` resolves against 0 x 0 and `rotate(45deg)` turns about the corner - (20, 20)
  is on the turned box's edge, so the harness check "the compositor paints the box turned" failed. The
  engine corrects the value right after the solve (`GpuValueCache::refresh_transform_values`), and every
  live CPU backend renders from those values (headless dll, e2e cpu_backend, callbacks.rs screenshot:
  `CpuRenderState::from_gpu_cache` + its maps into `allocate_layers_from_display_list`). Translation has
  no origin, which is why the translate test passed.
- Wrong side: TEST (its renderer inputs differ from every real backend's).
- Fix: `4fdbd3a40` - one `live_state(lw)` helper (`from_gpu_cache`) for both paths; unused `HashMap` import
  dropped; assertions unchanged.
- Confidence: high for the cause; medium-high that the rest passes (the PAINT7 flat-walk transform code
  reads `render_state.transforms` first, as the compositor does).
- File: layout/tests/the_incremental_raster_paints_a_transformed_box_where_the_compositor_does.rs.

### a_border_defaults_to_a_medium_width_in_the_text_colour::a_border_style_alone_draws_a_medium_border
- Root cause: the compact cache. WPT8 (2ecd332e0) made the used width one rule,
  `getters::used_border_width(declared, style)` (0 for none / hidden, the declared width, else medium),
  with "not declared" arriving as `MultiValue::Initial` / `None`. The normal-state FAST path could never
  say "not declared": `CompactNodeProps::default()` stored an undeclared border width as raw 0 = a declared
  `0px`. Box model and painter both saw 0, so `border-top-style: solid` alone had no border (the slow path -
  e.g. a hovered box - did get 3 px).
- Wrong side: CODE (Chrome: medium = 3 px).
- Fix: `5cc29c251` - css/src/compact_cache.rs: the four border-width defaults are `I16_INITIAL`, which the
  layout getter (`get_css_property_pixel!`: `MultiValue::Initial`) and the painter (`declared_border_info`:
  `None`) already decode as undeclared; every other reader treats it as 0 as before (fc.rs collapsed
  table decode, text-box-trim / inline-span `Exact`-only matches, `decode_resolved_px_i16` -> None, the
  layout fingerprint hashes it consistently). The css unit test that pinned the default as `Some(0.0)` now
  pins `I16_INITIAL` / `None` (test was stating the bug).
- Confidence: medium-high. Behaviour change by design: any box with a border STYLE and no width in its
  resting state now has a 3 px border (Chrome does; azul's slow path already did). Audited: UA (hr, button)
  and the theme helpers (`decl::border*`) always pair width + style; no widget CSS string sets a style alone.
- File: css/src/compact_cache.rs.

### an_hr_is_a_two_pixel_inset_rule_as_wide_as_its_block::an_authors_single_border_keeps_the_rule_one_pixel
- Root cause: the CSS parser. `parse_combined_css_property` read a bare `none` as the CSS-wide keyword for
  every shorthand but `list-style`: `border: none` became twelve `CssPropertyValue::None` longhands. The
  compact cache applies only exact values, so the hr kept its UA `border-*-style: inset`, and the widths
  read as undeclared (`medium`): bottom inset 3 px + the author's 1 px top = 400 x 4. The longhand
  `border-*-style: none` had the same fault in `parse_css_property`.
- Wrong side: CODE (Chrome 400 x 1; `none` is a typed value of `border-style`).
- Fix: `c9d2bb710` - css/src/props/property.rs: `has_typed_none` covers `border`, `border-top/-right/
  -bottom/-left`, `border-style` (combined) and the four `border-*-style` longhands, so they reach
  `parse_style_border` (style none, initial width and colour) / `parse_style_border_style` /
  `parse_border_*_style`, as `display` / `float` / `object-fit` already do.
- Confidence: high. Visible side effects (all now as in Chrome): the rich text editor's rule
  (`border: none; border-top: 1px solid`, rich_text_editor.rs:1165) was 4 px and is 1 px; AzWidgets'
  `border: 1px solid ...; border-top-style: none` (examples/azul-widgets/src/lib.rs:498) loses its top
  edge; the debugger's `border: none` buttons lose the UA button border; css/src/system.rs:2294
  `.csd-controls-only { border-bottom: none }` really has no bottom border.
- File: css/src/props/property.rs.

## Seen, not fixed (for later rounds)
- The DOCUMENT loader (`parse_xml_to_styled_dom`, `parse_html_to_styled_dom`: reftests, the debug server's
  `mount`) builds no SVG geometry at all: an inline `<svg>` in such a document paints nothing (Chrome draws
  it). Fix: move the SVG part of core `apply_xml_node_attributes` (viewBox + intrinsic size, shape box,
  fill / stroke props, geometry) into one function over an attribute getter and call it from
  `open_fast_node` too (inside_svg = the sink's `svgs > 0`). NOT SMALL (two crates, every document).
- The display list's baked `PushReferenceFrame` matrix is computed before the solve (previous pass's
  sizes): on a first pass a percentage `transform-origin` / `translate()` is resolved against 0. Live
  renderers override it; a consumer without the GPU values (the exit-animation zombie list, a list kept
  for print) shows `rotate()` about the corner on the first frame.
- A CPU component preview / tray icon (`render_component_preview`) paints the viewport's scrollbar when its
  content overflows the frame (what svg_paint hit): an icon one strut taller than its frame gets a grey
  thumb. Chrome's headless screenshots hide scrollbars; a preview probably should too.
- `getters::get_border_info` returns the DECLARED border for every node with svg data - `<svg>` itself
  (ViewBox) and clip-mask nodes included, not just shapes whose border slots carry the stroke - so an
  `<svg>` with a style-only border gets 3 px in the block layout but 0 in taffy.
- An SVG shape with `stroke` but no `stroke-width` strokes nothing (SVG's initial stroke-width is 1).
