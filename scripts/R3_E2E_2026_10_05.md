## Bug 1 - a Modal button that changes app state does not rebuild the main window

Reproduction: `python3 scripts/azerp_e2e.py --bin target/release/AzERP` (capped) fails at step 3: "the asset
does not read checked out to Katherine Johnson". The check-out form's Save wrote both files (AZERP_SAVED x2),
but the main window still read "In use". Steps 4 / 4b fail the same way (R2-APPS).

Root cause (engine, every backend): a `Modal` is a transient window. Its content is the owner window's
extracted subtree, so a refresh inside it must rebuild the OWNER. `process_window_events` already does this:
in a popup it turns `ShouldRegenerateDomCurrentWindow` into `ShouldRegenerateDomAllWindows`. But a script's
click reaches a window as the debug server's TIMER change (`QueueWindowStateSequence`; keys and text arrive
as `ModifyWindowState` / `CreateTextInput`). The shared `PlatformWindow::process_timers_and_threads` fanned out
to the other windows only when a callback itself returned `Update::RefreshDomAllWindows`. It read the change
pass's `ShouldRegenerateDomAllWindows` only as "rebuild this window". So the popup rebuilt from its stale
mailbox, and the owner was never rebuilt until a `redraw` op.

On desktop, a real pointer click already fanned out through the event arms: macOS
`convert_result_with_fanout`, the X11 / Wayland / Win32 handlers, and the headless `pump_once` event loop. So
the bug hit every E2E op inside a Modal on every backend. It also hit any app timer, thread write-back, resumed
request or TextChanged reply whose rebuild was owed inside a popup.

Side: engine. Fix (d0b97e739): `process_timers_and_threads` fans out ONCE, after every answer is in (text
notifications included). It does so for a callback's `RefreshDomAllWindows`, for a change whose pass returned
`ShouldRegenerateDomAllWindows`, and for any rebuild owed by a popup (`transient::mailbox_of` - the same rule
the event pass applies). The old early fan-out block is gone, so nothing fans out twice.

RED test (bada0e9f9), in dll/src/desktop/shell2/headless/tests/e2e_host.rs:
- A headless window shows "Drill press" and a `<transient-window open>` (viewport anchor, no light-dismiss -
  what a Modal is) holding a 120x40 Delete button whose MouseUp sets `deleted` and returns `RefreshDom`.
- A timer in the popup window queues move / down / up at (60, 20), as the debug server's `click` does.
- It pumps root and children 6 times, then asserts: the click ran (harness), the root shows "Deleted" and no
  "Drill press", and the popup window is gone.

## Bug 2 - AzNews / AzCode screenshots blank, a 22,598 px / infinite layer

Reproduction: AzNews `--sample --screen feed --size 1200x760` (headless, debug server). The screenshot is a
dark window with one "Tech" label. stderr: "[compositor] layer for node None requested at 379.68x22598 logical -
past MAX_LAYER_DIM". AzCode `--sample` shows the same ("48xinf - not finite"). `get_all_nodes_layout` gives the
whole OfficeShell chain an infinite height (JSON null), in AzNews and in AzCode:
- AzNews: from the column under the theme scope (node 2) through the shell, its body, the split panes and
  their halves to the three panes. The article list itself is 22,598 px, unclipped.
- AzCode: from node 2 through the shell to the side bar / editor panes.

Bisected live with `set_node_css_override` on the prebuilt apps:
- Hiding the 891-article list, the navigation, the reading pane, the ribbon or the status bar changes nothing.
- Setting the panes' `height: 100%` (AzNews 47 / 538 / 4797 + 536; AzCode 22 + 63) to `auto` makes the chain
  finite: AzNews 760 / 668, AzCode 800 / 749. Putting one pane's 100% back makes it infinite again.
- With the panes' 100% intact but the content-measured flex bases removed (`flex-basis: 0px` on nodes 2 and
  43), every pane resolves 100% = 668, the article list is 603 tall and scrolls, and the app renders normally.

Root cause (engine, layout/src/solver3/fc.rs `layout_flex_grid`): each pane is a `display: flex; height:
100%` box in a split pane's `display: block` half. Measuring the half's content height (a flex basis, a row's
cross size) lays it out under an INDEFINITE height, which `available_size` carries as INFINITY.
`resolve_explicit_dimension_height` resolved the pane's percentage against that: 100% x inf = inf. That went to
taffy as a known height, so the half's content and every content-sized flex item above it became infinite. The
compositor then skipped the layers (blank screenshots). A node with an infinite rect also has no clickable
centre, which is most likely AzNews' "click: could not resolve the click target" (not checked separately).

Chrome (and CSS 2.2 10.5 / css-sizing-3 5.2.1): a percentage of an indefinite size behaves as auto. The app
CSS is valid. Side: engine.

Fix (09de0bfc7): a new `definite_or_auto` wraps both `resolve_explicit_dimension_*` results at their only call
site. A non-finite explicit size (a percentage, or a calc() with percent terms, against the measurement's
INFINITY) becomes `(None, false)`, i.e. auto (content-sized). `calculate_used_size_for_node` already keeps the
same net for widths. The final layout, where the stretched half is definite, still resolves the 100% (shown by
the override run above). Width is covered too, because the same multiplication exists for `width: 100%` under a
max-content width measure.

RED test (acb8578c7): appended to `window_layout_tests` in layout/src/solver3/fc.rs, next to the code. The DOM
is body (600px, flex column) > flex-grow column > split row (`height: 100%`) > `display: block` half
(`flex-basis: 0`) > `height: 100%` flex pane > 50px row. The test asserts that column, split, half and pane are
all finite and 600 px (Chrome 600).

Verify after the build:

  acb8578c7, green at 09de0bfc7). Also run `cargo test -p azul-layout --lib window_layout_tests` and the
