# Where miniword's RSS goes

Measured 2026-08-07 on azul `743eb5837`, release, no `MINIWORD_SHOT`.
Document: `big.md`, a 960-line markdown (~60k characters, ~40 A4 pages),
opened via `MINIWORD_OPEN` (argv is ignored — see §7h).

**These numbers describe CURRENT master, not a stale build.** azul has
moved 50 commits past `743eb5837` while this map was written, and
**every one of them touched only `scripts/`** — verified with
`git diff --name-only 743eb5837..HEAD`, which lists no path outside that
directory. The app side (`pdf2html` `b931edb`) has a clean tree and no
source file newer than the measured binary. The profiled binary therefore
matches both source trees exactly; re-measuring today would re-derive
these figures, not different ones.

**Two configurations, and the difference matters:**

    windowed (Wayland, what the user runs)   126.1 MB
    headless (what most of this report maps)  ~103 MB

**This is a map, not a proposal.** No optimizations are recommended here;
several are implied and are deliberately left for the reader.

## SUMMARY — read this first

**126.1 MB windowed on a 960-line markdown.** It splits cleanly, and the
split is the most useful fact in this report (§7h):

    73.1 MB   FIXED    — paid by a blank document in a window
    53.0 MB   DOCUMENT — 95% of it heap

**Two denominators appear in this report and they are not
interchangeable:** a document's RSS delta (72.3 MB on realistic content)
and the part of it still RETAINED at exit (65.0 MB). Shares of shaped
text are quoted against the RETAINED figure, because that is what the
allocation filters measure — 51.4 of 65.0 is **79%**; against the RSS
delta it would be 71%.

On REALISTIC (100%-distinct) content the document costs 72.3 MB in RSS
(65.0 MB of it retained at exit), and shaped text is **79% of that
retained cost** (§7t). `big.md` is 98% duplicate lines, so the
53.0 MB figure and everything derived from it is a FLOOR (§7s).

Framebuffer sites (`AzulPixmap::new`, `CompositorState::new`) and the CSS
churn sites appear at **delta 0** — they are floor costs, unchanged by
the document. That is the check that this table is measuring the right
thing.

**A second view, by OWNER, which deliberately does NOT sum.** Totalling
every allocation whose backtrace contains a function (§7m) is the better
way to price a subsystem, but the rows overlap by construction — an
allocation under `text3::cache` that goes through `Vec::clone` counts in
both:

    azul_layout::text3::cache      33.74 MB / 81 sites   <- all shaped text
      perform_fragment_layout      17.06 MB /  3 sites
      shape_visual_items_...        7.63 MB / 33 sites
    LayoutTree as Clone::clone      3.60 MB /  7 sites   <- the duplicate
    LayoutTreeBuilder::build        3.20 MB /  4 sites

Use the first table to see where the megabytes are; use the second to
price a subsystem. Do not add them together.

**The document's 49 MB is TWO layouts, not one.** 17.04 MB of it
(~35%) is miniword's own pagination layout of the whole document at A4
width, run from inside the engine's layout callback (§7p). That
separation is deliberate — it keeps PDF page-breaking out of azul — and
this report does not call it waste. It does now price it.

**Six things that decide what to do about it:**

1. **It is all live data.** 71.37 MB of a 75.02 MB peak is still held at
   SIGTERM; the engine measures `unreturned` at 2.5 MiB and glibc
   tunables move RSS by <350 kB. There is nothing to reclaim — only
   things to allocate less of, or retain less of.
2. **Two separate problems at two scales.** 15.6 MB of frame buffers is
   paid whether the document is blank or 960 lines — 21% of the blank
   floor. Shaped text is ~0.5 MB blank and 31.8 MB at 960 lines. One
   effort will not fix both, and they need different kinds of fix.
3. **Growth is LINEAR — 49.3 kB/line on repeated content, 69.7 on
   unique (§7r, §7u).** A large constant, not an algorithmic problem, so
   nothing here argues for a structural rewrite. **But `big.md` is only
   17 distinct lines out of 960**, so every figure in this report is a
   FLOOR: unique content costs 40% more per line and 32% more per
   character. 3 839 repeated lines MEASURES 267.8 MB; 10 000 unique lines
   extrapolates to ~768 MB, and that last figure is an extrapolation.
4. **Only one line has no defence.** Shaped text costs **959 B per
   cluster** (engine accounting) or **1 459 B** (allocator bytes) on
   realistic content — **~140-240x Gecko's retained ~6 B/char**, the only
   published figure that measures the same thing (§10, §12). Everything else
   in both tables has a reason worth keeping. It is also **79%** of the
   document's RETAINED cost (51.4 of 65.0 MB), so it is simultaneously the least defensible and the
   largest item.
5. **The engine cannot see 16% of its own live heap.**
   `AZ_PROFILE=memory` covers StyledDom + Solver3 + text cache, and
   reports none of the 15.6 MB of frame buffers.
6. **A GPU backend makes it WORSE by 67 MB, measured** (§7n). It removes
   ~9.3 MB of framebuffer and adds ~65 MB of driver residency. The CPU
   framebuffers are the cheap option; do not reach for the GPU to save
   memory.

Fonts are NOT the lever (settled by measurement), an arena is NOT the
lever (settled by the user, corroborated by Servo's own benchmark), and
the app-side pagination layout being separate from the engine's is
intentional.

**Seven of my own claims were corrected while building this**, each
recorded inline with its cause. The reusable ones: check a profiler's
runtime against the workload's before trusting its peak; add your own
summary table up; and confirm the workload actually ran the workload —
a convincing plateau can be a blank document (§7h).

**This is a map, not a proposal.** No optimizations are recommended here;
several are implied and are deliberately left for the reader.

### Two caveats that change how you read anything else here

1. **`AZ_PROFILE=memory` over-reports its own `TextShapingCache` by
   >=3.4 MB.** The SmallVec inline-slot double-count fixed in
   `layout_tree.rs` was never applied to `text3/cache.rs:6189` and
   `:6199` (§12). If you run the engine's report yourself, subtract it.
   Its `accounted / rss` line is also a MID-RUN SNAPSHOT taken right
   after layout, not the settled state (§11).
2. **~7.2 MB of the shaped-text figure is unexplained** — 16% of that
   line, 5% of the application (§14). Four candidates were investigated
   and ruled out; the residual is stated rather than folded into a
   neighbour. Closing it needs the engine's report extended to walk
   `layout_results` and to accept an app-registered cache, which is a
   code change this report does not make.

## 1. The heap is almost entirely LIVE DATA

**Both instruments, same run, 32.9 s, `AZ_PROFILE=memory` + heaptrack:**

| Source | Number |
|---|---:|
| peak RSS (heaptrack included) | **106.20 MB** |
| heaptrack peak heap consumption | **75.02 MB** |
| heaptrack total live at SIGTERM | **71.37 MB** |
| `[heap]` resident (smaps, same process) | **62.9 MB** |
| engine self-report GRAND TOTAL | **26.58 MB** |
| engine's own `after layout` reading | current rss 84.9 MiB, peak 87.4, **unreturned 2.5 MiB** |

**The heap holds ~75 MB of LIVE allocations.** There is no large pool of
freed-but-retained memory: the engine measures `unreturned` at **2.5 MiB**,
and glibc tunables move RSS by under 350 kB (below). Optimising this means
allocating less or retaining less — there is no slop to reclaim.

### Two of my own earlier headlines were WRONG. Both retracted.

**Retracted #1 — "half the heap is not data" / "~38 MB of allocator
retention".** That came from a heaptrack run reporting a 38.87 MB peak.
**That run lasted 3.98 s and was killed before layout finished.** The
valid run lasts 32.9 s and reports 75.02 MB. The 38.87 MB was a partial
measurement of an incomplete workload, compared against an `[heap]` figure
from a *different* run — two errors compounding into a confident wrong
conclusion.

**Retracted #2 — the glibc explanation.** Tested directly, peak RSS:

    baseline                        102 764 kB
    MALLOC_ARENA_MAX=1              102 620 kB
    MALLOC_TRIM_THRESHOLD_=131072   102 824 kB
    MALLOC_MMAP_THRESHOLD_=65536    102 476 kB

All within ~350 kB. Refuted independently of #1, and consistent with the
engine's own `unreturned=2.5 MiB`.

**Lesson for whoever reads this next:** check the profiler's *runtime*
against the workload's runtime before trusting its peak. A profile that
ends early looks exactly like a profile of a smaller program.

## 1c. THE MAP CLOSES — heaptrack and smaps reconcile within 4.7%

> **THE "0.2%" IN THIS SECTION'S ORIGINAL TITLE WAS A UNIT ARTIFACT (§21).**
> `[heap] 62.9 + [anon] 12.0 = 74.9` is smaps, i.e. **MiB**; `75.02` is
> heaptrack's **decimal MB**. 74.9 MiB is **78.54 MB**, so the gap is
> **3.52 MB — 4.7%, not 0.2%**, off by a factor of 23. The two numbers
> looked identical only because neither was converted, and 4.7% is
> approximately the MiB/MB ratio itself (4.86%) — which is the signature
> of exactly this mistake.
>
> **The attribution in this section stands**; what does not is the
> precision claimed for it. And the two quantities are not strictly
> comparable in any case: heaptrack's figure is a PEAK, smaps' is
> resident at one moment.

The last unattributed mapping was `[anon]`: 12.0 MB resident of 537.6 MB
mapped, producer unknown. Measured directly:

- **The process is SINGLE-THREADED** (1 entry in `/proc/<pid>/task`), so
  none of it is thread stacks. That guess is retracted.
- 40 anon mappings; the largest is **7.8 MB mapped / 7.82 MB resident** —
  one fully-resident mapping.

That 7.8 MB is the same memory heaptrack attributes to `AzulPixmap::new`
(7.72 MB). glibc serves allocations above `MMAP_THRESHOLD` with `mmap`, so
a large pixmap lands in `[anon]` and never appears in `[heap]`. The two
instruments were labelling the same bytes differently.

So the accounting closes:

    [heap]  62.9 MiB +  [anon]  12.0 MiB =  74.9 MiB  =  78.54 MB
    heaptrack peak heap consumption                    =  75.02 MB
    ------------------------------------------------------------
    gap                                                    3.52 MB (4.7%)

| Owner | Resident | Instrument |
|---|---:|---|
| live allocations (`[heap]` + large mmap'd) | 74.9 MiB / 78.5 MB | both, within 4.7% |
| miniword binary text/rodata | 11.6 MB | smaps |
| font files (mmap'd, mostly untouched) | 8.8 MB | smaps |
| libc / libm / other shared objects | ~3 MB | smaps |
| **total** | **~98-106 MB** | matches VmRSS across runs |

**Nothing is unexplained at the mapping level** — though see §21: the

- Nothing else moves materially. Shaped text, layout tree, font

neither was attempted.

## 7h. THE WINDOWED MAP — fixed vs document, and four frame buffers

§7g established that the real app is ~23 MB larger than headless but left

### The trap: miniword ignores argv

hit exactly:

| what | predicted | **measured** |
|---|---:|---:|
| `/memfd:azul-fb` = `stride*h*2` (`wayland/mod.rs:5666`, *"TWO buffers in one pool"*) | 1280x800x4x**2** = 8 000 kB | **8 000 kB** |
| the large `[anon]` region | 1280x800x4x**2** = 8 000 kB | **8 008 kB** (+8 kB page header) |

**Total: 16 008 kB = 15.6 MB held in FOUR full-size 1280x800 RGBA
buffers** — two Wayland shm (double-buffered for the compositor) and two
CPU-side pixmaps. That is **21% of the blank windowed floor** and 12.4%
of the loaded application. It supersedes the 11.82 MB / two-surface
figure elsewhere in this report, which counted only the heap side.

This also explains `[anon]`, previously carried as a vague 12 MB: 8 008
kB of it is that pixmap pair, 1 196 kB is one further region, and the
rest is small. It is ~10.8 MB blank and 12.0 MB loaded, i.e. **`[anon]`
is fixed, not document-driven** — consistent with glibc serving
allocations above its mmap threshold outside `[heap]`.

### Justified?

- The four buffers are **defensible but not free**. Double-buffering the
  Wayland surface is required to avoid tearing; a CPU-side pixmap is
  required because this is the software path. Whether BOTH need to be
  double-buffered is a real question, and the honest answer is that this
  report does not settle it — one shm buffer plus one CPU pixmap would be
  8 MB, and the cost of that would be measured in frame pacing.
- The resize path is **correct**: `resize_surface` does
  `drop(cpu_opt.take())` BEFORE allocating the replacement
  (`wayland/mod.rs:5862`), so a resize never holds two pools at once. No
  transient doubling. This was listed as unmeasured in §7g; it is now
  answered at source level.
- On a GPU path these buffers would move to driver memory and largely
  leave RSS. **Not measured** — this machine ran the CPU fallback.

## 7n. THE GPU PATH COSTS 67+ MB MORE — measured, not assumed

§7h and §7l both listed "what a GPU path moves out of RSS" as unmeasured.
`AZ_BACKEND=gpu` makes it measurable, and the answer inverts the
assumption written in §7h ("these buffers would move to driver memory and
largely leave RSS").

| | CPU (default) | **GPU** |
|---|---:|---:|
| VmRSS | 126.1 MB | **193.3 MB** (a second run: 243.6) |
| `[heap]` | 69.6 | 70.6 — **unchanged** |
| `[anon]` | 12.0 | 10.5 |
| `/memfd:azul-fb` | 7.8 | **absent** |
| miniword binary | 14.1 | 16.5 |
| GPU driver stack | — | **~65 MB** |

The driver stack, itemised:

    25.7 MB  libLLVM.so.20.1                (Mesa's shader compiler)
    13.6 MB  libnvidia-gpucomp.so.580
    11.5 MB  /dev/nvidiactl                 (mapped device memory)
    10.8 MB  libnvidia-eglcore.so.580
     3.2 MB  libgallium-25.2.8
     ~1.5 MB libEGL_nvidia, libnvidia-glsi, libGLdispatch

**The GPU path does exactly what §7h predicted for the buffers** — the
7.8 MB shm mapping disappears and `[anon]` drops 1.5 MB, so ~9.3 MB of
framebuffer leaves RSS. It then pays ~65 MB of driver residency plus
2.4 MB of extra binary pages to get it. **Net +67 MB.**

**So the 15.6 MB of CPU framebuffers is the CHEAP option**, and any
proposal to move rendering to the GPU *in order to save memory* is
refuted on this machine before it is written.

**Honest limits on this measurement, because they are large:**

- **The two GPU runs disagreed by 50 MB** (193.3 vs 243.6 MB). GPU driver
  residency is not deterministic between runs the way the CPU path is
  (which reproduced to 64 kB, §7h). The DIRECTION is unambiguous; treat
  the magnitude as a range, not a figure.
- **This is one machine, one driver** — nvidia 580 on KDE Wayland, with
  Mesa/gallium also loaded. A different GPU stack would give different
  numbers. What generalises is the shape: a GPU driver is tens of MB of
  resident library, and framebuffers are single-digit MB.
- GPU engagement is confirmed by evidence, not by a log line: nvidia EGL
  libraries mapped, `/dev/nvidiactl` resident at 11.5 MB, and the shm
  framebuffer absent. The backend did not silently fall back to CPU.

### Correction: the CPU pixmaps are NOT a double-buffer pair

§7l left open "whether BOTH buffer pairs need double-buffering". The
question was mis-framed by me, and the source answers it:

- The **memfd** pair IS a true double-buffer — `stride * height * 2`,
  one pool, two `wl_buffer` slots, so the compositor can read one while
  the client writes the other (`wayland/mod.rs:5666`).
- The **CPU pair is not a pair at all.** They have different jobs:
  `AzulPixmap::new` from `render_frame` is the render target, and
  `CompositorState` (`cpurender/compositor.rs:33`) holds
  `layers: HashMap<LayerId, Layer>`, each layer owning its own pixel
  buffer — the 4.10 MB is the ROOT LAYER. Render into one, composite into
  the other.

So there is exactly one double-buffer in the process, and it is the one
the Wayland protocol requires. The other two full-size buffers are a
render/composite split. Whether that split needs two full-size buffers is
a real question; "is it double-buffered twice" was not.

**`big.md` has 17 distinct lines out of 960.** Every figure in this
report — 126.1 MB total, 36.1 MB shaped text, 49.3 kB/line — was measured
on a document that is 98% repeated content. The `doc-N.md` size variants
used for the scaling law were `big.md` cycled, so they are 98% duplicate
too.

The text pipeline carries an `inline_content_hash`
(`text3/cache.rs:6343`), so identical content can coalesce. That makes
every number in this report a potential **floor** rather than a typical
value. Tested rather than assumed:

| document | lines | chars | distinct lines | VmHWM | `[heap]` |
|---|---:|---:|---:|---:|---:|
| `big.md` | 960 | 31 120 | **16 of 640 non-empty (2.0%)** | 126.1 MB | 71.2 |
| unique | 960 | 32 966 | **640 of 640 non-empty (100%)** | **145.4 MB** | **90.5** |
| `doc-1920` | 1 920 | 62 240 | 17 (0.9%) | 173.2 | 125.1 |
| unique | 1 920 | 65 832 | **1 279 of 1 279 non-empty (100%)** | **211.5 MB** | — |

**Unique content costs 40% more per line.**

    repeated content    49.3 kB/line     RSS = 78.6 + 0.0493 x lines
    unique content      68.9 kB/line     RSS = 79.3 + 0.0689 x lines

    (66 112 kB over 960 added unique lines; the two intercepts agree to
     0.7 MB, which is the check — the FLOOR is the same, only the
     per-line slope changes.)

Per character: **1.52 kB/char repeated vs 2.01 kB/char unique, +32%.**

### What this changes

- **The scaling law understated real documents by 40%.** §7r's 49.3
  kB/line is correct for what it measured and is now labelled as the
  repeated-content case.
- **10 000 lines projects to ~768 MB**, not the ~572 MB in §7r.
  Extrapolation, labelled as such.
- **It does NOT change the shape of the problem.** Growth is still
  linear, still a large constant, and the floor is unchanged at ~79 MB.
  Nothing here argues for a structural rewrite that did not already.
- **The other figures are floors too.** 36.1 MB of shaped text on
  `big.md` would be higher on genuinely varied prose. This report did not
  re-derive the per-owner breakdown on a unique document, so §7m's
  numbers stand as measured — on 98%-duplicate content.

### RETRACTED: "even 68.9 kB/line is probably still low"

An earlier draft of this section said my "unique" documents were only 67%
distinct, and inferred (labelled as inference) that a fully-distinct
document would cost ~79 kB/line. **That is wrong. Retracted.**

The 67% came from `sort -u` over ALL lines — and 320 of the 960 lines are
BLANK, collapsing to one entry. Blank lines shape to nothing and cannot
cost shaped-text memory. Counting only non-empty lines:

| document | total | non-empty | distinct non-empty |
|---|---:|---:|---:|
| `big.md` | 960 | 640 | **16 (2.0%)** |
| unique | 960 | 640 | **640 (100%)** |
| unique 1920 | 1 920 | 1 279 | **1 279 (100%)** |

**The unique documents are already 100% distinct**, and both documents
have the same 640 non-empty lines, so the comparison is
apples-to-apples across the full range from 2% to 100%.

**68.9 kB/line is therefore the realistic figure, not a floor**, and the
~768 MB projection for 10 000 lines is the realistic projection rather
than an underestimate. There is no further penalty waiting above it.

This is the eleventh correction in this report and the second retraction
of an INFERENCE that was correctly labelled as one at the time. The label
is what made it cheap to withdraw: no measurement depended on it.

### Why this was worth catching

The map's purpose is to decide where optimisation effort goes. A
benchmark that is 98% duplicate flatters exactly the subsystem the map
identifies as the biggest problem — content-keyed shaped-text caching.
Had this gone unchecked, the report would have understated the main
target by 40% while pointing at it.

## 10. THE PER-CLUSTER COST, AND HOW GOOD THE BENCHMARK COMPARISON IS

§9 rests its only unqualified **NO** on shaped text being "349-445 B per
cluster against HarfBuzz's ~24 B/glyph and Gecko's ~6 B/char — 15-70x".
That is the most consequential sentence in this report, it came from a
research summary rather than from anything measured here, and
[[azul-memory-optimization-plan]] records that **no published
bytes-per-character figure for RETAINED shaped text was ever found**.
Both halves needed checking.

### The measured per-cluster cost, on realistic content

`AZ_PROFILE=memory` on the 100%-distinct document:

    32 937 clusters, 32 937 glyphs (1:1 — Latin, one glyph per cluster)

    warm.inline          10 383 KiB  ->    322 B/cluster  (engine's own figure)
    TextShapingCache     20 454 KiB  ->    636 B/cluster
                         ----------       -----
    both buckets         30 837 KiB  ->    959 B/cluster  (engine accounting)

    heaptrack, text3::cache            ->  1 459 B/cluster  (allocator bytes)

**The report's 349-445 B/cluster was measured on the 98%-duplicate
document and is superseded.** On realistic content it is **959 B/cluster
by the engine's own accounting and 1 459 B by allocator bytes** — two to
four times worse than the figure §9 argued from.

### The two instruments disagree by 63%, and that is not hidden

> **Two corrections to this section's own arithmetic.** The engine figure
> was written as "30.8", which is 30 837 KiB divided by 1000 — **neither
> MB nor MiB**. It is **31.58 MB** (30.11 MiB). And the heaptrack side was
> locale-truncated (§19). The disagreement is **63%**, not the 56% this
> section originally computed from a mis-scaled number and a truncated
> one. Against the §12-corrected engine figure of <=28.09 MB it is 83%.

    engine self-report   31.58 MB of shaped text   (30 837 KiB)
    heaptrack filter     51.43 MB

*(The engine figure here predates §12, which found the report over-counts
`TextShapingCache` by >=3.4 MB — corrected it is <=28.09 MB. The
disagreement discussed below is therefore wider, not narrower.)*

Both were measured on the same document in the same configuration. The
explanation offered here at the time — that the engine sums `len`-based
sizes while heaptrack counts capacity — **was checked and is FALSE**
(§12): both sides already multiply by `.capacity()`. What actually
accounts for the gap, established later, is that the engine walks only
its OWN two buckets while a `text3::cache` backtrace filter also catches
font loading (§11) and **miniword's separate thread-local pagination
cache** (§13), which the engine structurally cannot see. ~9.9 MB remains
unexplained after both (§14). Treat 31.58 as the floor of what
the data structures logically hold and 51.4 as what the allocator gives
back to the process.

Either number supports §9's verdict. The gap matters for anyone measuring
an optimisation, which is why it is stated rather than averaged away.

### How good is the external comparison? Mixed, and one half is a category error

| benchmark | what it actually measures | comparable to ours? |
|---|---|---|
| HarfBuzz ~24 B/glyph (`hb_glyph_info_t` + `hb_glyph_position_t`) | the **transient shaping output buffer** | **NO — category error.** That buffer is freed after shaping. Ours is retained layout state carrying style, source indices and cluster text. Comparing them overstates the case. |

Against the one genuinely comparable figure, **959 B/cluster is ~160x
Gecko's ~6 B/char**, not 15-70x.

> **Both ends of that moved later, in opposite directions.** §12 found the
> engine over-counts, so its per-cluster figure is **<=853 B (~142x)**;
> §19's locale fix raised the allocator side to **1 460 B (~243x)**. The
> current range is **~140-240x**, and the lower bound is itself an upper
> bound because `per_item_shaped`'s share of the over-count was never
> quantified.

§9's verdict was right and its arithmetic was too kind, but it reached

**Corrected claim:** the defensible statement is *"~140-240x a shipping

## 12. THE CAPACITY HYPOTHESIS IS REFUTED — and the engine's report over-counts
<!-- rss-map-check: historical — this section's subject IS a correction, so it cites superseded values by design -->


§11 guessed the 13.8 MB instrument gap was `Vec`/HashMap capacity slack,
and said proving it needed engine instrumentation "this report may not
make". **Both halves of that were wrong.** The brief permits
instrumentation needed to measure; and no instrumentation was needed,
because the source answers it.

### Refuted: the engine ALREADY counts capacity

    layout_tree.rs:935   cached.layout.items.capacity() * size_of::<PositionedItem>()
    layout_tree.rs:937   cached.item_metrics.capacity() * size_of::<InlineItemMetrics>()
    cache.rs:6178        arc.capacity() * size_of::<LogicalItem>()
    cache.rs:6186        arc.capacity() * size_of::<ShapedItem>()
    cache.rs:6196        arc.clusters.capacity() * size_of::<ShapedItem>()

Every bucket on both sides of the comparison is capacity-based.
**Capacity slack cannot explain the gap.** §11's inference is withdrawn —
it was labelled as inference, which is again what made it cheap to drop.

### Found instead: the SmallVec double-count survives in TWO places

`layout_tree.rs:952` carries the fix for a defect this project already
hit once (d41a15dbe) — a `SmallVec<[ShapedGlyph; 1]>`'s first element
lives INSIDE the `ShapedCluster`, so counting full `capacity()` charges
one 96-byte glyph twice per cluster:

    let spilled = c.glyphs.capacity().saturating_sub(1);   // CORRECT

**`text3/cache.rs` never got that fix.** Two sites still charge the full
capacity, each on the line after already counting the cluster via
`size_of::<ShapedItem>()`:

    cache.rs:6189   r.shaped_glyph_bytes  += c.glyphs.capacity() * size_of::<ShapedGlyph>();
    cache.rs:6199   r.per_item_shaped_bytes += c.glyphs.capacity() * size_of::<ShapedGlyph>();

**On Latin text every cluster has exactly one glyph, so `capacity()` is 1
and the ENTIRE charge is the already-counted inline slot.**

### What that does to the numbers

`shaped_glyph_bytes` is reported at **3 403 KiB**, and for single-glyph
clusters all of it is double-counted:

| | reported | corrected |
|---|---:|---:|
| `warm.inline` (has the fix) | 10 383 KiB | 10 383 KiB |
| `TextShapingCache` | 20 454 KiB | **<= 17 051 KiB** |
| engine shaped-text total | 31.58 MB | **<= 28.09 MB** |
| per cluster, engine | 959 B | **<= 853 B** |

`per_item_shaped` contains the same error at `cache.rs:6199`, but its
glyph bytes are folded into one total rather than reported separately, so
**that over-count is NOT quantified here.** The corrected figures above
are therefore upper bounds; the true engine number is lower still.

### The reconciliation got WORSE, and that is the honest outcome

    heaptrack, less font loading (§11)   48.09 MB
    engine, corrected                  <= 28.09 MB
    ------------------------------------------------
    UNRECONCILED                       >= 20.00 MB

Removing a wrong hypothesis and fixing an over-count widened the gap
rather than closing it. **The cause of the remaining discrepancy is
unknown.** It is not capacity slack, and it is not font loading. Naming
it is all this report can honestly do.

### Not fixed here, deliberately

The two lines are a one-line change each, with a correct precedent 30
lines away in another file. **This report does not make it** — the user

## 13. MOST OF THE GAP IS THE APP-SIDE PAGINATION CACHE — mechanism proven

§12 left >=20.00 MB unreconciled between heaptrack's `text3::cache`
(48.09 MB, font loading removed) and the engine's corrected shaped-text
figure (<=28.09 MB), with the cause unknown. *(Figures locale-corrected
per §19; this section originally read 17.31 / 45.40.)*

### The mechanism, proven at source rather than inferred

**miniword keeps its own layout cache, and the engine's report cannot
see it:**

    miniword/src/document.rs:407   thread_local! static LAYOUT_CACHE: Solver3LayoutCache
    miniword/src/document.rs:493   thread_local! static FONT_MANAGER
    azul/layout/src/window.rs:3144 let sc = self.layout_cache.memory_report();

`AZ_PROFILE=memory` walks `self.layout_cache` — the `LayoutWindow`'s own.
The app-side pagination layout lives in a **thread-local belonging to
miniword**, structurally invisible to it. heaptrack, which filters on
backtrace, sees both.

This is the same separation the user described as intentional. It is not
being called waste; it is being identified as the reason two instruments
disagree.

### How much of the gap it actually explains — 51%, not all of it

The totals looked seductive when both were truncated — pagination 18.10
against a 17.31 gap, a 4% match it would have been easy to declare
solved. **Locale-corrected they are 21.20 and 20.00 — still a 6% match,
and still not the answer.** Decomposing says why. Pagination's 21.20 MB breaks down as:

| MB | site | in a `text3::cache` filter? |
|---:|---|---|
| 9.57 | `finish_grow` (site B) = `perform_fragment_layout` <- `layout_flow` | **yes** |
| 2.93 | `Vec::clone` | no |
| **1.62** | **`LayoutTreeBuilder::build`, 5 calls — pagination builds its OWN layout tree** | no |
| 1.54 | `slice::to_vec` | no |
| 1.29 | `spec_from_iter_nested` | no |
| 1.65 | `allsorts::read_to_vec` x2 — font tables | no |
| 0.54 | `finish_grow` (site A) | yes |

**Only ~10.11 MB of pagination's 21.20 MB is text3-filtered shaped text.** The rest
is its own layout tree, its own font-table decode and assorted Vec
growth, none of which is inside the 48.09 MB figure the gap was computed
from. So pagination explains **~10.1 of 20.00 MB — 51%**, not the 58%
this section claimed before the locale correction.

    gap                                  20.00 MB
    pagination's shaped text            -10.11 MB
    ------------------------------------------------
    STILL UNEXPLAINED                    ~9.9 MB

*(The per-site rows above were hand-read and are CORRECT; it was the
87-site TOTAL that the locale bug truncated, 18.10 -> 21.20. §13's
original complaint that "rows 19.14 exceed the total 18.10" therefore
resolves the other way: the rows were right, the total was wrong. Rows
now sum to 20.24 against 21.20.)*

### A candidate ruled out

The layout-tree deep clone (§7m, 3.60 MB) does **not** contribute:
`LayoutTree`'s inline layout is `pub layout: Arc<UnifiedLayout>`
(`layout_tree.rs:232`), so cloning the tree bumps a refcount rather than
copying the shaped text. Ruled out by type, not by measurement.

### It also refines §7k

§7k attributed the 9.11 MB `finish_grow` site B to
`perform_fragment_layout <- layout_flow` without saying *whose* layout.
**It is almost entirely the app-side pagination layout** — 9.57 of that
site's bytes sit under `compute_document_pagination` on this document.
One of the two dominant shaping sites belongs to the app, not the engine.

### My own arithmetic was wrong on the way here

Reading the top-10 sites off the screen and adding them by hand gave
20.0 MB — larger than the 18.10 MB total for all 87 sites, which is
impossible. The parser was right and my eyes were wrong (the `-A2` output
interleaves sub-stack lines with top-level ones). Caught by checking that
the sum is monotonic in `n`: 16.93 at n=10, 18.10 at n=87, stable at
n=250. **A subset exceeding its superset is the cheapest possible
self-check and it should be run every time.**

## 15. THE ENGINE'S TRAVERSAL IS COMPLETE — so the residual is mis-framed

§14 proposed closing the ~7.2 MB by extending the engine's report to walk
`layout_results`. **That remedy would not have worked**, and §14 itself
contains the reason: miniword has one DOM and its `layout_results` entry
is Arc-shared, so walking it finds ~0. Correcting my own proposed next
step before anyone spends time on it.

### Source audit: does the engine count everything in what it walks?

| structure | heap-owning fields | counted? |
|---|---|---|
| `UnifiedLayout` | `items: Vec<PositionedItem>`, `overflow` | **yes** — `items.capacity()` |
| `PositionedItem` -> `ShapedItem::Cluster` | — | yes, via `size_of` |
| `ShapedCluster` | `text: String`; `glyphs: SmallVec<[ShapedGlyph;1]>` | **yes** — `text.capacity()` + spilled glyphs |
| `ShapedGlyph` | `style: Arc<StyleProperties>` | **no** — but 419 distinct x 248 B = **~104 KB**, negligible |
| `ShapedItem::CombinedBlock` | `glyphs: ShapedGlyphVec` | **no** — the walk only matches the `Cluster` arm (`layout_tree.rs:951`). Tate-chu-yoko; **zero on Latin markdown**, would matter on vertical CJK |

**The `warm.inline` traversal is complete to within ~100 KB for this
document.** The engine is not under-counting shaped text — apart from the
SmallVec over-count in the *other* file (§12), which makes it over-count.

### So the residual is not what §11-§14 called it

It has been described throughout as "unexplained shaped text". It is not.
The engine walks the shaped-text structures completely, so the ~7.2 MB is
**allocations that flow through `text3::cache` code but are OWNED by
something that is not a shaped-text cache.** A backtrace filter attributes
by *who allocated*, an object walk attributes by *who owns* — and those
two questions have different answers for any buffer that is built by the
text pipeline and handed to another subsystem.

That is a better characterisation, and it changes what would close it:
not more coverage of the text caches (they are already complete), but an
ownership-side accounting of whatever receives text3's output. The
display list is the obvious first place to look —
`DisplayListGenerator::paint_inline_content` already appears at 0.62 MB
in the document table, and it is reached from text3.

> **MEASURED IN §16 AND IT IS NOT THERE: 1.68 MB across 2 sites**, which
> cannot be a ~20 MB residual. This suggestion was wrong. §16 eliminated
> it as the sixth and last hypothesis and closed the search.

**Not investigated further.** This report has taken the question as far
as backtrace filtering can, and the next step is a different kind of
measurement rather than more of the same.

### Status of the residual, finally

    ~7.2 MB   16% of the shaped-text line, 5% of the application
              NOT under-counting by the engine (traversal audited, complete)
              NOT capacity slack, tree clone, multi-DOM, or the shaper (§14)
              IS allocations attributed to text3 by backtrace whose OWNER
              is elsewhere — most likely consumers of shaped output

## 16. THE DISPLAY-LIST HYPOTHESIS IS REFUTED — and the search stops here

§15 reframed the ~7.2 MB as allocations flowing through `text3` but owned
elsewhere, and named the display list as "the obvious first place to
look". **Measured, and it is not there.**

| consumer of text3 output | retained | sites |
|---|---:|---:|
| `solver3::display_list` (whole module) | **1.66 MB** | 2 |
| `DisplayListGenerator` | 1.66 MB | 2 |
| `paint_inline_content` | 1.66 MB | 2 |
| `cpurender` (raster + compositor) | 9.25 MB | 23 |
| **`solver3::sizing`** (intrinsic widths) | **19.21 MB** | 39 |

The three display-list filters return identical totals because they
resolve to the same two sites. **1.66 MB cannot be a 7.2 MB residual**,
so my own stated next step was wrong. `cpurender`'s 9.25 MB is the two
pixmaps (8.2, §7h) plus raster scratch — already accounted.

### What the sweep did find: the sizing pass holds 19.21 MB

`solver3::sizing` — the `IntrinsicSizeCalculator` — is reached by 39
sites holding 19.21 MB, against the 7.63 MB that
`shape_visual_items_with_per_item_cache` holds directly (§7m). Filters
overlap, so these are not additive; what the number establishes is that
**the intrinsic-width pass is a first-class memory holder in its own
right**, not a thin caller of the shaper.

That reinforces, from a third direction, the finding this report keeps
arriving at: **the document's text is measured once and laid out once,
and both passes retain their output** (§7k, §7t, §10). It does not add a
new owner — `per_item_shaped` is 9.52 MB of the engine's own
`TextShapingCache` — but it does say where the retention is initiated.

### The search for the residual stops here, deliberately

Candidates eliminated across §§12-16: capacity slack, the layout-tree
clone, the multi-DOM blind spot, the shaper, incomplete engine
traversal, and now the display list. Six hypotheses, all refuted by
measurement or by source.

**Backtrace attribution has been exhausted.** Every remaining question
about the ~7.2 MB is an ownership question, and heaptrack answers "who
allocated", not "who owns". Closing it needs an object-graph walk that
does not exist in the engine today, and building one is a larger job than
a map warrants — it would need the full battery and the reftest gate, and
it would be work done to explain **5% of the application**.

**The residual stands at ~7.2 MB, bounded, characterised, and named.**
That is the honest end of this investigation rather than a seventh
hypothesis.

## 17. HOW TO RE-MEASURE — `scripts/rss-baseline.sh`

A map is only useful if a later change can be measured the same way. The
procedure is now a committed script rather than prose scattered across
sixteen sections, with every trap that cost a run encoded in its header.

    scripts/rss-baseline.sh gen              # deterministic 100%-distinct corpus
    scripts/rss-baseline.sh rss  <file.md>   # settled RSS + mapping breakdown
    scripts/rss-baseline.sh heap <file.md>   # heaptrack + per-owner filter totals

`gen` is seeded, so the corpus reproduces byte-for-byte on any machine —
**the scratchpad documents this report was built on are not durable, and
a baseline you cannot regenerate is not a baseline.**

### WARNING: the script's corpus is NOT the report's corpus

**Do not compare a `rss-baseline.sh` reading against a figure from this
report.** They are different documents:

| | non-empty lines | VmHWM |
|---|---:|---:|
| `doc-uniq.md` — what §§7s-20 measured (scratchpad, not durable) | 640 | **145.4** |
| `uniq-960.md` — what `gen` produces (committed, reproducible) | 786 | **147.9** |

Both are 960 total lines and 100% distinct, but the structural mix
differs, so they are not the same workload and **their 2.5 MB difference
is corpus, not regression.**

This matters precisely for the job the script exists to do: measure an
optimisation. Someone who runs `gen`, gets 147.9, and compares it with
this report's 145.4 would read a 2.5 MB regression that does not exist.
**Baseline and re-measure with the SAME corpus — the script's — and
compare those two numbers to each other**, never one of them against the
report.

The report's figures were not re-derived on `uniq-960.md` because doing so
would renumber every realistic-content value for no gain in insight; the
proportions and verdicts are corpus-independent.

### The committed baseline

azul `743eb5837`, 1280x800, CPU backend:

| lines | non-empty | VmHWM | `[heap]` |
|---:|---:|---:|---:|
| 240 | 197 | 96 152 kB | 41.5 MB |
| 960 | 786 | 147 860 kB | 90.6 MB |
| 1 920 | 1 571 | 217 088 kB | 164.3 MB |

    marginal   71.8 then 72.1 kB/line — flat
    fit        RSS(MB) = 78.7 + 0.0721 x lines

**The 78.7 MB intercept reproduces across three independently generated
corpora** (78.5 / 78.7 / 79.3, §7r / §7u / here). That is a useful
property for whoever optimises: **a change in the INTERCEPT is a change to
fixed cost; a change in the SLOPE is a change to per-line cost.** Most
optimisations move exactly one, and reading a single total hides which.

### The traps it encodes, so they cannot be repeated

1. **`MINIWORD_OPEN`, never argv** — argv is ignored and a blank document
   plateaus convincingly (§7h).
2. **Never `MINIWORD_SHOT`** while profiling — `process::exit(0)` skips
   heaptrack's flush.
3. **Export the variable; never `heaptrack … env VAR=x ./app`** — that
   traces `env` and flushes nothing (§7k).
4. **Wait for a plateau, not a clock** — heaptrack slows startup ~10x.
5. **Use the distinct corpus.** `big.md` is 98% duplicate lines, so a
   caching change measured against it looks ~40% better than it is (§7s).

The script also prints per-owner filter totals for `text3::cache`,
`compute_document_pagination`, `LayoutTreeBuilder`, `solver3::sizing` and
`ParsedFont`, so the owners this report identifies can be tracked
individually rather than through one RSS number.

## 18. THE ORIGINAL QUESTION, ANSWERED IN ITS OWN TERMS

The job was posed as:

> `[heap]` 76.6 MB resident, engine self-report accounts for 26.58 MiB
> (33.5%). **~50 MB of heap is unexplained — that is the job.**

Everything above answers it piecewise. This answers it directly.

**The engine's report was never going to account for that 50 MB, and the
reasons are structural, not arithmetic.** `AZ_PROFILE=memory` walks
StyledDom + Solver3 + TextShapingCache on the `LayoutWindow` it belongs
to. Four things fall outside that walk by construction:

The premise counts **`[heap]` 76.6 MB**, and `[anon]` is listed
separately at 12 MB. So the frame buffers do **not** belong in this
answer — the two CPU pixmaps live in `[anon]` (§7h: an 8 008 kB region),
and the 7.8 MB `memfd` pair does not exist headless at all. Anything
charged against the 76.6 MB must actually be in `[heap]`:

| in `[heap]`, invisible to the engine's report | why | size |
|---|---|---|
| **miniword's pagination layout** | a `thread_local!` in `document.rs:407`, not the window's cache. The report walks `self.layout_cache` (`window.rs:3144`). Mechanism proven, §13 | **17.0 MB** on `big.md` |
| **freed-but-unreturned allocations** | a live-object walk cannot see them, but glibc keeps them in RSS. The startup CSS churn is the bulk, §7i | **~5.2 MB** |
| **decoded font tables** | `ParsedFont` copies out of the mmap; not a layout structure, §7j | **~3.1 MB** fixed + document part |
| | | **~25.3 MB** |

**Roughly half the gap, from three categories that are invisible by
design rather than missing.** *(~25.3 MB after the §19 locale correction;
this read ~22.8 when pagination was truncated to 14.5.)* The rest is shaped text beyond the two
buckets the engine names, Vec growth, and hundreds of sites below the
reporting threshold — plus, pointing the other way, **the engine's
26.58 MiB was itself INFLATED by >=3.4 MB** by the SmallVec double-count
(§12), so the accounted fraction was lower than 33.5% and the gap
slightly larger than stated.

*(An earlier draft of this section put the 15.6 MB of frame buffers in
this table and reached "~38 MB of the ~50". Wrong twice over: those
buffers are in `[anon]`, not `[heap]`, and half of them are the
windowed-only `memfd` while the premise describes a headless run. Charging
non-heap, wrong-configuration memory against a heap gap is exactly the
category error §10 caught in the HarfBuzz comparison.)*

### The premise that turned out to be wrong

The framing assumed the missing memory was *engine data the instrument
had failed to reach*. It mostly is not. It is **memory that is not the
engine's**: an application-side layout in an application-side cache,
window buffers, allocator retention, and font decode. The single largest
piece — 17.0 MB of pagination — belongs to the deliberate app/GUI
separation the user described as intentional, and this report prices it
without calling it waste.

That reframing is the most useful thing in this document. **A profile
that "accounts for 33.5%" sounds like an instrument problem and is
actually an ownership question**, and the two lead to completely
different work: one says "improve the report", the other says "decide who
should be holding this".

### What IS engine data, and indefensible

Of what remains after those four categories, one line dominates and one
verdict stands: **shaped text, 51.4 MB on realistic content, 79% of a
document's cost, ~140-240x Gecko's retained per-character figure, and
retained TWICE through separate measure and layout passes** (§7k, §10,
§7t). Two smaller undefended lines sit beside it — a 2.7 MB second copy
of the layout tree and the 5.2 MB CSS churn above.

**Two of the three are duplication**, which is a different problem from
"the struct is too big" and was found by backtrace rather than by reading
struct definitions.

## 19. A LOCALE BUG IN MY OWN INSTRUMENT — every filter total was low
<!-- rss-map-check: historical — this section's subject IS a correction, so it cites superseded values by design -->


Auditing every table in this report (by summing them programmatically
rather than by eye) found §13's pagination decomposition summing to
19.14 MB against its own stated 18.10 MB total. A subset exceeding its
superset — the check §13 itself calls "the cheapest self-check there is".

The cause is not that table. **It is the parser behind every
`--filter-bt-function` total in this report.**

    $ locale                       LANG=de_DE.UTF-8
    $ echo '9.57M' | awk '{print substr($1,1,length($1)-1)+0}'
    9
    $ echo '9.57M' | LC_ALL=C awk '{print substr($1,1,length($1)-1)+0}'
    9.57

**Under a comma-decimal locale, awk reads the period as a thousands
separator and truncates.** Every per-site M value lost its fraction, so
every filter total in §§7m, 7t, 10-16 is UNDERSTATED.

### Corrected totals

| figure | reported | **corrected** | error |
|---|---:|---:|---:|
| `text3::cache` (shaped text) | 48.07 | **51.43** | +7.0% |
| app-side pagination | 18.10 | **21.20** | +17.1% |
| `solver3::sizing` | 19.21 | **20.12** | +4.7% |
| `LayoutTree::clone` | 2.69 | **3.60** | +33.8% |
| `ParsedFont` | 10.44 | **11.73** | +12.4% |
| `FontManager` (in text3) | 2.67 | **3.34** | +25.1% |

**The relative error is worst on the SMALL figures**, because a truncated
fraction is a larger share of a small total — which is exactly backwards
from where one would look for it.

### What it changes, and what it does not

**No conclusion flips.** Every figure moves the same direction, so the
ordering, the proportions and all six verdicts stand:

- Shaped text is still the dominant line and still undefended — **51.4 MB
  rather than 48.1**, and the per-cluster figure becomes 959 B (engine) to
  **1 460 B** (allocator, was 1 378).
- Pagination is still ~29% of layout and still justified — 21.2 MB.
- The layout-tree duplicate is still undefended, at **3.6 MB not 2.7**.
- The §11/§14 instrument gap widens: `text3` 51.43 less `FontManager`
  3.34 = **48.09 MB against the engine's <=28.09**, so the unreconciled
  residual is **~20 MB, not ~17.3** — and §16's decision to stop
  searching stands, since the cause is unchanged.

### The part that mattered most

**`scripts/rss-baseline.sh` had the same bug**, and it is the durable
artifact — it would have silently understated every future measurement,
including any measurement of an optimisation's benefit. Fixed
(`LC_ALL=C` on both parsers), its recorded baseline re-measured, its
negative control re-run and still firing, and the locale trap added to
the five already in its header.

**Sixth instrument failure this job, and the first in an instrument I
wrote.** The others were heaptrack's, the engine's, or the workload's.
The lesson generalises past this bug: **a tool that formats output in
your locale will also parse in it**, and a decimal separator is not a
detail when every number in a report passes through one line of awk.

| `/proc/<pid>/smaps`, `/proc/<pid>/status` | **KiB** (1024 B) | `kB` |
| the engine's `AZ_PROFILE=memory` | **KiB** | `KiB` (honest) |
| `heaptrack_print` | **decimal MB/K** (1000 B) | `M`, `K` |

So the two instruments this report compares **do not share a unit**, and
a smaps figure divided by 1024 is MiB while a heaptrack figure is MB.
They differ by 4.9%.

### The headline figure, stated three ways

    VmHWM 126 092 KiB   =  123.1 MiB
                        =  129.1 MB  (decimal)
                        =  126.1     <- what this report says: KiB/1000,
                                        which is NEITHER unit

**Most RSS figures in this report are KiB/1000.** That is the common
sloppy convention (treating the kernel's "kB" label literally), it is
internally consistent across every smaps-derived number here, and
renumbering 2 600 lines to fix a 2.4% labelling error would risk more
than it repairs. **They are therefore comparable with each other and
NOT directly comparable with heaptrack's MB.** Where this report puts the
two side by side, read on.

### A cross-check this invalidates

§7i concluded that the blank floor's malloc heap is fully accounted for:

> `[heap]` 19.1 + `[anon]` 10.8 = **29.9 MB measured vs 29.37 MB
> profiled**, 0.5 MB apart.

Those 19.1 and 10.8 are KiB/1024, i.e. **MiB**; 29.37 is heaptrack's
**decimal MB**. Converted properly:

    29.9 MiB = 31.35 MB   against heaptrack's 29.37 MB
    gap = 1.98 MB, not 0.5 MB — FOUR TIMES larger

The conclusion **survives but is weaker than stated**: ~94% of the blank
floor's malloc heap is accounted for by the profiler, not ~98%. The
remaining ~2 MB is the same class as the sub-threshold tail (§7m) and
does not change any verdict.

### What is NOT affected

- **Arithmetic within one tool.** §7h's framebuffer prediction
  (`1280x800x4x2 = 8 000 KiB` against a measured `8 000 KiB`) is exact —
  both sides are KiB.
- **Ratios between figures from the same tool.** All the filter-based
  comparisons in §§7m-20 are heaptrack-vs-heaptrack.
- **The scaling law.** Every point in §7r/§7u is a VmHWM reading in the

- **Every verdict in §9.**

## 22. THE BLIND SPOT §7l NAMED IS NOW MEASURED — 15.6 MiB, and it is NOT the resize retention

§7l recorded that the engine's `AZ_PROFILE=memory` walk reports only
`self.layout_cache`, and never visits `layout_results: BTreeMap<DomId,
DomLayoutResult>` — whose every entry owns a `StyledDom` **and** a
`LayoutTree` **by value** (`layout/src/window.rs:651`). That gap is now
closed. Measured on `big.md`, real window, three frames:

    [MEM] GRAND TOTAL (StyledDom + Solver3 + TextCache)  24 057 KiB
    [MEM] layout_results  1 DOM(s), 15 987 KiB  (StyledDom 2 740 + LayoutTree 13 246 KiB)

So engine-owned layout state is **~39.1 MiB, not the 23.5 MiB the GRAND
TOTAL claims** — the walk was seeing 60% of it. Every `accounted / rss`
ratio in this report predates that and is correspondingly understated. The
two are reported separately rather than summed, because whether the
`LayoutTree` in `layout_results` is a distinct allocation from
`layout_cache.tree` or an alias of it is not established here, and adding
them would assert an answer this measurement does not have.

### It does NOT explain the ~40 MiB resize retention

This was the leading hypothesis for §7-open's unexplained retention, and it
is refuted: the figure is **byte-identical on all three frames** (15 987
KiB at frame 0, at the first resize, and at the second), while live memory
goes 100.8 -> 141.5 MiB across the same frames. Flat is flat.

### THE MEASUREMENT THAT NEARLY WENT IN THE REPORT AS A FINDING

The first version of this walk printed, confidently and on every frame:

    [MEM] layout_results   0 DOM(s), 0 KiB

That reads as a clean refutation — "the map is empty, the hypothesis is
dead" — and it was nearly written up as one. It was an artifact of WHERE
the walk sat in the frame. `layout_results.clear()` runs at `window.rs:1282`
early in a full relayout; the insert that refills it for a **real window**
is at `window.rs:3591`, at the tail. The main `[MEM]` block sits between
them, so it observes a window in which the map is empty **by construction**.
The one insert that does precede it, `window.rs:3108`, is behind `if
self.skip_gpu_sync` — the **headless** path only. Measured headless, the
same code would have printed a plausible non-zero and hidden the placement
bug entirely.

The generalisable form, and the reason this is written down: **a zero is not
a measurement.** Any instrument that reports "nothing here" is also
consistent with "not looking", and the two are indistinguishable from the
output alone. Before a zero is allowed to refute anything, it must be shown
to be capable of being non-zero — here, by relocating the walk past the
insert and watching it read 15 987 KiB. That is the same negative-control
discipline as [[azul-gates-with-wrong-premises]], applied to a probe rather
than an assertion: an instrument that cannot fail is not reporting.

Note this failure mode is invisible to the whole verification battery. The
walk is behind `AZ_PROFILE=memory`, off in every test; the tests pass
identically whether it reads 0 or 15 987. Nothing but reading the number
against a plausible expectation would have caught it.

## 24. THE RESIZE RETENTION — three candidates refuted, and the headline number was the instrument

The largest unexplained item at the end of §22 was ~40 MiB of live memory
retained by the first window resize while the engine's own walk moved
+11 KiB. It is now smaller than that, and better understood.

### The measurement that was being misread

I had been quoting one line — `live (uordblks)` — from output that also
contains a full RSS census. Read whole:

| | frame 0 | frame 1 (resize) | frame 2 (resize) |
|---|---:|---:|---:|
| `[heap]` | 95 940 KiB | 127 404 KiB | 128 128 KiB |
| `[anon]` (incl. pixmaps) | 18 956 KiB | 4 304 KiB | 4 304 KiB |
| `hblkhd` (mmapped) | 23.7 MiB | 1.7 MiB | 1.7 MiB |
| framebuffer (memfd) | — | 4 000 KiB | — |
| **TOTAL RSS** | **146.0 MiB** | **168.4 MiB** | **165.5 MiB** |
| `live (uordblks)` | 100.8 MiB | 141.5 MiB | 141.8 MiB |

`hblkhd` collapses by **22.0 MiB** at exactly the frame `[heap]` grows by
**30.7 MiB**, while total RSS rises **+22.4 MiB**.

`uordblks` counts main-arena allocations and **not** mmapped chunks. An
allocation migrating from mmap into the arena therefore raises `uordblks`
while allocating nothing new. That is consistent with the whole gap between
the two figures: +40.7 MiB by `uordblks` against +22.4 MiB of actual RSS.

**INFERENCE, not proof.** The arithmetic fits (22 MiB leaves mmap; ~18 MiB of
the discrepancy is unexplained by anything else) but per-chunk provenance has
not been established. Proving it needs heaptrack across both frames.

**What is solid: real retention on the first resize is +22.4 MiB RSS, not
+40.7 MiB.** The larger number was the instrument, not the program.

This is the same failure as the KiB/MB confusion in §21 and the "peak sits
above settled" mechanism that had to be retracted: when two figures for
nominally the same quantity disagree, establish **what each one counts**
before proposing a mechanism for the difference.

### Three candidates, all refuted by measurement

| candidate | verdict | evidence |
|---|---|---|
| `layout_results` | REFUTED | byte-identical 15 987 KiB on all three frames (§22) |
| engine caches | REFUTED | the walk moves +11 KiB across the whole sequence |
| app pagination cache | REFUTED | probe fires ONCE at startup, never during a resize |
| framebuffers | REFUTED | 3.9 MiB, and memfd-backed so it cannot appear in `uordblks` at all |

The pagination probe is worth noting as a method point: it printed once and
then stayed silent. A silence that follows a proven-firing probe means "did
not run"; a silence with no prior firing means nothing at all. That
distinction is what made the `0 DOM(s)` reading in §22 worthless and this one
usable.

### The app-side pagination layout, measured at last

    [MEM][app] pagination LAYOUT_CACHE = 12 622 KiB (tree true, positions 1041)

**12.6 MiB.** This is the separate A4-width layout the user ruled INTENTIONAL
— reported, not called waste. It supersedes the ~20 MB read off the
`compute_document_pagination` heaptrack filter, which overlaps other owners by
construction and so was never a clean figure for this cache alone.

### Not a leak

Frame 2 settles: `[heap]` +724 KiB, RSS **−2.9 MiB**. The resize path is a
one-time step to a larger working set plus an allocator regime change, not
unbounded growth.

### What remains unattributed

**~22.4 MiB of genuine RSS growth on the first resize.** Nothing in the engine
walk moves with it, `layout_results` is flat, pagination is not invoked, and
framebuffers are ruled out by construction. No candidate remains from the list
worked through here.

Stated as unattributed rather than assigned to a neighbour. The next probe is
heaptrack over a two-resize run comparing `-p` against `-l` — the only tool

## 26. RESOLVED — the resize growth is allocator high-water, not retained data

The controlled comparison §25 asked for: same corpus (`big.md`), same binary,
one variable — whether the E2E scenario drives resizes.

| | no resize | 2 resizes | delta |
|---|---:|---:|---:|
| peak heap | 83.85 M | 145.98 M | **+62.13 M** |
| total leaked (RETAINED) | 73.02 M | 75.66 M | **+2.64 M** |
| `display_list` retained | 36.34 M | 39.18 M | +2.84 M |
| `text3::cache` retained | 36.08 M | 33.46 M | **−2.62 M** |

**A resize costs +62 M of PEAK and +2.6 M of RETAINED.** That is the whole
answer to §24, and it is not what any of the candidate hypotheses predicted.

The 22.4 MB of RSS growth is **glibc's arena staying expanded after a large
transient spike**. Live bytes barely moved; the allocator simply did not
return the pages. This is consistent with every other observation:

- `[heap]` +30.7 MiB while `hblkhd` fell 22.0 MiB (§24) — the arena grew and
  large chunks stopped being served by mmap;
- frame 2 settles at RSS −2.9 MiB — a high-water mark decaying, not a leak;
- the engine's object walk moves +11 KiB — because there genuinely is almost
  nothing new retained to walk.

### §25's candidate is REFUTED

`display_list` was named there as the leading candidate on the strength of
being the largest retained owner (39.18 M). Under control it grows by
**+2.84 M**, not 22.4. Being the biggest owner said nothing about being the
one that GREW — a whole-run total cannot answer a delta question, which §25
listed as a reason not to trust it and which the control has now confirmed.

Note also `text3::cache` retains **LESS** with resizes (−2.62 M). Re-laying
out at a new width evidently drops shaped runs the old width had cached. Two
owners moving in opposite directions is exactly why the per-filter totals
must not be summed.

### Method

Four hypotheses were tested against this number and all four failed:
`layout_results`, the engine caches, the app pagination cache, framebuffers —
plus `display_list` here. The reason they all failed is that they were all
answers to the wrong question: they ask *what is holding memory*, and the
number came from *memory that is held by nobody*.

The only thing that distinguished it was a controlled before/after on one
variable. That is now the third time in this report a
plausible-mechanism-that-fits lost to a one-variable comparison; the previous
two were the retracted per-page duplication and peak-by-site vs
live-by-owner.

### Consequence for the optimisation plan (NOT a recommendation)

Reducing retained bytes will not move this 22.4 MB, because it is not
retained bytes. What would move it is reducing the transient PEAK of a
relayout — or `malloc_trim`, which is an allocator behaviour question, and
the no-custom-allocator ruling does not obviously cover it either way. Left
for the user.

## 27. malloc_trim MEASURED — it works, and recovers ~1.5 of ~22 MB

Added `probe::malloc_trim()` (dlsym, so a missing symbol cannot break the
link) called after relayout behind `AZ_MALLOC_TRIM=1`. A/B on the same
scenario, one variable:

| | frame 0 | frame 1 | frame 2 |
|---|---:|---:|---:|
| no trim | 146.0 MiB | 164.9 MiB | **168.9 MiB** |
| `AZ_MALLOC_TRIM=1` | 145.9 MiB | 162.0 MiB | **167.4 MiB** |

It reports `released=Some(true)` on every call, so the call is doing
something. It recovers **~1.5 MiB of the ~22 MB** §26 attributed to arena
high-water.

**That is informative, not disappointing.** `malloc_trim` can only return
pages at the TOP of the heap plus free ranges it can `madvise` away.
Recovering 7% means the arena is **not** holding one contiguous free block —
it is FRAGMENTED, with live allocations interleaved among the freed relayout
scratch. §26 said the pages are "not returned"; this refines it to **not
returnable in their current arrangement**.

Consequence: trimming is not the lever. Reducing the transient PEAK of a
relayout — so the arena never has to grow — acts on the cause; trimming acts
on a symptom that fragmentation has already made unreachable.

NOT a recommendation to enable it by default: 1.5 MiB against the cost of
walking the free lists on every relayout is a poor trade on this evidence.
It stays opt-in.

## 28. TWO STRUCTURAL GAPS IN THE PROBE ITSELF (user-raised, not yet done)

**1. `feature = "probe"` is a COMPILE-TIME flag and should not be.** A user
who wants an accurate memory report or a frame CPU breakdown currently has to
REBUILD. The right shape is: `probe` compiled into `build-dll` always, with a
RUNTIME flag to enable it, because measuring RSS on every frame does cost
performance and must be switchable — but switchable without a recompile.
Already visible as a defect in this report: `current_rss_bytes` is behind the
feature, so §27's trim logging had to use `rss_census()` instead, and
`AZ_PROFILE=heap` silently reports 0 without the feature rather than saying it
cannot measure.

**2. The report should expose ALLOCATOR SPECIFICS, so a user can see what
§26 and §27 took two days to establish.** The engine already reads
`mallinfo2`; what it does not do is present it as "you resized, so N pages
are now over-allocated". That is the shape of the answer a user needs, and it
is derivable from figures already collected (`arena`, `hblkhd`, `keepcost`,
`fordblks` against live).

USER RULING CLARIFIED: "no custom allocator" means do not REPLACE the
allocator. It does NOT forbid using allocator-specific APIs to inspect and
steer the one we have — `malloc_trim`, and the equivalents in jemalloc /
mimalloc / rpmalloc — at moments the engine knows are good, such as after a
frame settles. This report had been treating the ruling more broadly than it
was meant.

## 29. A WAYLAND SHM LEAK — 1 279 pools and 2 558 buffers, from the user's own log

`pdf2html/log5.txt`, captured by the user from a live interactive session,
ends in a Wayland teardown dump:

    warning: queue 0x... destroyed while proxies still attached:
      wl_buffer@3868 still attached
      wl_shm_pool@3866 still attached
      ... (down to @25)

Counted:

| proxy | still attached at teardown |
|---|---:|
| `wl_shm_pool` | **1 279** |
| `wl_buffer` | **2 558** (exactly 2 per pool — the two ShmSlots) |

Every `wl_shm_pool` is backed by an `mmap`'d shared region sized for the
window (`width x height x 4 x 2 slots`). 1 279 of them were created and none
were destroyed.

**This is the first candidate found in this whole report that could account
for `[anon]` behaviour** — the job statement's `[anon] 12 MB resident of
537 MB reserved`. A leaked pool's mapping stays reserved; only pages actually
touched stay resident. Reserved-far-exceeds-resident is exactly the signature
of accumulated, mostly-untouched mappings.

**NOT yet root-caused, and the obvious suspect is innocent.**
`impl Drop for CpuFallbackState` (`mod.rs:5821`) is correct on inspection: it
destroys every slot buffer, destroys the pool, `munmap`s the region and closes
the fd, in the right order. And `resize_surface` (`mod.rs:5852`) does
`drop(cpu_opt.take())` before rebuilding, which would run it. If Drop ran
1 279 times nothing would be attached — so those states never reached Drop,
and WHERE they escape is the open question.

Directions, none verified:
- `CpuFallbackState::new` failing AFTER `wl_shm_create_pool` succeeds leaks the
  pool with no struct to drop (`mod.rs:5728`);
- pools created somewhere other than `resize_surface` / the `Cpu(None)`
  initialiser;
- a per-present rather than per-resize creation path.

Count them first: 1 279 pools against the number of configure events in the
same run tells you immediately whether this is one-per-resize (a Drop that is
not running) or many-per-resize (a creation path nobody is tracking).

### Consequence for §24-§27

Those sections characterise "a resize" using the `AZ_E2E` path. The user
reports the MOUSE path relayouts correctly and the E2E path does not — the
opposite of the assumption recorded earlier in this report, which is now
withdrawn. Until the two paths are shown to agree, the resize numbers describe
the E2E path only. The +62 MB transient peak and +2.6 MB retained are real
measurements of *something*; what they are measurements *of* is now in
question.

### §29a. Protocol semantics, LOOKED UP rather than inferred

From the Wayland protocol specification (wayland.app/protocols/wayland):

- **`wl_shm_pool.destroy`**: *"A buffer will keep a reference to the pool it
  was created from so it is valid to destroy the pool immediately after
  creating a buffer from it."*
- **`wl_buffer.destroy`**: *"If and how you need to release the backing
  storage is defined by the buffer factory interface."* The `release` event
  is what tells the client the compositor is done: on receiving it *"the
  client is immediately free to reuse the buffer and its backing storage."*

**Consequence — a concrete fix that does not depend on root-causing the
leak.** `CpuFallbackState` holds `pool` for its whole lifetime and destroys it
only in Drop. The protocol says the pool may be destroyed as soon as the
buffers exist, because each buffer holds its own reference. Destroying it at
the end of `CpuFallbackState::new` removes all **1 279** leaked pool proxies
whatever the reason the states escape Drop, and is strictly more correct than
what is there now.

It does NOT fix the 2 558 leaked `wl_buffer`s or the leaked `mmap`s — those
still need the escape path found. Partial, and labelled as such.

The `busy` flag on `ShmSlot` is the `release`-event bookkeeping the second
quote requires, so that part of the design is already right.

Sources: https://wayland.app/protocols/wayland

## 30. ROOT CAUSE of the E2E resize: nothing resizes the platform surface

The user reported that a MOUSE resize relayouts correctly and an E2E-driven
resize leaves part of the window blank, as if the compositor scaled a texture.
Both halves are explained by one gap.

**The mouse path** (Wayland): `xdg_toplevel_configure_handler`
(`events.rs:1537`) updates `current_window_state.size.dimensions`, requests
regeneration, AND calls **`resize_surface(width, height)`**
(`events.rs:1620`), which drops the old `CpuFallbackState` and rebuilds the
shm buffers at the new size (`mod.rs:5852`).

**The E2E path**: `DebugEvent::Resize` (`e2e/full.rs:11534`) clones the window
state, sets `size.dimensions`, and applies it via
`CallbackChange::ModifyWindowState`. That lands in the cross-platform
`apply_user_change` (`dll/src/desktop/shell2/common/event.rs`), whose
size-change branch does exactly one thing:

    if size_changed || dpi_changed {
        self.request_regeneration(RelayoutReason::Resize);
    }

**There is no platform-surface resize anywhere on this path.** The engine
relayouts at the new size; the Wayland buffer keeps the old dimensions. The
compositor is handed old-size content for a new-size window — blank where the
buffer does not reach, scaled where it does.

That file is cross-platform and `resize_surface` is Wayland-specific, so the
fix is a hook: `ModifyWindowState` must, on `size_changed`, ask the platform
window to resize its surface — the same call the configure handler already
makes. Every backend needs the equivalent (X11 has its own ConfigureNotify
path, Windows/macOS likewise), so this is a gap in the cross-platform seam,
not a Wayland bug.

### This invalidates §24-§27 as measurements of "a resize"

Those sections measured the E2E path. That path relayouts the ENGINE but never
reallocates the platform buffer, so the +62 MB transient peak and +2.6 MB
retained describe **a relayout without a surface reallocation**. A real
user-driven resize additionally drops and rebuilds the shm pool and buffers
every configure — which §29 shows happening 1 279 times in one session.

The §26 conclusion (resize growth is allocator high-water, not retained data)
is about heap allocations and is unaffected in its own terms. But it must NOT
be quoted as "what a user-driven resize costs" until re-measured on the mouse
path, because the mouse path does strictly more work.

## 31. THE FRAGMENTATION CURVE WAS ALREADY IN THE OUTPUT

The engine's allocator block already reports fragmentation and already
answered the question §27 spent a build cycle measuring. Across the three
frames of the resize scenario:

| | frame 0 | frame 1 (resize) | frame 2 (resize) |
|---|---:|---:|---:|
| live (uordblks) | 100.8 MiB | 141.5 MiB | 141.8 MiB |
| **freed, still held** | 3.3 MiB (**3%**) | 3.3 MiB (**2%**) | **26.8 MiB (16%)** |
| arena | 104.0 MiB | 144.8 MiB | 168.5 MiB |
| **releasable by trim** | **0.0 MiB** | **0.0 MiB** | **0.0 MiB** |

Two things fall straight out.

**1. `releasable by trim` is ZERO on every frame.** That is `keepcost`, the
top-most releasable block. It PREDICTED the §27 result before the measurement
was taken: there is nothing at the top of the heap to give back. The ~1.5 MiB
`malloc_trim` did recover came from `madvise`-able ranges below the top, which
is the only thing left for it to find. **This line was printing on every frame
while that experiment was being built and run**, and was not read — the fourth
time in this report that skimming past output produced work that the output
had already answered.

**2. The fragmentation SPIKE is on the second resize, not the first.**
3% -> 2% -> 16%. Freed-but-held goes 3.3 -> 3.3 -> 26.8 MiB. The first resize
GROWS the arena (104 -> 144.8) and uses what it takes; the second reuses the
now-large arena and leaves 26.8 MiB stranded inside it. That is the signature
of many small allocations of a different size class than the ones freed —
which is why the space is unusable for the next relayout AND unreturnable to
the OS.

So the answer to "at what point does fragmentation go up" is: **the second and
subsequent relayouts, not the first.** A single resize looks clean; the
pattern only appears when the arena is reused.

### What this adds to §26

§26 attributed the RSS growth to arena high-water. This refines the mechanism:
the arena grows once (first resize) and then FRAGMENTS (second resize). Those
are two distinct effects with two distinct fixes — the first is about peak
size, the second about allocation size-class churn — and only the second is
what the user identified as "lots of micro allocations".

The metric the user asked to see in the report is therefore already present.
What was missing is this reading of it, and a `keepcost` line that says WHY
it is zero rather than leaving a bare 0.0 to be skimmed past.

## 32. THE SHM LEAK IS CONFIGURE-PATH-SPECIFIC — read off data already collected

§29 counted 1 279 leaked `wl_shm_pool` and 2 558 `wl_buffer` proxies in the
user's INTERACTIVE session. The obvious next step looked like instrumenting
the pool lifetime. It was not necessary: the RSS census already answers
whether the leak reproduces on the E2E path.

`[anon]` across the three frames of the E2E resize scenario:

    frame 0   18 956 KiB  (18.5 MiB)
    frame 1    4 304 KiB   (4.2 MiB)   <- after a resize
    frame 2    4 304 KiB   (4.2 MiB)   <- after a second resize

At 1280x800 ARGB8888 a pool is `w x h x 4 x 2 slots` ~ 8 MB. If pools
accumulated, `[anon]` would rise by roughly that per resize. It **falls** and
then holds **exactly flat** — 4 304 KiB twice, not approximately.

**Conclusion: the pool leak does NOT reproduce on the E2E path. `Drop` runs
correctly there.** Both paths call the same `resize_surface` and the same
`impl Drop for CpuFallbackState`, so the defect is not in that shared code —
it is in something the COMPOSITOR-CONFIGURE path does differently.

That is a real narrowing and it cost no new instrumentation. What differs
between the paths, as candidates for the next investigation:

- the interactive path calls `resize_surface` from INSIDE a Wayland listener
  callback (`xdg_toplevel_configure_handler`), i.e. during
  `wl_display_dispatch`; the E2E path calls it from `apply_user_change`,
  outside dispatch;
- a drag-resize produces MANY configures in rapid succession, so buffers are
  far more likely to be still BUSY (no `release` event yet) when the state is
  dropped;
- 1 279 is a plausible count for a drag session and an implausible one for
  three programmatic resizes, so the leak may be rate-dependent rather than
  unconditional.

NONE of these is verified. The measurement that would separate them is the one
§29 already asked for: count pools created against configure events in the
SAME interactive run.
