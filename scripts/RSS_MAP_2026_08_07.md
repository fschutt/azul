# Where miniword's 103 MB of RSS goes

Measured 2026-08-07 on azul `743eb5837`, release, headless, no
`MINIWORD_SHOT`. Document: `big.md`, a 960-line markdown (~60k characters,
~40 A4 pages).

**This is a map, not a proposal.** No optimizations are recommended here;
several are implied and are deliberately left for the reader.

---

## 1. The heap is almost entirely LIVE DATA

**Both instruments, same run, 32.9 s, `AZ_PROFILE=memory` + heaptrack:**

| Source | Number |
|---|---:|
| peak RSS (heaptrack included) | **106.20 MB** |
| heaptrack peak heap consumption | **75.02 MB** |
| heaptrack total live at SIGTERM | **71.37 MB** |
| `[heap]` resident (smaps, same process) | **62.9 MB** |
| engine self-report GRAND TOTAL | **26.58 MB** |
| engine's own `after layout` reading | current rss 84.9 MiB, peak 87.4, **unreturned 2.5 MiB** |

**The heap holds ~75 MB of LIVE allocations.** There is no large pool of
freed-but-retained memory: the engine measures `unreturned` at **2.5 MiB**,
and glibc tunables move RSS by under 350 kB (below). Optimising this means
allocating less or retaining less — there is no slop to reclaim.

### Two of my own earlier headlines were WRONG. Both retracted.

**Retracted #1 — "half the heap is not data" / "~38 MB of allocator
retention".** That came from a heaptrack run reporting a 38.87 MB peak.
**That run lasted 3.98 s and was killed before layout finished.** The
valid run lasts 32.9 s and reports 75.02 MB. The 38.87 MB was a partial
measurement of an incomplete workload, compared against an `[heap]` figure
from a *different* run — two errors compounding into a confident wrong
conclusion.

**Retracted #2 — the glibc explanation.** Tested directly, peak RSS:

    baseline                        102 764 kB
    MALLOC_ARENA_MAX=1              102 620 kB
    MALLOC_TRIM_THRESHOLD_=131072   102 824 kB
    MALLOC_MMAP_THRESHOLD_=65536    102 476 kB

All within ~350 kB. Refuted independently of #1, and consistent with the
engine's own `unreturned=2.5 MiB`.

**Lesson for whoever reads this next:** check the profiler's *runtime*
against the workload's runtime before trusting its peak. A profile that
ends early looks exactly like a profile of a smaller program.

## 1c. THE MAP CLOSES — heaptrack and smaps reconcile within 0.2%

The last unattributed mapping was `[anon]`: 12.0 MB resident of 537.6 MB
mapped, producer unknown. Measured directly:

- **The process is SINGLE-THREADED** (1 entry in `/proc/<pid>/task`), so
  none of it is thread stacks. That guess is retracted.
- 40 anon mappings; the largest is **7.8 MB mapped / 7.82 MB resident** —
  one fully-resident mapping.

That 7.8 MB is the same memory heaptrack attributes to `AzulPixmap::new`
(7.72 MB). glibc serves allocations above `MMAP_THRESHOLD` with `mmap`, so
a large pixmap lands in `[anon]` and never appears in `[heap]`. The two
instruments were labelling the same bytes differently.

So the accounting closes:

    [heap]  62.9 MB  +  [anon]  12.0 MB  =  74.9 MB
    heaptrack peak heap consumption      =  75.02 MB

| Owner | Resident | Instrument |
|---|---:|---|
| live allocations (`[heap]` + large mmap'd) | 74.9 MB | both, agreeing |
| miniword binary text/rodata | 11.6 MB | smaps |
| font files (mmap'd, mostly untouched) | 8.8 MB | smaps |
| libc / libm / other shared objects | ~3 MB | smaps |
| **total** | **~98-106 MB** | matches VmRSS across runs |

**Nothing is unexplained at the mapping level.** One gap remains a level
down: the ~15.6 MB of live allocations below heaptrack's reporting cut.

## 2. Full RSS breakdown

From `/proc/<pid>/smaps`, aggregated by mapping:

| Owner | Resident | Mapped | Notes |
|---|---:|---:|---|
| `[heap]` | 76.6 MB | 79.7 MB | of which **38.87 MB live**, ~38 MB allocator-held |
| miniword binary | 11.7 MB | 24.6 MB | text+rodata pages actually touched |
| `[anon]` | 12.0 MB | 537.6 MB | **mapped ≠ resident**; address-space reserve |
| font files (59 mappings) | 8.8 MB | 18.8 MB | mmap'd; untouched pages cost nothing |
| libc / libm / other .so | ~3 MB | ~5 MB | |
| **Total** | **~103 MB** | | matches VmRSS |

Two traps worth naming:

- **`[anon]` maps 537 MB and is 12 MB resident.** Anyone reading VSZ
  instead of RSS will chase half a gigabyte that does not exist.
- **Fonts are not the problem.** 8.8 MB resident against 18.8 MB mapped and
  99 MB of CJK/emoji faces on disk. `NotoSansCJK` etc. barely register;
  `DroidSansFallbackFull.ttf` is 3.8 MB mapped and 0.3 MB resident.
  rust-fontconfig's mmap is doing exactly what it claims. Lazy font
  loading would buy single-digit MB on THIS workload. (A CJK-heavy
  document is a different case and needs its own measurement.)

### Cross-check against the engine's own report

`AZ_PROFILE=memory` accounts for **26.58 MiB**:

    StyledDom             2 740 KiB
    Solver3 LayoutCache  16 807 KiB   (warm.inline 13 516)
    TextShapingCache     10 586 KiB
    styles                  109 distinct Arc<StyleProperties> / 31 086 glyphs

26.58 MB of a 38.87 MB live heap = **68% accounted by the engine itself**.
The remaining ~12 MB of live heap is font parsing (4.25 MB), the display
list (1.56 MB), and unattributed small allocations.

**The engine's report and heaptrack agree.** That is worth stating: two
independent instruments, built at different times, land within noise of
each other on the same workload.

## 4. The largest single stack, and why it is not waste

The 8.30 MB stack runs `miniword::layout` → `editor_screen` →
`paginate_cached_with_fonts` → `compute_break_paths_with_fonts` →
`compute_document_pagination` → … → `perform_fragment_layout`.

That is **miniword's own pagination layout**, separate from the engine's
layout for display. Per the project owner this separation is deliberate —
app-side paging concerns are kept out of azul rather than building PDF
specifics into the engine. It is reported here for size only.

Its cost is roughly 8.3 MB of Vec growth plus its share of the layout tree
and text caches. There are two full layouts of this document in the
process, by design.

## 5. What scales with the document, and what does not

| Configuration | Peak RSS |
|---|---:|
| blank document | 55.0 MB |
| `t.md` (24 lines, 1 page) | 61.9 MB |
| `big.md` (960 lines, ~40 pages) | 103.1 MB (was 120.9 before `743eb5837`) |

So: a **~55 MB floor** plus ~48 MB for this document. The floor is binary
(11.7) + fonts (8.8) + `[anon]` (12) + a baseline heap.

**A retracted claim, kept so it is not re-derived:** an earlier note in
this session read the curve as "~1.5 MB per PAGE" and asserted pagination
built a Dom + StyledDom + layout per page. The arithmetic fit; the
mechanism was inference and is wrong. The document is laid out as ONE tree
(1 329 nodes, 31 086 clusters), twice (app + engine) — not forty times.

## 6. Per-character cost, for scale

`warm.inline` is 13.5 MB of the 16.8 MB layout cache — **80%** — across
31 086 shaped clusters, i.e. roughly one cluster per character.

Pinned struct sizes (`layout/tests/struct_sizes.rs`): `PositionedItem`
200 B, `ShapedItem` 184 B, `ShapedCluster` 176 B, `ShapedGlyph` 96 B,
`LayoutFontMetrics` 32 B (copied into every glyph), `LayoutNodeWarm`
1 176 B.

For external scale: HarfBuzz's own documented buffer format is ~24 B/glyph
(`hb_glyph_info_t` + `hb_glyph_position_t`), and Gecko's full retained cost
is ~6 B/char (4-byte CompressedGlyph + 2-byte UTF-16), 11 B/char with its
word cache. Gecko's retained textruns end up at **0.14% of layout memory**.
Ours are 80%.

No engine publishes a bytes-per-character figure for retained shaped text
(checked: Skia, Gecko, Blink, Qt, LibreOffice, Zed, Warp, Levien), so
these are the only external yardsticks available.

## 6b. The tail: 92% attributed at call-site level

`heaptrack_print -n 30` (the default reports 10) covers **69.11 MB of the
75.02 MB live heap — 92%**. The tail below the top ten holds no hidden
large owner; it is genuinely diffuse. Grouped:

| Group | MB | Call sites |
|---|---:|---|
| **Font machinery (parse + tables)** | **~7.5** | `ParsedFont::from_provider` 4.25, `allsorts::ReadArray::read_to_vec` 1.12 + 0.64 + 0.28, `ReadScopeOwned::new` 0.37, `FcFontCache::insert_builder_font` 0.45 + 0.36, `ParsedFont::from_bytes` 0.35 |
| Widget DOM construction | ~1.4 | `Button::dom` 0.93 over 4 236 calls, `register_material_icons` 0.45 |
| Glyph raster cache | ~0.75 | `get_or_build_cells_lcd` 0.48, `build_path_from_contours` 0.27 |
| Display list painting | 0.61 | `DisplayListGenerator::paint_inline…` |
| Shaping (beyond the 21.9 MB) | 0.75 | `shape_text_internal` |
| App document model | 0.45 | `DocumentModel::from_path` |
| Font chain resolution | 0.36 | `resolve_font_chain_impl`, 502 432 calls |

**Font machinery is ~7.5 MB of live heap**, which is SEPARATE from the
8.8 MB of mmap'd font files in section 2 — that is the parsed/decoded
form, not the file bytes. Together fonts cost ~16 MB of the ~100 MB.
Still not the dominant cost, but three times what the mmap figure alone
suggested, and worth stating precisely since "fonts are not the problem"
is a settled ruling that could otherwise be over-read.

Remaining unattributed: **~5.9 MB (8%)** below the 30th entry, spread
across hundreds of small sites. Not worth further passes; a flamegraph
would only subdivide it further.

transient-spike problem.

### Correction: text shaping is 42%, not 29%

An earlier version of this table listed shaping at 21.90 MB and a
9.11 MB `RawVec::finish_grow` entry separately, then failed to sum to
75.02 — it came up ~10 MB short. Regrouping by owner shows the 9.11 MB of
Vec growth sits *beneath* `perform_fragment_layout` → `layout_flow`; it
IS shaping. **Text shaping owns 31.76 MB, 42% of the live heap.** Caught
by adding the table up, which is the only reason it was found.

### 7c. FIXED vs PER-DOCUMENT, by owner

The same heaptrack analysis run on a BLANK document, differenced against
big.md. This separates "the cost of having a window at all" from "the
cost of this document" at call-site granularity, which the RSS-level
floor figure could not.

| Owner | blank | big.md | delta |
|---|---:|---:|---:|
| Text shaping | 0.53 | 31.76 | **+31.22** |
| **Pixmaps** | **11.82** | **11.82** | **0.00** |
| Font machinery | 3.16 | 8.18 | +5.02 |
| Other / unnamed | 3.28 | 6.64 | +3.36 |
| Layout tree | 0.37 | 3.68 | +3.31 |
| Layout results | 0.00 | 3.18 | +3.18 |
| Cached inline layout | 0.00 | 2.47 | +2.47 |
| **Widget DOM / icons** | **1.37** | **1.37** | **0.00** |
| top-N total | 20.54 | 69.11 | +48.56 |
| peak heap | **25.84** | **75.02** | +49.18 |
| peak RSS | **55.5** | ~103 | +47.5 |

**Two findings worth separating:**

1. **The framebuffer pair does not scale with the document — 11.82 MB in
   both.** They are window-sized, not document-sized, which is what one
   would want. But that means **pixmaps are 46% of the blank document's
   live heap (11.82 of 25.84 MB)**. At small document sizes the
   framebuffers ARE the memory; at large ones shaping is. These are two
   different problems and a single "reduce memory" effort will hit one
   and miss the other.

2. **Text shaping is essentially all per-document** (0.53 → 31.76). It
   contributes almost nothing to the floor and almost everything to the
   growth. Combined with §6's per-character figures, this is the line
   that decides whether a 10k-line document is usable.

Font machinery splits: ~3.2 MB fixed (the base faces any window loads)
plus ~5.0 MB for the additional faces this document's text pulled in.

### The map in one paragraph

~23 MB is fixed cost anyone pays (binary, shared libraries, mmap'd font
files). ~17 MB is fonts across both forms (8.8 mapped + 8.2 decoded).
~12 MB is the double-buffered framebuffer the damage system requires.
The remaining ~50 MB is retained layout and text for ONE 960-line
document — and **31.76 MB of that, 42% of the live heap, is shaped
text**. Every other line in this map has a reason worth defending. That
one does not.

The blank-document floor is 55 MB, the document adds ~48 MB. Two
different problems: the floor is binary + fonts + buffers, the growth is
shaped text.

## 8. Method notes

- heaptrack with `MINIWORD_SHOT` set yields an EMPTY profile (3 KB): the
  screenshot callback ends in `std::process::exit(0)` and skips the atexit
  flush. Run headless without it, let it settle, SIGTERM.
- `pgrep -f "release/miniword"` matches the heaptrack wrapper, not the
  child. Use `pgrep -x miniword`.
- The engine's own report ends with `GRAND TOTAL` and `accounted / rss`
  lines. Read the whole output — grepping past them cost two ticks and a
  wrong conclusion that the instrumentation was missing.
