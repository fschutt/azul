# Where miniword's RSS goes

Measured 2026-08-07 on azul `743eb5837`, release, no `MINIWORD_SHOT`.
Document: `big.md`, a 960-line markdown (~60k characters, ~40 A4 pages),
opened via `MINIWORD_OPEN` (argv is ignored — see §7h).

**Two configurations, and the difference matters:**

    windowed (Wayland, what the user runs)   126.1 MB
    headless (what most of this report maps)  ~103 MB

**This is a map, not a proposal.** No optimizations are recommended here;
several are implied and are deliberately left for the reader.

---

## SUMMARY — read this first

**126.1 MB windowed on a 960-line markdown.** It splits cleanly, and the
split is the most useful fact in this report (§7h):

    73.1 MB   FIXED    — paid by a blank document in a window
    53.0 MB   DOCUMENT — 95% of it heap, and 60% of THAT is shaped text

### The fixed 73.1 MB

| MB | What | Justified? |
|---:|---|---|
| 15.6 | **FOUR 1280x800 RGBA buffers** — 2 Wayland shm + 2 CPU pixmaps | defensible; verified THREE ways (§7h, §7i) |
| 13.9 | miniword binary text/rodata | fixed cost of a 31 MB binary |
| 8.8 | Font FILES, mmap'd, mostly untouched | yes — refuted as a target |
| ~7 | GTK / glib / libc / libstdc++ / epoxy | not ours |
| **5.2** | **Transient CSS clone churn** — ~24 500 vector clones, freed but never returned to the OS | **no defence offered** (§7i) |
| ~3.5 | Widget DOM, `RefAny`, `BTreeMap`, glyph/raster scratch | window-driven |
| ~3.2 | Font MACHINERY, fixed part | yes |
| ~2.7 | `slice::to_vec`, retained, single owner not identified | **not attributed** |
| ~13 | Remainder — small mappings, stacks, loader, allocator metadata | partly attributed; see §7b |

### The 53.0 MB the document costs

| MB | What | Scales with |
|---:|---|---|
| 31.8 | **Shaped text** (`layout_flow` / `perform_fragment_layout`) | document |
| ~5 | Font machinery, document part | document |
| 3.7 | Layout tree (1 329 nodes) | document |
| 3.4 | Vec growth with no named owner | document |
| 3.2 | Per-DOM layout results | document |
| 2.5 | Cached inline layout | document |
| 5.9 | Diffuse tail, hundreds of sites — **NOT attributed** | mixed |

**Five things that decide what to do about it:**

1. **It is all live data.** 71.37 MB of a 75.02 MB peak is still held at
   SIGTERM; the engine measures `unreturned` at 2.5 MiB and glibc
   tunables move RSS by <350 kB. There is nothing to reclaim — only
   things to allocate less of, or retain less of.
2. **Two separate problems at two scales.** 15.6 MB of frame buffers is
   paid whether the document is blank or 960 lines — 21% of the blank
   floor. Shaped text is ~0.5 MB blank and 31.8 MB at 960 lines. One
   effort will not fix both, and they need different kinds of fix.
3. **Growth is LINEAR at ~47 kB/line** and slightly sublinear at scale —
   a large constant, not an algorithmic problem. Measured at 24 / 960 /
   1 920 / 3 840 lines. Extrapolates to ~515 MB for 10 000 lines;
   3 840 lines already measures 231 MB.
4. **Only one line has no defence.** Shaped text costs 349-445 B per
   cluster against HarfBuzz's documented ~24 B/glyph and Gecko's
   ~6 B/char — 15-70x. Everything else in both tables has a reason worth
   keeping. It is also 60% of the document cost, so it is simultaneously
   the least defensible and the largest item.
5. **The engine cannot see 16% of its own live heap.**
   `AZ_PROFILE=memory` covers StyledDom + Solver3 + text cache, and
   reports none of the 15.6 MB of frame buffers.

Fonts are NOT the lever (settled by measurement), an arena is NOT the
lever (settled by the user, corroborated by Servo's own benchmark), and
the app-side pagination layout being separate from the engine's is
intentional.

**Seven of my own claims were corrected while building this**, each
recorded inline with its cause. The reusable ones: check a profiler's
runtime against the workload's before trusting its peak; add your own
summary table up; and confirm the workload actually ran the workload —
a convincing plateau can be a blank document (§7h).

**This is a map, not a proposal.** No optimizations are recommended here;
several are implied and are deliberately left for the reader.

## 1. The heap is almost entirely LIVE DATA

**Both instruments, same run, 32.9 s, `AZ_PROFILE=memory` + heaptrack:**

| Source | Number |
|---|---:|
| peak RSS (heaptrack included) | **106.20 MB** |
| heaptrack peak heap consumption | **75.02 MB** |
| heaptrack total live at SIGTERM | **71.37 MB** |
| `[heap]` resident (smaps, same process) | **62.9 MB** |
| engine self-report GRAND TOTAL | **26.58 MB** |
| engine's own `after layout` reading | current rss 84.9 MiB, peak 87.4, **unreturned 2.5 MiB** |

**The heap holds ~75 MB of LIVE allocations.** There is no large pool of
freed-but-retained memory: the engine measures `unreturned` at **2.5 MiB**,
and glibc tunables move RSS by under 350 kB (below). Optimising this means
allocating less or retaining less — there is no slop to reclaim.

### Two of my own earlier headlines were WRONG. Both retracted.

**Retracted #1 — "half the heap is not data" / "~38 MB of allocator
retention".** That came from a heaptrack run reporting a 38.87 MB peak.
**That run lasted 3.98 s and was killed before layout finished.** The
valid run lasts 32.9 s and reports 75.02 MB. The 38.87 MB was a partial
measurement of an incomplete workload, compared against an `[heap]` figure
from a *different* run — two errors compounding into a confident wrong
conclusion.

**Retracted #2 — the glibc explanation.** Tested directly, peak RSS:

    baseline                        102 764 kB
    MALLOC_ARENA_MAX=1              102 620 kB
    MALLOC_TRIM_THRESHOLD_=131072   102 824 kB
    MALLOC_MMAP_THRESHOLD_=65536    102 476 kB

All within ~350 kB. Refuted independently of #1, and consistent with the
engine's own `unreturned=2.5 MiB`.

**Lesson for whoever reads this next:** check the profiler's *runtime*
against the workload's runtime before trusting its peak. A profile that
ends early looks exactly like a profile of a smaller program.

## 1c. THE MAP CLOSES — heaptrack and smaps reconcile within 0.2%

The last unattributed mapping was `[anon]`: 12.0 MB resident of 537.6 MB
mapped, producer unknown. Measured directly:

- **The process is SINGLE-THREADED** (1 entry in `/proc/<pid>/task`), so
  none of it is thread stacks. That guess is retracted.
- 40 anon mappings; the largest is **7.8 MB mapped / 7.82 MB resident** —
  one fully-resident mapping.

That 7.8 MB is the same memory heaptrack attributes to `AzulPixmap::new`
(7.72 MB). glibc serves allocations above `MMAP_THRESHOLD` with `mmap`, so
a large pixmap lands in `[anon]` and never appears in `[heap]`. The two
instruments were labelling the same bytes differently.

So the accounting closes:

    [heap]  62.9 MB  +  [anon]  12.0 MB  =  74.9 MB
    heaptrack peak heap consumption      =  75.02 MB

| Owner | Resident | Instrument |
|---|---:|---|
| live allocations (`[heap]` + large mmap'd) | 74.9 MB | both, agreeing |
| miniword binary text/rodata | 11.6 MB | smaps |
| font files (mmap'd, mostly untouched) | 8.8 MB | smaps |
| libc / libm / other shared objects | ~3 MB | smaps |
| **total** | **~98-106 MB** | matches VmRSS across runs |

**Nothing is unexplained at the mapping level.** One gap remains a level
down: the ~15.6 MB of live allocations below heaptrack's reporting cut.

## 2. Full RSS breakdown

From `/proc/<pid>/smaps`, aggregated by mapping:

| Owner | Resident | Mapped | Notes |
|---|---:|---:|---|
| `[heap]` | 76.6 MB | 79.7 MB | of which **38.87 MB live**, ~38 MB allocator-held |
| miniword binary | 11.7 MB | 24.6 MB | text+rodata pages actually touched |
| `[anon]` | 12.0 MB | 537.6 MB | **mapped ≠ resident**; address-space reserve |
| font files (59 mappings) | 8.8 MB | 18.8 MB | mmap'd; untouched pages cost nothing |
| libc / libm / other .so | ~3 MB | ~5 MB | |
| **Total** | **~103 MB** | | matches VmRSS |

Two traps worth naming:

- **`[anon]` maps 537 MB and is 12 MB resident.** Anyone reading VSZ
  instead of RSS will chase half a gigabyte that does not exist.
- **Fonts are not the problem.** 8.8 MB resident against 18.8 MB mapped and
  99 MB of CJK/emoji faces on disk. `NotoSansCJK` etc. barely register;
  `DroidSansFallbackFull.ttf` is 3.8 MB mapped and 0.3 MB resident.
  rust-fontconfig's mmap is doing exactly what it claims. Lazy font
  loading would buy single-digit MB on THIS workload. (A CJK-heavy
  document is a different case and needs its own measurement.)

## 4. The largest single stack, and why it is not waste

The 8.30 MB stack runs `miniword::layout` → `editor_screen` →
`paginate_cached_with_fonts` → `compute_break_paths_with_fonts` →
`compute_document_pagination` → … → `perform_fragment_layout`.

That is **miniword's own pagination layout**, separate from the engine's
layout for display. Per the project owner this separation is deliberate —
app-side paging concerns are kept out of azul rather than building PDF
specifics into the engine. It is reported here for size only.

Its cost is roughly 8.3 MB of Vec growth plus its share of the layout tree
and text caches. There are two full layouts of this document in the
process, by design.

## 5. What scales with the document, and what does not

| Configuration | Peak RSS |
|---|---:|
| blank document | 55.0 MB |
| `t.md` (24 lines, 1 page) | 61.9 MB |
| `big.md` (960 lines, ~40 pages) | 103.1 MB (was 120.9 before `743eb5837`) |

So: a **~55 MB floor** plus ~48 MB for this document. The floor is binary
(11.7) + fonts (8.8) + `[anon]` (12) + a baseline heap.

**A retracted claim, kept so it is not re-derived:** an earlier note in
this session read the curve as "~1.5 MB per PAGE" and asserted pagination
built a Dom + StyledDom + layout per page. The arithmetic fit; the
mechanism was inference and is wrong. The document is laid out as ONE tree
(1 329 nodes, 31 086 clusters), twice (app + engine) — not forty times.

## 6. Per-character cost, for scale

`warm.inline` is 13.5 MB of the 16.8 MB layout cache — **80%** — across
31 086 shaped clusters, i.e. roughly one cluster per character.

Pinned struct sizes (`layout/tests/struct_sizes.rs`): `PositionedItem`
200 B, `ShapedItem` 184 B, `ShapedCluster` 176 B, `ShapedGlyph` 96 B,
`LayoutFontMetrics` 32 B (copied into every glyph), `LayoutNodeWarm`
1 176 B.

For external scale: HarfBuzz's own documented buffer format is ~24 B/glyph
(`hb_glyph_info_t` + `hb_glyph_position_t`), and Gecko's full retained cost
is ~6 B/char (4-byte CompressedGlyph + 2-byte UTF-16), 11 B/char with its
word cache. Gecko's retained textruns end up at **0.14% of layout memory**.
Ours are 80%.

No engine publishes a bytes-per-character figure for retained shaped text
(checked: Skia, Gecko, Blink, Qt, LibreOffice, Zed, Warp, Levien), so
these are the only external yardsticks available.

### 7d. The scaling law — MEASURED, linear at ~47 kB per line

Four document sizes, same binary, same run configuration:

| Document | lines | peak RSS | over the 55 MB floor | per line |
|---|---:|---:|---:|---:|
| `t.md` | 24 | 61.2 MB | 6.2 MB | 258 kB |
| `big.md` | 960 | 102.8 MB | 47.8 MB | 49.8 kB |
| `big2.md` | 1 920 | 148.7 MB | 93.7 MB | 48.8 kB |
| `big4.md` | 3 840 | 231.5 MB | 176.5 MB | 46.0 kB |

**Linear, ~47 kB per line, and stable from 960 lines upward.** Doubling
960→1920 multiplies the over-floor cost by 1.96; 1920→3840 by 1.88 —
very slightly SUBlinear, i.e. caches are helping a little at scale. There
is no superlinear blow-up hiding here, which is worth knowing: the
problem is a large constant, not an algorithmic one.

The 24-line figure (258 kB/line) is not a contradiction — at that size
the per-document cost is dominated by fixed per-document setup rather
than by content.

**Grounded extrapolation, replacing the hand-wave this report previously
carried:** at 46 kB/line a 10 000-line document costs
`55 + 10 000 x 0.046 = ~515 MB`. A 3 840-line document already measures
231 MB. For a word processor those are the sizes that decide usability,
and they follow from the ~47 kB/line constant — which is in turn mostly
the 31.76 MB of shaped text from §7b.

### 7c. FIXED vs PER-DOCUMENT, by owner

The same heaptrack analysis run on a BLANK document, differenced against
big.md. This separates "the cost of having a window at all" from "the
cost of this document" at call-site granularity, which the RSS-level
floor figure could not.

| Owner | blank | big.md | delta |
|---|---:|---:|---:|
| Text shaping | 0.53 | 31.76 | **+31.22** |
| **Pixmaps** | **11.82** | **11.82** | **0.00** |
| Font machinery | 3.16 | 8.18 | +5.02 |
| Other / unnamed | 3.28 | 6.64 | +3.36 |
| Layout tree | 0.37 | 3.68 | +3.31 |
| Layout results | 0.00 | 3.18 | +3.18 |
| Cached inline layout | 0.00 | 2.47 | +2.47 |
| **Widget DOM / icons** | **1.37** | **1.37** | **0.00** |
| top-N total | 20.54 | 69.11 | +48.56 |
| peak heap | **25.84** | **75.02** | +49.18 |
| peak RSS | **55.5** | ~103 | +47.5 |

**Two findings worth separating:**

1. **The framebuffer pair does not scale with the document — 11.82 MB in
   both.** They are window-sized, not document-sized, which is what one
   would want. But that means **pixmaps are 46% of the blank document's
   live heap (11.82 of 25.84 MB)**. At small document sizes the
   framebuffers ARE the memory; at large ones shaping is. These are two
   different problems and a single "reduce memory" effort will hit one
   and miss the other.

2. **Text shaping is essentially all per-document** (0.53 → 31.76). It
   contributes almost nothing to the floor and almost everything to the
   growth. Combined with §6's per-character figures, this is the line
   that decides whether a 10k-line document is usable.

Font machinery splits: ~3.2 MB fixed (the base faces any window loads)
plus ~5.0 MB for the additional faces this document's text pulled in.

### The map in one paragraph

~23 MB is fixed cost anyone pays (binary, shared libraries, mmap'd font
files). ~17 MB is fonts across both forms (8.8 mapped + 8.2 decoded).
~12 MB is the double-buffered framebuffer the damage system requires.
The remaining ~50 MB is retained layout and text for ONE 960-line
document — and **31.76 MB of that, 42% of the live heap, is shaped
text**. Every other line in this map has a reason worth defending. That
one does not.

The blank-document floor is 55 MB, the document adds ~48 MB. Two
different problems: the floor is binary + fonts + buffers, the growth is
shaped text.

## 7e. Reproducibility — the map is not one lucky run

Every headline number above came from a single heaptrack profile. A
second independent run of the same configuration:

| Group | run 1 | run 2 | diff |
|---|---:|---:|---:|
| Text shaping | 31.76 | 31.76 | +0.00 |
| Pixmaps | 11.82 | 11.82 | +0.00 |
| Font machinery | 8.18 | 8.20 | +0.02 |
| Other / unnamed | 8.01 | 8.01 | +0.00 |
| Layout tree | 3.68 | 3.68 | +0.00 |
| Layout results | 3.18 | 3.18 | +0.00 |
| Cached inline layout | 2.47 | 2.47 | +0.00 |
| top-30 total | 69.11 | 69.13 | +0.02 |
| **peak heap** | **75.02** | **75.03** | **+0.01** |
| total leaked | 71.37 | 71.39 | +0.02 |

**Largest per-group difference: 0.02 MB.** The workload is deterministic
— same document, same fonts, no threads, no timing-dependent work — so
this is what one should expect, but it had not been demonstrated. Every
figure in this report can be treated as exact to ~0.02 MB rather than as
a single sample.

That also means an optimisation experiment can trust a difference of
0.1 MB as real signal, which is a useful thing to know before starting.

implementation, so it is the strongest available check that the map is
measuring reality rather than a shared assumption.

Blank document (chosen because valgrind is ~20x slower and a 33 s run is

| Instrument | blank-document peak heap |
|---|---:|
| heaptrack | 25.84 MB |
| **valgrind massif** | **24.62 MB** (+0.94 MB admin) |

**Within 1.2 MB, i.e. ~5%.** massif's figure excludes allocator
bookkeeping that heaptrack's includes, which is the expected direction
and roughly the expected size for ~670 k allocations.

So the blank-document floor of ~25 MB of live heap is confirmed by three
instruments that share no code: heaptrack, valgrind massif, and azul's
own `AZ_PROFILE=memory` accounting. Nothing in this map rests on a single
tool's view.

## 7g. SCOPE CORRECTION — the real windowed app is ~23 MB LARGER

Everything above was measured HEADLESS. The user's actual complaint came
from a real Wayland window, so the map has to be checked against one.

Same document, same binary, real Wayland session:

| | headless | **windowed** | delta |
|---|---:|---:|---:|
| **VmRSS** | 98.4-103.9 MB | **126.0 MB** | **+23 to +27** |
| `[heap]` | 61-63 MB | 69.4 MB | +7 |
| binary | 11.6 MB | 14.0 MB | +2.4 |
| `[anon]` | 12.0 MB | 12.0 MB | 0 |
| **`/memfd:azul-fb`** | **absent** | **7.8 MB** | **+7.8** |
| libgtk-3 + Wayland libs | absent | ~1.5 MB | +1.5 |

**A THIRD framebuffer exists that headless never allocates.**
`/memfd:azul-fb` is the Wayland shared-memory surface — 7.8 MB, which is
1280 x 800 x 4 B x 2, i.e. DOUBLE-BUFFERED. Combined with the two
heap-side pixmaps (`render_frame` 4.10 + `CompositorState` 4.10), the
real application holds **~16 MB of full-size frame buffers** for a
1280x800 window, not the 11.8 MB this report states elsewhere.

The extra 2.4 MB of binary residency and ~1.5 MB of GTK/Wayland library
pages are the cost of the platform backend being exercised at all;
neither is azul data.

**What this changes:**

- Section 7b's table and the SUMMARY describe the HEADLESS process.
  They are correct for what they measured and understate the shipping
  application by ~23 MB.
- The framebuffer line is the one that moves: 11.8 MB -> ~16 MB, and it
  is now **three** surfaces, not two.
- Nothing else moves materially. Shaped text, layout tree, font
  machinery and the scaling law are all document-driven and unaffected by
  the presenting backend.

**Not measured, and named rather than guessed:** whether the 7.8 MB shm
buffer is retained across frames or recreated per resize, and whether a
GPU/EGL backend would replace it with driver-side memory that never
appears in RSS at all. Both are answerable with the same technique and
neither was attempted.

## 7h. THE WINDOWED MAP — fixed vs document, and four frame buffers

§7g established that the real app is ~23 MB larger than headless but left
two questions open. Both are now closed, and closing them turned up a
measurement trap that invalidated two profiling runs.

### The trap: miniword ignores argv

`miniword` has NO argv handling. The document is opened by the
**`MINIWORD_OPEN` environment variable** (`src/main.rs:688`). Two
heaptrack runs launched as `heaptrack ./miniword big.md` therefore
profiled a BLANK document while appearing to succeed — the window opened,
fonts loaded, and RSS plateaued convincingly at 81.3 MB.

What exposed it was not the log but an inconsistency in the numbers:
heap was 21.3 MB where headless-with-document is 61-63 MB. **A plateau
proves the process stopped changing, not that it did the work.** Both
runs were discarded.

This also forced a re-check of §7g's 126 MB, which could have had the
same defect. It does not: re-measured with `MINIWORD_OPEN` set, RSS is
**126 092 kB against the earlier 126 028 kB — a 64 kB difference**, so
that figure was measured correctly and stands.

### Fixed vs per-document, on the REAL configuration

The report's fixed/document split (§7c) was headless. Measured windowed,
same binary, both settled to a plateau:

| | RSS | `[heap]` | binary | `[anon]` | memfd |
|---|---:|---:|---:|---:|---:|
| windowed, **blank** | **73.1 MB** | 19.1 | 13.9 | 10.8 | 7.8 |
| windowed, **big.md** | **126.1 MB** | 69.6 | 14.1 | 12.0 | 7.8 |
| **the document costs** | **53.0** | **50.5** | +0.2 | +1.2 | **0** |

Two things fall out that the headless map could not show:

1. **The document is 53.0 MB and 95% of it is `[heap]`** (50.5 of 53.0).
   It touches the binary by 0.2 MB, `[anon]` by 1.2 MB, and the
   framebuffer not at all. Everything document-driven is heap.
2. **The blank windowed floor is 73.1 MB**, against 55.0 MB headless.
   **+18.1 MB is the price of having a real window** — the shm buffer,
   more binary pages, and the GTK/Wayland/epoxy libraries.

### FOUR frame buffers, 15.6 MB, verified against arithmetic

The window is **1280x800**, set literally in `src/main.rs:741-742`. That
makes the buffers predictable instead of inferred, and both predictions
hit exactly:

| what | predicted | **measured** |
|---|---:|---:|
| `/memfd:azul-fb` = `stride*h*2` (`wayland/mod.rs:5666`, *"TWO buffers in one pool"*) | 1280x800x4x**2** = 8 000 kB | **8 000 kB** |
| the large `[anon]` region | 1280x800x4x**2** = 8 000 kB | **8 008 kB** (+8 kB page header) |

**Total: 16 008 kB = 15.6 MB held in FOUR full-size 1280x800 RGBA
buffers** — two Wayland shm (double-buffered for the compositor) and two
CPU-side pixmaps. That is **21% of the blank windowed floor** and 12.4%
of the loaded application. It supersedes the 11.82 MB / two-surface
figure elsewhere in this report, which counted only the heap side.

This also explains `[anon]`, previously carried as a vague 12 MB: 8 008
kB of it is that pixmap pair, 1 196 kB is one further region, and the
rest is small. It is ~10.8 MB blank and 12.0 MB loaded, i.e. **`[anon]`
is fixed, not document-driven** — consistent with glibc serving
allocations above its mmap threshold outside `[heap]`.

### Justified?

- The four buffers are **defensible but not free**. Double-buffering the
  Wayland surface is required to avoid tearing; a CPU-side pixmap is
  required because this is the software path. Whether BOTH need to be
  double-buffered is a real question, and the honest answer is that this
  report does not settle it — one shm buffer plus one CPU pixmap would be
  8 MB, and the cost of that would be measured in frame pacing.
- The resize path is **correct**: `resize_surface` does
  `drop(cpu_opt.take())` BEFORE allocating the replacement
  (`wayland/mod.rs:5862`), so a resize never holds two pools at once. No
  transient doubling. This was listed as unmeasured in §7g; it is now
  answered at source level.
- On a GPU path these buffers would move to driver memory and largely
  leave RSS. **Not measured** — this machine ran the CPU fallback.

## 7i. THE BLANK FLOOR, ATTRIBUTED — and it is mostly CSS churn

The document side of this map was well covered; the 73.1 MB FIXED floor
was not. Profiled directly (heaptrack, windowed, no document, killed on a
plateau):

    peak heap   29.37 MB      retained at exit   23.41 MB (79.7%)
                              TRANSIENT           5.96 MB

That 29.37 MB cross-checks against the mappings independently:
`[heap]` 19.1 + `[anon]` 10.8 = **29.9 MB measured vs 29.37 MB profiled**,
0.5 MB apart. The blank floor's malloc heap is fully accounted for.

### Top sites, peak vs retained

| MB peak | MB retained | calls | site |

| 4.10 | 4.10 | 5 | `cpurender::pixmap::AzulPixmap::new` |
| 2.71 | 2.71 | 112 | `slice::to_vec` |
| **2.02** | **<0.19** | **14 690** | **`CssDeclarationVec::clone`** |
| **1.90** | 0.95 | **8 472** | **`Css: From<CssPropertyWithConditionsVec>`** |
| 1.43 | 0.75 | 44 496 | `RawVec::finish_grow` |
| **1.37** | **<0.19** | **1 350** | **`CssRuleBlockVec::clone`** |
| 1.17 | 1.17 | 10 469 | `RawVec::finish_grow` |
| 0.96 | 0.96 | **205 154** | `String::clone` |
| 0.83 | 0.83 | 1 484 | `BTreeMap::clone` |

### Two findings

**1. The two pixmaps are 8.20 MB and fully retained** — and 8.20 MB is
exactly the 8 008 kB `[anon]` region from §7h, reached by a completely
different instrument. Framebuffer attribution is now confirmed three
ways: predicted arithmetic, `smaps`, and allocation backtrace.

**2. Nearly all the transient peak is CSS vector cloning.** On a document
with NO CONTENT, ~24 500 clone calls of CSS vectors allocate ~5.3 MB that
is gone by exit:

    CssDeclarationVec::clone           2.02 MB transient  (14 690 calls)
    CssRuleBlockVec::clone             1.37 MB transient  ( 1 350 calls)
    Css::From<...WithConditionsVec>    0.95 MB transient  ( 8 472 calls)
    CssPropertyWithConditionsVec       0.21 MB transient  (   600 calls)
                                       ------
                                       4.55 MB of the 5.96 MB transient

Adding the half of `RawVec::finish_grow` that is also transient (0.68 MB)
reaches 5.2 MB, i.e. **87% of the blank floor's transient peak**.
INFERENCE, flagged as such: that the `finish_grow` traffic belongs to the
same clones is not proven by the backtrace, only strongly suggested by
the call counts moving together.

`String::clone` at **205 154 calls** for 0.96 MB retained is the same
story by a different route — ~5 bytes average per call means these are
short strings, and the count rather than the size is what stands out.

**Why it matters even though it is transient:** peak RSS is what the user
sees in `VmHWM`, and glibc does not return this to the OS (§1). A
transient 5 MB spike during startup is a permanent 5 MB of RSS
afterwards. It is transient in the *allocator*, not in the process.

**Is it justified?** The retained CSS (0.95 MB) plainly is — the ribbon
has a real stylesheet. The 24 500 CLONES are not obviously justified by
anything in this report; they are the cost of the widget/DOM construction
path passing CSS by value. This report does not propose a fix and has not
established that one is cheap.

## 8. Method notes

- heaptrack with `MINIWORD_SHOT` set yields an EMPTY profile (3 KB): the
  screenshot callback ends in `std::process::exit(0)` and skips the atexit
  flush. Run headless without it, let it settle, SIGTERM.
- `pgrep -f "release/miniword"` matches the heaptrack wrapper, not the
  child. Use `pgrep -x miniword`.
- The engine's own report ends with `GRAND TOTAL` and `accounted / rss`
  lines. Read the whole output — grepping past them cost two ticks and a
  wrong conclusion that the instrumentation was missing.
