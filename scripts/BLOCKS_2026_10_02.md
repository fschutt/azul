## What was built

### 1. One selection model - `ListSelection` (DEDUP_OFFICE D20, DEDUP_WIDGETS_API F6)
- `layout/src/widgets/list_selection.rs` (new, registered in `widgets/mod.rs`): a sorted set of `u64`
  keys + `anchor` + `focus` + `keep_one`. Explorer's rules written once over a private `Order`
  (positions `0..count`, or keys in their visible order): click, Ctrl toggle (keep_one: never empties -
  a slide rail), Shift extend, Ctrl+Shift add_range, `select`/`select_in` dispatch, `apply` (builder),
  select all / clear / invert, retain (after a re-listing; keyed orders searched sorted), select_keys,
  arrows (`step`/`step_in`: Shift extends, Ctrl moves the focus alone, clamped, nothing focused ->
  first / last), toggle_focused (Ctrl+Space), `key_of(&str)` (the hasher `NodeData::set_key` uses) for
  string ids. 12 RED-then-GREEN tests.
- Keys are `u64` (MessageRow / ToDoBar / Timeline ids are u64) -> new primitive `U64Vec` in
  `css/src/corety.rs` (next to U32Vec). Keyed orders are taken as an owned `U64Vec` (a Rust app passes
  a `Vec<u64>`; a slice would be a `U64VecSlice` it cannot build).
- Adopted: MessageList (its `MessageListSelection` goes; docs + test point at ListSelection), AzMail
  (`lib.rs`, `ui_main.rs`), the showcase (`azul-widgets/src/mail.rs`), AzShow (rail = ListSelection
  with keep_one keyed by slide index; canvas = ListSelection of element ids, Shift toggles like Ctrl;
  `selected_slides()` / `selected_ids()`), AzTasks (`key_of(task id)` over the shown order: select_in,
  step_in, retain_in; `is_selected` / `selected_ids`), AzDrive (`model::Selection` is now a thin key
  adapter: the names it met with their keys, so `keys()` reads back in the visible order - now an
  owned `Vec<String>`; its 4 tests unchanged).
- Behaviour changes (all toward Explorer's rule): Ctrl+Shift adds the range in AzShow's rail and
  AzTasks (it replaced it); a Ctrl+click that deselects moves the anchor in AzShow's rail too;
  MessageList's first Shift+click with no anchor selects the row alone (the old anchor defaulted to 0).

### 2. One undo / redo snapshot stack - `azul_appkit::UndoHistory<T>` (DEDUP_OFFICE D10)
- `examples/azul-appkit/src/history.rs` (new, `pub use history::UndoHistory`): the app owns the
  current state; `checkpoint(label, before)` before an edit (drops the redo branch);
  `checkpoint_with(label, coalesce, || before)` builds the snapshot lazily and merges a run with the
  same coalescing key until `seal()` / undo / redo / another edit; `undo(&mut current)` / `redo` /
  `jump(index, &mut current)` swap; `undo_label` / `redo_label` (menu text), `labels` +
  `current_index` (History panel: the oldest state kept, then one row per step); `VecDeque` under
  `with_limit(n)` (no `Vec::remove(0)` memmove). Plain Rust (a snapshot of an app type cannot cross the
  C API). 7 RED-then-GREEN tests.
- Adopted: AzPhoto (`raster/history.rs` deleted; TileEngine keeps `UndoHistory<Document>` limit 60;
  ops checkpoint the document before them with the op's coalescing key; a stroke checkpoints the
  document from before it - new field `stroke_before`), AzVideoCut (`model::History` deleted;
  `UndoHistory<Sequence>` limit 200, serde-skipped with a fresh default; `undo_label` now borrows -
  two status lines copy it before undoing), AzShow (`undo`/`redo` Vecs and the `transforming` flag go;
  a canvas drag is one step via the coalescing key "transform", sealed on commit). The three apps
  depend on `azul-appkit` (no `azul` feature); `Cargo.lock` updated by hand (3 dependency lines).

### 4. Preset shells delegate their chrome to OfficeShell (DEDUP_WIDGETS_API F29)
- The chrome lives on `OfficeShell` alone: the presets drop their copies of title row, ribbon,
  backstage, status bar, `on_pane_focus`, `on_pane_resize`, theme (whatever each passed straight
  through) - 42 setter pairs, their fields and initializers. Callers write
  `XShell::create(..).<pane knobs>.office_shell().with_title_row(..).with_ribbon(..)`.
- Kept where the preset places the slot itself: BrowserShell `ribbon` (stacked over its address bar),
  TimelineShell / CanvasShell `menu_bar`, RecordsShell `tabs`, MediaShell `now_playing`, CallShell
  `header` / `controls`. CanvasShell and CallShell keep `theme` (they style their own rows with it)
  and gain `office_shell()` like the others (their `build()` became `office_shell_in()`).
- Updated: every preset's tests (the chrome is set on the converted shell), the shells fixtures
  (`shells/mod.rs every_shell`), and the call sites in AzContacts, AzDrive, AzMail (main + compose),
  AzNotes, AzPhoto, AzSheets, AzShells, AzShow, AzTasks. Same DOMs.

### 5. Close guard - "Save changes?" (DEDUP_OFFICE N14 / A16)
- `CallbackInfo::prevent_window_close()` (`layout/src/callbacks.rs`, after `modify_window_state`):
  clears `flags.close_requested` on the window state the callback queued LAST (or the current one),
  so the veto keeps what the callback changed before it - the AzMail / AzNotes hand-cleared copy
  loses a title change made in the same callback. Call it last.
- `CloseGuard` (`layout/src/widgets/close_guard.rs`, new, registered): wraps the window's content; its
  `Window(CloseRequested)` hook holds the close while `dirty` and someone listens, reporting `Ask`
  (the veto queued after the app's answer); while `asking` it shows the standard `MessageBox`
  (Question; "Save changes to \"<doc>\"?" / "Your changes will be lost if you don't save them." /
  Save, Don't Save, Cancel - all settable) in a `Modal` titled by the app. Save and Don't Save mark
  a shared flag so the close they lead to passes (the guard's own `close_window` after Don't Save, the
  app's after its save); Cancel and the modal's Escape / close report `Cancel`. 8 RED-then-GREEN tests.
