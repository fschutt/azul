## What was built

Every gap: a RED unit test commit (test names are sentences), then the fix.

1. **A raw `str` return is a critical FFI error** (`mod.rs`). New `check_function_signatures(api_data,
   additional_type_names)`, run by the scan: every argument / return type of an api.json function or constructor must
   be a C scalar (`FFI_SCALARS`, the `core::ffi` family included - `c_int` is used today), an api.json class, a generic
   parameter of the class / function, or a type this round's patches add. A raw `str` in any spelling (`str`, `&str`,
   `Optionstr`, `OptionStr`, `Option<&str>`) is the new critical kind `RawStrInSignature` (with its own FIX text); any
   other unknown name is the existing critical `UndefinedTypeReference` (the variant existed, nothing produced it).
   Checked against today's api.json (python replica): clean; against api.json before 59647294f: exactly
   `RichRun.as_str -> str` and `RichRun.link_str -> Optionstr`.
   And `autofix add` writes a borrowed str correctly: `convert_return_type_for_ffi` now returns a `ReturnConversion`:
   `&str` -> `String` with fn_body `azul_css::AzString::from(<call>)`; `Option<&str>` / `Option<String>` ->
   `OptionString` with `<call>.map(|s| azul_css::AzString::from(s)).into()` (`OptionString` converts from
   `Option<AzString>` only, so the old `.into()` on an `Option<std String>` did not compile either).
2. **api.json functions whose Rust method is gone** (`function_diff.rs` `gone_api_functions`, scan in `mod.rs`).
   An entry whose fn_body calls `object.m(..)` (the first `object.` of the body) or `<the class's path>::m(..)` while
   the class's source type has no method `m` - and its source file has no `fn m(` / `fn m<` (safety net for generic
   methods the index does not extract) - is gone. Not judged: a class without a source type, or whose api.json path
   names another type (looked up by the class's own path first); macro-made types (impl_vec! / impl_option!); types
   with a `Deref` impl; any other body shape; derive / std-trait methods (`clone`, `to_string`, `eq`, ...). The scan
   prints them ("N api.json function(s) call a Rust method that is gone") and writes one
   `NNNN_remove_fns_<Class>.patch.json` per class removing exactly those functions / constructors
   (`generate_remove_entries_patch`; `generate_remove_functions_patch` now delegates to it). Classes the round removes
   as a whole are skipped.
3. **A std `String` argument is converted** (`type_index.rs`, `function_diff.rs`). The index spells a std `String`
   and an `AzString` both `String`; `MethodArg` now keeps `source_ty`, the type's last path segment as written
   (`String`, `AzString`, or `S` for `S: Into<AzString>`). `autofix add` writes `text.into_library_owned_string()` for
   a std `String`, `&text.into_library_owned_string()` for `&String`, `&text` for `&AzString` (all through the
   template accessor, which matches whole arguments only). An existing entry that passes the AzString to a std
   `String` parameter as it is (`object.set_text(text)`) is reported by the signature-drift check ("the source takes
   a std `String`, the fn_body passes the AzString as it is") - `autofix list` and the scan show it.
4. **`autofix add X.m` after a pending `remove X.m`** (new `autofix/pending.rs`, `patch/mod.rs`, add wiring).
   `PendingRemovals::read(dir, class)` collects what the patch folder removes from a class (both patch formats);
   the add takes its candidates against `pending.apply_to(class)` (api.json as the pending patches leave it), and
   after writing its patch `supersede_pending_removals` drops each re-added name from the pending removal of the SAME
   map (functions / constructors), rewriting the pending file or deleting it when empty. The add's merge replaces the
   old entry in place, so the result does not depend on the apply order (the test applies both orders). A pending
   removal of the WHOLE class stops the add with a message (apply first). Also: a patch folder now applies in
   file-name order (`ApiPatch::from_directory_with_context` sorted; `read_dir` order is the file system's), so the
   scan's `NNNN_` numbering holds and a pending `add_*` goes before a later `remove_*` of the same entry.
5. **THE wildcard rule** (`function_diff.rs` `wildcard_skip_reason`). `autofix add Type.*` takes a method only when
   its whole signature crosses the FFI as written: no borrowed return (`&T`, `&str`, `&[T]`, `&mut T`, `Option<&T>`),
   and every argument and the return type, spelled as api.json spells it (`&str` -> `String`, `&T` -> `*const T`,
   `Option<X>` -> `OptionX`), is a scalar, the type itself, or a type the FFI carries (`ffi_carries`: an api.json type,
   a struct / enum with a C or transparent repr, a callback typedef, a type alias, a macro-made Vec / Option /
   Result). `Vec<T>`, slices, tuples, `Option<&str>` arguments, `Instant`, a struct without a C repr: Rust-only. A
   method named explicitly (`autofix add Type.method`) is not filtered. Rule chosen over `#[doc(hidden)]` / a
   `// api: skip` marker because it needs no source edits and removes exactly the build breakers; a helper that HAS
   an FFI form but is not API stays `pub(crate)` (house rule). `api_candidate_methods` takes the `carries` predicate
   (one selection for every add path, as before).
6. **A type that lost its C repr** (`diff.rs`). No `ReprChanged` modification when the source has no repr (a `None`
   in the patch means "leave it": the modify changed nothing and came back every round). An unreachable api.json
   type is kept only while its source still exposes it - `still_exposed_in_source`: a struct / enum with no repr at
   all cannot be exposed, so it is removed like a type whose source is gone (all three removal guards). No other patch
   of a removed type competes with the removal (modifications, additions, path fixes, module moves are dropped - a
   module move used to take the class away from the module the removal targets). The scan drops the FFI warnings of
   the classes it removes; a REACHABLE type without a C repr is reported (the existing critical `StructMissingReprC` /
   `EnumMissingReprC`), not patched.
7. **`autofix remove module.Type`** removes a whole class: one parser `parse_remove_spec` (`module.Type.fn`,
   `Type.fn`, `module.Type`, `Type`; a two-part item is a class when its first part is a module that has it) returning
   `RemoveTarget { Class, Function }` with its `patch`, `file_name`, `describe`; `autofix remove` and `autofix
   difficult remove` both use it (their two hand-rolled parsers are gone).
8. **Regression test** for 178af99a9 (a removal targets the module the class is in) - it was missing.

## Seen broken, not fixed (out of scope or another owner)
- `autofix add T.m` BY NAME for a method returning `&T` (not str) still writes the return by value with no
  `.clone()` (`object.block(i)` returning `&RichBlock` as `RichBlock`): does not compile. The wildcard skips these.
- `Option<T>` ARGUMENTS are not converted by add (`Option<i32>` is written as is; the new signature check now flags
  it as an undefined type, so it can no longer reach the codegen silently). `&mut String` args are left as before.
- `&[T]` arguments map to `{T}VecRef`, which mostly does not exist (the house convention is `XxxVecSlice`).
- The suffix accessors (`.as_str()` for `&str`, `.as_slice()`) are spliced with `replace("name)")`, which also hits an
  argument whose name ENDS with another's (`text` inside `context)`); the string conversions added here use the
  template path (whole-argument matches). Worth moving `.as_str()` / `.as_slice()` to templates too.
- `ClassPatch::is_empty()` ignores `remove_functions` / `remove_constructors` / the `remove_*` derive lists (used by
  the apply side to decide whether to insert a missing class from a patch).
