## 1. Ruling 1 - focus the nearest focusable ancestor across a VirtualView

User: "yeah, as you decided, nearest focus parent".

- Root cause: `layout/src/managers/hover.rs::focusable_under_pointer` (the ONE click-to-focus rule the dll and
  the e2e runner share) walked the front-most hit's OWN dom and stopped at its root, so a click on plain text in
  a VirtualView page BLURRED instead of focusing the focusable box around the view.
- Fix: it now walks `azul_core::events::get_event_path` - the path events already bubble along (EVENTS7),
  which continues at the node hosting a child dom - so focus and bubbling agree about the ancestors. It takes a
  4th closure `host_of(dom)`; `dll/src/desktop/shell2/common/event.rs` (click-to-focus) and
  `layout/src/e2e/runner.rs` (its mirror) pass `virtual_view_manager.host_of_nested_dom`. The 9g-ii-e-ii
  guarantee stays: only the front-most hit's path counts (a focusable node merely UNDER the page, off its host
  chain, never takes the click).
- The plain (non-VirtualView) case already focused the nearest focusable ancestor; pinned by a test.
- Tests: `layout/src/e2e/focus_across_virtual_view_tests.rs` (a child module of runner.rs, appended at its end -
  it needs the crate-private `run_e2e_test_keeping_runner`): click plain text in a VirtualView inside a
  focusable `div#host` -> the host is focused (RED before); the plain case; nothing focusable anywhere -> no
  focus. `managers/hover.rs` unit tests updated to the ruling (the old "does not focus the host beneath" test
  now puts the focusable node off the host chain and still expects `None`).

## 2. Ruling 2 - a line holding only an inline-block is as tall as in Chrome

User: "Chrome is the reference, so yes, and then we just need to adjust the icons css or whatever".

Chrome 154 vs the prebuilt engine (16px Arial, `<div id=p><span id=b style="display:inline-block">`):

| case | Chrome p / b.y | azul (prebuilt) |
|---|---|---|
| 10px box, line-height normal | 18 / 4 | 10 / 2.8 |
| 10px box, line-height 20px | 20 / 5 | 10 / 4.8 |
| 10px box, line-height 0 | 10 / 0 | 10 / 0 |
| 40px box | 44 / 0 | 40 |
| 10px box, vertical-align top | 18 / 0 | 10 |
| 10px box, vertical-align middle | 18 / 4.84 | 10 / 11.8 |
| 24px box middle (an icon) | 24 / 0 | 24 / 16 (outside its line) |
| "x" + 24px box middle | 24 / 0 | 30.15 / 16.15 |
| 24px box bottom | 24 / 0 | 24 / 3.2 |
| 10px box, vertical-align -5px | 19 / 9 | 10 / 7.8 |
| inline-flex button (32px) alone / beside "x" | 32 / 32 | 32 / 36 |
| x + two-line inline-block | 36 | 40 |
| empty `<span></span>` / `<a name>` alone | 0 | 19.2 |

Root causes and fixes (RED test first each, Chrome's numbers):

1. (text3, `perform_fragment_layout`) The IFC was measured by its ITEMS; a line of only atomic inlines measured
   its box, not its line box (which `position_one_line` already built with the strut). Now such a line (a box
   with a height, no text cluster) records its line box (`atomic_line_box_top` / `_bottom`) and the IFC's
   bounds become the union with them. 1adee2882 (reshaped from 60a535026, see section 4).
2. (solver3 `getters.rs::collect_font_stacks_from_styled_dom`) The strut's face was only loaded when some TEXT
   node used the block's font: a block holding only boxes took a 0.8em / 0.2em strut guess and `normal` as 1em
   (16 instead of 18). Phase 1 now also keys the PARENT of every inline-level box. 9fdf0e0d8.
3. (text3, `position_one_line` / `calculate_line_metrics`) `vertical-align: middle` moved the box DOWN by half
   the x-height (sign); the line box counted every baseline-relative box by its UNSHIFTED extents (middle,
   text-top, text-bottom, lengths); the strut joined the line box only after the top / bottom pass. ONE helper
   `baseline_shift(align, ascent, descent, constraints)` is now read by both the line box and the placement;
   the strut starts pass 1. `sub` / `super` are unchanged (see Left). bb434c120.
4. (solver3 `fc.rs::layout_flex_grid`) A flex / grid container reported NO baseline, so every inline-flex
   button sat on its line by its bottom edge (36 instead of 32 beside text; alone on a line it would now hang
   the strut's descent below itself). It now reports its first line box's baseline (`first_line_baseline`,
   the table cells' walk; Flexbox 8.5 / Grid 10.6). The 10.8.1 overflow rule is the inline-block's alone:
   `measure_atomic_inline` reads a flex / grid box's overflow as visible for its baseline (Chrome: an
   `overflow: hidden` inline-flex sits on its label). d79e4b720.
5. (solver3 `fc.rs::collect_inline_span_recursive`) An empty inline element was emulated as a line-height-tall
   box on the baseline (19.2px, Chrome 0); with fix 1 it would have grown to 23.2. CSS 2.1 9.4.2: with no
   margins / padding / borders it is now a phantom (contributes nothing). 3d9dfaefd.

Tests: `layout/tests/a_line_holding_only_an_inline_block_is_as_tall_as_its_strut.rs` (11 tests: strut, line-
height, line-height 0, tall box, top, middle, middle icon alone / beside text, bottom, length, no text in the
document, phantom line) and `layout/tests/an_atomic_inline_sits_on_the_baseline_of_its_content.rs` (9 tests:

appended to `layout/tests/all.rs`. Font-dependent numbers have a 1px tolerance (Arial / Liberation Sans share
metrics); CSS-fixed ones are exact.

## 3. Widgets whose CSS was adjusted: NONE - and why

The brief expected icon CSS adjustments. I scanned what actually holds lines of only atomic inlines, on the
prebuilt binaries (capped, one at a time; `target/rulings8/scan.py` dumps every dom's layout tree, rects,
hierarchy and the computed `display` of flex children; `analyze.py` finds IFC roots whose lines hold atomic
inlines and no text): AzWidgets (98 widget classes on screen), AzMail (`--sample`), AzWriter, AzDrive,
AzCalendar, AzNotes, AzSheets, AzShow, AzPhoto, AzTasks, AzContacts, AzPaint, AzDashboard, AzMeet, AzReview,
AzBuilder, AzCalculator, AzSetup, AzShells, AzMaps (AzVideoCut skipped: video).

Result - every atomic-only line found is a wrapper around a TEXT-labelled inline-flex `Button`:
`__azul-native-dialog` > `.dialog-invoker` (inline-block) > button; `.path-input-browse`;
`.todo-bar-task-title` (AzWidgets, AzTasks); `.empty-state-action` (AzDrive, AzContacts);
`.reading-pane-sender` / `.reading-pane-footer-line` (link buttons). With fix 4 (and MAILREF8's inline-block
baseline for the invoker's inline-block) these sit on their label's baseline: the line stays exactly the
button's height, as in Chrome (probe: a 32px button alone on a line -> 32). No image / SVG icon sits alone in a
block container (icons live in flex rows - blockified, no line box), no widget uses `vertical-align`, and the
titlebar's InlineBlock control glyph, the ribbon combo wrapper, the statusbar label view, tooltip, popover,
combobox and drop-down all sit in flex containers or beside text. So nothing relied on the old behaviour once
the baselines are right; changing CSS would have been a workaround. To re-check after the build: run
`target/rulings8/scan_all.sh <Apps>` style scans again and compare the heights of the wrappers listed above
(expected unchanged: 31px buttons stay 31px).
