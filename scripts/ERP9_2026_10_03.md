## The architecture decision: the view-JSON interpreter, first slice

The ERP README says the screens are interpreted at run time from the ERP's JSON ("a native interpreter is a
like-for-like replacement"; s3 "erp-views crate: serde models of ui.*.json, menu.json; view -> azul Dom
interpreter; condition evaluator; column formatters"), and the asset-management plan calls this module "a good
first module for the native interpreter". So that IS the architecture, and its first slice is built here, inside
the app crate (`src/views/`, app-local as the README's table says):

- `views/mod.rs`: serde models of the ERP's view dialect (`table`, `table_embedded`, `form`, `form_modal`,
  `detail`, `wizard`, `report`, `custom`, ... unknown types parse as `Unknown`), path routing with `:id`
  parameters (a literal segment beats a parameter: `/accounting/assets/new` is the form, not the detail of an
  asset called "new"), labels (`en.json`; else the key made readable - the ERP's translations are all empty),
  `api` path -> record kind and parent filter (`/api/assets/maintenance?asset_id=:id`).
- `views/spec.rs`: a view as the screen needs it: DataTable columns, typed form fields (text / textarea /
  date / decimal / integer / select / reference), buttons (link / named action / submit / cancel), detail tabs,
  wizard steps; the `condition` grammar (`a == 'x'`, `!=`, `&&`, `||`; unreadable -> shows) and the field rules
  (`required`, `min` / `max`, the type) as sentences.
- `views/rows.rs`: records by ERP field name (`ViewRecord::value` / `set`, computed `book_value`, `category`,
  `asset_name`, `asset_count`), a table's cells (`grid`), a form's texts and back (`apply`, all or nothing).
- `views/erp.ui.assets.json` is the ERP repo's own `json/ui/ui.assets.json`, unchanged: a test proves the
  interpreter reads the dialect as it is. `views/ui.assets.json` is what AzERP runs: the ERP's four views
  CORRECTED per the asset-management plan's "Problems in the definitions" (the form now has `residual_value`,
  both depreciation methods, location, serial number, the declining rate with a `condition`, the service
  interval; `category` is a reference, not free text) plus the views no ERP JSON defines yet (categories,
  locations, maintenance log + form, check-outs + form, disposal, reports, CSV import) and a `menu`. The account
  ids (`asset_account_id` ...) are left out: there is no ledger yet (see "Left").
- The named panels the JSON only names are hand-built (`ui/panels.rs`): FixedAssetOverviewPanel,
  DepreciationSchedulePanel, DepreciationRunPreview, AssetReportsPanel, AssetImportPanel.

## What was built

Model (plain Rust, unit-tested):
- `money.rs`: amounts in integer minor units (never floats): `format_amount` ("1,596.64"), `file_amount`
  ("1596.64"), `parse_amount` (English and German notation, currency signs/codes, `(12)` / `12-` negatives,
  refuses more than two decimals), `div_round` (half away from zero).
- `model.rs`: Asset, Category, Location, MaintenanceEntry, Checkout - one JSON file each, ERP schema field names,
  `format` + `version` header (a newer version is left alone, never guessed at), money as decimal strings, days as
  `YYYY-MM-DD`; Method / Status / MaintenanceKind codes; `Asset::problems`, `Asset::rate_bp`.
- `depreciation.rs`: schedules by calendar year with monthly pro rata (start month and disposal month count);
  straight-line (each year's share rounded, the final year takes the rest: 1,596.64 / 3 = 532.21, 532.21,
  532.22 exactly as the plan's sample), declining balance (rate of the book value, switching to straight-line
  over the remaining months when that is more, never below the residual), life 0 = low-value write-off;
  `book_value_on(day)` accrues month by month; `disposal_result` (gain / loss). A property test runs 300
  combinations and checks every schedule ends exactly at the residual value.
- `store.rs`: the data tree `erp/assets|categories|locations|maintenance|checkouts/<uuid>.json`,
  `erp/exports/<name>.csv`; `load` of a GetAll (unreadable / misnamed / newer files are named, not loaded); the
  `Book` (get / put / remove generic over the kinds, logs newest first, open check-out, next asset number,
  removing an asset removes its logs).
- `csv_io.rs`: export of the register (ERP header names, plain amounts, codes, names for category / location, the
  book value on the day) and of a schedule and a depreciation-run journal; import through the `csv` crate
  (separator guessed from the header line, BOM dropped), columns mapped by `guess` (ERP names, English labels,
  German headers like Inventarnummer / Anschaffungskosten / Nutzungsdauer) or by the user; a row whose number is
  in the register updates only its mapped cells, others create assets; categories / locations matched by name
  or created; rows that cannot be read are left out and named with their line.
- `reports.rs`: totals on a day, groups by category / location, the depreciation forecast by year, next service
  and services due, overdue check-outs.
- `sample.rs`: the `--sample` register (Mustermann GmbH: 5 categories, 3 locations, 12 assets incl. a
  low-value asset and a sold van, check-outs (one overdue), a maintenance log), relative to today.
- `app.rs`: the window-less state: routed navigation (`open(path)`: a `form` / `form_modal` view opens a draft
  OVER the page, anything else becomes the page; Back), saving every form (asset numbers unique; check-out /
  maintenance / disposal on the asset they were opened on; a check-out refused while one is open), check-in,
  delete, exports and the depreciation run's journal into `erp/exports/`, load, the sample (an empty register
  only), CSV import preview / mapping / commit, row paths. Every change queues its files in azul-pim's
  `WriteQueue` (one write per key, one batch in flight).

Window (`ui/`): azul's S6 `RecordsShell` in `ShellThemeScope::body()` (accent Slate), `NoTitle` + appkit's title
row; the tab row = the views' menu (Register, Categories, Locations, Maintenance, Check-outs, Reports); a
`table` view = a read-only DataTable over the grid (sort / filter / copy are the widget's; Enter or a
double-click opens the row action); a `detail` view = header (title, subtitle, status pill, the actions whose
condition holds) + TabHeader + panel (overview, schedule table + book-value line Chart, embedded tables);
`form` views in the RecordsShell form pane, `form_modal` views in a Modal; the reports (figures, bar charts by
category and by year, services due, overdue check-outs), the depreciation-run wizard, the CSV import (FileDialog
-> appkit `spawn_outside_read`, a DropDown per column, Import). Writes: the queue's batch becomes appkit
`FileJob`s on appkit's file thread (`kit::spawn_file_jobs`), answers in `on_files`. A CloseGuard (with a
dirty check) holds a window close while a form has edits. Settings / About / shortcuts are appkit's.
Switches: `--screen register|categories|locations|maintenance|checkouts|reports|import|run|settings`,
`--theme`, `--mode`, `--size`, `--shot`, `--sample`, `--data-dir`, a `.csv` file argument (imported once the
records are in); `AZERP_TODAY=YYYY-MM-DD` pins the day (E2E). Stdout lines for scripts are listed in
`ui/mod.rs`.

E2E: `scripts/azerp_e2e.py` (sample register, new asset + its schedule (75.00 first year), check-out / check-in,
maintenance, a refused form, CSV export, reports, the depreciation run journal, dark mode, then a restart on
the same folder: 13 assets read back and a CSV argument imported).

Registered: root `Cargo.toml` members (appended), `scripts/workspace_test_members.txt` (`tested: AzERP`),
`.github/workflows/rust.yml` dll_tests step "Run AzERP tests" (after AzDashboard's).

## Decisions made unattended (also in the progress file)
- D1 the interpreter (above). D2 one crate `AzERP` with sections (README s6 question 2). D3 money in minor units,
  no `rust_decimal` (not in Cargo.lock). D4 one JSON per record, exports into the data tree. D5 CSV through the
  `csv` crate. D6 "Run and post" writes the run's journal CSV into `erp/exports/` (no ledger exists).
  D7 the ERP original view file is checked in as the dialect fixture (the user's own repo). D8 AzERP talks to
  no outside service (coordinator rule: nothing personal leaves the machine).
- Record ids: `azul_storage::ids::new_uuid()` (plain-Rust form of `Uuid::from_seed(random_seed())`, the same
  seed source) - the state is plain Rust and tested without libazul.
