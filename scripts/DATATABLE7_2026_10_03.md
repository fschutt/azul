## What was built

### `layout/src/widgets/data_table.rs` (NEW, ~3,950 lines) + `data_table_tests.rs` (NEW, ~700 lines)

A `DataTable` widget for "sortable / filterable / editable tables over 500k x 25 rows":

- **Data by callback** - `DataTable::with_data_source(data, cb)`: `cb(data, DataTableCellRef { row, column })
  -> DataTableCell { text, value }` (the shown text, and the number a Number / Date column sorts and
  range-filters by; NaN = blank). `row` is always the APP's row index. Only the rows in view are asked for.
- **Virtualized in whole rows** - the scroll-window pattern of `CellGrid` (decision D1): the table builds the
  rows from `view.top` until its viewport is full and the frozen columns, then whole columns from
  `view.left_column`. Sticky header and filter row by construction; its own vertical and horizontal scroll
  bars (track click pages, thumb drag scrolls through all 500k rows); the wheel scrolls whole rows (Shift:
  columns). 500k rows build the same 9 x 4 window as 1,000 (test).
- **Sort** - a header click sorts ascending / descending / unsorted (stable, blanks last either way); Shift+
  click adds the column as one more key (multi-column, `Sales ▼1`, `Region ▲2` in the headers). Text is
  compared case-folded.
- **Filter row** - one filter per column under the header, edited in place (Ctrl/Cmd+F or a click), applied
  as you type. Text: contains, `=x` equals. Number: `5` (what shows as 5, to the typed decimals), `>5`,
  `>=5`, `<5`, `<=5`, `5..10`, open ends. Date (`value` = days since 1970-01-01): `2024`, `2024-03`,
  `2024-03-05`, comparisons and ranges of them. Anything else falls back to "the text contains it".
- **Sorting / filtering 500k rows off the UI thread** (decision D3): a table of <= 20,000 rows
  (`DATA_TABLE_SYNC_ROWS`) is ordered in the handler; a bigger one starts the ORDER JOB: a Timer reads the
  keys of the involved columns only (the plan) through the app's data callback, 25,000 rows per tick, on the
  UI thread (the callback is the app's and may be a managed-language host's, which must be called on the UI
  thread, and the app's data is borrowed there); then the plain keys go to an azul `Thread` which filters and
  stable-sorts them; the write-back finds the table's LATEST view (the table node carries its id as marker
  and its handler payload as dataset, decision D4) and fires `OrderReady` with `view.order` filled - a scroll
  or a selection made while sorting is kept, a superseded job (older query serial) stops at its next tick /
  is dropped. Meanwhile the table says "Sorting 500,000 rows..." and is `Busy` for screen readers, and
  stays fully usable.
- **Editing** - F2, Enter or a double-click edits an editable cell (a typed character starts an edit that
  replaces it); Enter keeps it, Tab keeps it and moves right (Shift+Tab left), Escape cancels; a click
  elsewhere keeps it. The app validates through `with_on_edit(data, cb)`: `cb(data, info, DataTableEdit {
  text, cell }) -> DataTableEditResult { message, accepted }` - a refused edit stays open and the app hears
  `EditRefused` with the reason. Enter on a read-only cell (or a double-click) reports `Activate`.
- **Selection** via `ListSelection` keyed by the app's rows: click, Ctrl/Cmd+click toggles, Shift+click /
  Shift+arrows extend in the order the rows SHOW (the keyed `_in` methods when a query ordered them), Ctrl
  /Cmd+arrow moves the cursor alone, Ctrl+A, Ctrl+Space, drag-select; a filter keeps only the rows still
  shown selected.
- **Keyboard** - arrows, Page Up / Down, Home / End (columns), Ctrl/Cmd+Home / End (rows), Ctrl/Cmd+C copies
  the selected rows (titles + rows, TSV and an HTML table, capped at 50,000 rows) - taken as the table's own
  key, because on a non-editing focus the engine leaves Ctrl+C to the app (no Copy event would come).
- **Column resize** - drag a header's right edge; the width is kept in `view.widths` (no app code needed).
- **Frozen columns** (`with_frozen_columns(n)`) with the cell grid's freeze line.
- **a11y** - the table is ONE focus stop, role `Grid`, value "Row 12 of 500,000, Sales", `Multiselectable`,
  `Busy` while sorting; the header a `Row` of `ColumnHeader`s carrying **aria-sort** (new
  `AccessibilityState::SortedAscending` / `SortedDescending`, mapped to accesskit's sort direction - an
  engine addition, see below); each row a `Row` with its index in the WHOLE table and `Selected`; each cell a
  `GridCell` named by its column title with its text as value; filters `Text` fields named "Filter <title>";
  the notice a live region; the scroll bars `ScrollBar`s.
- **Themes** - flat and flora looks APPENDED to `themes/flat.rs` / `themes/flora.rs` under
  `// ==== data_table ====`, both modes via the themed pairs; follows the app theme when not pinned.
- **App-owned state** - the `DataTableView` (sort, filters, order, selection, scroll, widths, edit, drag);
  every `DataTableEvent` carries the next view (store `event.view`).
- Manifest: appended to `every_widget_dom`, the CHROME contrast group and the wheel takers in `widgets/mod.rs`.

## Decisions (also in `scripts/DATATABLE7.PROGRESS.md`)

- D1 scroll window, not `VirtualView`: EVENTS7's open bug ("an event into a VirtualView child never reaches
  the parent DOM") and the one-focus-stop key handling; whole-row scrolling keeps 500k rows exact in f32.
- D2 the filter row and the cell editor are drawn by the table: key events BUBBLE from a focused descendant
  (Focus filters fire in the bubble phase, core/src/events.rs), so a TextInput inside would also drive the
  table's keys.
- D3 / D4 the order job, as above. Why not everything on a Thread: the data callback belongs to the app
  (managed hosts, the app's own borrow of its data); why not everything on the UI thread: a 500k sort is
  30-150 ms. The keys are read 25,000 rows per tick; only the columns the query needs are read.
- D5 reuse instead of twins: `cell_grid::{axis_bands, band_at, take_wheel, cursor_in}` made `pub(crate)`
  (one word each), `CellGridHorizontalAlign` as the column alignment, `CellGridSize(Vec)` for widths,
  `cells_to_tsv` / `cells_to_html` for copy, `date_picker::days_in_month`, `ListSelection`, `widget_p_with_text`.
- D6 the dashboard's data are generated, not stored (no Drive writes); edits live in memory.

## Seen / for other tasks

- CellGrid's Ctrl+C / X / V go through `FocusEventFilter::Copy / Cut / Paste`, but since the wave-6 shortcut
  rule (core/src/events.rs ~5292: an editing shortcut is the engine's only on a text-editing focus or a
  selection) a focused grid node gets no Copy event - its copy is probably dead (WIDGETS7 / EVENTS7: verify;
  the DataTable takes Ctrl+C in its key handler for this reason).
- Twin (NO DUPLICATION): CellGrid's `edit_key` caret arithmetic (Left / Right / Home / End / Back / Delete)
  is the same as `data_table::line_edit`; CellGrid could call `line_edit` (WIDGETS7 owns the file).
- `ListSelection::retain_in` sorts the listed keys (O(n log n)); at `OrderReady` over 500k rows that is
  ~30 ms on the UI thread when a selection exists - acceptable, but a bitmap version would be O(n).
