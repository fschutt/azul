## What was built

### Engine: scheduled notifications (engine backlog item 14, the AzClock part)
The shape of scripts/NOTIFICATIONS_RESEARCH_2026_09_28.md section 6.5 (`NotificationSchedule::At`),
as small as it can be:

- `azul_core::notification::Notification` gains ONE field, `deliver_at: OptionU64` (ms since 1970,
  UTC; the LAST field, 8-aligned like all the others, no padding) and `with_deliver_at(unix_ms)`.
  `None` = now (as before); a time in the past or under a second away = now; a later time SCHEDULES.
- macOS / iOS (`dll/src/desktop/notifications/apple.rs`): a one-shot
  `UNTimeIntervalNotificationTrigger` instead of the nil trigger - UN keeps it and fires it while
  the app is not running. Withdraw already removed pending requests.
- Windows (`windows.rs`, the toast path): a `ScheduledToastNotification` +
  `ToastNotifier::AddToSchedule` (tag + group = the id; a re-post removes the old one first);
  withdraw also takes it off the schedule (`GetScheduledToastNotifications` / `RemoveFromSchedule`).
  `PlatformNotifier::can_schedule()` is false on the balloon fallback.
- Everything else (freedesktop / portal, Android until its alarm receiver exists, the balloon):
  the service HOLDS the notification (`azul_layout::managers::notification::ScheduledNotifications`:
  one per id, soonest first, bounded at 1024 - a refused one becomes a `Failed` event), a small
  deadline thread sleeps on the WALL clock (at most 30 s at a time, so a suspend delays it no
  more) and calls `loop_waker::wake()`; the pump posts what is due. Unavailable backends fail the
  post at once. Headless records the post with its time.
- Pure helpers in `wire` (tested on every host): `delivery_delay_ms`, `apple_trigger_interval`,
  `windows_datetime` (100 ns ticks since 1601).
- E2E: `assert_notification` takes `scheduled` (bool) and `deliver_at` (exact ms).

### AzClock (`examples/azul-clock`, package AzClock, lib azclock, bin AzClock)
Model (plain Rust, unit-tested without a window):
- `alarm.rs`: time of day + RRULE repeat (azul-pim's `rrule::Rule::dates`) + label / sound / snooze;
  occurrences as instants in ANY `chrono::TimeZone` - DST by RFC 5545 3.3.5 / Temporal
  "compatible": a time in the spring-forward gap rings as much later as the gap (02:30 -> 03:30
  CEST), a time in the fall-back overlap rings once, at the earlier instant. A repeating alarm's
  first day rings only if the repeat names it (and a COUNT then counts one more). `due` (a ring that
  came, up to 30 min late after a sleep, else skipped), `snooze`, `arm` (a one-time alarm arms for
  the next time its time comes; everything before now counts as rung), `rang` (one-time alarms
  switch off), repeat labels ("Weekdays", "Mon Wed Fri", "Every 2 weeks on Monday").
- `timer.rs`: the countdown state machine (Idle / Running{ends_at} / Paused{remaining} /
  Finished{at}) derived from the wall clock: a slow frame loses nothing, a running timer survives a
  restart, +1 min on every state.
- `stopwatch.rs`: elapsed + laps (fastest / slowest), laps as tab-separated text.
- `world.rs`: cities on IANA zones (chrono-tz), offsets, abbreviations, day / night,
  today / tomorrow / yesterday, the search over every zone (azul-pim's folded `Query`), reorder.
- `schedule.rs`: what the OS gets - up to 7 slots per alarm within 8 days (fixed ids
  `azclock-alarm-<uuid>-<k>`: a re-post REPLACES, no bookkeeping), the snooze, running timers,
  the soonest 60 (Apple keeps 64), payloads (`alarm:<uuid>:<ms>`, `snooze:..`, `timer:<uuid>`) that
  survive the process, and the diff against the last plan.
- `store.rs`: `clock/alarms/<uuid>.json`, `clock/timers/<uuid>.json`, `clock/world.json`,
  `clock/stopwatch.json` (+ appkit's `clock/settings.json`); load jobs, reading back (a damaged file
  costs that record), the plan's sample data.
- `fmt.rs` (texts), `tone.rs` (bells / beep / chime synthesised into PCM for `AudioSink`).

Window (`src/ui/`): azul-appkit kit (switches, data root, settings page, About, shortcuts),
S9 `UtilityShell` + `Titlebar` (NoTitle), `ShellThemeScope::body()`, flat / flora x light / dark.
- World: an analog face of rotated divs (CSS `transform: rotate`), the digital time with the zone
  abbreviation, the city rows (click = show it on the face, Up, Remove), "Add city" = a Modal with
  a search field and a button per result.
- Alarms: rows (time, label, repeat, "in 15 h 58 min", snoozed), a `Switch` each, click = the
  editor (a Modal: `TimePicker` 24 h / 12 h, Once / Every day / Weekdays / Weekends shortcuts plus
  azul's `DateRepeatPicker` for any repeat, label, sound `DropDown`, snooze `NumberInput`,
  Delete / Cancel / Save; a toast "Alarm set for ... from now").
- Timer: the big countdown, a `ProgressBar` for the ring (TODO(WIDGETS9B): Gauge), Start / Pause,
  Reset, +1 min, presets 1 / 3 / 5 / 10 / 25 min, every timer in a list.
- Stopwatch: a text node with a marker that a 30 Hz timer retexts in place (`change_node_text`, no
  relayout; the timer runs only while the stopwatch runs on screen), Lap / Start-Stop / Reset /
  Copy laps (Mod+C), lap rows with fastest / slowest.
- Ringing: a Modal (time, label, Snooze N min / Dismiss; a timer: "Time is up", +1 min / Dismiss),
  the tone through `AudioSink` (kept 1.5 s ahead), the window un-minimized and raised; it ends by
  itself after "Ring for" minutes.
- The OS: after every change `schedule::plan` + `diff` -> `post_notification(... .with_deliver_at())`
  / `withdraw_notification`, buttons "snooze" / "dismiss". The app-level handler
  (`AppConfig::set_notification_handler`) gets every event - also the tap that launched AzClock -
  and snoozes / dismisses / opens the screen by the payload; a `Failed` event says why the system
  will not ring while AzClock is closed.
- Linux (and wherever notifications cannot be scheduled): closing the window while an alarm or a
  timer is armed MINIMIZES it instead ("Keep running", settings), Mod+Q quits for real.
- Settings page (Clock / Alarms sections): 12-hour times, Ring while closed (OS scheduling on/off),
  Keep running, Ring for; the kit's Appearance / Data / Shortcuts / About.
- Keys: Alt+1..4 screens, Mod+N new, Mod+Q quit, Space snooze / Escape dismiss while ringing,
  Space / L / R / Mod+C on the stopwatch, Space / + on the timer; Mod+, settings, F1 shortcuts.
- stdout for scripts: AZCLOCK_SCREEN / LOADED / SAVED / SCHEDULED / RING / DISMISSED / SNOOZED /
  NOTIFICATION / ALARM_SAVED / ALARM_SWITCH / CITY_ADDED / COPIED / KEPT_RUNNING.

`scripts/azclock_e2e.py`: the headless walk (sample files on disk, the OS schedule, the alarm rows
and switch, the editor's Save as a fourth file, world + add Lima, the 1 min preset, the stopwatch,
settings Flora + Dark, screenshots; `--ring` waits for the 1 min timer to ring and dismisses it).

Registered: root `Cargo.toml` members, `scripts/workspace_test_members.txt`, a `dll_tests` step in

## Decisions (also in the progress file)
- Time zones: chrono + chrono-tz 0.10 (in Cargo.lock through ironcalc_base) and iana-time-zone 0.1
  (in the lock through chrono's `clock`, same `fallback` feature) - the plan's `jiff` is not in the
  lock. No new crate. AzClock also depends on the workspace crates azul-appkit, azul-pim,
  azul-storage. Cargo.lock gains the AzClock package entry (no new external packages).
- DST rule: RFC 5545 3.3.5 (see above), not "the first valid instant after the gap" of the research
  doc - RRULE, azul-pim and Temporal all read it so.
- API: one optional delivery time, not rule-based OS repeats: the app expands its repeats (DST-
  correct, every backend can hold one-shot instants, Windows cannot repeat at all, UN calendar
  triggers cannot say "every 2 weeks" or follow a moved DST rule) and tops them up on every start.
- Apple: a time-interval trigger (calendar-independent; a calendar trigger's components would be in
  the user's calendar, which need not be Gregorian). See "least sure" for the sleep question.
- While AzClock runs, both the OS notification and the in-window ring fire at the alarm's time
  (banner + overlay); Dismiss in the window withdraws the snooze / timer notification.
- The scheduled ids are fixed slots, so nothing about what the OS holds is persisted.

## api.json (for `azul-doc autofix`)
- `Notification` (module `notification`): struct field `deliver_at: OptionU64`, appended as the LAST
  field (after `callback`). Doc: "When to show it: milliseconds since 1970 (UTC). None (the default)
  shows it at once, and so does a time in the past or less than a second away. A later time
  SCHEDULES it: the OS keeps it and shows it then - also while the app is not running - on macOS /
  iOS (a time-interval trigger) and Windows (a scheduled toast); elsewhere the running process holds
  it. Withdrawing the id cancels it."
- `Notification.with_deliver_at`: `fn_args: [{"self": "value"}, {"unix_ms": "u64"}]`,
  `returns: Notification`, `fn_body: "object.with_deliver_at(unix_ms)"`, doc "Show it at unix_ms
  (milliseconds since 1970, UTC) instead of now - see Notification::deliver_at."
- AzClock calls `Notification::with_deliver_at` - it compiles only after this is generated.
