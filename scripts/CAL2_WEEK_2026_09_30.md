day and zoom in / out with the trackpad (like azmaps does), so I can zoom in to a part of the day. also
clicking at a certain point to add an event at that day (with a transient window popover) doesn't work as it
does in google calendar."

- The parent's run of the E2E (7 of 7 stages failed). Two engine bugs came out of it, fixed with RED tests.

  - event titles are clipped;
  - the "No meeting server is set" line is gone;
  - there is a default server and a Settings menu;
  - AzMeet links are made offline and synced later, so making an event with a link always works.

## Why the whole day could not be reached
The cause is in the app, not in the engine:
1. The week only ever held 08:00 - 20:00. The hours before and after were not in the DOM at all.
2. Nothing in the window scrolled (no `overflow-y` anywhere).
3. The flex chain (body > main > week) had no `min-height: 0`. A flex item keeps its content height as its
   minimum, so even a scroll area would have grown instead of scrolling.

A layout pin test checks the exact structure the app now uses. It is expected GREEN.

## Engine changes (round 2)
1. **`core/src/styled_dom.rs` `is_layout_equivalent`** also compares the author CSS the cascade ran with,
   `get_css_property_cache().retained_author_css`. That holds every node's `Dom::with_css` sheet.
   - Before, a rebuild that only changed `with_css` values was treated as "same layout" and kept the old
     one. That is why the pinch reached the app (its `scroll_to` was in the log) but the hours did not grow.
   - The same stale layout hit any app that moves or resizes a block, or changes a colour, only through
     `with_css`.
   - RED: `is_layout_equivalent_rejects_a_changed_node_stylesheet` (`core/src/styled_dom_test.rs`).
2. **`dll/src/desktop/shell2/common/event.rs` `dispatch_accessibility_events`**: the Default action's
   filter is the Hover `Click` filter now, and it was skipped. It becomes an `EventType::Click` at the node,
   as Enter and Space do.
   - Before, a screen reader's press, and the E2E `accessibility_action default` on Save / Cancel, ran
     nothing.
   - RED: `a_screen_readers_default_action_runs_the_nodes_click_callback_once` (headless tests in
     `dll/src/desktop/shell2/headless/mod.rs`).
3. **Cumulative pinch** (`layout/src/managers/gesture.rs` and every shell). `DetectedPinch.scale` is the
   scale since the gesture began, and the new last field `began` marks the gesture's first update, once
   per gesture. Consumers zoom by `scale / previous`, with previous = 1.0 on `began`.
   - macOS: `magnifyWithEvent:` reports each event's own magnification. The new
     `GestureAndDragManager::trackpad_magnify(phase, delta, centre)` multiplies the deltas up over the
     NSEvent phase:
     - Began: resets to 1.0 and sets `began`;
     - Changed / Stationary: `scale *= 1 + delta`;
     - Ended / Cancelled: ends the gesture and injects nothing;
     - an update with no gesture open begins one.

     This was the AzMaps jitter: +2 % then +1 % had been injected as 1.02 then 1.01, which reads as
     zooming in and then back out.
   - Touch (`detect_pinch`): already current / initial distance. `began` holds until
     `note_pinch_dispatched`, which each pass end calls next to `clear_native_gesture`.
   - iOS: the BEGAN update is injected too.
   - Android: `NativeGestureBridge.java` multiplies `getScaleFactor()` up from `onScaleBegin`. It takes a
     new `began` argument, so both the JNI signature and the Rust side changed.
   - Wayland / X11: already cumulative; the first update gets `began`.
   - Windows: GID_ZOOM was already cumulative. The DirectManipulation transform is forwarded as it is
     instead of being differenced into deltas. A synthesized Ctrl+wheel notch is a one-update gesture.
   - Map widget: `pinch_anchor` holds the gesture's last cumulative scale, and
     `dz = log2(scale / previous)`.
   - E2E `pinch` op: takes an optional `began`, default true.
   - RED tests:
     - `trackpad_magnify_deltas_add_up_to_a_growing_cumulative_scale` ([+0.02, +0.01, +0.03] gives a
       rising scale, and Began resets it);
     - `a_trackpad_pinch_ends_and_an_update_without_a_begin_opens_a_new_one`;
     - `a_touch_pinch_begins_once_per_pair_of_touches`;
     - map: `a_zoom_in_pinch_only_zooms_in_and_a_second_pinch_starts_where_the_first_ended`;
     - AzCalendar: `a_zoom_in_pinch_only_grows_the_hour_and_a_second_pinch_does_not_jump`.

### api.json impact
- `DetectedPinch`: new field **`began: bool`, the LAST field** of the repr(C) struct. Its doc (ASCII):
  "This is the first update of its gesture (once per gesture): `scale` is measured from 1.0 here, and a
  new gesture starts no matter what the last one ended at."
- `DetectedPinch.scale`: the doc now reads "Scale since the gesture began (< 1.0 pinched in, > 1.0 spread
  out)".
- Nothing else is public. `TrackpadGesturePhase`, `trackpad_magnify` and `note_pinch_dispatched` are
  internal to the layout crate and the shells.
- Round 1's API list is unchanged. Round 2's app code also uses the menu API (`Menu`, `MenuItem::string`,
  `StringMenuItem::create / with_children / with_callback`, `Dom::with_menu_bar`) and timers
  (`Timer::create / with_interval / with_delay`, `CallbackInfo::add_timer / get_system_time_fn`,
  `TimerCallbackReturn`). All of these already exist.

## What was built (the app)

### Scroll (round 1)
- The week holds 00:00 - 24:00.
- The day-header row sits above the scroll area `#week-scroll` (`flex-grow: 1; flex-basis: 0;
  min-height: 0; overflow-y: auto`). The hour gutter scrolls with the grid.
- The week opens at 08:00, or on today's week at the whole hour an hour before now (`AfterMount`).
- Today's column has a red "now" line.
- A saved event that is out of view scrolls the week to it.

### Zoom
- `CalState.hour_px`: 20 - 240 px, default 48.
- **Persisted (round 2)** in `<data dir>/settings.txt` as `week_hour_px=`, read at start. It is saved a
  second after a zoom step, one timer at a time, so a pinch writes at most once a second.
- Pinch: `PinchIn` / `PinchOut` on `#week-grid`, handled by `week::pinch_step(previous cumulative scale,
  {scale, began})`.
- Ctrl / Cmd + wheel: `2^(dy/240)` per event, bounded to 0.8 - 1.25, with `prevent_default`. A plain wheel
  scrolls.
- The time under the pointer stays under it: `week::zoom_scroll`, applied with `scroll_to_unclamped`.

### Click / drag to create (Google Calendar style)
Unchanged from round 1:
- A click makes a one-hour draft snapped to the quarter hour; a drag spans every quarter hour it touches.
  Both stay inside the day.
- The draft (`#draft`) carries a `<transient-window>` popover (`#draft-panel`) with:
  - the title (`#draft-title`), focused;
  - the day and time (`#draft-when`);
  - "Add AzMeet link";
  - Cancel and Save.
- Enter or Save saves; Escape, Cancel or a press outside drops the draft.
- A press on an existing event is left alone.

### Offline-first AzMeet links (round 2, the user's request)
- **Save never waits on the network.** With "Add AzMeet link" ticked, the link is made in the app.
  - `meeting::new_room_id` draws 130 random bits in the server's room-id alphabet: 26 characters of
    lower-case Crockford base32. That is the same shape AzMeet reads (`meet_rooms::parse_room_key`).
  - The event file is written at once with `"meeting": {"link": "azlin://meet/<id>", "server": ...,
    "pending": true}`.
  - Files from before have no `pending` and count as registered.
- **Sync.** Each pending link is registered with `POST <server>/rooms {"room", "starts_at", "ends_at"}`
  (UTC), one azul `Thread` each, at these times:
  - right after the save;
  - when the week mounts;
  - every `AZCAL_SYNC_SECONDS` (default 30);
  - on "Sync meeting links now".

  The answer has to name the same room (`meeting::registered_meeting`). The file is then rewritten with
  the code and times, `pending` drops out, and `AZCAL_SYNCED <link>` is printed on stdout.
- **When a registration fails:**
  - unreachable, 429 and 5xx are tried again (`meeting::sync_again`);
  - a refusal is not tried again until "Sync meeting links now" or a new server;
  - an old Worker that ignores `room` and makes its own room counts as a refusal, with a message that it
    needs the update.
- **What the week shows:** an event whose link waits shows "AzMeet link waits for the server". "Join
  meeting" appears only once the link is registered.
- **Default server, no warning:** the server is taken from the first of these that is set:
  1. the saved setting;
  2. `AZMEET_WORKER`;
  3. the built-in `AZMEET_DEFAULT_WORKER`;
  4. AzMeet's local `http://127.0.0.1:8787`.

  This is the same order as AzMeet's (`meet_rooms::server_prefill`), so there always is a server. The "No
  meeting server is set: start ..." line is gone. The footer shows the server and how many links wait.
- **Settings menu:** the menu bar has Settings > "Meeting server..." and "Sync meeting links now".
  - "Meeting server..." opens a sheet right of the week with:
    - the server field (`#settings-server`, checked by `meet_rooms::normalize_server`);
    - the sync status;
    - "Sync now", Cancel and Save.
  - Save writes `meeting_server=` in AzMeet's settings format and moves the links still waiting to the
    new server.
  - Registered links stay with the server that has their room.
- **Worker** (`azul-apps/cf-workers/meet`, `scripts/cal2/meet-0002`):
  - `POST /rooms` with `"room"` registers that id: 201, or 200 when it is already there (idempotent);
  - a malformed id gets 400 `invalid_room`;
  - without `"room"` the Worker mints a room as before;
  - the README has a "Links made offline" section.
  - `node --test`: RED 64 pass / 5 fail, GREEN 69 / 69, run here.

### Clipped titles (round 2)
- Event blocks have `overflow: hidden`. The title and time are single lines (`white-space: nowrap;
  overflow: hidden; text-overflow: ellipsis`).
- The draft clips its text in an inner box, because its popover is its child too.

### Settings file
`settings.rs` owns `<data dir>/settings.txt`: `key=value` lines in AzMeet's format.
- `write_line` keeps every other line and replaces the file atomically, so the server and the zoom do not
  overwrite each other.
- A file longer than AzMeet reads is ignored.

### Titlebar
Untouched: the toolbar and `WindowDecorations` are as they were. The Settings entry lives in the menu bar
(the native menu on macOS), not in the toolbar.

## How sure (nothing compiled)
- `rustfmt --check` passes on every changed Rust file: the parts touched, where a file already had
  unrelated formatting differences.
- Every new API call was checked against the generated link-dynamic bindings in the scratchpad copy of
  `target/codegen` (`dll_api_external.rs`, `reexports.rs`). That covers:
  - the menu types in `azul::menu`, and `CallbackType` in `azul::callbacks`;
  - `Timer`, `TimerId`, `Duration`, `TimerCallbackInfo` and `TimerCallbackReturn` in the prelude;
  - `SystemTimeDiff` in `azul::time`;
  - the `AzTimerCallbackInfo.callback_info` field;
  - `From<Vec<MenuItem>> for MenuItemVec`.
- The Worker patches were run with `node --test`: RED 64 / 5, GREEN 69 / 69.

Least sure, in order:
1. That the headless backend runs app timers while the E2E pumps frames. The offline sync retry
   (`AZCAL_SYNC_SECONDS`) and the zoom save depend on it.
   - If it does not, `offline_links.py` still registers the link when the Worker comes up only if a save
     or a mount happens after that. The zoom stage would then fail on "settings.txt to keep the zoom".
2. A thread started from a timer callback (`info.callback_info.add_thread`, in `on_sync_tick`). Timer
   changes go through the same `CallbackChange` list as other callbacks.
3. The Windows DirectManipulation change (`direct_manipulation.rs`): it was reasoned from the API docs, not
   run.
4. The Android JNI signature change. `NativeGestureBridge.java` and the Rust `extern` have to be rebuilt
   together.

## What is left
1. The headless popup limit, round 1's engine follow-up: headless child windows never run a pass. Because
   of it, the E2E drives the popover's nodes in DOM 0 and cannot press Enter or Escape in the popup
   itself.
2. On platforms with classic (non-overlay) scrollbars, the header can be misaligned by up to the
   scrollbar width.
3. The Settings sheet is reached only through the menu bar. A platform or backend without a menu bar
   (headless) cannot open it; the E2E does not need it.
4. Moving or resizing existing events by dragging, all-day events and overnight events are not built.
