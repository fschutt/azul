# ANIM8 - "animations don't work at all anymore" (wave 8, 2026-10-03)

Branch `wt/anim8` (base 45c6bf98b). User: "animations don't work at all anymore, i.e. the AzWidgets toggle?
or the hover animation over buttons, it immediately transitions". Seen on the prebuilt wave-7 AzWidgets /
AzCalculator (headless, capped runner, one app at a time), root-caused, RED first, fixed. Nothing compiled.

## What was wrong - three separate causes

### 1. The toggle: the rebuilt Switch took the identity of ANOTHER switch (the regression)

Seen (AZ_E2E scenario `scripts/anim8_switch_scenario_gen.py`, prebuilt AzWidgets at 900x1300): after a
click, the toggled Switch's TRACK (node 207) got a FLIP slide of translate (490, 7425) - from the
ShellSettingsDialog's switch 7400 px further down the page - and over the debug server (real clock) the
knob sometimes stood at its END value on the first frame while a 15 px FLIP slide ran on it.

Root cause, two pieces that only meet since AzWidgets' Dialogs section (bfc38710f, 2026-10-01) put a
second Switch on the same page:

- The click handler writes imperatively (`set_css_property` -> `NodeData::upsert_inline_css_property`),
  which REMOVES the declaration where it stood and APPENDS it as a rule of its own.
- `impl Hash for NodeData` (core/src/dom.rs) folded the inline declarations' discriminants IN ORDER.

So after the click the toggled switch no longer hashed like a fresh build of itself, but exactly like the
untouched twin, and `reconcile_dom`'s pass A2 (exact SUBTREE hash, gated only by the nearest ancestor
with a terminal id - here none) gave the rebuilt switch (the app returns RefreshDom) the twin's identity.
Everything keyed by identity followed the wrong node: the FLIP "first" rect (the slide from 7400 px
away), `css_transitions` and the user overrides (`remap_node_ids`, `migrate_user_overrides_from`) - the
toggled switch snapped while its tween went to the other one.

Fix (1a2be0ff6): the inline part of the node hash is ORDER-FREE - a count plus a wrapping sum of
per-property hashes (WHICH properties a node declares, never in which order; values stay out as before).
Hash/Eq contract unchanged (equal nodes still hash equal). RED: core/src/diff_test.rs
`a_toggled_widget_keeps_its_identity` (b57bb6bb7).

### 2. The hover "animation" never existed - a pointer state change never started a transition

Seen (`e2e/css-hover-transition.json` on the prebuilt AzCalculator, AZ_E2E): a node declaring
`animation: background 200ms linear` and a `:hover` background snaps on the first frame, 0 transitions.
Only two places ever seeded a `CssTransition`: the rebuild diff (`begin_reconciliation`) and an imperative
write (`apply_node_css_change`). The `:hover` / `:active` / `:focus` restyle
(`StyledDom::restyle_on_state_change`, called from the shell's `apply_hover_restyle` /
`apply_active_restyle` / `apply_focus_restyle_in_dom` and the scripted runner) never did - and no widget
declared a fade anyway (no theme file contains an `animation`). Not a regression: a missing feature the
user expects. Built in the engine:

- `LayoutWindow::seed_state_change_transitions(dom, before)` + `LayoutWindow::node_states(dom, nodes)`
  (60f3f4580): the third seeding path. The NEW state's `animation` governs (CSS after-change style). A
  property still in flight restarts from the value ON SCREEN (the transition's override - the restyle's
  own diff cannot see it, the override answers for both states) toward what the new state cascades to,
  so a fade reverses where it stands; an app-written override and an imperative tween in flight are left
  alone; a 0 ms declaration means "at once" (063c009d8).
- Wired (d58dbdf13): dll `common/event.rs` hover / active / focus restyles and layout `e2e/runner.rs`
  hover / focus restyles snapshot the states before the flip and seed after it (before the "nothing
  changed" early return).
- The Button declares it (d5cebf5a7): `decl::state_fade(props, ms)` = `animation: <props> <ms> ease-out`
  plus the same list at 0 ms on `:active` - a press shows at once, its release eases back, like a native
  button. flat's and flora's Button push it for their own face (`decl::BUTTON_FACE`: background + the
  four border colours, `BUTTON_FADE_MS` = 120); a link (an underline) and a caller-owned style (ribbon,
  chrome parts) declare none.
- flora's faces are gradients, and a background tween understood one solid colour: it held the start face
  to the midpoint, then jumped. `background::interpolate_background_layers` (dd4bb436d) tweens layer
  lists that pair up (colour/colour, linear gradients of the same direction, extend mode and stop
  positions); anything else keeps the half-way switch.

### 3. A rebuild under the pointer faded a hovered node out (found while building 2)

`begin_reconciliation` read the NEW tree at rest - the shell re-applies `:hover` / `:active` / `:focus`
only AFTER the diff (`apply_runtime_states_before_layout`) - so a hovered node that declares a fade read
"hover face -> resting face" on every rebuild: with the Button fade, every button whose callback returns
RefreshDom would fade out under the pointer and snap back. Fix (d3ed2527f): `with_interaction_of` - the
diff reads the new node in the window-owned states it gets back (hover, active, focused, focus-within,
backdrop, dragging, drag-over, seat focus) from the node it replaces; DOM-owned ones (disabled, checked)
stay the new tree's. The paint-dirt classification of the same diff stops flagging hovered nodes too.
RED: layout/tests/a_rebuild_under_the_pointer_starts_no_transition.rs (0d5e3fd53).
