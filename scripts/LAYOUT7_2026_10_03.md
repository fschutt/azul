## 1. What was built, item by item

1. **An absolutely positioned child does not split its parent's line; the marker rides the first line.**
   Three root causes (Chrome / prebuilt: check item 20 / 40 px, `<div>one<div abs/> two</div>` 20 / 40,
   `<li>Item<div>block</div></li>` 40 / 60, `<li><p>a</p><p>b</p></li>` 40 / 60, nested 20 / 40):
   - `is_block_level` counted an abspos block as a block child: anonymous wrappers split the line and
     `has_only_inline_children` said "no IFC". ONE rule now, `layout_tree::in_flow_block_level_mask`:
     an out-of-flow block goes with the inline content around it (Blink's rule), and stays a direct
     child only where there is none (between blocks / beside collapsible white space - no anonymous
     block of white space). Used by the fresh tree (`process_block_children`, anonymous table cells),
     the reconciler (`reconcile_recursive`, `reconcile_table_children`, `layout_relevant_child_count`)
     and `has_only_inline_children`.
   - The `::marker` box of a BLOCK list item was laid out by `layout_bfc` as an in-flow IFC of the
     LI's DOM node, whose collection walked the li's DOM children: a marker line of its own that
     repainted the loose text. "Case 2" put a marker on EVERY IFC whose parent was a list item, the
     anonymous block none. Now ONE rule, `fc::marker_line_host` (the IFC holding the item's first
     line box: the item, else the first IFC down its first in-flow block children);
     `markers_on_first_line` puts the marker at the start of that IFC (anonymous ones included;
     `push_marker_content` is the old inline code, moved); `layout_bfc`, the intrinsic sizes and
     `process_out_of_flow_children` pass a marker that has such a line by (`is_marker_on_a_line`); a
     marker with no line to ride (an empty item) is still a line of its own, holding only its marker.
     The O(n) scan of all tree nodes per IFC to find the list item is gone.
   - `list-style-type: none` made a marker box anyway, with the text " " (the separator appended to an
     empty string); and the type was read from the list CONTAINER before the item's own (inherited)
     value. `create_marker_pseudo_element` returns `Option` and makes no box for none; the type is the
     item's own.
2. **A block inside an inline is split around it** (CSS 2.2 s9.2.1.1; `<a><img style="display:block">`,
   every linked picture of a newsletter). The block was "inlinified" into the line and had no box
   (`<div><a><span block 40px>` 20 / 40 px). `layout_tree::inline_holds_a_block` +
   `split_inlines_around_blocks`: an in-flow, non-replaced inline box holding an in-flow block-level box
   (directly or through other such inlines) is replaced by its children among the block container's
   children; the content around the block goes into anonymous blocks, the block is their sibling.
   Fresh tree, reconciler and `has_only_inline_children` use the one helper; fc.rs's twin walk
   `inline_children_hold_a_block` (cells) is deleted.
3. **A border-box min / max-width bounds the border box of an auto-width box** (AzMail's paper: 524 /
   500). `calculate_used_size_for_node` clamped the content width with border-box min/max and added the
   padding after; the content width now goes into border-box space for the clamp and back. The
   intrinsic floor of a length min-width sheds the border box's border and padding (`min-width: 300px`
   inline-block 324 / 300). Also fixes `max-width` + border-box on stretched blocks (324 -> 300).
4. **`width: fit-content` shrinks to its content.** The keyword never parsed (only the function):
   dropped, the box was `auto` (74 / 500). It parses as `fit-content(100%)`; the argument takes the
   place of the available space (stretch-fit = argument less margins, borders, padding); a fit-content
   size is a content size (`width_is_quantitative` no longer counts it). Two more causes found on the
   way: a block IFC root holding only atomic inlines was measured as an inline box (0 wide: `width:
   max-content` around an inline-block was 0, Chrome 50), and intrinsic-keyword boxes were not
   shrink-to-fit contexts (the static-DOM short-circuit handed them zero intrinsics).
5. **An anonymous table cell keeps its blocks' margins** (`display: table; padding: 12px` around
   `<p>Hi</p>`: 76 / 44). `fc::establishes_new_bfc` said "no" to every DOM-less box but the table
   wrapper; an anonymous cell (FormattingContext::TableCell) is a BFC root now.
6. **CSS `zoom`** (Chrome's model, CSS Viewport 1): the property (`normal | <number> | <percentage>`,
   not inherited; parse, print, cascade, transition) and its effect: the effective zoom is the product
   of `zoom` over the node and its ancestors (`getters::get_effective_zoom`, a per-cascade memo in
   core's `CssPropertyCache::resolved_zooms`, empty - no index read - when nothing zooms). ONE rule,
   `getters::scale_length_for_zoom` / `zoomed_length`: px / pt / in / cm / mm scale by it, rem by it
   relative to the root's, em / % / viewport units do not (em follows the zoomed font size, % the
   zoomed containing block). Applied to: the element font size (`get_element_font_size`; the text's
   StyleProperties take that one resolution in a zoomed document), margins / padding / borders
   (`UnresolvedBoxProps::resolve`), width / height / min / max (used size, constraints, intrinsic
   overrides, flex / grid explicit sizes, fit-content argument), an image's natural size,
   line-height / letter-spacing / word-spacing lengths, positioned offsets, a vertical-align length.
   For OFFICE7: AzMail can put `zoom: <n>` on the reading pane / paper now.
7. **AzMail's account wizard stopped at page 2** (RED `cc7040ae5`). Root cause in core's
   `reconcile_dom`, exact-subtree pass A2: it refused a match only when the IMMEDIATE parents'
   terminal identities (key / CSS id) differed, so page 2's `#acct-imap-host > p > "x"` took page 1's
   `#acct-name > p > "x"` text node (both parents the anonymous `p`) and the text overlay - the typed
   name, the caret - followed it into the host field. The gate is now the nearest ancestor WITH a
   terminal identity (one pre-order pass per tree); anonymous containers (re-pagination) are still
   crossed. The RED layout test called `layout_new_generation` alone - a path no app takes, where
   node-keyed state is never moved or dropped - and now installs each page the way the shells'
   `regenerate_layout` and the E2E runner do (`begin_reconciliation`, `layout_new_generation`,
   `finish_reconciliation`); a core unit test pins the mechanism.
8. **Inline-block in an inline span sized from max-content: already fixed** (TEXTENG, wave 5:
   `measure_atomic_inline` in the span arm), pinned by
   `layout/tests/an_inline_block_inside_a_span_is_sized_by_its_own_css.rs`; the probe matches Chrome
   (px, %, auto). The ledger item is stale. No change.
9. **The narrow-table assertion: already restored** (TABLES wave 5, `f120ecc14`: each cell exactly two
   baselines, the 3.9.3 split). The inline-block min-content bug `56b105f60` dodged was the font-stack
   off-by-one (MAILENG6 `2b5bae827`), pinned by `text_beside_an_italic_or_bold_box_keeps_a_font`; probe:
   a `width: 1px` table of `<i>` boxes 106 = Chrome, the 220px prose table 131.8 / 82.2 vs Chrome
   131.6 / 82.5. No change.
10. **A block taller than a page.** The engine already SPLITS it (CSS Fragmentation: a paragraph
   between its line boxes; a monolithic box taller than the page is sliced - paged media permits
   slicing - pinned by a new test). AzWriter overflowed its sheet because a mid-block break was only
   addressable by `break_path` (the first block whose TOP is at/after the break - nothing for a break
   inside the last block) and the FFI handle carried nothing else. Now each `StructuralBreak` names the
   block it splits (`line_path`, `paged_layout::spine_line_split_at_y`; one path builder
   `child_index_path`), and `PaginationSnapshot` exposes `break_line_path` / `break_line_start_run` /
   `break_line_start_byte`. page_breaks.rs untouched. The consumer change is WIDGETS7's / OFFICE7's
   (section 7).

## 6. Seen broken, not fixed here (owner)

- **text3 / TEXT7**: a line holding only atomic inlines is measured by its items, not its line box
  (text3 cache.rs ~11570, deliberate: "an `<svg>` alone on a line keeps its box's height"); Chrome
  (standards mode) includes the strut: a 10px inline-block in a `line-height: 20px` block makes a
  20px line (azul 10). Every icon-only line differs by the strut's descent; changing it moves every
  icon button, so it needs a LOOK pass.
- **text3 / TEXT7**: sizing.rs's intrinsic widths count the container's text-indent for an anonymous
  block after a nested block too (TEXT7's new code); the layout no longer indents it.
- **PAINT7 (display_list.rs)**: CSS zoom does not reach paint-only lengths - border-radius, box-shadow,
  outline, text-decoration thickness, background size / position px, scrollbar sizes.
- **WIDGETS7 (rich_text_editor.rs `page_doms`) + OFFICE7 (azul-writer paginate.rs
  `starts_from_breaks`)**: pages hold whole blocks. With `PaginationSnapshot::break_line_path` /
  `break_line_start_run` / `break_line_start_byte` a page can start inside a block at (block, run,
  byte): `page_doms` needs page starts of that form (the first block of a page rendered from the byte
  on, the last up to it), AzWriter's `starts_from_breaks` must keep the line start instead of skipping
  breaks whose `break_path[0]` is not past the last start.
- **OFFICE7 (AzMail)**: use `zoom` on the reading pane / paper instead of the em scaling.
