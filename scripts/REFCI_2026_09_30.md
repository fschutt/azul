## 2. How each runner works and how to run it

### 2.0 The pages in `doc/working/` (azul-doc reftest: does azul pixel-match Chrome?)

`vendor_wpt.py` writes every TEST page (never a reference) a second time as
`doc/working/wpt-<flat name>.xht` (`css/CSS2/tables/border-collapse-005.html` ->
`wpt-CSS2-tables-border-collapse-005.xht`, `html/rendering/non-replaced-elements/...` ->
`wpt-html-rendering-...`, `local/ua/...` -> `wpt-local-ua-...`), the same strict XHTML as
`tests/wpt/normalized/` with the root in the XHTML namespace (Chrome reads a `.xht` as XML and
styles the elements only in that namespace; azul ignores the attribute) and the page's
`<title>` and `assert`/`flags` metas kept for the report. `azul-doc reftest` (`doc/src/reftest/`,
the `test_heavy` job) then renders each `.xht` of `doc/working/` at 1920x1080 in Chrome (CDP,
hermetic fontconfig, aliased text on both sides) and in azul and passes it when fewer than
0.5 % of the pixels differ. `doc/reftest_baseline.txt` is that pipeline's known-pass list: a
listed test that stops passing is a regression, a new pass is reported as a gain. None of the
210 `wpt-*` pages is listed yet; add each as it starts passing. Re-generate with
`python3 scripts/refci/vendor_wpt.py --from-vendored` (no WPT checkout needed).

Two reftest mechanisms now exist on purpose and answer different questions: 2.0 asks "does
azul paint this page like Chrome" (the oracle is a browser, so it needs Chrome and the hermetic
fonts, and it is one screenshot per page), 2.1 asks "does azul paint the test like its
reference" (WPT's own pass condition, fuzzy allowances, no browser, exact). If the user wants
only one, 2.1's `reftest.rs` is self-contained and can be dropped; the editing suite does not
depend on it.

### 2.1 WPT reftests and editing: `layout/tests/wpt/` (Rust, `--test wpt`)

One test target, `harness = false`, behind the `wpt_tests` feature (so `cargo test --tests`
on the dev profile never runs it), registered in `layout/Cargo.toml` at the end:

```text
cargo test --release -p azul-layout --features wpt_tests --test wpt              # both suites
cargo test --release -p azul-layout --features wpt_tests --test wpt -- reftest    # one suite
cargo test --release -p azul-layout --features wpt_tests --test wpt -- editing insertparagraph   # + filter
AZ_WPT_BLESS=1 cargo test --release -p azul-layout --features wpt_tests --test wpt   # rewrite the lists
```

- `reftest.rs`: each page of `tests/wpt/normalized/` goes `azul_layout::xml::parse_xml` ->
  `dom_from_parsed_xml` -> `StyledDom::create_from_dom` -> a fresh 800x600 `LayoutWindow`
  (one `FcFontCache::build()` for the run) -> `cpurender::render_with_font_manager`. Test and
  reference are compared with `cpurender::pixel_diff` under WPT's rules (wptrunner
  `check_pass`): at least one `match` reference must match and every `mismatch` must differ;
  "match" = zero differing pixels, or the largest per-channel delta and the pixel count inside
  the page's `<meta name=fuzzy>` ranges. A `*-crash.html` passes when it renders. A panic in
  parse/layout/paint is caught and reported as ERROR, not a crash of the run. Every failure gets
  a `test | reference | difference` PNG under `$AZ_WPT_OUT/reftest_diffs/` (default
  `target/wpt/`).
- `editing.rs`: a case's markup goes into `<div contenteditable="true">`, the `[ ] { }` markers
  are removed and become the selection (`caret_at_node_byte` on the session a click opened, or
  `set_cross_block_selection` across blocks); then each command is what a user does:
  `insertparagraph` = Enter and `insertlinebreak` = Shift+Enter (through
  `keyboard_default_action` -> `record_structural_default_action` / a typed `"\n"`), `delete` /
  `forwarddelete` = Backspace / Delete (the default action, else `apply_selection_op` Delete),
  `inserttext` = `record_text_input` + `apply_text_changeset`. A recorded structural edit is
  applied to the case's `Dom` with `document_edit::apply_document_operation` and acknowledged;
  text edits are read back through `styled_dom_with_edits`. The host's content is serialized as
  tags and text only (void elements `<br/>`) and compared with `expected_canonical`, markers
  stripped. Attributes are not compared in v1. `bold italic underline createlink
  insertunorderedlist insertorderedlist indent outdent` have no engine operation (azul records
  no inline wrap, list or quote change for a selection; apps toggle their own model) and report
  UNSUPPORTED - the hook to wire one in is `run_command`.
- `expect.rs`: the shared gate. Expectation line format `STATUS[@os] id gap [# note]`; any
  non-PASS status matches any non-pass outcome (a FAIL that turns into an ERROR is not a
  regression); `@macos,linux` limits a line to those hosts. The summary prints counts, the
  failures per engine gap, the regressions and unexpected passes, then the first
  `AZ_WPT_SHOW` (default 20) expected failures; it writes `<suite>_results.tsv` and
  `<suite>_expectations.suggested.txt`, and prints libtest's `running N tests` / `test result:`
  lines so `scripts/zero_test_guard.sh --strict` accepts the step. Exit 1 only on a regression
  or an unexpected pass (never when blessing).

### 2.2 Mail corpus vs Chrome: `scripts/refci/mail_boxes.py` (Python, stdlib only)

```text
AZ_LINK_PATH=$PWD/target/azul-lib cargo build --release -p AzMail --bin azmail-sanitize
python3 scripts/refci/mail_boxes.py [--only cerberus] [--sanitizer normalize|azmail|none] [--out DIR]
```

Needs Chrome/Chromium (`CHROME=<binary>`), a prebuilt azul app whose dylib has the debug server
(`AZUL_APP`, default `target/release/AzPaint`; `AZUL_LIB_DIR`, default `target/azul-lib`),
and `target/release/azmail-sanitize` (else `--sanitizer normalize` runs the page through
`htmlnorm.py` instead: well-formed, nothing removed).

Per mail: sanitize -> give every element a class `azr-<n>` -> render the same document in
headless Chrome (`cdp.py`: DevTools protocol over `--remote-debugging-pipe`, so no WebSocket
client and no port; every host name maps to NOTFOUND, nothing is fetched) and in azul
(`azul_debug.py`: the `mount` op) at the same viewport with the same base font pinned ->
compare `getBoundingClientRect()` with `get_all_nodes_layout` element by element (x/y within
4 px, width/height within 4 px or 10 %; inline boxes skipped because azul reports no rect for
them). Output: `index.html` (per mail the FIRST element that diverges in document order - the
root cause more often than the biggest box -, the worst mismatches, both full-page screenshots
with those boxes outlined), `summary.tsv`, `<mail>/boxes.json`. Exit 0 unless a mail could not
be processed (`--fail-on-mismatch` makes mismatches fail too).

Memory rules baked in (2026-09-30 kernel panic): `azul_debug.py` runs ONE app, killed past
1500 MB RSS or after its time budget, restarted every 8 mails (and every 25 pages in the sweep);
`AZUL_CAPPED_RUNNER=<run_capped.sh>` delegates to the parent's wrapper instead. Chrome is one
instance, closed on exit.

## 3. CI wiring (`.github/workflows/rust.yml`)

- **`test_heavy`** (existing, unchanged): `azul-doc reftest` picks up the 210 `doc/working/wpt-*.xht`
  pages automatically; its Chrome reference-image cache is keyed on `hashFiles('doc/working/*.xht')`,
  so the first run after this lands re-renders the references (Chrome, ~1 s per page). The gate
  is `doc/reftest_baseline.txt`, untouched.
- **`wpt_reference`** (new job, fast lane, needs the preflight jobs like `test_lib`): installs
  `fonts-dejavu-core fonts-noto-core fonts-noto-mono` (test and reference share the engine and
  the fonts, so any family will do, but the pages need some), runs
  `cargo test --release -p azul-layout --features wpt_tests --test wpt 2>&1 | tee wpt.txt`
  and `scripts/zero_test_guard.sh --strict wpt.txt`, uploads `target/wpt/` (results TSVs,
  suggested expectations, diff images) as `wpt-reference-results`. Red only on a regression or
  an unexpected pass.
- **`mail_corpus_vs_chrome`** (new, on demand): `workflow_dispatch` gained a boolean input
  `mail_corpus`; the job builds the dylib with `build-dll,debug-server`, AzMail with
  `azmail-sanitize`, sets up Chrome 150 (the same action the `test_heavy` reftests use), runs
  `mail_boxes.py` and uploads the report. Not a gate (fonts differ between the engines); its
  value is the per-mail first divergence. Chrome IS on the GitHub runners
  (`browser-actions/setup-chrome`), so making it a push job is a one-line change once the boxes
  are stable enough to gate on.
- `scripts/preflight_contracts.py` passes with the new jobs; the workflow parses.
- No new workspace member, so `scripts/workspace_test_members.txt` is unchanged; the runner is
  a test target of `azul-layout`, `required-features` keeps it out of `test_lib`'s `--tests`.

### 3.3 The seeds are not blessed

The author could not compile, so:

- `tests/wpt/reftest_expectations.txt` lists the 144 reftests that did not pass in the sweep
  (section 4) with that sweep's pixel counts as notes;
- `tests/wpt/editing_expectations.txt` lists EVERY case (403 UNSUPPORTED, 300 FAIL).

The runner's fonts and renderer differ from the sweep's (a fresh `LayoutWindow` per page, the
CPU renderer's own text AA), so the first real run WILL disagree somewhere. Run once with
`AZ_WPT_BLESS=1` (both files are rewritten from the run, notes kept), commit, and CI is green
from there. Anti-aliasing-level differences (`maxdiff 23, pixels < 200`, e.g.
`vertical-align-nested-top-001`, `u-and-ins-are-underlined`) may flap between renders; if they
do, set `AZ_TEXT_AA=legacy` for the run as `doc/src/reftest/mod.rs pin_comparison_text_blend`
does, or give those tests a `fuzzy` line in `selection.txt`... (fuzzy comes from the page's
`<meta>`, so the local copies can carry one).

## 5. Mail corpus vs Chrome

Run locally (Chrome 154, AzPaint on the 2026-09-30 dylib, `--sanitizer normalize` because
`azmail-sanitize` is not built yet; 760x1100; 23 s for the corpus). 18 mails, 874 mismatched
boxes; every mail diverges from its first or second element on:

| Mail | Boxes | Mismatched | First divergence (document order) |
|---|---|---|---|
| cerberus fluid / hybrid / responsive | 77 / 170 / 153 | 77 / 169 / 152 | `<center>` +210 px tall; the 600 px `<table>` is **2886 px wide** in azul |
| exploration 01 newsletter | 31 | 30 | the 760 px outer `<table>` is **2168 px wide** |
| 02 Gmail reply | 20 | 20 | the outer `<div>` is 35 px shorter; every quoted block sits 15-30 px too far left and 69-86 px too high |
| 03 Outlook reply | 24 | 24 | the outer `<div>` is 170 px taller |
| 04 receipt | 30 | 30 | the `<table>` is 165 px wider and 98 px shorter; the price cells are 283 px too far left |
| 05 Apple Mail reply | 8 | 8 | the outer `<div>` is 18 px shorter |
| 06 Thunderbird reply | 7 | 5 | `<blockquote>` 40 px too far left, 80 px too wide (no UA margins) |
| 07 hostile | 9 | 7 | `<form>` 53 px taller |
| 08 legacy upper-case | 16 | 15 | `<TABLE WIDTH=300>` is 78 px wide (the attribute is ignored) |
| leemunroe, mailgun x3, postmark x3 | 27-77 | 27-75 | `<tbody>` has no box; tables 67-187 px shorter; in postmark/receipt a `<tr>` of the second row group sits at y=2 instead of y=1152 |

By tag: `td` 216/222 mismatched, `tr` 194/200, `table` 115/119, `tbody` 119/119 (**no box at
all in azul, every time**), `p` 86/88, `div` 54/56. By side: y 660, width 560, height 440,
x 404. The root causes this points at, in order of reach:

1. **Table auto width is not capped by the containing block**: a `width="100%"` /
   `max-width: 600px` table grows to its max-content width (2168-2886 px at a 760 px
   viewport), so everything in newsletters shifts (E-TABLE).
2. **Row groups (`tbody`/`thead`/`tfoot`) have no box**: no rect, no border (sweep), and in
   `postmark/receipt` the rows of a later row group are positioned from the table's top
   (E-TABLE, new sub-item E-TABLE-ROWGROUP).
3. **Legacy attributes** (`width`, `cellpadding`, `bgcolor`, `<center>`, `<font>`) ignored
   (E-LEGACY) - `--sanitizer azmail` rewrites some of them, so the numbers will improve with
   the real sanitizer; the engine gap stays for anything the sanitizer does not rewrite.
4. **UA margins** missing on `blockquote`, `p` inside quotes, and `<div><br></div>` having no
   height (E-UA, E-BR): the Gmail/Apple/Thunderbird replies are 18-86 px off vertically.

The report (`index.html`) shows these with both screenshots and the boxes outlined; run it
after each engine fix to watch the first-divergence column move down the document.

Two things the screenshots showed and the tool now handles: Chrome on a Mac in dark mode
applied the templates' `@media (prefers-color-scheme: dark)` rules (the postmark receipt came
out dark in Chrome, light in azul), so `cdp.py` emulates `prefers-color-scheme: light` for
every page (`44fa524fa`'s follow-up commit); and the Gmail reply confirms E-BR and the missing
blockquote/paragraph margins visually - azul's copy is the same text vertically compressed,
with the second quote level not indented.

## 7. Mail-client data worth using

- **caniemail** (`hteumeuleu/caniemail`, MIT): `https://www.caniemail.com/api/data.json`
  (api 1.0.4, updated 2026-09-16) lists ~180 HTML/CSS features with per-client support
  (`gmail`, `outlook` windows/macos/ios/android/web, `apple-mail`, `thunderbird`, `yahoo`,
  ...; values `y`/`n`/`a`/`u`). Use it to PRIORITISE the backlog: a feature Gmail and Outlook
  both support is one mail relies on (tables, `border-collapse`, `padding`, `bgcolor`,
  `background-color`, `display: inline-block`, `linear-gradient` only partially); a feature no
  client supports (grid, `position: fixed`) can stay a sanitizer drop. A small script that joins
  `data.json` with `tests/wpt/selection.txt`'s gaps would rank the table above by client reach;
  not built.
- **hteumeuleu/email-bugs** (no licence, 112 issues, labels per client): known CLIENT bugs
  (Gmail dark mode inversion, Outlook's 65x image stretch cap, Yahoo dropping `class` on
  `<img>`, Laposte/SFR commenting out `<style>`). Useful for the compose side (what to avoid in
  the HTML AzMail sends), not for the reading pane.

## 8. RTF: reference converters and whether a round-trip test is worth it

- **LibreOffice headless**: `soffice --headless --convert-to "html:HTML (StarWriter)" --outdir out
  file.rtf` and `soffice --headless --convert-to "rtf:Rich Text Format" file.html` (filter names
  from the Writer filter list; `--convert-to odt` for the model). It reads and writes RTF well
  (Word's dialect included: tables, lists, images, fonts). Not on the GitHub runner images;
  `apt-get install libreoffice-writer` is ~400 MB and 2-3 minutes, fine for an on-demand job.
- **pandoc**: reads AND writes RTF (`-f rtf`, `-t rtf`; the reader arrived in pandoc 3.0).
  pandoc is preinstalled on the ubuntu runner images. Its model is a document AST, so a
  round-trip through pandoc normalizes (it keeps headings, lists, tables, bold/italic, links;
  drops most layout).
- **Worth adding?** azul today only WRITES RTF (the clipboard copy path,
  `dll/src/desktop/shell2/common/clipboard.rs`, styled runs -> RTF) and reads none. A round-trip
  test therefore has one useful direction now: `azul RTF -> pandoc -f rtf -t html` (or
  LibreOffice -> HTML) and check that bold/italic/size/colour/family survive - cheap (pandoc is
  on the runners), deterministic, and it would catch a malformed RTF header or escape that Word
  or TextEdit would refuse. A full round trip (import -> export -> compare) only makes sense
  once an RTF reader exists (RTF import is not planned in the AzMail exploration; mail carries
  HTML, RTF only matters for the clipboard and TNEF attachments). Recommendation: add the
  one-way pandoc check as a small Python test in `scripts/refci/` when the clipboard writer is
  next touched; do not build LibreOffice into CI for it.
