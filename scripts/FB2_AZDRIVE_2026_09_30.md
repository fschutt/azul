## 1. Engine bugs found and fixed (RED `21ec8e748`, fixes `2b044c710` `5ac7bea4c` `6be87f2d6`)

Found by mounting the Explorer layout (address bar, tree, groups, tiles with capacity bars,
details pane) into the released engine with the debug server's `mount` op and reading node rects
(`get_node_layout`), then bisecting the HTML and tracing with `AZ_TAFFY_DEBUG=1` /
`AZ_PROFILE=cpu`. Test: `layout/tests/flex_items_keep_the_size_their_container_gave_them.rs`
(registered at the end of `layout/tests/all.rs`), four tests, one group per mechanism:

- **A. A measure overwrote a laid-out item** (`taffy_bridge.rs`, `compute_child_layout` +
  `compute_non_flex_layout`). Every taffy call - `RunMode::ComputeSize` measures included, cache
  hits included - wrote its result into `node.used_size`. A block parent measures its flex row a
  second time after the row's final layout (a min-content height query); the column's final layout
  then came from taffy's cache, so the bar's final layout never ran again and it kept its measured
  2 px. Symptom: a drive tile's capacity bar 2 px wide, a `flex-grow: 1` column 260 px. Fix: only a
  `PerformLayout` writes `used_size`, children's positions, scrollbar info and the overflow size;
  a measure hands the previous `used_size` back afterwards (it still resets it for its own
  `layout_bfc` run, as before).
- **B. A definite-width item was measured at min-content** (`compute_non_flex_layout`). taffy's
  own leaf algorithm resolves `width: 140px` into the known width before measuring
  (`SizingMode::InherentSize`); the bridge did not, laid the item's text out at the longest word
  and answered "140 wide, 8 lines tall"; taffy served that entry for the real 140 px query. Symptom:
  a wrapping row of 140 px items (and the block around it) four times too tall. Fix:
  `own_definite_width` (a length, or a percentage of a known parent width, clamped by min / max
  width, plus padding + border under content-box sizing) fills `known_dimensions.width` when taffy
  passes none; the cache entry keeps the original query as its key.
- **C. A second layout pass re-laid a flex item out on its own** (`cache.rs`,
  `calculate_layout_for_subtree`'s layout-cache HIT branch). It recursed into each child through
  `calculate_layout_for_subtree` - a flex item as a block with an auto height - so a `flex-grow: 1`
  pane that is itself a flex container shrank to its content on the second pass; a scroll box
  (`overflow-y: auto`) in the pane is enough to make the engine lay the page out twice. Symptom:
  AzDrive's main row (tree | content) 80 px tall instead of the window's 720. Fix: on a hit of a
  Flex / Grid container, the items' sizes and positions are taffy's (in the tree): set the relative
  position and `position_flex_child_descendants`, as the miss path's `process_inflow_child` does.

Open (not fixed, reported): a measure's `layout_bfc` run still writes the measured block's
DESCENDANTS' used sizes and IFC layouts; a final layout of the same subtree re-runs them, so
nothing was seen to break, but the memo-with-side-effect shape (ci_green_and_layout_cache_2026_09_07)
remains below the node the fix guards.

## 2. Engine API: disk space (RED `1c44ac86e`, GREEN `75135142c`)

`azul_layout::file::disk_space(path) -> Option<DiskSpace { total, free }>` and
`FilePath::disk_space(&self)`: Apple `statfs` (its `statvfs` counts blocks in 32 bits), other unix
`statvfs` (`f_frsize` units), Windows `GetDiskFreeSpaceExW` from kernel32 declared locally (no new
crate); `free` = what an unprivileged caller may still write; `None` for a missing / empty path or
an unsupported target. `libc` is now enabled by the `extra` feature (it was in the tree through
`probe`). The Db engine's private statvfs / GetDiskFreeSpaceExW twin
(`dll/src/desktop/extra/sqlite/mod.rs::free_bytes_at`) now calls it - one free-space helper.
