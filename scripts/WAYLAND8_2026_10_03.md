## 1. What KDE changed (sources read 2026-10-03)

- Phoronix, 2026-05-07, "KDE Plasma 6.7 To Provide A Much Better Experience For CPU-Based Rendering"
  -> Xaver Hugl's blog "Making wl_shm fast" (https://zamundaaa.github.io/wayland/2026/05/06/making-wl-shm-fast.html)
  -> KWin MR !9178 "opengl/egldisplay: allow importing shm buffers through udmabuf" (merged 2026-05-05,
  Plasma 6.7, KDE bugs 506240 / 513295) -> Qt change https://codereview.qt-project.org/c/qt/qtbase/+/733869
  "platforms/wayland: allocate shm buffers to be usable as udmabufs" (merged 2026-05-06, picked to 6.11;
  +18/-2 lines in `qwaylandshmbackingstore.cpp`). I read the MR diff (GitLab API), the Qt diff (Gerrit REST)
  and the kernel's `drivers/dma-buf/udmabuf.c` / `mm/gup.c`.
- THE COPY THAT WENT AWAY is compositor-side. Before: for every committed `wl_shm` buffer KWin (GL renderer)
  did a BLOCKING copy on its main thread into a GPU-accessible staging buffer, then a GPU upload into a texture
  (on an iGPU that is system RAM -> system RAM twice). With a HiDPI CPU-rendered app (KDevelop scrolling) KWin
  sat at 80-90 % of one core and the cursor stuttered. After: KWin opens `/dev/udmabuf`, wraps the client's
  memfd pages of that buffer into a dma-buf (`UDMABUF_CREATE`, no copy, the pages are pinned), imports it with
  `EGL_LINUX_DMA_BUF_EXT` as a LINEAR image with `pitch = stride`, and samples the client's memory directly.
  Import cached per `wl_buffer`. Any failure -> the old copy path. Result: ~20 % instead of 80-90 %.
- No protocol change. Whether the zero-copy path is taken depends ONLY on how the CLIENT allocated the buffer:
  - KWin: `offset % page_size == 0`; it imports `align_up(height * stride, page_size)` bytes from there.
  - kernel `udmabuf`: the fd is a memfd (shmem / hugetlbfs) that carries `F_SEAL_SHRINK` and carries neither
    `F_SEAL_WRITE` nor `F_SEAL_FUTURE_WRITE` (`check_memfd_seals`); offset and size `PAGE_ALIGNED`;
    `memfd_pin_folios` refuses a range whose last byte is at or past the file size.
  - the GPU driver: the EGL import of a LINEAR dma-buf must accept the pitch. 256 bytes is what Qt picked as
    "what all common GPUs can read from" (there is no feedback channel for the real requirement).
- Qt's whole client change: `stride = align_up(width * 4, 256)`, `alloc = align_up(stride * height,
  getpagesize())` (Qt already used one memfd per buffer, and already created it with sealing allowed and
  `F_SEAL_SHRINK` set). Cost: under one page per buffer plus the row padding (Xaver: about 1.6 % at 3840 px).
- Side effect for clients: with udmabuf the compositor keeps the CURRENT buffer referenced until the next
  buffer replaces it AND the GPU work that sampled it has finished (`UDmabufReleasePoint`). The old copy path
  released a shm buffer right after its upload. So a client now alternates buffers every frame; a client
  that renders only into a released buffer (we do) stays correct, it just sees `wl_buffer.release` later.

## 2. What we did before (Wayland CPU present)
- Pool: ONE memfd with two tightly packed slots. The file could never carry the F_SEAL_SHRINK seal the kernel's
  udmabuf requires. Rows were width*4 bytes; slot 1 started on a page boundary only when w*h % 1024 == 0; the pool was
  rebuilt on every configure.
- Per frame: the renderer already draws straight into the free slot (0 client copies); when the frame switches slots
  it copies the previous frame's changed areas over from the other slot. On compositors advertising only ARGB8888
  (KWin at 8-bit) an extra in-place R/B swap over the damage (still there). Protocol: one sendmsg per frame (attach,
  per-rect damage_buffer, frame, commit).
- Compositor side: KWin always took its old path - a 1080p full frame cost ~8.3 MB copied twice.
- Memory: two slots for the window's whole life (2 x 8.3 MB at 1080p).
- Duplication: the window pool, the tooltip and screen capture each had their own memfd-then-shm_open code.

## 3. Does it apply to a client like us?
Yes. Our side of KDE's speed-up is exactly Qt's allocation change (Gerrit 733869, 18 lines):

| Rule (who checks) | Before | Now |
|---|---|---|
| memfd sealed F_SEAL_SHRINK, no write seals (kernel) | never | always |
| slot offset page-aligned (KWin + kernel) | slot 1 rarely | every slot |
| page-rounded range inside the file (kernel) | slot 1 often not | every slot |
| row pitch a multiple of 256 bytes (GPU driver) | only widths divisible by 64 | always |

## 4. What this branch changes - Wayland
- New wayland/shm.rs: the ONE allocator (window / popup pool, tooltip, screen capture). The memfd is created sealable,
  then sealed SHRINK|SEAL after sizing; rows padded to 256 bytes; every slot page-aligned. `udmabuf_importable`
  encodes the kernel + KWin rule; with AZ_WL_TRACE=1 the pool trace prints `udmabuf=yes|no pitch256=yes|no`.
- Padded rows everywhere rows are indexed: the renderer gets a slot as a pitch-wide pixmap
  (`CpuBackend::native_target_row_padding_px` tells render_frame how much is padding - before, it refused any target
  wider than the frame). New `headless::copy_rgba_rects_into` is the one pitch-aware damage copy (legacy present, the
  popup copy - a single linear copy before, which would have sheared -, the tooltip, X11).
- An idle window holds ONE buffer: after 1 s without a frame, wait_for_events releases the spare slot
  (wl_buffer.destroy + fallocate(PUNCH_HOLE|KEEP_SIZE), freeing the pages for us and the compositor); the poll
  timeout is capped at that deadline; re-created only when a frame finds the kept slot still held. 1080p idle:
  16.6 MB -> 8.3 MB.
- Per frame after, on KWin 6.7: the compositor copies 0 bytes; we copy the previous frame's damage once (catch-up),
  because with udmabuf KWin holds the current buffer until it is replaced, so slots alternate every frame.

## 5. X11: before and after MIT-SHM
- Before: each damaged rect packed + swizzled into a heap buffer, XPutImage'd through the socket, copied by the
  server - a full 1080p frame ~8.3 MB swizzled + 8.3 MB through the socket + the server's read and copy.
- After (x11/shm.rs + pure decisions in common/x11_host.rs): probe once per window (AZ_X11_SHM=0 switch; DISPLAY must
  be a local socket - any host name incl. localhost:10 from ssh -X counts as remote; libXext loaded like XShape;
  XShmQueryExtension). Damage is swizzled straight into a SysV segment, one XShmPutImage per rect (~40 bytes each on
  the socket). Attach under an error trap + XSync; the segment id is removed at once (cannot leak). The segment is
  written only when no earlier put still reads it (else XSync first); ShmCompletion events counted in handle_event.
  On resize the segment is kept while it holds the frame and is at most 2x too big. Any failure drops MIT-SHM for
  that window for good, and the same frame goes out through the unchanged XPutImage loop. Drop detaches the segment
  while the display is still open.
