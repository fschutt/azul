## 1. Bitrate adaptation

**Engine: `VideoEncoder::set_bitrate(kbps) -> bool`** (`video_codec/mod.rs`). The rate sits in an
atomic the encoder's codec thread reads before each frame (a change never waits for room in the
three-frame queue and is never lost when it is full); a changed rate goes to the engine:
`VtEncoder::set_bitrate` sets the live session's `AverageBitRate` (VideoToolbox takes it
mid-stream - same session, same reference frames, no keyframe; what WebRTC's VideoToolbox
encoder does) and keeps it for a session re-made for frames in another format; one helper
`average_bitrate_bps` turns kbit/s into the SInt32 property for the open and the change. Vulkan
Video re-makes its session (see 3). wasm stub returns false.

**AzMeet: `rate.rs` `RateControl`** (pure, unit-tested). The signal is each receiver's queue: the
H.264 packets sent and not acknowledged (`SendWindow::in_flight`; receivers acknowledge every
five). One encoder serves every receiver of a rendition, so the worst receiver decides, and the
most it had in flight since the last decision counts (acknowledgements come in batches). Every
500 ms: at half the send window (12) the rate drops to 70 % (floor a quarter of the ladder rate,
at least 64 kbit/s) and holds 2 s; at a third of it (8) or less it rises 5 % a decision (about
10 % a second, at least 10 kbit/s) up to the rendition's ladder rate; in between it stays. The
encoder hears only changes. The uplink estimate is deliberately NOT a ceiling: it is the larger of
what was sent and cwnd / RTT, so a rate lowered for one slow link would lower what is sent, then
the estimate, then every stream - a spiral down (written in `rate.rs`'s docs).

Wiring (`lib.rs`): `VideoOut.rate` (per rendition, at its ladder rate); `adapt_rates` runs every
pump after the encoders' packets went out, feeds it the in-flight count of every peer that gets
the stream as H.264 now (`stream_targets`) and calls `set_bitrate`; a re-opened encoder (resize,
reopen) opens at the adapted rate; stdout `AZMEET_RATE <rendition> <kbps>`; the statistics'
sending line ends ", H.264 at 600 of 1000 kbps".

## 2. Opus voice

**Engine: `AudioEncoder` / `AudioDecoder`** (`audio/codec.rs`, `audio/opus_apple.rs`). Native per
platform like `VideoEncoder`: Apple's AudioToolbox `AudioConverter` (dlopen'd: `AudioConverterNew`
/ `Dispose` / `FillComplexBuffer` / `Get/SetProperty`; no build-time link, a missing symbol
leaves the handles closed). An encoder is one converter from interleaved f32 PCM at the app's
rate (1-2 channels; the converter resamples) to Opus 48 kHz, 960 frames a packet, at the asked
bit rate; its input callback hands out everything queued in one buffer kept alive until the next
callback and answers `'nodt'` when dry (ends the call, not the stream). A decoder is the converter
back, one packet per `decode`. Honest handles: closed off Apple with the reason said once; frames
in another rate or channel count are refused. wasm stubs.

Checked on this Mac (macOS 15.5) by replaying opus_apple.rs's exact calls from Python ctypes
(same ASBDs, same streaming callback, same fill loops): 50 x 20 ms of a 440 Hz tone -> 50
packets, 3913 bytes (31 kbit/s), largest 117 bytes; decoded 47 880 samples (840 for the first
packet, then 960), 440 Hz share 1.000, rms 0.213 for 0.212 sent; 44.1 kHz in and out works too;
the decoder needs no magic cookie (so it opens no encoder for one - ded162435).

**AzMeet** (`audio.rs` pure rules, `lib.rs` wiring): codec byte 2 = Opus in the same frame layout
(one shared header writer / reader `frame_header` / `read_header`; rate 48000; lengths in bytes;
`frame_codec` tells the codecs apart); `OpusFramer` (sequence numbers, the newest three packets a
frame, as the PCM packetizer); caps bit 2 "decodes Opus" (an older AzMeet never sets it);
`send_opus`: Opus only when this side's encoder opened and EVERY peer said yes (forwarders pass
one stream on), else PCM; `OpusOrder`: a receiver decodes each Opus packet the first time a frame
brings it, in order, never one older than the newest decoded (an Opus decoder carries state),
whether or not it is deafened (the active speaker is still measured), then pushes the decoded PCM
into the same jitter buffer; a codec switch starts that origin's jitter buffer over (the codecs
number apart); a peer that leaves drops its decoder. `mix_to_mono` is now the one mixdown (the
packetizer uses it). stdout `AZMEET_AUDIO opus|pcm`. Voice: 768 kbit/s -> 32 kbit/s (x3
redundancy: 2.3 Mbit/s -> 96 kbit/s).

## 3. H.264 encode off Apple (no more JPEG where the GPU encodes)

**`core::resources::rgba_to_nv12`** - the encode direction of the one YCbCr table:
`RgbToYuv` holds the 16.16 RGB -> YCbCr weights of the four NV12 formats (each chroma row closed to
zero, so grey stays 128); luma per pixel, each Cb,Cr pair from its 2x2 block (1, 2 or 4 pixels at
an odd edge). Studio values exact (601 red 81/90/240, 709 red 63/102/240, ...). Twin found:
AzVideoCut's app-local `export::rgba_to_i420` (BT.601 video, I420) - it can become
`rgba_to_nv12` + a de-interleave; not touched here.

**`video_codec/encode_vulkan.rs`** (`az_gpu_video`: x86_64 Linux glibc / Windows with
`video-native`, the decoder's gate): gpu-video's `BytesEncoderH264` on a device opened for
encoding; low-latency preset, VBR at the rate (peaks at twice, 1 s buffer), an IDR every 60
frames, SPS / PPS inline; NV12 frames as they are, RGBA8 / BGRA8 converted once; colour tags follow
the frames (a session per NV12 format, as VideoToolbox); `set_bitrate` re-makes the session (no
live rate change in gpu-video; the next frame is a keyframe). `EncodeEngine` (Vt | Vulkan) is the
one per-backend dispatch (like `DecodeEngine`); `encode_engine` asks the driver for
`VK_KHR_video_encode_h264` once per process (`provision::vulkan_encode_h264`, the probe the
hardware check already used), so a handle opens only where the GPU encodes. AzMeet needs no
change: it already opens `VideoEncoder` and falls back to JPEG only where none opens.

## 4. Echo cancellation

**Engine: `EchoCanceller`** (`audio/echo.rs`, pure Rust, every target; wasm stub passes through).
A partitioned-block frequency-domain adaptive filter (overlap-save MDF): blocks of 256 samples
(128 at 24 kHz and below), FFT 512, as many partitions as the tail needs; per-bin NLMS normalized
by the far end's power over all partitions (step 0.8); the gradient constraint on one partition
per block, round robin. Double talk: two filters as in Speex - the background adapts every block,
the foreground makes the output and takes the background's coefficients only when Speex's
significance test says it cancels better (the improvement must stand out against how far the two
outputs differ; a near-end voice raises both errors alike); a background that got significantly
worse is reset. The microphone passes when the output would be louder. `EchoStream` cuts blocks
from the far-end FIFO (capped at tail + two blocks) and the microphone, returns as many samples
as came in, one block later (5.3 ms at 48 kHz). The state is behind a Mutex (far end from the
playout thread, microphone from the UI thread). `erle_db` reports the last half second.

Tuned in a Python model of the same structure on the tests' synthetic rooms (white-noise far end;
20 ms delay + 80 ms reverberation, 6 dB down) at 48 kHz: echo 21.9 / 35.7 / 44.9 dB down in
seconds 1 / 2 / 3; during speech-like double talk 44.9 dB with the voice within 0.1 dB; a changed
path (35 ms, 60 ms, -3 dB) relearned to 31.6 dB two seconds after (16 kHz model). The FFT and the
overlap-save code were replayed in Python against a direct DFT. Known limit: a steady near-end
TONE while the far end plays is partly learned (an adaptive filter notches a sinusoid; the model
showed it) - speech is not a steady tone; Speex's adaptive step (leak estimate) is the next step.
No residual-echo suppressor or comfort noise yet; one rate for both ends.

**AzMeet:** the playout owns an `EchoCanceller` (48 kHz, 300 ms tail) whenever it plays on a
device (never headless; `AZMEET_ECHO_CANCEL=0` for headphones); every turn it plays, the peers'
samples at the microphone's rate are mixed and fed as the far end; `send_audio` passes the
microphone (mixed to mono) through `process` before the codec. Peers at another rate play
uncancelled (no resampler).

## 5. Zero copy (steps 2-3): designed, not built - why

VIDEO_PATH made VideoToolbox decode NV12 at the TILE's size; what is left per decoded frame is
one copy of the tile's NV12 (568x320: 272 KB, ~0.1 ms) plus its texture upload. Steps 2-3 touch the
image model (core), the renderer (`wr_translate2`, the external image handler), the CPU
rasterizer and the capture workers - every app's display path - and can only be verified on a
GPU window with a real camera, which this run cannot do. Decision: design precisely, build next
wave with a GPU check. Integration points:

1. core: `DecodedImage::Native(NativeSurface)` - a retained `CVPixelBufferRef` / `IOSurfaceRef`
   with width, height, format (BGRA8 or an NV12 variant) and a release fn; `ImageRef::new_native`.
2. `wr_translate2::register_frame_resources`: a native image becomes external image(s) -
   BGRA: one `ExternalImageType::TextureHandle(ImageBufferKind::TextureRect)`; NV12: two (plane 0
   R8, plane 1 RG8) for the `YuvImage` compositor2 already pushes for raw NV12.
3. `Compositor::lock` (the `ExternalImageHandler`): on the first lock in a frame, bind a
   `GL_TEXTURE_RECTANGLE` texture to the IOSurface with `CGLTexImageIOSurface2D(ctx, target,
   internal, w, h, format, type, surface, plane)` (BGRA: `GL_RGBA8` / `GL_BGRA` /
   `GL_UNSIGNED_INT_8_8_8_8_REV`; NV12 planes `GL_R8`/`GL_RED` and `GL_RG8`/`GL_RG`), return
   `NativeTexture` with texel uvs; textures cached per surface, deleted with the image's stale key
   two epochs later. Check that the vendored WebRender compiled `brush_image` / `brush_yuv_image`
   with `TEXTURE_RECT`.
4. cpurender / headless: lock the buffer read-only and run the existing BGRA / NV12 row paths.
5. API: `VideoDecoder::recv_image() -> OptionImageRef` (native on Apple GPU windows, raw
   elsewhere), so AzMeet calls `change_node_image` without touching bytes.
6. Step 3 (encode): a `FrameConsumer` kind "H.264 at kbps" in capture_common; the macOS capture
   delegates hand the retained `CVPixelBuffer` to a `VtEncoder` owned by the capture worker
   (`VTCompressionSessionEncodeFrame(pixelBuffer)`; renditions through `VTPixelTransferSession`
   into each session's pool); packets out through the consumer's writeback. Saves the capture copy
   (1.4 MB per 720p frame) and the pool copy.
Worth it for galleries: nine tiles at 30 fps are ~73 MB/s of copies and uploads today.
