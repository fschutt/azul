# A11YPATCH8 - the accessibility tree sends patches, and nothing when nothing changed (wave 8, 2026-10-03)

Branch `wt/a11ypatch8` (base 5745afee6). Nothing compiled (house rule); the "after" numbers are expectations.

## Measured (prebuilt AzWidgets of 0de2a2529, headless 900x1300, `/Users/fschutt/Development/azul-work/a11yp8/`)

- `a11y_update_tree`: 2880 - 3194 us per call (`AZ_PROFILE=cpu`, 3472-node page, 4 DOMs; six samples).
- Unprofiled: a knob tick (`incremental_relayout`) 19.9 - 21.7 ms, a no-op relayout 11.1 - 11.6 ms. The a11y
  rebuild is ~3 ms of each: ~15% of a tick, ~27% of a no-op relayout - and every pass published the WHOLE tree
  (~3500 nodes), which every platform adapter re-diffed, with no screen reader running too.
- It ran after EVERY layout pass (`layout_and_generate_display_list_impl` tail) and once more after every
  `regenerate_layout` (the dll's `refill_a11y_tree_after_regeneration`): ~6 ms per DOM rebuild.
- Why the tick profiles never showed it (LAYOUTPERF8B saw it only "in the no-op relayout"): the telemetry
  `FramePump` around every present and every `regenerate_layout` DRAINED AND DISCARDED the probe buffer (telemetry
  off), so every span after a relayout's last per-DOM flush vanished - `a11y_update_tree`,
  `shell_incremental_relayout`, `register_scroll_nodes`, `cpu_hit_tester_rebuild`. The visible a11y spans were the
  refill's. Fixed here (below); from the next build those spans show in the next pass's `[CPU]` table.

## What was built

### layout/src/managers/a11y.rs - a retained tree, diffed per frame
- `A11yRetainedTree` (in `A11yManager::retained`): every published node with the SIGNATURE of the inputs it was
  built from (`RetainedA11yNode { inputs, seen, content, children }`), the document order and the focus.
- `A11yManager::refresh(&A11yTreeInputs)` - THE pass every layout runs (`LayoutWindow::update_a11y_tree` calls it):
  per exposed node it hashes the inputs (`node_signature`: node type + text, attributes, flags, AccessibilityInfo,
  focusable / activation, the direct children's text or the text override, the caret on it, whether it has a box,
  its screen bounds, its scroll state). Equal signature: the node is reused, NOT built. Changed: it is built
  (`build_content`, the old per-node code verbatim) and compared with what was published. The child lists are
  linked as before (nearest exposed ancestor, `enforce_child_invariants`) and compared too. Then:
  - first pass / after a resync: the whole tree (`tree: Some`);
  - otherwise a PATCH (`tree: None`) of the new and changed nodes in document order (a removed node leaves with its
    parent's new child list; a moved node with both parents), or a focus-only patch;
  - NOTHING when nothing a screen reader can see changed.
  `A11yManager::last_pass: A11yPassStats { nodes, built, sent, removed, published, full }` counts each pass.
- `update_tree` (the static full build, tests and reference) is now a from-scratch `rebuild_retained` + `full_update`:
  the same tree, the same node order, the same property order as before.
- `publish`: a patch is validated IN PLACE against the mirror (`A11yTreeMirror::apply_patch_in_place`: O(patch + what
  it removes); the old `apply` cloned the whole children map per update) and the mirror (`delivered`) now advances at
  publish (`pending_post` is gone); a full tree must be complete on its own. It also deep-cloned the parked update
  on every publish (`prev.clone()`) - gone. `fold` merges into a parked update and drops the nodes the new patch cut
  loose (a removed node in an update is an orphan for the consumer).
- `resend_full_tree()` (next pass publishes the whole tree), `full_tree()`, `published_node(id)` (the tree as the
  adapter holds it), `note_published_node(..)` (the text-edit increment keeps the retained tree in step).
- `A11yIdHasher` / `A11yIdMap`: the id-keyed per-frame maps hash with one multiply instead of SipHash.

### layout/src/window.rs - the a11y call site only (ANIMFRAME8 owns the rest)
- `update_a11y_tree` builds `A11yTreeInputs` and calls `refresh`; a panic mid-pass resyncs.
- `update_a11y_tree_incremental`: on success `note_published_node`; on a refusal `resend_full_tree` + a full pass
  (the contract test still sees a FULL fallback).

### dll - the platform side (macOS, Windows UIA, AT-SPI)
- `common/accessibility.rs` `A11yTreeFeed`: the complete tree an adapter may need on activation is kept as a node map
  (`CompleteTree`), not one `TreeUpdate`: a patch merges at its own cost (it scanned the whole node list per node and
  rebuilt a children map of the whole tree per update before); the whole tree is assembled only for an activation.
- `A11yTreeFeed::missed()`: with patches, an update an adapter did not take (busy `try_lock` on Windows / AT-SPI, a
  caught panic on all three) is no longer healed by the next full tree - the next update it gets is the complete
  tree. Called in `windows/accessibility.rs`, `linux/x11/accessibility.rs` (X11 + Wayland), `macos/accessibility.rs`.
- `macos/mod.rs` `init_accessibility`: the macOS adapter is created lazily after the first layout with an empty feed;
  it now asks for the whole tree (`resend_full_tree`) before its first push. Windows / Linux create theirs with the
  window and see the first full tree.
- Nothing re-sends the full tree otherwise: an ACTIVE adapter gets the patch as published.

### layout/src/telemetry/mod.rs - the profiler fix
- `drain_probe_events` -> `drain_probe_events_for(cpu_report)`: with telemetry not collecting, a frame pump leaves the
  spans to the `AZ_PROFILE=cpu` report (which drains them per layout pass) and still drops them when there is no
  report; a report with no layout pass for long is capped at 2^20 buffered events.

## Decision: bounds of a moving node

Sent every frame they change, as a one-node patch, no throttle. accesskit 0.24 has no lazy / on-demand bounds; a
screen reader draws its cursor from the tree it holds. What cost 3 ms was rebuilding and re-sending ~3500 nodes,
not one node's rect; throttling would need a timer to land the final position (as the scroll rebuild does) for no
measurable gain. A `transform` animation (ANIMFRAME8's knob) does not relayout, so it does not run the pass at all
(a11y bounds are layout boxes, as before).

## Left / follow-ups

1. The dll's `refill_a11y_tree_after_regeneration` (event.rs, ANIMFRAME8's file) is now a redundant second pass per
   `regenerate_layout` (the layout tail already ran one): it finds nothing and costs ~1 ms of hashing. Drop it, or
   keep it only for a regenerate that skipped the layout pass.
2. The remaining per-frame cost is the signatures (SipHash over ~3500 nodes) + linking. A per-node content epoch
   bumped by every `NodeData` mutation (window.rs, event.rs, widgets, e2e runner write node data in place today)
   would let a pass hash only the geometry; I did not add it (many owners, a missed site = a stale screen reader).
3. iOS / Android rebuild their whole `A11ySnapshot` after every regenerate; they could skip it when
   `a11y_manager.last_pass.published` is false.
4. With `AZ_PROFILE=cpu` AND telemetry collecting, telemetry still drains the buffer first (it wins); documented.
