## What was built

### `layout/src/widgets/code_view.rs` (NEW, ~3,300 lines) + `code_view_tests.rs` (NEW, 31 tests)

`CodeView`: the editing surface of a code editor over as many lines as the app has.

- **Generic over its data** (DataTable / CellGrid pattern): `with_data_source(data, cb)`, `cb(data, line: u32) ->
  CodeViewLine { text, spans: CodeViewSpanVec }` - a span is `{ start, end, kind: CodeTokenKind }` (byte range +
  one of 17 kinds: Keyword, Type, Function, StringLiteral, Number, Comment, Constant, Macro, Attribute, Operator,
  Punctuation, Variable, Tag, Heading, Link, Invalid, Plain). Only the lines in view are asked for (the test: lines
  500,000..500,022 of a million, each once).
- **Virtualised in whole lines**: `view.top_line: u32` / `left_column` (the scroll window of CellGrid / DataTable),
  the view's own scroll bar (thumb drag through every line, track pages), the wheel scrolls whole lines (Shift:
  columns). **The f64 question** (PLAN): still true for pixel space - scroll offsets are f32 (`LogicalPosition`),
  exact only to 2^24 px = 16.7 M px (~880k lines at 19 px; the infinity example's 1M x 22 px = 22 M px already
  steps in 2 px at its end). CodeView never makes a pixel extent, so it needs no f64 and is exact for any length.
- **The app owns the text and the state**: `CodeViewView { cursors, top_line, left_column, visible_lines,
  visible_columns, char_width, drag... }`; every action reports `CodeViewEvent { view (store it), edits, text,
  kind: Edit | Move | Scroll | Undo | Redo | Copy }`. Edits are `CodeViewEdit { start, end, text }` in the text
  BEFORE the event, last in the text first, so the app applies them in order.
- **Keys** (one Tab stop): typing replaces every selection; arrows / Shift / word jumps (Option on macOS, Ctrl
  elsewhere; Cmd+arrows = line / text ends on macOS); Up / Down keep the visual column through short lines;
  smart Home; Mod+Home / End; Page Up / Down move caret and view; Enter keeps the indentation (+1 level after
  `{ ( [`); Backspace / Delete (word, macOS Cmd: to line start) join lines; Tab: spaces to the next tab stop or
  indent the selected lines (Shift+Tab outdents, the selection carried); Mod+A / C / X (a whole line without a
  selection) / V (one line per cursor when the counts match) / Z / Shift+Z / Y (the app's history) / D (select the
  word, then add its next occurrence, whole-word when the needle is a word, wrapping); Escape drops extra cursors.
  Keys the view does not take (Mod+F, S, G, W, F3) bubble to the app. Read-only: moves and copies only.
- **Pointer**: press (Shift extends, Alt adds a cursor), drag-select with edge auto-scroll, double-click word,
  line-number click selects the line, the scroll bar. The column width is measured once per view
  (`measure_dom_shrink_to_fit` of 64 zeros in the view's face, kept in `view.char_width`) and the view's box at
  every action (`get_node_size`), so paging / caret reveal use the real size even when the app's viewport hint is
  larger.
- **Drawing**: per line a gutter number + the runs (tabs expanded, clipped to the horizontal window), the caret as
  a zero-width slot with a 2 px bar (so it sits exactly between glyphs without moving them), selections as run
  backgrounds and a selected-break marker, the current line tinted. OS monospace face
  (`SystemFontType::Monospace`).
- **Looks** APPENDED under `// ==== code_view ====`: `themes/flat.rs` (page white / flat night page, VS Code
  Light+ / Dark+ token inks) and `themes/flora.rs` (the `--fl-code-bg/-fg/-bd` ink panel in both modes, as the
  planning doc names it the default editor theme; warm token inks). Follows the app theme when not pinned.
- **a11y**: `Text` role, named, value "Line 12 of 400, byte 5"; the scroll bar a `ScrollBar`.
- Manifest (`widgets/mod.rs`): `pub mod code_view;` (appended after `chart`), `every_widget_dom` + `("code_view",
  fixtures::sample().dom())`, the CHROME contrast group, the wheel takers list.

### `examples/azul-code` (NEW crate `AzCode`, lib `azcode`)

- `buffer.rs` - **the piece table** (decision D3): the read file kept once, an add buffer, pieces with their break
  counts, prefix sums; line N found by two binary searches; `apply(&[Edit])` = ONE undo step (consecutive typing
  merged), undo / redo return the caret and the changed lines, dirty tracking survives undo to the saved state,
  CRLF and BOM read and written back. Tests: 500 random edits against a String, a million lines after 200 edits.
- `highlight.rs` - **syntect, incremental by line** (decision D4): checkpoints every 64 lines, a cache of coloured
  lines with their end state, an edit keeps everything above its line and turns the checkpoints below it STALE
  (shifted), taken back the moment a walk reaches one with an EQUAL parse state (an edit that does not open a
  comment re-parses a few dozen lines, not the file - tested: < 128 lines for line 300 after an edit at line 10);
  a line > 1,500 lines below anything known returns `None` and is walked on an azul Thread (`HighlightJob`,
  `adopt`, a generation guard drops walks overtaken by edits). Scopes map to `CodeTokenKind`s (azul's themes
  colour them).
- `search.rs` - find / replace with azul-appkit's one matcher (line by line, case / whole word), next / previous
  with wrap, replace all as one undo step, go to line (`120` / `120:5`).
- `workspace.rs` - the explorer model (folders first, listed lazily, depth-first rows = TreeView's click index - 1)
  and the tabs.
- `storage.rs` - the workspace through azul-storage's `Drive` on azul Threads: list one folder level, read, write
  (`LocalDrive::without_manifest` for a folder of the user's, the data tree's drive for the sample); the

- `sample.rs` - the `--sample` workspace written once into the data tree `code/sample/` (a small crate, README,

- `app.rs` / `commands.rs` / `ui.rs` / `lib.rs` / `ids.rs` - the window: S8 `DeveloperShell` (activity bar Files /
  Find, the explorer `TreeView`, the search panel listing the matches of the file in front, `TabHeader` tabs with

## Decisions (details in the progress file)

D1 CodeView generic over its data (FFI: no handle type, a 40 MB buffer cannot be a value cloned per event). D2 whole-
line windowing, not a VirtualView (exact for any length, no nested DOM - DATATABLE7 D1). D3 piece table in the app
crate (plain Rust; a second user moves it to azul-appkit). D4 syntect over tree-sitter: pure Rust via fancy-regex
(already in Cargo.lock), 50+ grammars in one crate, a line-oriented `Clone + Eq` parse state that IS line
virtualisation's incremental model, Send for the Thread; tree-sitter needs a C toolchain per grammar (mobile / wasm),
a whole-document tree and churns its API - it is the later upgrade for folding / outline. D5 caret in the flow, char
width only for pointer -> column. D6 copy / cut in the key handler (DataTable's rule), paste through the Paste
event (CellGrid's), undo / redo reported to the app.
