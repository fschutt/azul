## What was built

### 1. Storage manifest - `<data root>/.azlin/cache` (examples/azul-storage)
- New module `azul_storage::manifest`. The `LocalDrive` of the data tree keeps the manifest ITSELF on
  every `put` / `delete` / `rename` (file or folder) / `copy` / `delete_folder` (apps call nothing new):
  key -> size, mtime (seconds), content hash (lowercase hex SHA-256 = the hash SigV4 already sends as
  `x-amz-content-sha256` for an upload).
- File format (documented in the module doc): UTF-8 text, one record per line, applied in order:
  header `azlin-cache 1 <last snapshot size, 16 digits>`, `+ <size> <mtime|-> <sha256> <key>`,
  `- <key>` (a key ending in `/` = the folder with everything under it), `> <from> <to>` (rename; keys
  or folders). Keys are percent-encoded exactly as SigV4 encodes a path (`sigv4::uri_encode`, `/` kept;
  new `sigv4::uri_decode` is its inverse), so no key holds a space or line break. APPEND = one line in
  one `write` (O_APPEND: safe across threads and processes); REWRITE = a snapshot (one `+` line per
  object) written next to the file and renamed over it (`write_atomically`), done when the file grew past
  twice its last snapshot and 256 KiB; records another writer appended meanwhile are re-applied before
  the rename. A torn last line (crash mid-append) and unknown records are skipped.
- The manifest is a CACHE: a manifest write that fails never fails the data write (a FILE named
  `.azlin` in the way is tested); a lost record costs the sync work, never a missed change, because:
- `manifest::diff(&Manifest, &D) where D: Drive + ?Sized` (so `&dyn Drive` works): `Changes { added,
  modified, deleted }` (each in key order) of a drive against a manifest. Size differs -> modified;
  same size and same mtime -> unchanged without reading; same size, other mtime -> the bytes are hashed
  (streamed from the file on a local drive, `sigv4::sha256_hex_of`) - a rewrite with the same bytes is
  no change. Folder markers and `.azlin/` are not content.
- `manifest::changes(base, now)`: manifest vs manifest by size + hash, no I/O.
- `LocalDrive::manifest()`, `manifest_path()`, `refresh_manifest()` (records what changed outside the
  drive's own calls, returns it), `keeps_manifest()`.
- `.azlin/` at a drive's root is the drive's bookkeeping: never listed (`read_level` / `walk` skip it,
  listing `.azlin/` is empty) and no key may name it (`InvalidKey` "it is the drive's own bookkeeping").
- `LocalDrive::without_manifest(root)`: a folder that is NOT the data tree (Downloads, the user's home,
  a folder the user added as a drive) - writing there leaves no `.azlin/`. `config::DriveEntry::open`
  (the drives in `drives.json`, AzDrive's Home) uses it.
- How the later S3 / database sync uses it: (1) `refresh_manifest()` on the local tree (a listing plus
  stats; only files the app did not write through the drive and whose size/time moved are hashed) ->
  the local manifest L is exact. (2) The sync keeps its own manifest S of the last successful sync (same
  format, e.g. `.azlin/synced`, written by the sync with each object's remote ETag/time beside it).
  `changes(S, L)` = what to upload / delete remotely, with no I/O. (3) `diff(&S, &s3_drive)` (or a
  listing compared by ETag) = what changed in the bucket since -> download. A key in both = conflict.
  (4) The upload's SigV4 payload hash IS L's hash, so nothing is read twice. The `S3Drive` needs nothing
  (it is the sync target).

### 2. One data root + legacy migration (examples/azul-appkit)
- New module `azul_appkit::migrate`: `migrate_app_data(os_data_dir, root, app_folder) -> Migration
  { moved, kept, failed }`. Hooked into `ui::create_kit` (signature unchanged) right after the data root
  is resolved; a line on stderr says what moved (`Migration::summary`).
- Rules: only for the DEFAULT root (`<OS data dir>/Azlin`; a `--data-dir` / `$AZLIN_DATA` root is never
  migrated into); only the STARTING app's own folder `<legacy>/<app_folder>/` with legacy in
  `LEGACY_DIRS = ["azul", "Azul", "AzNotes"]` (AzShow/AzVideoCut `azul/show|videocut`, AzPhoto
  `Azul/photo`, AzNotes `AzNotes/notes` - the same keys the data root uses); `fs::rename` per file
  (copy-then-remove across file systems), NEVER over an existing file (kept + named in the note), emptied
  folders removed, a `MOVED-TO-AZLIN.txt` note APPENDED in the legacy folder when something moved;
  idempotent (a second run moves nothing, writes no note); `azul/`'s own files (azul's `styles/`,
  telemetry config) and other apps' folders stay. Per-app on purpose: an app that still reads its legacy
  folder (not yet on appkit) keeps its data until it moves to the kit itself.
- Decision: files moved by the migration are not hashed at startup (a video folder can be GBs); they
  show up as `added` in the first `diff` / `refresh_manifest`, which is what a first sync wants.

### 4. CLOSE
- `FullWindowState::close_callback` removed (struct, Default, the two tests' asserts, the five backend
  initialisers, the event-diff destructuring in common/event.rs, core's `WindowFlags::close_requested`
  doc, the windowing guide - now describes CloseRequested + `prevent_window_close` + CloseGuard).
- Findings (all fixed at the shared root, common/event.rs):
  - App-raised closes (`CallbackInfo::close_window` -> `CallbackChange::CloseWindow`; the CSD titlebar's
    close button -> a `ModifyWindowState` raising `flags.close_requested`) never reached CloseRequested
    on ANY backend: headless closed in `pump_once` phase 2b, X11/Wayland in the run.rs loop, macOS in
    `sync_window_state` straight from the state diff, and Windows did NOTHING at all (no code on the run
    loop's path read the raised flag).
  - `request_window_close` with the flag already up snapshotted it as up -> no false->true transition ->
    `WindowClose` never fired (macOS' drain_loop_work "run it so the app's close callback still gets its
    veto" never vetoed anything).
  - The headless window manager close (`HeadlessEvent::Close`) closed outright.
- Fix: `CommonWindowState::close_unconfirmed` marks an app-raised close (set only on a false->true
  raise); `request_window_close` lowers an already-raised flag and takes that as the baseline;
  `PlatformWindow::run_close_protocol(site)` builds a DOM rebuild the app's last callback asked for
  FIRST (so a thread's writeback "saved + RefreshDom + close_window" is not held by the stale DOM's
  CloseGuard), then runs the protocol; `PlatformWindow::confirm_app_close(site)` = the backend-loop
  half (runs it once for an owed app close, raises a regeneration when a veto asked for a new DOM).
  Backends: headless (`HeadlessEvent::Close` -> run_close_protocol; phase 2b -> confirm_app_close first);
  Linux run loop (`LinuxWindow::confirm_app_close()` before the `close_requested()` check); X11
  WM_DELETE_WINDOW -> run_close_protocol; macOS (`sync_window_state` acts only on a confirmed close,
  `process_close_event` -> run_close_protocol); Windows (`post_app_close`: the end of every input pass
  and of every timer/thread/menu sync posts WM_CLOSE; WM_CLOSE -> run_close_protocol). Deferred (loop),
  not nested inside the callback pass - that is what makes the save-on-a-thread flow right.
- CloseGuard (BLOCKS) already listens to `Window(CloseRequested)` and vetoes with
  `prevent_window_close` - checked, unchanged; its doc now says how closes reach it. `prevent_window_close`
  (callbacks.rs) unchanged: the headless test proves a veto keeps the title set in the same callback.
