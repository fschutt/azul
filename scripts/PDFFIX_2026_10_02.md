Branch `wt/pdffix`, base `dfa3e14b8`. Nothing compiled (house rule). Every
behaviour change has a RED test commit before its fix. No api.json change.
`layout/src/solver3/page_breaks.rs` and

## Item 2 - content clipped by `overflow: hidden` made extra pages

**Root cause.** `display_list::calculate_display_list_height`
(layout/src/solver3/display_list.rs) is the one "paged extent" function:
`page_breaks::compute_page_breaks*` (page_breaks.rs:284 and :772 call it),
the slicer `paginate_pages_impl`, and `PagedLayoutResult::total_content_height`
all measure by it. It took the bottom of EVERY item's bounds and never looked
at the clip stack. An abspos block in `.page { position: relative; height:
<page>; overflow: hidden }` is painted inside the page box's clip (its scroll
chain reopens the containing block's clip), but its text items still pushed
the extent past the page, so `page_spans` made a second (empty) page. The
root cause is NOT in page_breaks.rs.

**Fix (06b3b986b).** The extent walks the clip stack: `PushClip`,
`PushScrollFrame` (an `overflow: hidden` box with content to scroll opens a
scroll frame, not a clip) and `PushImageMaskClip` open a clip intersected with
the enclosing one, their pops close it, and every item counts with its
VISIBLE part only. A clip marker's own rect still counts (it is the clipping
box) within the clips around it, so an empty fixed-height box still extends
the document. Paged layout never has a viewport scroll frame
(`compute_scrollbar_info_core` returns no bars when a fragmentation context is
set), so the root content is never clipped to one page. `intersect_or` now
delegates to the new `intersect_rects`.

**Tests.** 7488a015b: `layout/tests/content_clipped_by_an_overflow_hidden_box_adds_no_pages.rs`
(page box + block both clipping -> 1 page; page box alone clipping its abspos
block -> 1 page; control: unclipped text still pages) and two display_list
unit tests (`calculate_display_list_height_ends_where_the_enclosing_clip_ends`,
`..._clips_by_scroll_frames_and_nested_clips`). `pagination_dom_breaks::paginate`
became `pub(crate)` so the new test reuses it.

**For page_breaks.rs (not edited, owned by another session).** A page box
that is a hair taller than the page (842pt CSS height in an 841.89pt page,
pt->px rounding) still makes a sub-pixel last page: there is no tolerance at
the END of the document. `compute_page_breaks_from_forced` line 827
(`while y < total_height`) and line 918 (the second copy), `compute_page_breaks_impl`
line 390 (`if naive >= total_height`), and `page_spans` lines 877 / 939
(`if page_start < total_height`) should compare against
`total_height - MERGE_WINDOW_PX` (line 102, 1px), the same window the break
merging already uses, so a remainder under 1px never becomes a page.

## Item 1 - `column-count` on a block (issue #481)

**Root cause.** `layout_bfc` had no multi-column layout. `column-count` /
`column-width` only reached text3 for an inline formatting context ROOT
(`translate_to_text3_constraints`), so a `<div style="column-count: 2">` with
block children laid them out in one full-width column.

The children do NOT see the property, contrary to the issue's guess:
`get_property_slow` (core/src/prop_cache.rs) walks inline -> rules matched to
THIS node -> global `*` -> `cascaded_props` (only `is_inheritable()` types are
copied there, ~L2000-2090) -> `computed_values` (gated on `is_inheritable`) ->
UA; ColumnCount is not inheritable. `DOM_HAS_COLUMN_COUNT` is a DOM-wide "some
node declared it" bit that only gates the lookup; it is never a value. The
issue's numbers are those of single-column paragraphs: with Helvetica AFM
widths the ALPHA paragraph at the full 340pt width breaks into 3 lines whose
last, "nineteen twenty twentyone twentytwo twentythree.", puts
"twentythree." at x=242.1 (reported 242), line 3 at y~71 (reported 71), and
BETA at 91.2 (reported 91); two 160pt columns would give "twentythree." alone
at x=220 and BETA at ~105.

One real "child sees the columns" path existed and is fixed (81a24e9d0): an
ANONYMOUS block box (loose text beside a block) resolves its style through the
element it sits in (`ifc_root_dom_id` falls back to the parent), and
`translate_to_text3_constraints` read that element's columns as the box's own.

**Design (user ruling: refactor first, no hack).** Not the K30b
fragmentainer/token path: it re-lays per fragmentainer, and a box split over
two columns would need two positions in one display list (one position per
node; the page loop gets away with it because each page is its own display
list); fragment passes also never split inline contexts. Instead azul's own
pagination model, "one continuous layout, then the break analysis", with the
column boxes for pages:

1. Refactor (41e7b532c): new `layout/src/solver3/multicol.rs` - `column_style`
   is THE reader of a box's column declarations (gated on the compact cache's
   DOM-wide bits), `ColumnStyle::geometry` THE resolution of N and W (CSS
   Multicol 1 §3.4, now spec-exact when both are set: column-count is the
   maximum), `ColumnGeometry::column_x / advance` the placement (rtl runs right
   to left, overflow columns continue). `translate_to_text3_constraints` uses
   it; text3's own IFC-root split is unchanged.
2. text3 `ColumnFlow` (e66fddccb): `UnifiedConstraints::column_flow` (line
   indices where a further column starts, the column advance, the further
   columns' top). `perform_fragment_layout` honours it when the context has no
   columns of its own: same line breaks, lines moved. Reaches text3 through the
   new `LayoutConstraints::column_flow` (None at all twelve existing literals);
   layout_ifc's reuse hash folds it in.
3. `multicol::plan_columns` (4ca187646, unit tests): the in-flow children as
   FlowBoxes (border-box top/bottom, plus the lines of a splittable box),
   break opportunities between siblings and between two lines, greedy in-order
   fill, `column-fill: balance` by bisecting the smallest column height that
   needs at most N columns (capped by a definite height; `auto` with a definite
   height fills in turn), overflow columns for what a capped height cannot fit.
4. A multi-column container establishes a BFC (7f6d11759, CSS Multicol 1 §2):
   `establishes_new_bfc` via `multicol::is_multicol_container`.
5. `layout_bfc` (26129366b): `block_columns` narrows the children's containing
   block to one column; Pass 1 and Pass 2 run unchanged at that width
   (`flow_cross_size` replaces `constraints.available_size.cross` at its four
   uses - identical for every other block); `distribute_into_columns` plans and
   moves children to (column x, y - column start); `split_into_columns` lays a
   paragraph the plan breaks between lines out again with a `column_flow`,
   moves its atomic inlines, and shrinks its box to its first fragment. The
   container is as tall as its tallest column. Plain inline formatting context
   children split; BFC roots, replaced boxes and anything else move whole.
6. Incremental layout (same commit): `promote_layout_roots_to_containers`
   lifts a layout root inside a multi-column flow to the outermost multi-column
   container around it (re-stacking block siblings would pile the columns into
   one); its node closure now reports multi-column containers
   (`multicol::is_multicol_box`) in both callers (cache.rs reconcile, mod.rs
   css-dirty channel).
7. Paged output (cf4ab81b2): a split paragraph has lines ABOVE its box; its
   paged `TextLayout` item (printpdf draws glyphs at `bounds.origin` + item
   position, the slicer intersects `bounds`) reached a whole layout height below
   the box and missed the lines above. Such a layout's TextLayout now carries a
   copy moved down to start at 0 under an origin moved up by as much (glyphs
   unchanged; every other TextLayout keeps the cached Arc).

**Tests.** 0e275ee03: `layout/tests/a_multicol_block_flows_its_children_through_its_columns.rs`
- four 40px paragraphs two per column (positions, widths, container height
80), column-gap, column-width-derived count, a paragraph continuing at the top
of the next column between two of its lines, rtl, a fixed-height container
running on into overflow columns; pins (green before and after): a lone inline
context keeps text3's split, the child resolves no column-count of its own.
0aa475d5c adds a guard for loose text (anonymous box) - green before, and after
the full fix; it would only fail with the BFC layout without 81a24e9d0.
60ccc01c2: the split paragraph on 80px columns stays on one 100px page.
`multicol.rs` unit tests: the geometry (§3.4), placement, and nine planner
cases.

## Least sure of the behaviour

- The planner reads a paragraph's line extents from its items (the line boxes
  are not stored): a break falls midway between two lines' ink, i.e. on the
  line box boundary for symmetric half-leading. Breaks are LINE INDICES, so the
  split itself is exact; only the column height can be off by a fraction of the
  half-leading.
- The multicol RED test "a paragraph continues..." uses `line-height: 20px`
  and asserts loose pen bounds (first pen of column 2 above y=20, all pens
  above y=80, container under 100px tall).
- A paragraph's unsplit layout for the planner comes from Pass 2's float re-layout of
  every plain inline child (it always runs for those); a child that skipped it
  is not split (`splittable_lines` checks the stored layout's constraints).
- LayoutWindow's typing fast path (`try_incremental_text_relayout`) re-lays a
  split paragraph with its CACHED constraints, i.e. the old line-index breaks,
  until the container lays out again.

## Limits (follow-ups)

- Vertical writing modes and K30b fragment passes keep one column.
- Paragraphs next to floats in the column flow do not split (their lines
  wrapped around the floats; a split must break them identically).
- orphans / widows are not honoured at column breaks; `max-height` does not
  cap the columns; `column-span` and column rules are not laid out.
- A split box paints its background/border on its first fragment only, and
  hit-tests there (its continuation lines paint, but a click on them misses
  the box).
- On paper the columns are sliced by pages like any content; they do not
  re-balance per page.
- `translate_to_text3_constraints` reads the OTHER non-inherited properties
  of an anonymous box through the same parent fallback (shape-inside,
  line-clamp, initial-letter, text-box-trim) - same flaw as the columns had.

## Duplication seen (not fixed)

Rect intersection exists four times: `cpurender/pixmap.rs rect_intersection`,
`cpurender/compositor.rs intersect_logical_rects`,
`managers/focus_cursor.rs intersect`, and display_list.rs `intersect_rects`
(display_list.rs's own `intersect_or` now delegates to it). One
`LogicalRect::intersection` in core/src/geom.rs would replace them (needs the
api.json decision; cpurender is an optional feature, which is why
display_list.rs cannot use pixmap's).
