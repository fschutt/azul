## ENGINE fixes (unverified)

### 1. Headless: a modal's Escape is its own (AzReview, AzSetup)
Seen: Settings > About > Escape: the About box (a Modal = a transient window) vanished, its on_close never ran
(no `AZREVIEW_ABOUT closed`). Log: "[menu] the owner dismissed its menu windows (press=false escape=true)".
Root cause: every `<transient-window>` popup is a `WindowType::Menu` window (`transient::popup_window_state`),
and the headless `is_menu_window` took every Menu-type child for a window-based menu, so the owner's
`dismiss_menu_windows` closed open modals / popovers on any Escape or press (no `Dismissed`, key spent; a
closing popup also took the others down as "its menu chain"). Second gap: `deliver_forwarded_keys` was the
default no-op headless, so a key forwarded to the popup that holds the keyboard was never replayed.
Fix: `is_menu_window` = Menu type AND no transient mailbox (the rule `process_transient_dismissal` already
uses); headless `deliver_forwarded_keys` runs the pass of every child with forwarded keys (as X11 / macOS).
Commits: RED b764fe592, GREEN 238e8e612 (dll/src/desktop/shell2/headless/mod.rs).
Probe on today's binary: closing the box by its close button prints `closed` and the second Escape closes the
settings page, so the Dismissed path works headless.

### 2. A scripted pointer feeds the gesture sessions (AzTasks, AzShow)
Seen: AzTasks' planned-month drag (and AzShow's slide sorter) never dropped; the log showed only
"[DRAG] TextSelectionDrag", never DragStart. Root cause: the debug server's pointer ops arrive as
`ModifyWindowState` / `QueueWindowStateSequence`; those arms ran the event pass but never called
`record_input_sample` (every backend's mouse handler does; headless injected events too), so no input session
existed and `detect_drag` never fired.
Fix: `PlatformWindow::record_scripted_pointer_sample(was_down)` in both arms (press starts a session, release
ends it, a move is a sample; not for a transition the scrollbar layer took). The `double_click` op no longer
injects a native DoubleClick: its two press / release cycles now ARE one (the injection would be a second).
Commits: RED 22d564f60 + 32952e3ba, GREEN 9695862dc (dll/src/desktop/shell2/common/event.rs,
layout/src/e2e/full.rs).
Behaviour change for every script: two `click` ops on one spot within 500 ms are now a double click (click
count 2), and a held-button drag is a gesture (DragStart, Drag, DragEnd), as on a device.
Not done: the in-process runner (layout/src/e2e/runner.rs) does not feed gesture sessions either (and fails
`InjectNativeGesture` by name); no corpus scenario uses double_click / drags today.

### 3. close_window() from inside a modal closes the window that owns it (AzWriter)
Seen: "Save changes?" > Save saved (AZWRITER_SAVED), then "[transient] closing window reports itself
dismissed" - the QUESTION's window closed, the document window stayed. Root cause: a modal's content runs its
callbacks in the popup window; the save thread was started by the question's Save, its write-back replied in
the popup, and `close_window()` closed the popup. The CloseGuard's Don't Save calls `close_window()` from
inside its question the same way.
Fix: mailbox field `close_owner`; `CallbackChange::CloseWindow` in a (non-torn) popup posts it
(`transient::post_close_owner`) and wakes all windows; the parent's `sync_transient_windows` takes it
(`transient::take_close_owner`) and raises the same close request `CloseWindow` raises, so the close protocol
(CloseRequested / CloseGuard) still runs.
Commits: RED fcfce42a2, GREEN 199df4129 (dll/src/desktop/shell2/common/transient.rs, event.rs).
Open risk (not changed): a thread started from a popup callback lives in the popup's window; if the popup
closes before the thread replies, its write-back is dropped with it. In today's runs the reply came first.

### 4. A relatively positioned box moves its contents with it (AzReader)
Seen (the script passed): the right page of the first spread repeated the chapter's start, cut to page 2's
height. AzReader shows page N as the reading column under `position: relative; top: -<start>px` in a clip;
get_node_layout: the shifted box at y -265.8, the column inside it still at 236.2. Root cause:
`adjust_relative_positions` shifted the box and its subtree only for table rows; positions are absolute, so the
content of every other relative box stayed where normal flow put it.
Fix: every descendant takes the box's delta (nested relative boxes add up).
Commits: RED da8623f2e, GREEN 5db6092da (layout/src/solver3/positioning.rs).
Note: a pass starts from the cached positions and the relative pass runs over every node, so a relative box
no layout root re-positions would be shifted twice; that exposure existed for the box itself before and now
covers its subtree. A probe on today's build saw no drift of the box across theme / mode / resize / hover.
