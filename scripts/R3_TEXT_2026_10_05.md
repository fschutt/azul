### text3 sub / super pins (4) - TEST wrong, 1ac9f57b2
Chrome (LayoutNG baseline shift): sub = parent font size / 5 + 1 down, super = / 3 + 1 up, and the line box
holds the shifted box. FIX9-LAYOUT 1.8 moved the engine to that rule; the pins still said 0.3 / 0.4 of the line
ascent. With the default 16px strut: super 6.3333 (Chrome's LayoutUnit 6.328), sub 4.2 (4.1875).
**About the coordinator's "do NOT update the regression_metrics pins to 0.0 / 1.0":** those two tests never
reach getters.rs - `layout_sc` builds `StyleProperties` / `UnifiedConstraints` by hand and sets
`constraints.vertical_align = Super/Sub` directly (the run's style stays Baseline, `get_item_vertical_align`
falls back to the constraint). So pdfocr issue 1 cannot be why they read 0.0 / 1.0; the values are text3's own
geometry, checked by hand: super - line ascent max(12.8 strut, 16 + 6.333) = 22.333, box top = 22.333 - 6.333
- 16 = 0, i.e. the raised box makes its line taller and its top IS the line top (what Chrome does with a lone
`<sup>` run); sub - ascent stays the strut's 12.8, top = 12.8 + 4.2 - 16 = 1.0. Because y = 0 alone cannot tell
a raise from no shift, the super test now ALSO pins the pitch of two raised lines (22.333 + 3.2 = 25.533, not
20) - a real measure of the raise. If the coordinator still prefers a non-zero pin, a tall-strut fixture
(strut 24/6: super top 1.667, sub 12.2) would show the shift directly; I did not change the fixture.
Files: layout/tests/text3_baseline_exact.rs, layout/tests/text3_regression_metrics.rs.

### an_inline_block_sits_on_its_last_lines_baseline - TEST wrong, a2b5b5142
`<p>X<span class="ib"><div>words</div></span>..` - a `<div>` start tag closes the open `<p>` (HTML 13.2.6.4.7
"close a p element"); azul's XML loaders run the same START_TAGS rows since 7325d3a39 (`div` = [CloseP,
Insert]), so the inline-block was EMPTY (no red) - in Chrome too. The block child is now a `display: block`
span. File: layout/tests/an_inline_block_sits_on_its_last_lines_baseline.rs.

### an_inline_box_paints_its_border_padding_and_margin float - CODE, 1fa2d7d34
`measure_intrinsic_widths` folded only cluster advances; the inline box's margin + border + padding were added by
`position_one_line` alone, so a float shrank to "Y" without the span's 40px padding. One helper
`inline_box_edge_advances(items, idx)` (factored out of position_one_line's `inline_offsets`) now feeds the
intrinsic scan too (line total; the word it sticks to). File: layout/src/text3/cache.rs.

### an_absolutely_positioned_child_does_not_split_its_parents_line (2) - CODE, 52939304c
`parse_css_property` turns a bare `none` into the CSS-wide `CssPropertyValue::None` unless the property is in
`has_typed_none`; ListStyleType was not, `get_property()` read it as no value, `get_list_style_type` fell to the
default Disc, and every `list-style-type: none` written as CSS text got a disc marker box (the 2 extra glyphs).
Added to `has_typed_none`. File: css/src/props/property.rs.

### css_zoom em - CODE, d31697263
layout_bfc re-resolves its children's box props (em against the child's own zoomed font, % against the real
containing block) - but AFTER Pass 1, which sizes each child with the tree-build placeholders (em against the
PARENT's font, % against the viewport) and whose `used_size` Pass 2 keeps. lldb: `resolve_box_props(z)` ran with
font 20 after z was sized with 16. The block moves above Pass 1. File: layout/src/solver3/fc.rs.
Note: this also changes the Pass-1 size of any block child with an em padding whose font size differs from its
parent's, or a % padding in a container narrower than the window - Chrome-correct, but a pin tuned to the old
size would move.

### line-height 5vh after a resize - CODE, 2c8051608

### pdfocr issue 1 (coordinator) - RED 38da0a480, GREEN 273b7c20a
RED test `solver3::fc::vertical_align_of_nested_inline_boxes_tests::sup_sub_and_vertical_align_super_shift_
their_text_and_a_nested_box_rides_the_shift` (product path, baseline differences, font-independent): the repro
shape (sup, a `vertical-align: super; font-size: 0.6em` span, sub) plus `<sup><i>1</i></sup>` and a sup in a sup.
Finding: the report's diagnosis (getters.rs gives a run the TEXT node's vertical-align) does not hold at HEAD for
the repro's direct shapes - `collect_inline_span_recursive` gives a span's text the SPAN's style, vertical-align
included (and `sizing::text_run_style` does the same), and printpdf draws every glyph at its own position
(`html/bridge.rs` reads `PdfPositionedGlyph.position`). So the three direct shapes are expected GREEN already at
38da0a480 (please re-run pdfocr's repro on this branch; if they still sit on the baseline there, the difference
is in printpdf's html2pdf path, not text3). What WAS broken is the nested case: a span nested in a shifted span
got its own (baseline) style, so the footnote mark `<sup><i>1</i></sup>` sat on the line, and a sup in a sup rose
by its own shift only. Fix: `fc::nested_vertical_align` - a baseline-aligned nested box takes its parent's
alignment; sub / super / lengths add up into one `Offset` raise, sub / super measured against the enclosing
box's font size (also settles FIX9-LAYOUT's round-2 note R2.6 for nested boxes); applied to nested spans,
inlinified blocks, atomic inlines inside a span and an empty span's strut box. File: layout/src/solver3/fc.rs.
