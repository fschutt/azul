### a_one_box_slide_does_not_re_lay_out_the_page::text_after_a_block_is_carried_over_by_the_next_layout - CODE, 985535765
- Symptom: "relayout 1 of an unchanged page found 7 nodes dirty" with 0 nodes fresh.
- Root cause: the page has exactly 7 DOM nodes, which is what the COLD pass marks intrinsic-dirty (every
  DOM-backed node is fresh; the anonymous wrapper is not counted). A reconcile of the unchanged page cannot
  produce 7 with nothing fresh (only its 4 non-leaf nodes can go children-dirty; no css dirt). An unchanged
  relayout takes `layout_document`'s Step 1.1 structural-identity display-list cache hit, which reset the
  patch flags but not `LayoutCache::last_intrinsic_dirty` - so the census kept the cold pass's 7. The Step 1.5
  early exit already sets it to 0 "so the census describes THIS pass"; the hit did not.
- Fix: the cache hit sets `cache.last_intrinsic_dirty = 0`. (solver3/mod.rs, one statement + comment.)
- Confidence: high (the arithmetic only fits the stale count; the fix is right regardless).

### a_one_box_slide_does_not_re_lay_out_the_page::a_knob_frame_costs_the_same_on_a_page_twice_as_long - CODE, 7b621fdc0
- Symptom: harness check "each frame ran a layout pass" with ALL counts 0 on both pages.
- Root cause: `layout_dom_recursive_impl` ends every DOM's pass with `Probe::drop_events()` when the
  AZ_PROFILE=cpu report is off (74ed1e579; it keeps AZ_PROFILE=memory runs bounded). It could not tell that
  case from a caller that switched recording on and drains the buffer itself: the test (set_recording(true),
  relayout, drain) read an empty buffer - and so did the telemetry bridge (`telemetry::init` arms the probe
  for consenting tiers to fill `app_phase_seconds{phase}`; every layout span was dropped before the frame pump
  drained). The test could never have passed with the `probe` feature on (default since 2026-08-29).
- Fix: the probe remembers who switched recording on (state 3 = `set_recording(true)`, a draining caller;
  state 1 = AZ_PROFILE) - new `Probe::drained_by_its_caller()`; the layout pass drops only when it is false.
  The telemetry frame pump's own rule (drop when not collecting and no CPU report, A11YPATCH8) is unchanged.
- Confidence: high for the harness failure; MEDIUM that the test is then green - its real bounds (text flows
  <= 4 and equal on 40 / 80 cards, no more flex items / formatting contexts on the long page) are now measured
  for the first time. LAYOUTPERF8C measured 0 re-flows / 11 taffy misses for AzWidgets' knob tick; FIX9 1.6
  (the knob is built fresh) and a253ffd49 (every ancestor's cache entry cleared) touch only the knob's chain.
- Side effect: `a_virtual_view_leaves_its_hosts_font_chains_in_place` (`font_load_missing <= 1` over a
  relayout) was vacuous for the same reason (it read 0 events) and now counts for real.

### a_face_fade_frame_is_patched_in_place::tweens_that_restyle_share_one_cascade_refresh_per_frame - TEST, fe90b5b1c
- Symptom: "the frame ran 0 epoch bumps" for two opacity tweens (expected 1).
- Root cause: the test used `opacity` as its example of tweens that need the cascade - true at d332a93fb.
  FIX9-PAINT 2.8 (aabe3db1e) put CSS opacity fades on the GPU value path (the layer binds its CSS opacity
  key; a frame publishes the value, patches the compact opacity byte, restyles nothing). The write's own
  display-list rebuild syncs the keys, so the layer exists before the first tick: 0 refreshes, the outcome
  2.8 wanted (pinned by window.rs `a_css_opacity_tween_frame_after_the_first_is_values_only`).
- Fix: the same rule, still exactly 1 refresh, with two `width` tweens (20 -> 40 px, `animation: width 150ms
  linear`): no in-place patch, no GPU value, both take the batched restyle path. Imports adjusted.
- Confidence: high for the diagnosis, medium-high for exactly 1 (no other epoch bump in a size-tween tick:
  checked `tick_animations`, `invalidate_resolved_font_sizes` does not bump).

### an_animation_frame_sends_assistive_technology_only_what_moved::every_published_patch_leaves_the_screen_reader_holding_the_fresh_tree - CODE, 21aa81ada
- Symptom: at "five cards added" (page(3) -> page(8), the first page taller than the 600 px window) the body
  on the consumer's side had no scroll surface; a fresh build made it scrollable. Earlier steps matched.
- Root cause: the accessibility scroll surface comes from the REGISTERED scroll states
  (`ScrollManager::a11y_scroll_info`), and the layout funnel ran `update_a11y_tree` before
  `register_scroll_nodes` (and before the caret reveal, which moves an offset): every pass built the tree
  against the previous pass's registration. With A11YPATCH8's retained tree the stale node stays published
  until a later pass rebuilds it.
- Fix: the a11y update moves below the registration and the reveal (window.rs funnel tail; neither reads
  a11y state; same cfg and result gate).
- Confidence: medium-high (the mismatch shown is exactly the scroll surface; the later "two passes folded"
  step was never reached before and is unverified).
