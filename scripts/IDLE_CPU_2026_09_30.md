# IDLE_CPU - report (2026-09-30)

Branch `wt/idle-cpu`, base `ab8d5a895`. Nothing was compiled (house rule);
every `.rs` file touched parses under `rustfmt --check`, the debugger JS
suites pass under node (`debugger-dnd` 19/19, `-extras` 17/17, `-export`
16/16, `-project` 13/13), and `scripts/idle_cpu_probe.py` was checked with a
synthetic `sample` report.

User report: "azmeet and azwidgets show 30% cpu, other apps 0.8% (never go
full idle)". Three user rulings joined during the task: cull animations
nobody can see; no internal timer may stay registered without work; no
hard-coded 16 ms / 60 fps - pace at the monitor's rate, with a cap.

## What was built

1. **Animation culling** (user ruling, first deliverable).
   `LayoutWindow::update_animation_culling` marks a live keyframe track
   CULLED when its window cannot show anything (hidden, minimized, or macOS
   `occlusionState` covered -> `LayoutWindow::window_occluded`), when its node
   is laid out nowhere (`display: none`), is `visibility: hidden`, or when the
   group the display list opens for it is outside every clip around it and
   the window, or under a fully transparent group. The on-screen half is
   `cpurender::node_groups_on_screen`: the display list's own answer (the
   group's content through its own and every enclosing frame's LIVE
   transform, moved by the scroll frames via the shared `ScrollStack`, cut to
   the clips). Culled tracks are not sampled (no value change, no damage),
   `needs_animation_frame` ignores them, and when only culled tracks remain
   the driver timer is removed and the tracks are PARKED; the first tick
   after a pass re-arms the driver fast-forwards them by the wall time they
   spent parked (right phase at once, one frame, no burst; animations started
   meanwhile take an ordinary first step). Refreshed at every driver tick and
   at the end of every pass (`arm_css_animation_timer_if_needed`), so a
   scroll back into view restarts frames on the next tick.
2. **Display link on demand** (macOS). `FramePacer`
   (`dll/src/desktop/shell2/common/frame_pacer.rs`, pure, unit-tested):
   `on_request -> Start | AlreadyRunning | DeliverNow`,
   `on_tick(pending) -> Render | Idle | Stop` (2 idle ticks), `suspend` /
   `resume` for occlusion and minimize. Every request goes through
   `MacOSWindow::request_frame` (`request_redraw` sets `redraw_requested` and
   calls it; it is the only writer besides the drawRect resize and the
   render's consume). The link is created stopped; start/stop never touch the
   leaked `DisplayLinkTarget` (only `retire_display_link` flips `alive`); a
   tick the link thread queued before a stop only renders pending work. The
   link used to POLL `display_list_dirty` / `regeneration_pending` every vsync;
   `request_frame_if_pending` is the safety net - the manual run loop calls it
   before it parks, the RunForever drain and both views' timer ticks (which
   also run in menu tracking / live resize) call it too. WebRender's
   frame-ready notifier on macOS now posts the loop waker's NSEvent (it relied
   on the always-on link).
   Survey: Windows (WaitMessage), X11 / Wayland single-window loops (fds +
   timerfds, Wayland frame callbacks per present) have no always-on pump.
3. **No idle internal timers** (user ruling A). Caret tween, blink and CSS
   driver already exist only while they have work (pinned). The debug-server
   poll (AZ_DEBUG; AzBuilder always) drops from 16 ms to 250 ms after a quiet
   second and back on the next request (`DebugPollPace`; the timer re-registers
   itself with the same RefAny). NOT event-driven: the server thread cannot
   fire a UI-thread timer early on every platform, so the first request after
   a quiet spell waits up to 250 ms. macOS RunForever's 33 ms repeating drain
   NSTimer became a `kCFRunLoopBeforeWaiting` observer in the common modes
   (once per loop turn that did something; not re-entered from a nested
   modal loop). `DEBUG_TIMER_ID` is one constant instead of three copies.
4. **Frame interval from the monitor** (user ruling B). ONE source per
   window: `LayoutWindow::frame_interval_nanos` = one refresh of the monitor
   the window is on (`current_window_state.monitor_id` in `monitors`, else
   primary, else first; `Monitor::refresh_rate_hz` reads the current mode the
   platforms already fill: NSScreen `maximumFramesPerSecond` (ProMotion 120),
   DEVMODE `dmDisplayFrequency`, XRandR crtc mode, `wl_output` mHz), capped by
   the new `RendererOptions::max_frame_rate` (None = the monitor's). Formula:
   `azul_core::window::frame_interval_nanos` (readings outside 20..=1000 Hz
   fall back to 60). Shells read it via `CommonWindowState::frame_interval`.
   Replaced: caret tween (16 ms), CSS driver (`CSS_ANIMATION_FRAME_MS`,
   removed), the animation clock's first step and frame test (1/60), the track
   step in `generate_frame`, the auto-scroll fallback, macOS thread-poll timer
   (`TIMER_INTERVAL_60FPS`, removed), X11 pacer (read per frame from the
   window, `detect_frame_interval` removed), Win32 thread poll + modal pump,
   Wayland thread poll, Android loop poll, headless timer poll, the Linux
   multi-window poll cap, the scroll-physics timer (six identical copies ->
   `scroll_timer::create_scroll_physics_timer`), the `60fps` doc. The E2E
   deterministic step is `E2E_TEST_FRAME_STEP_MICROS` (a named TEST default).
   Gesture thresholds were already time-based (pinned at 60 vs 120 Hz).
5. **Display-list reuse for rotate/fade ticks.** The CSS driver answered
   every tick with `ShouldUpdateDisplayListCurrentWindow` -> the whole
   window's list was rebuilt per frame (AzWidgets ~18%). Now
   `LayoutWindow::root_display_list_gpu_fingerprint` records the key
   population the root list was built from; while the live cache still has
   it (and no restyle is staged, no exit runs) `animation_tick_is_values_only`
   holds and the driver answers `ShouldReRenderCurrentWindow`. The CPU
   compositor already prefers live values and damages only the moved frame's
   old and new rects (`gpu_value_damage`). ONE "current animated values by
   key" source: `GpuValueCache::for_each_bound_value`, read by
   `cpurender::extract_gpu_values` and by WebRender's `synchronize_gpu_values`
   (which carried the scrollbar channels only - a values-only tick would have
   frozen animations on GPU; animated opacity never reached WebRender at all).
6. **Debug-server screenshots.** `take_native_screenshot` is answered from
   `ScreenshotCache` while `LayoutWindow::presented_frame_generation` stands
   still (`record_frame` + the new `note_frame_presented`, called by
   `CpuBackend::render_frame` and by WebRender transactions that request a
   frame). Only the native capture is cached (the CPU `take_screenshot`
   renders the current list and E2E scenarios step animations between shots
   without presenting). The encode stays on the UI thread: the op replies
   synchronously. Builder page: no periodic poll exists in `debugger.js` /
   `debugger-dnd.js` (pictures refresh on edits and node selection); a hidden
   page now defers the canvas refresh until `visibilitychange`
   (`pictureRefresh`), skips the inspector's native capture, and does not
   re-decode an identical picture.
7. `scripts/idle_cpu_probe.py` (stdlib only): launches each app with
   `DYLD_LIBRARY_PATH=target/azul-lib`, waits 8 s, samples `ps -o %cpu=` once
   a second for 10 s, kills it, prints mean / max; `--sample` adds macOS
   `sample` (3 s) and the top 15 azul frames of the main thread. Never drives
   input. Run it before and after:
   `python3 scripts/idle_cpu_probe.py --sample`. Targets: idle apps < 0.1 %CPU,
   AzWidgets (three visible spinners) well under 10 %CPU.

  field `max_frame_rate: OptionU32` - "The highest frame rate this window

## Behaviour notes / risks

- The CSS driver now returns ShouldReRender for values-only ticks on every
  backend. X11 / Wayland / Win32 render on ShouldReRender without a list
  rebuild; their CPU paths read live values like macOS. GPU paths now push
  animated / CSS transforms and opacities as dynamic properties every frame.
- Frame requests on macOS: a path that raised `display_list_dirty` or a
  regeneration WITHOUT calling `request_redraw` now waits until the loop's
  next `request_frame_if_pending` (end of the loop turn, timer ticks). All 50
  writers in the macOS shell were checked; the ones without a nearby
  `request_redraw` run inside a render or at window creation.
- Culling uses the root display list; a node without a group in the list
  (keys not minted yet, or it paints nothing of its own) is never culled.
  Clips inside a TRANSFORMED enclosing frame are ignored (conservative).
- A running CSS driver / scroll-physics timer keeps the interval it was
  armed with when the window moves to a monitor with another rate; the next
  arming picks the new rate (X11's pacer reads it every frame).

## What is left

- Debug-server polling is adaptive, not event-driven (see 3).
- Linux MULTI-window loop still caps `poll()` (now at the fastest window's
  frame, not 16 ms): the windows' timer fds are not in that poll set; the
  single-window loops park indefinitely.
- Android / iOS have no monitor list, so they pace at the 60 Hz fallback
  until `Display.getRefreshRate` / `UIScreen.maximumFramesPerSecond` feed
  `LayoutWindow::monitors`. The Android loop still polls at one frame while
  it has a surface (its Java-thread queues - notifications, a11y, theme -
  rely on that poll; blocking needs them to call the loop waker).
- Left as they are: the CoreMotion sample interval (a sensor rate) and the
  `SystemTick` clock's nominal 60 ticks/s (a clock unit for clockless
  targets, also used by `event_determination.rs` tests); the E2E runner's own
  scroll-physics timer copy (deterministic test timing); `ScrollPhysics::
  timer_interval_ms` presets (16) are now only the first-tick estimate when
  a shell arms the timer - its doc in css still says "should match the
  monitor refresh rate".
- Duplicates found: the two identical `ts` test helpers in
  `layout/src/managers/gesture.rs` (`touch_session_tests`,
  `autotest_generated`); the E2E runner's scroll-physics timer copy
  (`layout/src/e2e/runner.rs`) twin of `create_scroll_physics_timer`.
- Measure with `scripts/idle_cpu_probe.py --sample` before and after; if
  AzWidgets is still above target, `sample` shows whether the remaining cost
  is the CPU raster of the spinner rects or the per-tick culling walk
  (one display-list walk per driver tick and per pass end while tracks
  exist).
