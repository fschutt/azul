## 2. What was built

### Item 1 - the platform gate

* `E2eTest::only_on: Option<Vec<String>>` (`layout/src/e2e/full.rs`). Known hosts: `linux`,
  `windows`, `macos`, `ios`, `android`, `web` (`E2E_PLATFORMS`). The host is
  `e2e_host_platform()` = `std::env::consts::OS`, `"web"` on wasm32.
* `e2e_platform_gate(only_on, host)` decides it. The scenario runner (`resume_e2e_continuation_inner`)
  applies it before a test starts, so AZ_E2E, HTTP `run_e2e_tests`, `run_e2e_test` and
  `azul-doc e2e` agree:
  * off its hosts: no step runs (not even `setup`); `status: "skip"` plus
    `E2eTestResult::skip_reason` ("only on linux, windows; this host is macos");
  * an unknown name (`"macOS"`) or an empty list FAILS the test (a step named `only_on`).
* `render_report` (`report.rs`): SKIP whatever `expect` says, never a gate failure;
  `E2eVerdict::skipped`; summary `... N xpassed; N skipped; 0 measured; 0 filtered out`
  (was `0 ignored`). CI `e2e_headless` (`.github/workflows/rust.yml`) parses the fifth number into
  its accounted total.
* **Twins removed**: `dll/src/desktop/shell2/run.rs` had its own copy of the verdict tally and of
  the loader. `setup_e2e_runner` now uses `render_report` and `load_e2e_tests`; the shared loader
  learned the one thing the dll copy had: a file may hold an ARRAY of tests (decided by the first
  character, so an error inside an array is reported as such).
* `AZ_E2E=<directory>` (`run_e2e_dispatcher`, one child process per file) tallied exit codes per
  file, so an all-skipped file printed "ok". New `E2eVerdict::parse_summary` reads a child's
  summary line back; the dispatcher sums per test, prints `SKIP` (with the children's SKIP lines)
  for an all-skipped file and `ok (N skipped)` otherwise.
* **Third twin**: `azul-doc mobile`'s device-log reader (`doc/src/mobile/e2e.rs::field`) parsed the
  same line itself, and read "ok. 3 passed" as the number "ok." - it always reported 0 passed.
  It uses `parse_summary` now.
* `examples/azul-widgets/e2e/global_hotkey.json`: `..._linux_windows` (`Ctrl+Alt+K`,
  `only_on: [linux, windows]`) and `..._macos` (`Cmd+Shift+K`, `only_on: [macos]`), same flow.
  Its "1 time(s) since it was enabled" check was VACUOUS (`find_node_by_text` answers
  `found: false` instead of failing); each variant now follows it with `assert_response`
  `"found":true` and waits one more frame after the press.
* Guide `doc/guide/en/debugging/e2e-testing.md` "File and step shape": `only_on`, SKIP, and
  `expect: "fail"` (never documented).
* Debugger test list (`debugger.js`): a skip shows a `block` icon in the warning colour, not a
  failure.

### Item 2 - notifications

* `{ "op": "notification_event", "id", "kind": "click" | "action" | "dismiss" | "failed",
  "action"?, "reason"?, "payload"?, "launched_app"? }` (`DebugEvent::NotificationEvent`,
  `notification_event_from_op`). Builds the `NotificationEvent` a backend would and queues it into
  the mailbox (`queue_notification_event`); the run loop's notification pump routes it (the
  headless dll backend already pumps in Phase 1c), filling in the post's payload when the event
  brings none. Refused by name: empty `id`, unknown `kind`, `action` kind without `action`,
  `action` / `reason` on a kind that has none, full mailbox.
* The in-crate runner has no notification service: there the event only waits in the mailbox
  (documented on the variant and in the guide).
* `assert_notification` takes `payload` (a requirement on the picked post, like `action`).
* OP_POLICY: `notification_event` is **DENIED** for generated tests, since the generator runs
  scenarios in the in-crate runner, where no callback would ever run (red on arrival).
* AzWidgets: the demo's post carries `with_payload("azul-widgets-demo:show")`, and "Last event"
  appends `Payload: "..."` when an event brings one. New `examples/azul-widgets/e2e/notifications.json`
  (AZ_BACKEND=headless):
  1. post, assert the button and the payload;
  2. a button press, a click and a dismissal each reach `on_notification_event`, with the payload;
  3. withdraw; `count` 4.
* Guide: "Native notifications" section.

### Item 5 - `ScrollFocusedContainer`

* `LayoutWindow::scroll_focused_container_by_keyboard(focused, direction, amount, duration, now)`
  (`layout/src/window.rs`, next to `scroll_container_by_keyboard`). It anchors on `focused`, else
  on `HoverManager::current_hover_node_full` (the mouse's front-most hit). It then scrolls
  `find_scrollable_ancestor(anchor)` with `scroll_container_by_keyboard`.
* Runner: the new arm anchors on the key's seat focus and applies the scroll at once, like its
  `ScrollContainer` arm.
* dll arm (`event.rs`): calls the same helper. Its re-implemented magnitudes are gone, and so are
  three constants (`KEYBOARD_SCROLL_LINE_PX`, `KEYBOARD_SCROLL_DOCUMENT_MAX`,
  `DEFAULT_VIEWPORT_HEIGHT`). Behaviour differences:
  * Left / Right page by the box's WIDTH (was its height);
  * the unfocused anchor is the front-most hit by `hit_depth` (was the highest NodeId of the first
    DOM);
  * a box without bounds falls back to 800x600.

### Item 6 - `Dismissed`

* `Runner::dismiss_popups_on_escape` builds each node's event with
  `azul_core::diff::create_dismiss_event`, the constructor `dismiss_transient_window` uses in the
  dll. The event is anchored on the parent's rect in the viewport.
* It dispatches right after the dismissal and the owed focus restore, and returns what the
  handlers ask for. `process_window_events` folds that into the pass result, also when the spent
  Escape leaves no other event.

### Item 3 residual

* `get_cursor_state.position` now goes through `selection_range_info` (the `get_selection_state`
  reading): a byte offset with the affinity resolved.
* The doc comments said "grapheme cluster index" and "upstream / downstream"; they now describe
  what is reported.
* No corpus scenario reads `position`.
