## What was built

### Engine: partial image updates (RED first)

A canvas that repaints a brush dab keeps one image node and replaces its image per pointer
move. The content chokepoint only knew "the image changed", so the GPU backends re-uploaded the
whole image per dab (`update_image(.., DirtyRect::All)` in `upload_overlay_images`), although
`ImageDirtyRect::Partial` (azul_core) and WebRender's partial texture upload both existed -
nothing carried a rect from the app to them. Root cause fixed through the one chokepoint:

- `CallbackInfo::change_node_image_rect(dom_id, node_id, image, dirty_rect: LayoutRect)` (new):
  pushes `CallbackChange::ChangeNodeImage { .., dirty_rect: Some(r) }` (the variant gained
  `dirty_rect: Option<LayoutRect>`; `change_node_image` passes `None`).
- `ContentChange::Image { .., dirty_rect }` -> `apply_image_change(.., dirty_rect)` records, per
  image node, the region the renderer has not uploaded yet in the overlay
  (`ContentOverlay::image_dirty`): the union of every change since the last upload, `All` after a
  change without a rect, after a resize, or for a callback's own frame; remapped / dropped with
  its node.
- `ImageDirtyRect::{is_empty, union, clipped_to}` (core).
- `plan_overlay_image_uploads` takes `(slot, &ImageRef, pending)` and keeps the pending rect
  (clipped to the frame) when the node's key already holds a frame of the same pixel shape
  (format, size, stride, offset); a new key, a reshape and NV12 go up whole.
  `upload_overlay_images` passes it to `update_image` and clears the pending regions.
- `translate_dirty_rect` is the ONE azul -> WebRender dirty-rect translation:
  `translate_update_image` had its own inline copy (a twin), it now calls it.

Tests (RED `829b9a1a9`): core `resources_test` (union / empty / clip), `overlay::tests` (four),
`layout/tests/a_partial_image_change_leaves_its_rect_for_the_renderer.rs` (five, through
`apply_content_change`), `dll .. overlay_upload_tests` (four new; the three existing calls take
the new item shape).

Pointer pressure needed nothing: `CallbackInfo::get_pen_state` delivers it (AzPaint's path).

### `examples/azul-photo` (package `AzPhoto`, lib `azphoto`, bin `AzPhoto`, link-dynamic)

**Raster core** (`src/raster/`, no azul types except the dab stamp) behind the **`RasterEngine`**
trait (`engine.rs`): `document`, `size`, `active_layer`, `apply(Op)`, `begin_stroke` /
`stroke_to` / `end_stroke`, `take_dirty` (composite what changed, answer the document rect),
`composite`, `sample`, `undo` / `redo` / `jump_to`, `history`, `flatten_rgba`,
`replace_document`. The app holds it as `Box<dyn RasterEngine>`; `TileEngine` is the CPU tile
store; Graphite can implement the same trait later.

- `tile.rs`: 256 x 256 straight-RGBA8 tiles, `Arc`-shared, copied on write; a missing tile is
  transparent and free; a one-colour layer is ONE shared tile.
- `document.rs`: layer tree, selection; `Composite` with one dirty flag per tile, recomposited on
  **worker threads** (`std::thread::scope`, `available_parallelism`): blend modes (Normal,
  Multiply, Screen, Overlay, Darken, Lighten, Difference, Add - W3C separable formulas,
  premultiplied f32), opacity, non-destructive adjustment layers, isolated groups.
- `brush.rs`: stroke mask (`m += (1-m) * flow * dab`), opacity cap per stroke, spacing, pressure
  -> size / flow, pencil (hard, no AA), eraser, clone stamp (aligned offset, Alt-click source).
  The soft dab profile is azul's own: each stamp is painted once per radius with
  `RawImage::paint_dot` (single-sourced `brush_dab_coverage`) - no twin of it in the app.
- `selection.rs`: 8-bit masks; rect, ellipse and lasso polygon (exact horizontal coverage, 4
  sub-rows); add / subtract / intersect / replace; invert; feather; magic wand (tolerance,
  contiguous or global).
- `adjust.rs`: brightness/contrast, levels, monotone (Fritsch-Carlson) curves, hue/saturation,
  invert, threshold; per-channel ones become a 1024-entry table for compositing.
- `filter.rs`: ONE separable Gaussian (`blur_plane`, rows split across workers) used by the blur
  filter, sharpen (unsharp mask) and the selection feather; filters run inside the selection.
- `transform.rs`: affine with nearest / bilinear, flips, quarter turns, crop, move, resize (box
  average when shrinking), canvas placement.
- `history.rs`: whole-document states that share every untouched tile ("tile snapshots");
  undo recomposites only the tiles that differ (`changed_between`); slider runs coalesce into
  one state.

**The canvas** is ONE image node (`canvas.rs`): a `RenderImageCallback` draws the viewport at the
node's physical size (`view.rs`: zoom 1 .. 3200 %, pan, checkerboard, workspace, nearest when
zoomed in / footprint average when zoomed out, marching ants, marquee / lasso / crop / guide
overlays, navigator thumbnail). A stroke redraws only the view rect its dirty tiles map to and
hands exactly that rect to `change_node_image_rect` (stdout `AZPHOTO_UPDATE x y w h`); zoom /
pan / resize redraw all. The ants timer (200 ms) redraws only the selection's bounds.

**The editor** (`state.rs`, pure and tested; `commands.rs`, `ui.rs`, `lib.rs`): S2
`CanvasShell` with the app-drawn `Titlebar` (`NoTitle`) in a `ShellThemeScope`:
- menu row File / Edit / Image / Layer / Select / Filter / View / Help (one menu table: the
  in-window row opens each menu under its button; on macOS also the native menu bar with
  accelerators);
- options bar per tool (size, hardness, opacity, flow, pressure -> size / flow, selection mode,
  feather, tolerance, contiguous, sample all layers, shape kind, zoom buttons);
- tools column: move, rectangular / elliptical marquee, lasso, magic wand, crop, eyedropper,
  brush, pencil, eraser, paint bucket, gradient, clone stamp, text (shown, explains the engine
  gap), shape, hand, zoom; foreground / background chips (click swaps);
- canvas with rulers (DOM labels every 1..10000 px), the document tab (unsaved dot, close);
- panels: Navigator (thumbnail, zoom %), Color (two `ColorInput` pickers, swap / default,
  swatches), Layers (blend drop-down, opacity field + slider, rows with visibility, lock, group
  expand, kind icon; select by click, **reorder by dragging a row onto another**, a group row
  takes it in; new layer / group, duplicate, merge down, up / down, delete), Properties (the
  active adjustment's sliders, layer facts, selection size), Adjustments (six), History (click
  a state; undo / redo);
- status bar: zoom, document size, cursor position + RGB (updated in place through
  `StatusBar::update_segment_label`, no rebuild);
- sheets: New image (with the per-layer memory), Export (PNG / JPEG + quality), Image size,
  Canvas size, Gaussian blur, Sharpen, Rotate, Feather, About, Settings
  (`ShellSettingsLayout`: flat / flora, light / dark, the data folder);
- start screen: Open / New / Open sample, the saved documents (`ShellEmptyState` when none);
- shortcuts: tool letters (cycling within a key), `[ ]` size, digits = paint or layer opacity
  (Photoshop's), X / D colours, Ctrl/Cmd + Z / Shift+Z / Y / S / O / N / Shift+N / J / E /
  Shift+E / A / D / Shift+I / 0 / 1 / = / -; plain keys stay out of a focused text field;
  wheel pans, Ctrl/Cmd/Alt + wheel and pinch zoom about the pointer.

**Files**: open PNG / JPEG / WebP / GIF / BMP / TIFF / TGA through azul's decoder (`codec.rs`:
any decoded format -> RGBA8; open as a document or place as a layer); the native document is
`photo/<uuid>/doc.json` + `photo/<uuid>/layers/<layer>/<tx>_<ty>.png` (`storage.rs`, through
azul-storage's `Drive` on a `LocalDrive` at `AZPHOTO_DATA` / `<user data>/Azul`: tiles first,
doc.json last, stale tiles deleted); export PNG / JPEG (quality; flattened on white) into
`AZPHOTO_EXPORT_DIR` or through the save dialog. Every file operation runs on an azul `Thread`
(`jobs.rs`). `--sample`: the repo's 1920 x 1080 photo (`examples/assets/images/cat_image.jpg`,
`include_bytes!`) + a "Light leak" layer (gradient, Screen, 60 %) + a Curves adjustment.
`--open --screen --theme --mode --size --data --export-dir` (`args.rs`).

**Registered**: root `Cargo.toml` member, `scripts/workspace_test_members.txt`, the `dll_tests`
step "Run AzPhoto tests". `Cargo.lock` gains AzPhoto on the first build.

**E2E** `scripts/azphoto_e2e.py`: AzPhoto `--sample` headless (port 8781, its own data and export
folders): the document is 1920x1080 / 3 layers; selects the Photo layer, paints a 12-step
stroke, asserts the History ends in Brush and every `AZPHOTO_UPDATE` of the stroke is smaller
than the view (the dirty-rect path); adds a layer (4 layers), Move tool + key 5 = 50 %
(History "Opacity"), Ctrl+Z (back to "New Layer"); Ctrl+Shift+E + Export -> a PNG in the export
folder; Ctrl+S -> `photo/<uuid>/doc.json` (4 layers) + exactly the tiles it reported;
screenshots flat-light and flora-dark.

## api.json (via `azul-doc autofix add`, never by hand)

- `callbacks.CallbackInfo.change_node_image_rect(dom_id: DomId, node_id: NodeId, image:
  ImageRef, dirty_rect: LayoutRect)`, no return; fn_body
  `object.change_node_image_rect(dom_id, node_id, image, dirty_rect)`; doc: "Change the image of
  a node that differs from its previous image only inside `dirty_rect` (image pixels): the GPU
  renderer uploads only that rect. Rects of several changes before a frame add up; an image of
  another size or format is uploaded whole." (`LayoutRect` is `css.LayoutRect`, isize origin +
  size, already in api.json.)
- Nothing else: no new widget; `CallbackChange`, `ContentChange`, `ImageDirtyRect` and the
  overlay are Rust-internal.

The AzPhoto crate does not compile until that entry is generated (it calls
`info.change_node_image_rect`).

## Least-sure-to-compile spots (read twice, in this order)

1. `dll/src/desktop/wr_translate2.rs::upload_overlay_images`: the planner's iterator closure reads

   shared, the binding is `ref mut`), then `content_overlay.clear_image_dirty()` after the
   call. `translate_dirty_rect` returns `DirtyRect<i32, webrender::api::units::DevicePixel>`
   (the `ImageDirtyRect` alias of webrender_api).
2. `overlay_upload_tests` now imports `azul_css::props::basic::{LayoutPoint, LayoutRect,
   LayoutSize}` and `webrender::api::DirtyRect` and matches `DirtyRect` (it has no
   `PartialEq`) - azul-css is an optional dep of the dll, on under `build-dll`.
3. core `ImageDirtyRect` methods: `azul_css::props::basic::LayoutPoint::new`,
   `LayoutRect::zero()` (const fn), `isize::clamp`.
4. `layout/src/window.rs::apply_image_change(.., dirty_rect: Option<azul_css::..::LayoutRect>)`:
   `old` is read through `as_ref()` before it moves into the journal.
5. AzPhoto `storage.rs`: the serde shape (`#[serde(flatten)]` over an internally tagged
   `LayerKindFile`, `Adjustment` with its own `kind` tag one level down) - the scratch check
   stripped serde; azul-storage's API was stubbed from its source.
6. AzPhoto runtime assumptions (type-correct, behaviour unproven): `get_scroll_delta` on the
   canvas image node during a `Scroll` callback (AzCalendar's pattern), a `Button`'s Dom taking
   `with_accessibility_info(named(.., PushButton))` for an icon-only button, `ShellThemeScope`
   root extended with `with_css`, `Dom::create_icon` for the layer-kind glyph, the click op on
   `#layer-row-N` landing on the row (not its eye button).

## What is left

- **Text tool (engine gap)**: azul has no API that rasterises text into pixels (glyph raster is
  internal to cpurender); the tool is shown and explains itself. Needs e.g.
  `RawImage::draw_text(text, font, size, color, x, y)` in azul - not faked in the app.
- **CPU damage for partial updates**: the CPU backends still damage the whole image item on a
  `change_node_image_rect` (the DL diff sees the identity change); carrying the rect onto the
  item would narrow the re-raster. The GPU upload (the costly part) is partial now.
- The app still copies the whole view buffer into the new `ImageRef` per update (a memcpy, CPU
  only); a shared, copy-on-write image buffer would remove it.
- Move tool: applies on release (a guide line while dragging), no live preview; free transform
  handles; selection-only transforms.
- Not in azul's decoders: RAW, HEIC, AVIF, PSD; 16-bit documents; colour management (the plan's
  open questions).
- Graphite integration (path (c) then (b1)) behind `RasterEngine`; the histogram / curve-editor
  widgets the plan names (`Chart`, `CurveEditor`) - curves are sliders for now.
- Document tabs for several documents; drag-and-drop of files; image paste.
- Look at the screenshots (`azphoto-*.png`) once the E2E ran - the look is written, not seen.
