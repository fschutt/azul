## Per app

### AzMaps - fails today, should pass after the rebuild
- Failure: `Escape closes the About box first: expected 'closed', last 'open'`.
- Root cause (ENGINE, headless shell): two bugs.
  1. `HeadlessWindow::is_menu_window` treated every `WindowType::Menu` child as a
     window-based menu. A `<transient-window>` popup has that type too
     (`transient::popup_window_state`). So an Escape (or a press) that reached the owner
     made `dismiss_menu_windows` close the About modal's WINDOW behind its node's back. The
     node stayed open, `Dismissed` never fired, and the app still said `open`. A
     window-based menu is now the Menu type with NO mailbox, which is what `event.rs`'s
     popup side already said.
  2. Headless had no `deliver_forwarded_keys`. A key that the owner forwarded to a modal
     holding the keyboard sat in the modal's mailbox until the modal got input of its own,
     which never happens in a script. macOS, X11, Wayland and Win32 run the popup's pass at
     once; headless now does the same for its child windows.
- Commits: d6f17738d RED / 4bb84a779 GREEN (1); 3c603f3da RED / 881e6441b GREEN (2).
- Verified with a probe that sends Escape straight to the modal's window (`azul-transient`,
  the way macOS's key window gets it): the whole script passes on today's build. The script
  itself is unchanged.
- Rebuild + rerun: `cargo test -p azul-dll --test transient_window_layout` (the two new tests
  `an_escape_at_the_owner_of_a_popup_child_window_tells_the_app_it_was_dismissed` and
  `an_escape_at_the_owner_reaches_its_modal_dialogs_child_window_at_once`), then
  `python3 scripts/azmaps_e2e.py --bin target/release/AzMaps`.

### AzPhoto - fails today, should pass after the rebuild
- Failure: `timed out waiting for the undo`. One Cmd+Z undoes TWICE (History 3 -> 2 -> 1).
- Root cause (ENGINE, dll `common/event.rs`):
  - Mod+Z is both Edit > Undo's menu-bar accelerator and a canvas key-handler shortcut.
  - The shared accelerator dispatch (used on Windows, X11, Wayland, headless, and for every
    context menu) ran the menu item and then still dispatched the key-down to the DOM.
  - AppKit does not deliver the key-down of a performed key equivalent, and the Windows
    accelerator table turns it into a command. So the same app undid once on macOS and
    twice everywhere else.
  - Now a fired chord drops the primary seat's KeyDown events before the DOM dispatch, so no
    key handler and no default action sees it. The key-up still arrives.
- Commits: cd867df5c RED / c1a18d2b0 GREEN.
- SCRIPT (790ada8f8): key_up released the modifiers incorrectly; same fix as AzNotes.
- SCRIPT (7a861173a): two fixes.
  - "One Move state" compared the History COUNT, but the undo just before had left a redo
    tail that the move drops. The script now checks that the current step advances by one,
    at the tip.
  - The export sheet is a modal Dialog window. The script's client gains `popup()` and
    `click(..., window=)`.
- A probe that undoes through the History panel's button instead of Cmd+Z passes the WHOLE
  script on today's build: stroke, layer, opacity, undo, live move, text, export and save.
- Rebuild + rerun: `cargo test -p azul-dll a_fired_menu_chord_does_not_reach_the_windows_key_handlers`
