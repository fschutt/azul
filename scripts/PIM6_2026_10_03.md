## What was built

- **RecurrenceEditor widget** (`layout/src/widgets/recurrence_editor.rs`, both themes appended, manifest + the
  theme-contrast INPUTS group): how an appointment or a to-do repeats - never / daily / weekly on chosen weekdays
  / monthly on the start's day or its nth (fifth = last) weekday / yearly, every N (1-999), ending never / after
  N times / on a date (a DatePicker), and "Repeat from the day it is completed". COMPOSED of Segmented,
  NumberInput, toggle Buttons, DatePicker, CheckBox; each part folds its change into one `RecurrenceRule` and
  hands the whole rule to the app. `RecurrenceRule::to_rrule` / `from_rrule` speak RFC 5545 RRULE (the subset
  the form shows; anything else is `None`, the app keeps it as a custom rule). Options: week start, completion
  option, `end_option` / `month_weekday_option` (a to-do's repeat has neither). A Grouping named "Repeat",
  value = the RRULE. 19 tests (RRULE out / back, part changes, rows per frequency, week start, a click reports
  the whole rule, both themes light + dark, follows the app theme, structure declared once).
- **AzCalendar**
  - Event editor: the repeat rows are the RecurrenceEditor (`#editor-repeat`; a rule it cannot show says what it
    is, with "Replace"); the five Segmented rows, their six callbacks and the editor.rs helpers they needed are
    gone (DEDUP_EDITORS C5). The editor's date pickers are Monday-first like the navigator.
  - Close check (B29): the editor window's `CloseRequested` holds the close (`prevent_window_close`) while the form
    differs from the one it opened with (`EditorForm::changed_since`, `editor::close_answer`); Close / Cancel ask
    too. The question is azul's `CloseGuard` (Save / Don't Save / Cancel). Save & Close's own `close_window`
    (INFRA6: now through CloseRequested) closes without asking - the saved form is gone by then (tested).
  - "Edit this occurrence": a repeating event opens on the occurrence's day with "This occurrence (Wed 14 Oct) |
    The whole series" (`#editor-scope`); Save on one occurrence adds the day to the series' `except` and writes
    the occurrence as an event of its own (new id, no repeat, the form's edits).
  - Storage on the Drive (DEDUP_EDITORS B2): every durable write - events, calendars, settings.txt, the To-Do bar's
    tasks, exports - is queued (`azul_pim::write_queue`, two queues: the data folder and the task store) and a
    100 ms timer of the MAIN window hands each batch to a file thread (`azul_appkit::ui::spawn_file_jobs`); the
    answer finishes the batch, prints `AZCAL_SAVED` / `AZCAL_SYNCED` / `AZCAL_DELETED` / `AZCAL_EXPORTED` once
    the file landed (`AZCAL_SAVE_FAILED <key> <why>` otherwise), failures are retried at the sync tick. The main
    window's CloseRequested waits for writes on their way and says once what did not land. The import file is
    read by a file thread too. Exports go INTO the data tree (`exports/<name>.ics`, user ruling); the export's
    Browse (a save dialog to anywhere) is gone, the field takes a file name.
  - Week view: a block too short for two lines says "title, time" on one line (`week::block_lines`); its lines
    are clipped, not squeezed (`flex-shrink: 0`); the meeting line stays at any height.
- **AzTasks**
  - The task detail's "Custom..." repeat is the RecurrenceEditor (with the completion option, without end / nth
    weekday; `repeat_form.rs` converts `azul_pim::repeat::Repeat` both ways); the drop-downs, weekday buttons
    and four callbacks it replaces are gone. Typing the number does not rebuild the pane. The due-date and
    reminder DatePickers start on the week-start setting.
  - Theme and mode kept across restarts in `aztasks/settings.json` (azul-appkit's `AppSettings`; read before the
    window, `--theme` / `--mode` win for one run, saved through the write queue); the Mode control shows the kept
    choice (System included).
  - iCalendar VTODO import / export (`vtodo.rs`, on azul-pim's content lines and RRULE): Settings > Data >
    "Import and export": Import (path / Browse; read by a job thread; into the default list, after its tasks;
    `AZTASKS_IMPORTED <n> <path>`), Export (the list shown, else every task, to `aztasks/exports/<list>.ics` in
    the data tree through the queue; `AZTASKS_EXPORTED <n> <key>`). Reads DUE / DTSTART (date, floating, TZID
    wall time, UTC), PRIORITY, CATEGORIES, STATUS / COMPLETED, RRULE where a to-do's repeat can hold it; what it
    cannot read is said.
  - The window body is `ShellThemeScope::body()` (SMALL6; no UA margin); the list pane gets 0.6 of the room
    beside the reading pane (was 0.4), the navigation 0.22.
- **AzContacts**
  - The photo shows in the avatar (card, form, list rows): a `data:` URI decoded once (`RawImage::
    decode_image_bytes_any`, a 160 px thumbnail) for the contact shown and the form, kept by key (64 at most);
    a link / SVG / undecodable picture shows the initials.
  - The birthday on a DatePicker (a birthday without a year in 2000, so 29 February is on the grid), the year as a
    NumberInput, "Year unknown", "Add a birthday" - each writes the form's text field (kept).
  - CSV import with a column mapping (`csv.rs`): RFC 4180 quotes / line breaks, `,` `;` or tab, BOM; each column
    mapped by its Outlook / Google header (`guess`), changed per column in the import preview
    (`#import-column-<n>`, the rows are made again); then the vCard import's preview / Import.
  - The window body is `ShellThemeScope::body()`.
- **azul-pim** (ADDITIVE only): `write_queue` (AzTasks' write-behind queue moved whole; AzTasks re-exports it) and
  `data_uri` (standard base64 both ways, `data:` URIs; AzContacts' encoder twin removed).
- E2E scripts: `scripts/azcalendar_e2e.py` (editor stage on the RecurrenceEditor and "Save & Close never asks";
  new `close` and `occurrence` stages; the view lands in settings.txt), `scripts/aztasks_e2e.py` (export / import /
  Flora kept; restart count +1), `scripts/azcontacts_e2e.py` (birthday calendar + BDAY:--0101 in the file; a CSV
  import of 2 people with 5 mapped columns).

## api.json (module `widgets` unless named) - the RecurrenceEditor

Generate with `azul-doc autofix add` like CloseGuard's entries (its callback triple is the model).

- enum `RecurrenceFrequency` (repr C): `Never` (default), `Daily`, `Weekly`, `Monthly`, `Yearly`.
- enum `RecurrenceMonthly`: `DayOfMonth` (default), `Weekday`.
- enum `RecurrenceEnd`: `Never` (default), `AfterCount`, `OnDate`.
- struct `RecurrenceRule` (repr C; fields in this order): `start: DatePickerState`, `until: DatePickerState`,
  `interval: u32`, `count: u32`, `frequency: RecurrenceFrequency`, `monthly: RecurrenceMonthly`,
  `end: RecurrenceEnd`, `weekdays: u8` (bit 0 Monday .. bit 6 Sunday, 0 = the start's weekday),
  `from_completion: bool`.
  - constructor `create(start: DatePickerState)` -> `azul_layout::widgets::recurrence_editor::RecurrenceRule::create(start)`
  - `to_rrule(self: ref) -> String` -> `object.to_rrule()`
  - `from_rrule(rrule: String, start: DatePickerState) -> OptionRecurrenceRule` (static) ->
    `azul_layout::widgets::recurrence_editor::RecurrenceRule::from_rrule(rrule, start)`
- module `option`: `OptionRecurrenceRule` (made by `impl_option!` in the widget file).
- struct `RecurrenceEditorStateWrapper`: `inner: RecurrenceRule`, `on_change: OptionRecurrenceEditorOnChange`.
- struct `RecurrenceEditorOnChange` (`refany: RefAny`, `callback: RecurrenceEditorOnChangeCallback`) and
  `OptionRecurrenceEditorOnChange` (made by `impl_widget_callback!`).
- module `callbacks`: `RecurrenceEditorOnChangeCallbackType` = `extern "C" fn(RefAny, CallbackInfo, RecurrenceRule)
  -> Update`; module `dom` (as `CloseGuardOnEventCallback`): `RecurrenceEditorOnChangeCallback`; the managed
  callback statics of `impl_managed_callback!`: `AzApp_setRecurrenceEditorOnChangeCallbackInvoker`,
  `AzRecurrenceEditorOnChangeCallback_createFromHostHandle`, `..._createFromHostHandleByref`.
- struct `RecurrenceEditor` (repr C; fields in this order): `state: RecurrenceEditorStateWrapper`,
  `accessibility_name: OptionString`, `theme: OptionUiTheme`, `week_start: DatePickerWeekStart`,
  `completion_option: bool`, `end_option: bool`, `month_weekday_option: bool`.
  - constructor `create(rule: RecurrenceRule)`
  - `set_on_change(self: refmut, data: RefAny, callback: RecurrenceEditorOnChangeCallback)`,
    `with_on_change(self: value, data: RefAny, callback: RecurrenceEditorOnChangeCallback) -> RecurrenceEditor`
  - `set_week_start(self: refmut, week_start: DatePickerWeekStart)`, `with_week_start(self: value, ...) -> RecurrenceEditor`
  - `set_completion_option(self: refmut, shown: bool)`, `with_completion_option(self: value, shown: bool)`

## Decisions

- D1 RecurrenceEditor speaks RRULE text both ways; layout cannot depend on azul-pim, so its RRULE subset parser
  (and a `parse_basic_date`) is the one twin of `azul_pim::rrule` - kept, named here.
- D2 Weekday bits Monday first, 0 = the start's weekday; the editor's default week start Monday (RFC 5545 WKST).
- D3 AzCalendar's close veto is the app's own CloseRequested (state at close time); CloseGuard only shows the
  question (see INFRA6 above).
- D4 An occurrence edited alone becomes an independent event (new id, no repeat) and the series skips the day -
  the event file format has no RECURRENCE-ID; its .ics export is two unrelated events.
- D5 One write queue for the PIM apps (AzTasks' moved to azul-pim); AzCalendar runs two (data folder, task store)
  because they can be different roots. File threads start only from the main window (a thread started in the
  editor would answer a window Save & Close just closed).
- D6 Exports go into the data tree: AzCalendar `exports/<name>.ics`, AzTasks `aztasks/exports/<list>.ics`;
  AzCalendar's export Browse (a path outside the tree) removed.
- D7 AzTasks keeps its appearance in `aztasks/settings.json` (azul-appkit's file), not in the shared
  `tasks/settings.json` every app's To-Do bar reads.
- D8 AzContacts decodes photos only for the contact shown and the form (a list of 300 does not decode 300).
- D9 `__az<app>_` id / class prefix constants NOT done (coordinator: finishing over scope): ~300 ids across the
  three apps and five E2E scripts - one mechanical rename with the scripts, on SMALL6's `ids.rs` pattern.
