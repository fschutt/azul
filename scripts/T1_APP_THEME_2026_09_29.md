## 1. What an app gets

```rust
// startup (default "flat" = azul_css::dynamic_selector::DEFAULT_APP_THEME)
let config = AppConfig::create().with_theme("flora".into());
// runtime, from any callback: EVERY window's DOM is recreated under the new theme
info.set_theme("flat".into());
let now = info.get_theme();                  // AzString: the theme this window's DOM was built under
// in layout(): the theme being built for (branch STRUCTURE on it; CSS needs no branch)
let theme = info.get_theme_name();           // AzString
// in a widget's dom() (no info there):
let theme = azul_core::app_theme::current_theme();
```

```css
.card { padding: 8px; }                                  /* every theme */
@theme(flat)  { .card { background: #fff; } }            /* only while the app theme is flat */
@theme(flora) { .card { background: #f4efe6; }          /* only while it is flora */
                @theme(dark) { .card { background: #262521; } } }  /* flora's dark mode */
```

`@theme(light)` / `@theme(dark)` / `prefers-color-scheme` keep meaning the colour scheme. Any other
name is an app theme. A theme switch is a DOM RECREATION of every window (`RelayoutReason::AppThemeChange`),
never a restyle, because a theme may change a widget's structure. The colour scheme stays paint-only.

## 2. Design, with reasons

### 2.1 Found on the way: `@theme(flora)` used to apply everywhere

`parse_theme_condition` only knew `light` / `dark`. Any other name produced no condition, and an
@-rule block without conditions applies unconditionally. So before this branch, a widget's flora
block would have painted in every app, with the last block winning by source order.
`ThemeCondition::from_block_name` is now the one decision both parsers make:

- `light` / `dark` (any case) are the colour scheme.
- Any other name made of letters, digits, `-`, `_` and `:` becomes `Custom(name)`, kept as written
  and matched case-sensitively.
- An empty or malformed name is `None`.

The inline declaration parser also accepts the `theme(..)` spelling now.

### 2.2 A name, stored as a chain in the context

- **App choice: one `AzString`** (`AppConfig.theme`, `CallbackInfo::set_theme`). In the §7 design
  the chain is *derived* (AZ_THEME, prefix expansion, `fallback:` header, the app default as the
  floor). The app never sets a chain; it sets its theme. So the input is a name.
- **Matching context: `DynamicSelectorContext.theme_chain: StringVec`** (appended to the struct,
  not in api.json), which holds `[name]` today.
  - `Custom(x)` is live iff `x` is in the chain (`has_app_theme`).
  - It is never compared with the colour-scheme slot `ctx.theme`.
  - The context now has the shape §7 needs. The later refactor only changes how the chain is BUILT
    and adds rank to the sort key. The field type and the membership matcher stay the same.
- **`app_theme_chain(name)`** (css) is THE place the chain gets built.
  - §7's prefix expansion (`flora:pink` → `[flora:pink, flora]`), the `fallback:` list and the
    default floor all go there.
  - Deliberately no implicit default entry yet. Without rank in the sort key, a `[flora, flat]`
    chain would make flat's blocks compete with flora's by source order. It would also break
    "`@theme(flat)` only under flat". The doc comment on `app_theme_chain` says so.
- **`DEFAULT_APP_THEME = "flat"`** (css). This is the one spelling of the default. `AppConfig::create`,
  both context constructors and `azul_core::app_theme::app_theme()` all read it, so `native`
  becomes the default by changing that one line.

### 2.3 Where the state lives

| state | where | why |
|---|---|---|
| the app's choice | `azul_core::app_theme::{set_app_theme, app_theme}` (process-global `RwLock<Option<String>>`) | same reason as W4's `APP_COLOR_SCHEME`: a window opened after a switch starts in it. In core, not layout, so `LayoutCallbackInfo` (core) can fall back to it. |
| the theme a window's DOM was built under | `LayoutWindow::app_theme: AzString` | its cascade context reads this (`dynamic_selector_context` → `theme_chain`). Tests set it per window without publishing anything. |
| the theme the DOM being BUILT is for | `azul_core::app_theme::{ThemeScope, current_theme}` (thread-local scope, else the app's choice) | a widget's `dom()` has no `LayoutCallbackInfo`, but its structure may depend on the theme. Same seam shape as the style-dependency recorder. |

The engine enters the window's theme with `ThemeScope`:

- for the whole `regenerate_layout` pass (dll): `layout()`, the widgets it builds, VirtualViews
  laid out in that pass;
- around both form-control passes (`LayoutWindow::resolve_form_controls` and the one inside
  `style_user_dom_in_scope`), because those widgets are built AFTER `layout()` returned.

Outside a scope (an event callback building a fragment, a scroll-driven VirtualView),
`current_theme()` answers the app's choice. That is what every window shows once its pending
rebuild has run.

### 2.4 The name clash: `LayoutCallbackInfo::get_theme` is taken

`LayoutCallbackInfo::get_theme() -> DarkLightMode` is the colour scheme. It predates W4, W4 documents
it, and it declares `SystemStyleDependency::Theme`. The AzWidgets demo (untouchable here), azul-writer
and two test files call it. Changing its return type breaks all of them. So:

- **`LayoutCallbackInfo::get_theme_name() -> AzString`** is the name. It declares nothing, because
  a theme switch always re-runs `layout()`.
- **`CallbackInfo::get_theme() -> AzString`** is the name, as asked. That name was free.
- The two info types disagree on what `get_theme` means for now. It is type-safe in Rust/C, but a
  trap in Python. The fix belongs to the colour-scheme half of the AZ_THEME migration (§7.4 step 3):
  rename `LayoutCallbackInfo::get_theme` to `get_resolved_color_scheme` (the name `CallbackInfo`
  already uses), then make `get_theme` the name. Decision for Felix: do it then, or now with a
  one-line fix in the demo (`examples/azul-widgets/src/lib.rs:876`) and in
  `examples/azul-writer/src/lib.rs:871`.

### 2.5 The switch: one adoption point, no per-shell code

1. `CallbackChange::SetTheme { theme }` (dll `apply_user_change`) publishes the choice. If this
   window already shows the theme, it returns `DoNothing`.
2. Otherwise it calls `request_regeneration_all_windows()`. This is the existing registry walk on
   macOS, Win32, X11 and Wayland, the same fan-out `RefreshDomAllWindows` uses.
3. It drops this window's incremental caches, requests its rebuild tagged `AppThemeChange`, and
   returns `ShouldRegenerateDomCurrentWindow`.
4. `common::layout::regenerate_layout` is THE place a window adopts the theme:
   - If `layout_window.app_theme != app_theme()`, it takes the app's theme and tags the pass
     `AppThemeChange`, whatever tag its request carried (the walk asks with `RefreshDom`).
   - A window no walk reaches still adopts at its next rebuild. Unlike W4's colour scheme, this
     needs no per-shell `adopt_*` methods.
5. A theme rebuild takes the FULL path. The pre-cascade fingerprint skip and the
   layout-equivalence shortcut now step aside for `AppThemeChange`, as they already did for
   `ThemeChange`. Both keep the retained StyledDom without offering it the new context, and a
   migrated widget's DOM is usually identical across themes. The test
   `a_dom_identical_in_every_theme_still_repaints_in_the_new_theme` pins this.
6. `App::create` publishes `AppConfig::theme`. The E2E runner's `SetTheme` sets the window's theme,
   never the global one, and re-mounts the mounted document so the next pass rebuilds it.

Consequence of the one adoption point: in the dll, a window's `app_theme` follows the global at
every rebuild. A per-window theme pin (none exists) would need a flag that skips the sync.

## 3. Forward compatibility with §7 (where each later piece plugs in)

| §7 piece | where it goes | what stays |
|---|---|---|
| prefix chain `xyz:pink` → `[xyz:pink, xyz]`, `fallback:` header, default floor | `app_theme_chain` (css) | `theme_chain` field, membership matcher, `theme_conditions!`, every widget's blocks |
| rank in the sort key `(priority, rank, specificity, order)` | the cascade sort + inline resolution; rank = index in `ctx.theme_chain` | must land together with >1 chain entry |
| `AZ_THEME` = chain, `AZ_COLOR_SCHEME` = light/dark pin | seed `set_app_theme` from `AZ_THEME` in `App::create` (after `AppConfig::theme`, or as the head with the app theme as floor - decide), move the light/dark pin to `AZ_COLOR_SCHEME` | nothing here reads `AZ_THEME` today (untouched) |
| cascade-level `var()` | orthogonal: theme blocks set variables, consumers read them | - |
| rice loader over `css/<n>/` | wraps each file in `@theme(n)`; works with today's parser (`@theme(n)` is now a real condition) | - |
| `native` default | change `DEFAULT_APP_THEME` | - |

Spin-off names already survive parsing whole (`@theme(xyz:pink)` → `Custom("xyz:pink")`, tested).

## 4. The migration recipe (T2/T3 agents, per widget)

**Step 0, once, before the fan-out** (the parent or one agent). `layout/src/widgets/themes/mod.rs`
is a widget file, so I didn't touch it, and N agents adding it in parallel would conflict. Add:

```rust
impl UiTheme {
    pub const fn name(self) -> &'static str { match self { Self::Flat => "flat", Self::Flora => "flora" } }
    pub fn from_name(name: &str) -> Option<Self> { match name { "flat" => Some(Self::Flat), "flora" => Some(Self::Flora), _ => None } }
    /// The theme the DOM being built is for (the window's app theme); Flat for a name no widget knows.
    pub fn current() -> Self { Self::from_name(azul_core::app_theme::current_theme().as_str()).unwrap_or_default() }
}
```

Plus a test: `UiTheme::default().name() == azul_css::dynamic_selector::DEFAULT_APP_THEME`.

Also extend `widgets::theme_pairs::findings` (`layout/src/widgets/mod.rs`) to pair on the theme
name as well: `&& p.theme_names() == twin.theme_names()`. `is_light_half` already accepts a
theme-named light value.

**Per widget W** (Divider shown, the smallest; `divider.rs:191`):

```rust
pub fn dom(self) -> Dom {
    match self.theme.into_option() {
        // PINNED (`with_theme`): exactly today's path - that theme's structure and its
        // declarations UNCONDITIONED, so the pin holds whatever the app theme is.
        Some(UiTheme::Flora) => themes::flora::divider(self),
        Some(UiTheme::Flat) => themes::flat::divider(self),
        // FOLLOW THE APP THEME (the new default for None):
        None => {
            let structure = UiTheme::current();            // STRUCTURE only
            // node tree + marker class of `structure`, declarations of EVERY theme:
            //   [unconditional structural decls] ++ FLAT block ++ FLORA block
        }
    }
}
```

1. **Declarations: every theme's block, in two shapes.**
   - Const statics, the target the ledger asks for. One static per theme, each entry conditioned:

     ```rust
     static FLAT_FACE: &[P] = &[
         P::with_single_condition(bg(FLAT_BG), azul_css::theme_conditions!("flat")),
         P::with_single_condition(bg(FLAT_BG_DARK),
             azul_css::theme_conditions!("flat", DynamicSelector::Theme(ThemeCondition::Dark))),
         P::with_single_condition(bg(FLAT_HOT),
             azul_css::theme_conditions!("flat", DynamicSelector::PseudoState(PseudoStateType::Hover))),
     ];
     static FLORA_FACE: &[P] = &[ /* the same with "flora" */ ];
     ```

     Use the macro, not an inline `&[DynamicSelector::Theme(ThemeCondition::Custom(..))]`. A theme
     name is an `AzString` (it has a destructor), so an inline `&[..]` of one is never promoted to
     `'static` in an argument list and will not compile. The macro writes the `const` item. The
     theme name comes first, then dark, then the state (the compact cache flags a node dynamic from
     the FIRST non-pseudo condition, so keep the name first).
   - Runtime-built declarations (the `style_kit` / `decl` builders return `Vec`s):
     `flat_props.into_iter().map(|p| p.in_theme("flat")).chain(flora_props.into_iter().map(|p| p.in_theme("flora")))`.
     `in_theme` prepends the name and keeps dark and states.
   - Order on a node: unconditional structural declarations, then the flat block, then the flora
     block. The blocks are mutually exclusive, so their relative order is free, but state rules
     still go after resting ones within a block (last match wins, `style_kit` header).
   - Theme-independent declarations (display, flex direction, cursor) stay unconditional, once.
2. **Structure**: branch ONLY on `UiTheme::current()` (or `info.get_theme_name()` in app code). A
   node that exists only in flora's structure may carry just flora's block.
3. **Marker class**: the root keeps the marker of the structural theme
   (`style_kit::marker(structure)`). Live-restyle callbacks that read `theme_of_classes` then get
   the theme the widget was built for, which is the app theme.
4. **Pin (`with_theme`) = today's path, unchanged.** Keep today's generators as the pinned path.
   If a const static is shared between the pinned and the follow path, pin it with
   `p.without_theme_names()`. That strips the names and keeps dark and states.
5. **A caller-supplied style** (`container_style: Some(..)`, `divider_style: Some(..)`) stays
   unconditional. The caller chose it for every theme.
6. **Tests.**
   - Don't assert exact condition lists, like "`[Theme(Dark)]` and nothing else" (`button.rs:1878`).
     Evaluate through a context instead:
     `let ctx = DynamicSelectorContext { theme: ThemeCondition::Dark, ..Default::default() }.with_app_theme("flora");`
     then `props.iter().filter(|p| p.matches(&ctx))`, last match wins.
   - For structure tests, build under `let _t = azul_core::app_theme::ThemeScope::enter("flora".into());`.
   - Never call `set_app_theme` in the layout test binary (parallel tests).
7. **Order across the migration**: `None` now means "follow the app", and the default app theme is
   flat. So an app that chose nothing looks exactly as before, and pinned widgets are untouched.
8. **Demo (D1)**: once widgets are migrated, the widget-theme toggle becomes
   `info.set_theme(if flora { "flora" } else { "flat" }.into())`, and every `.with_theme(state.theme)`
   comes off. Otherwise each widget stays pinned and the toggle only works through the pin.
   `LayoutCallbackInfo::get_theme` in the demo stays the colour scheme (2.4).

**Sharp edge until §7's floor lands**: `set_theme("monokai")`, a name no widget knows, makes every
widget's flat AND flora blocks inert. Widgets then render their unconditional structure only, and
their structure falls back to Flat. Until the chain gets the default floor (with rank), only set
themes the widgets know. Alternatively, the migration could keep flat as the unconditional base
and emit only `@theme(flora)` overrides. That is safer today, but switching the default to `native`
would then mean re-migrating, so I did not recommend it.

## 7. Open questions / follow-ups

1. **FLIP on a theme switch.** `dll/.../common/layout.rs` sets
   `pending.animate_moves = relayout_reason != Resize`. A theme switch moves most widgets (padding
   and radii differ), so every widget would slide to its new place. Recommend treating
   `AppThemeChange` like `Resize` ("no state change, reflow in place"). It is one line, but I left
   it out because it had no test. Decide.
2. **Naming**: `get_theme_name` on `LayoutCallbackInfo`, `get_theme` on `CallbackInfo` (2.4).
3. **The unknown-theme sharp edge** (4, end). It goes away with §7's floor plus rank.
4. `CssMockEnvironment` has no app-theme override. Screenshot runs use `AppConfig::with_theme` or
   `set_app_theme`. Add one if reftests need to vary it.
5. No E2E op to switch the app theme (`e2e/full.rs:2984` only overrides light/dark). The runner
   handles `SetTheme` when a callback queues it.
6. Case: names are case-sensitive (`@theme(Flora)` does not match `flora`), like CSS custom
   idents, and consistent with the existing `match_theme_custom_compares_the_name`. Only
   `light` / `dark` are case-insensitive.

## 8. Least sure to compile

1. `azul_css::theme_conditions!`. `const CONDITIONS: &[DynamicSelector] = &[Theme(Custom(AzString::from_const_str($name))), $($c,)*]`
   inside a block, inside `static` initializers in external crates (css, layout and dll tests). It
   relies on lifetime extension of a const item's outermost `&[..]` holding a type with drop glue.
   Existing statics do the same (`static ROW_STYLE: &[CssPropertyWithConditions] = &[..]`), so it
   should hold.
2. `core/src/app_theme.rs`: `std::thread_local!` + `RefCell<Option<AzString>>` in a
   `#[cfg(feature = "std")] mod state`; the `const { .. }` initializer; `static RwLock<Option<String>>`
   (const `RwLock::new`).
3. `css/src/dynamic_selector.rs`: `rest.starts_with(char::is_whitespace)`, the nested or-pattern
   `ThemeCondition::Light | ThemeCondition::Custom(_)` in `is_light_half`, and
   `map_or(DEFAULT_APP_THEME, AzString::as_str)`.
4. `layout/src/window.rs`: `let _ = { let _theme = ThemeScope::enter(..); resolve_form_controls_in_dom(..) };`
   under `#[cfg(feature = "widgets")]`.
5. The test files' imports: `azul_css::props::layout::{LayoutWidth, LayoutHeight}`,
   `props::style::{StyleBackgroundContent, StyleBackgroundContentVec}`, and `ColorU::rgb` being
   `const` (it is).
6. The api.json-vs-Rust parity checks (codegen or doc) will flag `AppConfig.theme`,
   `RelayoutReason::AppThemeChange` and the new methods until autofix runs (6).
