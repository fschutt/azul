## 1. What was built, item by item (root causes)

### Item 1 - the table's used width (CSS 2.1 17.5.2.2)

- **Root cause (the 2886 px newsletter table):** `calculate_used_size_for_node` gave an auto-width
  `display: table` its MAX-content width whatever its containing block. A `width` smaller than the
  columns' minimum was taken as is.
- **Fix (`sizing.rs`):** auto width = `max(MIN, min(MAX, available))` (`available` = the containing
  block minus the table's margins, border, padding - the shrink-to-fit helper the floats use); after
  the box-sizing conversion the border box of every table is floored at `MIN + padding + border`
  (a `width: 10px`, a `max-width` cannot squeeze a table below its columns).
- **The intrinsic sizes behind MIN / MAX (`sizing.rs calculate_table_intrinsic_sizes`):** now the
  column model of `table_width` (below): a cell's own `width` makes its column constrained or a
  percentage column, `<col>`/`<colgroup>` widths count, the max-content is percentage-aware (a 50 %
  column of 100 px makes an auto table 200 px), the cell spacing (one per gutter, the outer two
  included) is part of it, and a caption's min-content is a floor (CAPMIN).
- **The intrinsic pass's definite-width override** (`calculate_intrinsic_recursive`) flattened a
  TABLE CELL's content sizes to its `width`; it no longer touches cells (the column algorithm reads
  the width itself and a width does not lower a column's minimum), and a table with a width
  contributes `max(width, MIN)`.
- **The layout (`fc.rs layout_table_fc`):** it re-resolved the table's `width` against its own
  content box (a percentage of the wrong box) and gave the WHOLE content width to the columns, so the
  spacing came on top and the laid-out table was wider than its used size. It now reads the used
  border box its formatting context's parent decided (`used_size`, set by
  `calculate_layout_for_subtree` / taffy / the abspos path before the table runs; the old resolution
  only when a measurement set none) and the columns share the content width minus the spacing.
- **UA (`core/src/ua_css.rs`):** HTML's `table { box-sizing: border-box; border-spacing: 2px;
  border-color: gray }` (a `<table width="600" border="1">` is 600 px outside; unstyled cells sit
  2 px apart). `BorderSpacing` joined `UA_PROPERTY_TYPES`.
- **One border-spacing resolution:** `fc::resolve_table_border_spacing` (0 when collapsed or
  anonymous) replaces two copies in `fc.rs` (layout_table_fc and position_table_cells) and serves the
  intrinsic sizes.

### Item 4 - percentage, fixed and auto columns (CSS Tables 3 3.8 / 3.9)

- **Root cause:** `calculate_column_widths_auto_with_width` gave every column a share of the excess
  in proportion to its max-content whatever its `width` said, and read no percentage:
  `<td width="100">a</td><td>a</td>` in a 400 px table came out 200 / 200 (WPT
  `table-cell-width-s`).
- **Fix:** new module `layout/src/solver3/table_width.rs`, the ONE implementation for the intrinsic
  sizes and the layout:
  - `ColumnConstraint { min, max, percent, constrained }`, `ColumnAccumulator` (cells -> column),
    `specified_width` (a cell's / col's `width` as a border-box length or a percentage),
    `column_element_widths` (`<colgroup>` / `<col>`);
  - `clamp_percentages`: percentages over 100 % are cut back left to right;
  - `table_min_max`: CSS Tables 3 3.9.1 (the percentage estimate);
  - `distribute_to_columns`: the four sizing guesses of 3.9.3 (min-content, min-content-percentage,
    min-content-specified, max-content), interpolated between the two the target falls between;
    the excess beyond the max-content guess goes to auto columns by max-content (equally if all are
    empty), else fixed columns, else percentage columns by percentage, else everyone.
  - Unit tests in the module.
- Step 2 of `calculate_column_widths_auto_with_width` builds the constraints from the measured
  min/max (Step 1, unchanged) plus the cells' and cols' widths and calls `distribute_to_columns`.

### Item 5 - nested tables

- **Root cause:** `calculate_table_intrinsic_sizes` measured every cell as an inline formatting
  context (`calculate_ifc_root_intrinsic_sizes`); a cell whose content is a table (or any block) has
  no inline content, so the outer table's min/max-content ignored the inner table and a shrink-to-fit
  outer table came out narrower than the table it holds.
- **Fix:** a cell's sizes are the ones the bottom-up pass stored on it (its block content's,
  including a nested table with its spacing, padding and border, counted once); the IFC measurement
  is only the fallback for a cell with no stored sizes. The layout path (the min/max-content
  measurement lays the cell out) already saw the inner table; with item 1 the inner table measures
  to its MIN / MAX under a min/max-content constraint.

### Item 2 - row groups, rows, columns, caption

- **Root cause (`tbody` 119/119 boxes missing; postmark receipt `tr` at y=2 instead of 1152):**
  `position_table_cells` returned the CELLS as the table's only positioned descendants, relative to
  the table itself; rows and row groups were kept at no position (a "don't add rows, it would
  double-offset the cells" workaround). Rows got a size, row groups none, columns none. And
  `analyze_table_structure` walked the children in document order, so a `<tfoot>` before the
  `<tbody>` was laid out on top.
- **Fix (`fc.rs`):**
  - rows are numbered in VISUAL order: the first header group first, the first footer group last
    (CSS 2.1 17.2);
  - `place_table_grid_boxes`: every grid box is placed relative to its PARENT's content box like any
    box - row groups, rows directly in the table and column groups are the table's positioned
    children (its `LayoutOutput.positions`); a row in a group is relative to the group, a cell to its
    row, a `<col>` to its group. A row spans the grid's columns (the outer spacing is outside it), a
    group its rows, a col its column, a colgroup its columns, over the rows' height;
  - the caption is laid out as the block box it is (`calculate_layout_for_subtree`, so it has a size
    and a box) inside its margins; a top caption moves every other positioned child down; the
    table's baseline is its first row's.
- **`cache.rs`:** on a layout-cache hit a table's children are positioned
  (`position_bfc_child_descendants`), never laid out again - a row group re-laid out as a block
  would wreck the grid. (Before, a hit re-laid every CELL out at the table's width with the cell's
  max-content as its box: a latent bug the old cell-only map hid.)
- **`display_list.rs`:** a table paints its own background AND border through the ordinary box
  painting (background images, shadow and radius included; the border is left to the resolved grid
  when collapsed), then `paint_table_items` paints layers 2-6. Its own border was never drawn in the
  separated model before (WPT `table-row-group-001`: the 2 px frame missing). A row's background now
  covers the row's box (it was the bounding box of its cells).

### Item 3 - presentational attributes

- **Root cause:** the attribute table (`core/src/xml_attributes.rs`) had no entry for `width height
  bgcolor border bordercolor cellpadding cellspacing align valign nowrap`; both XML loaders dropped
  them, so `<table width="600" cellpadding="0" cellspacing="0" bgcolor="#fff">` laid out as an auto
  table with the UA spacing and no background. There was no existing align/bgcolor mapping in the
  engine (only AzMail's sanitizer rewrote a few app-side).
- **Fix:**
  - the attribute table gains `AttributeScope::Tags(&[..])` and one entry per presentational
    attribute that KEEPS it on the node verbatim (`AttributeType::Custom`) - an app reads `<td
    width>` like any attribute, a built `Dom` with the attribute renders like markup, the code
    generator writes `.with_attribute(..)`;
  - `azul_core::xml::attributes::presentational_css(tag, attributes, enclosing_table)` is HTML's
    rendering-section mapping: dimension values (ignoring zero; a row's height keeps zero), legacy
    colours (`ff0000` without `#` is red), `border` (unparsable = 1 px; table `outset` frame, cells
    1 px `inset`, `solid` with a `bordercolor`; `border="0"` nothing), `bordercolor`, `cellspacing`
    -> `border-spacing`, `cellpadding` -> the cells' padding (own table only), `align` (table: float
    or auto margins; caption: caption-side or text-align; else text-align, `middle` = center),
    `valign`, `nowrap`;
  - `apply_presentational_hints(node_data, hierarchy)` runs at the start of
    `StyledDom::create_from_compact_dom` (every way to a `StyledDom` passes there) and puts the
    declarations IN FRONT of each element's inline style, so its `style` attribute still wins;
  - the inherited half of `align="center"` (`-webkit-center`): `fc.rs
    centers_blocks_the_legacy_way` + `layout_bfc` center a block child with no auto margins inside a
    `div / caption / thead / tbody / tfoot / tr / td / th` with `align=center|middle` (walking up while
    the computed `text-align` stays center) - the newsletter's `<td align="center"><table
    width="600">` centers the 600 px table.
- **Decision (unattended):** the attributes go through the attribute table, not the builtin
  components' arguments. Ruling A routed `href` (an element ARGUMENT) through the component; a
  presentational attribute is style the cascade derives, and the table-to-cell hints
  (`cellpadding`, `border`) need the enclosing table, which only a pass over the whole DOM has. If
  the user wants them declared as component fields too, that is additive.
- **Known deviation:** HTML ranks hints below every author stylesheet rule; azul's inline
  declarations outrank the stylesheet, so a stylesheet rule cannot override a hint yet (e.g. a mail's
  `@media (max-width: 600px) { .container { width: 100% !important } }` against `<table
  width="600" class="container">` - azul has no `!important` either). Fix later: a cascade layer for
  hints between the UA and the author sheet (`prop_cache.rs restyle`).

## 7. Notes for TABLE-B (their functions, not touched beyond what is listed)

- `calculate_column_widths_fixed` still receives the table's content width WITHOUT the spacing
  subtracted (`separated-border-model-003b/004a/004b` need it subtracted, and `col` widths from
  `table_width::column_element_widths` are available).
- Step 1 of `calculate_column_widths_auto_with_width` (the measurement, `distribute_cell_width_
  across_columns`) is unchanged; Step 2 is new. The intrinsic sizes' spanning-cell split moved with
  the rewrite of `calculate_table_intrinsic_sizes` (same even split, now on `ColumnConstraint`s) -
  if B changes the span rules, change both (or move them into `table_width`).
- A cell's min-content measurement of a fixed-width cell (`measure_cell_content_width`) lays its
  text out inside the cell's specified width (`calculate_used_size_for_node` gives the cell its CSS
  width), so a `<td width="100">long words</td>` column's minimum is its widest line at 100 px, not
  its longest word.
- Cells are now positioned relative to their ROW (and rows to their group): code that read a
  cell's `relative_position` as table-relative must add the row's. In this tree nothing else did
  (`paint_collapsed_table_borders` uses absolute paint rects).
- `paint_table_items` no longer paints layer 1; the table's border in the collapsed model is
  suppressed in the box painting (`table_is_border_collapsed`), as before.
