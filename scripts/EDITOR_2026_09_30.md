### Latent bug found (fixed with E-SET)

`shift_carets_across_generation` keyed its text snapshot by the host's contenteditable key only. A
session that moved to ANOTHER block of the same host (an arrow across paragraphs - E-ARROW, a click
into the next paragraph, the reset's caret) was diffed against the OLD block's text on the next layout
pass, and the two paragraphs' difference shifted a caret nothing had edited. The snapshot now carries
the block element too (`Option<(u64, NodeId, Vec<InlineContent>)>`).

### Twins found

- `document_selection_replacement`'s local `element` closure and the new `element_shell` were the same
  clone; one helper now (refactor commit).
- `ClipboardExtract` computed bold / italic inline; `StyleProperties::is_bold` / `is_italic` are the
  one rule now (the typing style and the rebuilt blocks read it too).
- The empty-run seed of `apply_one_text_changeset` is `seed_empty_run` (the inline paste needs it).
- `insert_text_with_line_breaks` is `insert_formatted_text` with no span.

## Behaviour changes to watch in the battery

- Plain arrows now cross blocks: any scenario / test that pressed Right at a paragraph's end (or
  Down on its last line) inside a multi-paragraph host and expected the caret to stay will move.
- Ctrl/Cmd+B / I / U in a rich host is a default action now (`ToggleTextFormat`); an app that used
  those keys through `VirtualKeyDown` without `prevent_default` also gets the engine's typing style.
- The cross-block delete's ReplaceChildren carries the ends' inline elements instead of one text run
  (AzWriter's applier is `apply_document_operation`, unchanged; an app that parsed the payload as one
  text child must read the subtree).
- The dll's default paste is `LayoutWindow::paste_clipboard_content`; with an HTML flavour it may
  record a structural edit (`ShouldIncrementalRelayout`) where it used to insert text.
- `ClipboardContent.html` is `Some` for any paste whose source offered HTML.
- `caret_text_snapshot` is a 3-tuple.

## What is left

- The paste's HTML goes through the XML loader's STRICT parser: markup with unquoted or boolean
  attributes (old Outlook, some Word pastes) does not parse and falls back to the plain text. The
  AzMail sanitizer (html5ever, app-side) can normalize before handing HTML on; a lenient azul HTML
  mode is E-XML-1.
- `<pre>` white space, `<font color>`, colours and sizes of pasted text are not carried (four formats +
  links + blocks only); tables paste as their cells' text.
- Ctrl+B over a SELECTION is still the app's (its model holds the runs; `get_document_selection`
  names the spans). The engine keeps the collapsed caret's typing style only.
- Backspace at the start of a quote's first paragraph records nothing (the mail rule "lower the quote
  level" is app-side, as the task said); the spec would outdent.
- `reset_editor_content` places the caret at a block edge only; an app wanting it elsewhere calls
  `move_cursor` / `set_selection` after its re-render.
- The e2e runner has no `paste` op (the dll's `PasteFromClipboard` path reads the OS clipboard); the
  paste tests drive `LayoutWindow::paste_clipboard_content` directly. A `paste_html` op would let a
  scenario paste markup headlessly.
