# TABLES - table layout at Chrome parity, wave 5 (2026-10-02)

Branch `wt/tables`, cut from `2e92c759b`. Nothing was compiled (house rule): every Rust file was
parse-checked with `rustfmt --edition 2021 --check` / `--emit stdout` (no new formatting diffs; the
remaining diffs in fc.rs, sizing.rs, cache.rs, layout_tree.rs are pre-existing). The parent compiles,
runs section 5 and re-measures the mail corpus.

**How the numbers below were obtained without compiling:** a probe (scratchpad `tables/probe.py`) lays
a snippet out in headless Chrome 154 AND in the prebuilt engine at the base (AzPaint's debug server,
`mount` op, one capped app per case) and prints both rects per id. Every RED test states Chrome's
numbers and was checked RED against the prebuilt engine. The prebuilt layout test binary
(`target/release/deps/all-978bc4fd9634d150`) ran the existing `table` tests at the base: 166 passed.

Caveat found on the way: the debug server reports an inline-block inside a table cell's line at the
cell's content origin. That was a real engine bug (item 3.4 below), not a reporting one.
