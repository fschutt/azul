# MAILHTML - mail HTML/CSS parity with Chrome (wave 5, 2026-10-02)

Branch `wt/mailhtml` from `2e92c759b`. Nothing was compiled (house rule); every Rust file was
parse-checked with `rustfmt --check`. The corpus work read the parent's baseline
(`target/refci/mail-baseline-2e92c759b`: both engines' boxes per mail, `chrome.html` = the
sanitized markup) and ran the prebuilt `azmail-sanitize` under a memory cap. The parent
re-measures with `scripts/refci/mail_boxes.py`.

## 1. What was built (root causes, per corpus finding)

Every item is RED test first, then the fix. Expected movement per mail is in section 2.

### 1.1 `max-height` clamps an auto height (cerberus x3, the first divergence)

- **Finding:** Cerberus hides its preheader as `<div style="max-height: 0; overflow: hidden">`.
  Chrome: 0px. Azul: 97px (its text), and every box below it 97px too low (cerberus-fluid's
  first divergence, and the y +97 behind most of the three Cerberus mails' mismatches).
- **Root cause:** `calculate_layout_for_subtree_fragment` (cache.rs, Phase 2.5) replaced the
  pre-layout placeholder height - which the sizing pass had clamped by min/max-height - with
  `max(placeholder, content)` (`apply_content_based_height`) and never applied `max-height`
  again. CSS 2.2 10.7: the content height is only the tentative height.
- **Fix:** new `sizing::clamp_auto_block_size` (min/max on the content box under
  `content-box`, on the border box under `border-box`; either axis, by writing mode) built on
  the existing `apply_height_constraints` / `apply_width_constraints`; Phase 2.5 calls it after
  the content-based height. Not for table boxes (CSS 2.2 17.5.3 leaves min/max-height
  undefined there; Chrome ignores max-height) nor for inline (non-replaced) boxes, recognised
  by their `display` (a first version excluded `FormattingContext::Inline`, which is ALSO a
  block that establishes an IFC - the preheader itself; fixed in `cf6f441bd`).
- Test: `layout/tests/an_auto_height_block_stops_growing_at_its_max_height.rs`.

### 1.2 `ex` and `ch` lengths (Gmail's quote indent)

- **Finding:** 02_gmail_reply: every quote level is `<blockquote style="margin: 0px 0px 0px
  0.8ex; border-left: 1px solid ...; padding-left: 1ex">`. Azul: quoted text 33px too far
  right and 12-16px too low.
- **Root cause:** `parse_pixel_value_inner` (css pixel.rs) knew no `ex` / `ch`, so the whole
  `margin` declaration was invalid and the blockquote kept the UA `1em 40px`.
- **Fix:** where a caller accepts `em`, `ex` and `ch` parse as half an em - CSS Values 4 6.1.1's
  fallback when the font's measure is not at hand (lengths are parsed without their font).
  No new `SizeMetric` (that is an FFI enum; see section 6).
- Tests: `css` lib `ex_and_ch_lengths_are_half_an_em`;
  `layout/tests/a_gmail_quote_is_indented_by_its_ex_margin.rs`.

### 1.3 Helvetica / Times / Courier line heights (postmark x3, "web fonts falling back")

- **Finding:** postmark's `"Nunito Sans", Helvetica, Arial` falls back to Helvetica in both
  engines. Chrome: a 16px line 18px, a 22px heading 25px. Azul: 16 and 22. Every postmark box
  below the first heading drifted up (y -5 and growing).
- **Root cause:** Apple's Helvetica has hhea 1577 / -471 / 0 at 2048 upem: `line-height:
  normal` is exactly 1em. Every browser on macOS adds 15% of ascent + descent to the ascent of
  Times, Helvetica and Courier (WebKit `SimpleFontDataMac`, Blink
  `FontMetrics::AscentDescentWithHacks`) to match the Microsoft fonts the web was made with.
- **Fix:** `font::parsed::browser_compat_ascent(postscript_name, ascent, descent)`, used by
  `ParsedFont::from_bytes_internal` for the layout metrics. Matched by the PostScript family
  (part before the first `-`): `Helvetica*`, `Times-*`, `Courier*` - Helvetica Neue
  (`HelveticaNeue`), Times New Roman and Courier New keep their metrics.
- Tests: `layout` lib `font::parsed::autotest_generated::helvetica_times_and_courier_get_the_
  browsers_ascent_adjustment` and `apples_helvetica_parses_with_a_line_height_like_arials`
  (the second checks the real `/System/Library/Fonts/Helvetica.ttc` and does nothing where
  the file does not exist).

### 1.4 The strut is the first available font (Gmail / Apple Mail blank lines)

- **Finding:** 02_gmail_reply / 05_apple_mail_reply write every blank line as
  `<div><br></div>`. Chrome: as tall as a text line (18px, 16px Arial). Azul: 16px, so every
  blank line was 2px short.
- **Root cause:** `translate_to_text3_constraints` (fc.rs) approximated the strut as 0.8 / 0.2
  em (the TODO said so): no line gap, not the font's proportions. A line holding only a break
  is the strut's `line-height: normal` tall.
- **Fix:** `fc::first_available_font_strut` resolves the IFC root's font chain to its first
  loaded face (the font manager's chain cache and parsed fonts, as `shape_placeholder_text`
  does) and gives the strut that face's ascent and descent at the root's font size, each with
  half the line gap: `normal` is then A + D + gap (a text line's height), while an explicit
  line height sees only the half-leading, which the shared gap does not move. The 0.8 / 0.2
  estimate stays while no face of the chain is loaded.
- Test: `layout/tests/a_blank_line_is_as_tall_as_a_line_of_text.rs`.

### 1.5 Only a link is underlined

- **Finding:** postmark invoice: "support team" (an `<a>` whose `{{support_url}}` href the
  sanitizer dropped) plain in Chrome, underlined in azul.
- **Root cause / fix:** the UA table underlined every `<a>`; HTML 15.3.4 underlines `:link`.
  The underline moves from the `A` element row into `ua_css::get_ua_link_property` (with the
  link colour and cursor). The old pin in `ua_css_test.rs` is updated.
- Test: `core` lib `ua_css::ua_css_test::only_an_a_with_an_href_is_underlined`.

### 1.6 An unresolved `<img>` from markup takes no space (DEDUP_EDITORS A3.8)

- **Root cause:** an `<img src>` whose picture nobody supplied yet is the loaders' `NullImage`
  tagged with its src; the sizing pass gave it the CSS 300x150 fallback - a hole for every
  pending (and every failed) download in AzMail.
- **Fix:** sizing.rs, the Image arm of the intrinsic sizes: an image whose layout image
  (`image_for_layout`, the cached picture or the placeholder) still has a `source_tag` and no
  natural size is 0x0, as a browser lays out a not-yet-available image without dimension
  attributes. `width`/`height` attributes still give it its box (they are the placeholder's
  size); render-callback images and VirtualViews keep 300x150. The display list still carries
  the placeholder with its src.
- Test: `layout/tests/an_unresolved_img_from_markup_takes_no_space.rs`.

### 1.7 `!important` no longer invalidates a declaration

- **Root cause:** the value parsers read `red !important` as the value and rejected it; mail
  CSS marks half its declarations important. (`mso-*` and unknown properties were already
  skipped one by one without dropping their rule - verified, and covered by the new test.)
- **Fix:** `parser2::strip_important` in `parse_declaration_resilient`, the one entry of the
  sheet parser and of `style` attributes (`!` + `important`, any case, white space allowed).
  The flag's PRECEDENCE is not modelled (section 5).
- Test: `css` lib `parser2::autotest_generated::an_important_declaration_keeps_its_value`.

### 1.8 DEDUP_EDITORS B20: AzMail reads mail with the engine's HTML parser

- `examples/azul-mail/src/html.rs` lost its own tokenizer (`run`, `parse_attributes`), its
  implied-end-tag repair (`implied_ends` / `close_item` / `pop_through`, `BLOCK` / `INLINE`)
  and its character references (`decode_references` + a ~150-name table + Windows-1252) -
  about 360 lines. The mail is parsed once by `Xml::create_from_html` (core's lenient
  tokenizer + `TreeBuilder`, `TreeRules::Html`) and the POLICY runs as a walk over the
  `XmlNode` tree: the drop list, the style-sheet scoping, dark-rule detection, image
  blocking, tracking pixels, the depth bound. Output is balanced by construction.
- What changes because the tree is now a browser's (each updated test is commented): a stray
  end tag closes nothing inside a cell; `</p>` alone is an empty `<p>`; a misnested `<i>`
  goes on after `</b>`; rows get their implied `<tbody>`; cells and rows outside a table are
  ignored; `&#0;` is U+FFFD; all 2231 named references decode; the `<body>` every document now
  has becomes a `div` only when it carries a kept attribute; a `<style>`'s raw text is no
  longer reference-decoded (HTML does not decode inside `<style>`).
- RED test: `the_sanitizer_builds_the_tree_a_browser_builds` (AzMail lib).

### 1.9 Presentational attributes reach azul's own HTML hints (legacy HTML)

- **Finding:** the sanitizer turned `align` / `bgcolor` / `width` into a subset of CSS (so
  `<table align=center>` became `text-align: center` - not a centred table) and dropped
  `cellpadding`, `cellspacing`, `border`, `bordercolor`, `height`, `nowrap`. Since TABLE-A/B,
  core's `xml::attributes::presentational_css` maps all of these exactly where Chrome does:
  the sanitizer's mapping was a second generator of the same CSS (NO DUPLICATION).
- **Change:** those attributes pass through as written on the elements they are written on
  (`PRESENTATIONAL`); `html_length` and the align/valign/bgcolor arms are gone. Where the
  sanitizer renames an element the engine cannot see them, so their meaning becomes style:
  `<body bgcolor text>`, `<font color face size>` (HTML's legacy font sizes 1-7, `+n`/`-n`, at
  a 16px medium: 10 13 16 18 24 32 48px), and a kept picture's `align` (float /
  vertical-align), `hspace` / `vspace` (margins) and `border`.
- RED test: `presentational_attributes_mean_what_they_mean_in_a_browser` (AzMail lib).
- Note for the measurement: the corpus' tables now carry `cellspacing="0" cellpadding="0"
  border="0" align="center"` in BOTH engines (before, both used the UA defaults); boxes move in
  both, so compare per box, not only the totals.

## 8. What is left (wave 6)

- **Chrome rounds font metrics** for `line-height: normal`: `lroundf(ascent) +
  lroundf(descent) + lroundf(lineGap)` (Blink `SimpleFontData::PlatformInit` /
  `FontMetrics`): Arial 16px is 14 + 3 + 1 = 18px, azul 18.4px. Every `normal` text line of a
  mail drifts 0.4px (10 lines = 4px = the tool's tolerance): the largest non-table drift left
  in the Gmail / Apple / postmark mails. Text engine (TEXTENG's line-height area).
- **TEXTENG:** text lines under an explicit `line-height: 20px` stack at 20.78 (cerberus,
  15px text; their item 1), and a DOM with ANY `line-height` gives every node without one
  `1.2em` instead of `normal` (`translate_to_text3_constraints`: the DOM-wide
  `DOM_HAS_LINE_HEIGHT` flag + `StyleLineHeight::default()` = 120%; their item 2's enum
  should carry `Normal`).
- **Percentage heights against an auto-height parent** (CSS 2.2 10.5: they compute to auto).
  Azul resolves them against the inherited available height (`layout_bfc`'s
  `children_containing_block_size`, the `height_is_auto` branch) - Chrome's quirks-mode
  behaviour. Mail templates' `body { height: 100% }` (mapped onto the paper) makes the paper
  exactly one viewport tall in azul, the mail overflowing below its background (mailgun x3
  azr-1/2, postmark x3, cerberus). NOT changed this wave: 49 `height: 100%` sites in apps and
  widgets may rely on it, and judging that needs a compiled build and the apps' E2E runs.
- **`!important` precedence:** the flag is now ignored instead of fatal; making an author
  `!important` beat inline styles needs a priority above `INLINE` for sheet rules, but
  `push_front_scope_for` treats every rule at or above `INLINE` as node-only - a separate
  importance flag on `CssRuleBlock` (an api.json struct) is the clean way.
- **`ex` / `ch` from the font** (the x-height, the advance of "0"): needs `SizeMetric::Ex` /
  `Ch` (an api.json enum) resolved where the font is known; today the 0.5em fallback.
- **The alt text of a broken picture:** Chrome shows it inline; azul lays it out 0x0.
- **AzMail policy, for the user to decide:** the sanitizer drops `class` and `id` but keeps the
  mail's class-based `<style>` rules (scoped to the paper) - they can never match (a mail's
  `.x` dark rules included). Keeping classes needs a prefix (`m-x`, rules rewritten) so that a
  mail cannot reach the app's own class names.
- **Engine presentational hints for `font`, `img`, `hr`, `body text`:** core's
  `presentational_css` has none; the sanitizer converts them for AzMail. With an engine
  generator the sanitizer could pass those through too (and printpdf's HTML would get them).
- **DEDUP_EDITORS B21** (the safe-link scheme list x3: AzMail compose.rs `safe_link`, html.rs,
  layout `paste_html.rs` `safe_href`) and the proposed exported `HtmlSanitizePolicy` remain.
- **Foster parenting:** text directly inside a `<table>` (postmark's `{{#each}}` template
  markers) stays where it is in core's tree builder; Chrome moves it before the table.
