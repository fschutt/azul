## 1. What azul drew, and why (measured)

- On macOS both CSS `system-ui` and the widgets' `system:ui` end at `/System/Library/Fonts/SFNS.ttf`
  ("System Font"): ONE variable font, axes wdth / opsz 17-96 (default 28) / GRAD / wght 1-1000, with
  an AAT `trak` table. CoreText's UI font (`CTFontCreateUIFontForLanguage`, also
  `CTFontCreateWithName("System Font", s)`) - what System Settings draws - is that file at
  **opsz = the point size** (clamped: everything up to 17pt is "SF Pro Text") **plus the `trak`
  tracking at that size on every glyph advance**. azul drew the DEFAULT instance (opsz 28, the
  tighter "SF Pro Display" spacing) untracked at every size.
- "Hello world agenda", Chrome 154 / CoreText / azul before:
  13px 116.27 / 116.26 / 104.24; 16px 139.16 / 139.15 / 128.29; 20px 168.02 / 168.01 / 160.36;
  28px 231.41 / 231.40 / 224.51; 40px 327.41 / 327.40 / 320.72; bold 16px 148.63 / 148.60.
  Chrome = CoreText to 1/64 px. Model check (fontTools): opsz instance advances + trak = CoreText
  exactly from 28px up; 0.2-0.35px wider below (one kern pair, "wo", -40 units at opsz 17 through
  a GPOS variation delta that a baked static instance does not carry).
- Chrome 154: `BlinkMacSystemFont` = `system-ui`; `-apple-system` is unknown to Chrome 154 (a lone
  one falls to Times); Safari draws it as the system font.
- Prebuilt AzPaint (production registry path), 16px: `system-ui` 128.30, `'System Font'` 128.30,
  Helvetica 136.98, `BlinkMacSystemFont` / `-apple-system` 136.98 (Helvetica: unknown names fell to
  sans-serif) and **`font-family: system:ui` written in markup 136.98** - the style attribute was cut
  at its second colon (`system`), see 2.6.
- Width change for the apps (new / old, SF regular): 11px x1.14, 12px x1.13, 13px x1.12, 14px x1.10,
  16px x1.09, 20px x1.05, 24px x1.03, 28px and up x1.02-1.03. Line heights do not change (hhea

## 2. What was built

1. **AAT tracking** (`font.rs` `parsed::Tracking`): `ParsedFont::tracking` holds the `trak` table's
   normal track (point size -> font units, linear between sizes, the end values beyond, offsets from
   the table start). `text3/default.rs` `shape_text_internal` adds it (scaled) to the advance of every
   glyph that starts a piece of the text and has an advance of its own (not zero-width marks, not
   multiple-substitution duplicates - HarfBuzz tracks per grapheme; CoreText puts it on the advance,
   no half offset). Only Apple's system faces carry the table (SFNS, SFNSItalic, SF Compact /
   Rounded / Hebrew ..., New York, Apple Color Emoji); Helvetica / Helvetica Neue / Menlo have none.
2. **Optical sizing** (CSS Fonts 4 `font-optical-sizing: auto`, as Chrome and CoreText):
   `FontSelector::optical_size` / `FontChainKey::optical_size` (whole CSS px, 0 = default;
   `text3::cache::optical_size_for(px)`); `getters::at_optical_size` - THE one place a stack gets it -
   is applied by `get_style_properties`; the font-stack collector keys its representatives on
   (family, weight, style, optical size) and builds each stack at that size.
   `getters::select_variable_instances` / `variable_instance` (were the weight-only
   `select_variable_weight_instances` / `variable_weight_instance`) bake a variable FILE at
   (wght, opsz clamped to the axis) through ONE bake, `font::parsed::bake_instance` (the old
   `bake_weight_instance` / `read_wght_axis` are thin calls of it / `read_variation_axis`).
   Memoised per process by the baked coordinates (11-17px share SF's opsz-17 instance) and per face
   for its axes. An instance is registered under a name of its own ("System Font @ wght 700 opsz
   17"), so no family query ever returns an instance in place of the file (a chain for another size
   would otherwise get one and keep it).
3. **The font-stack signature** (`window.rs`, the font block of `layout_and_generate_display_list`,
   minimal edit): it hashed only the per-node FAMILY hashes, so a relayout that changed only sizes
   (a zoom, a heading that grew) or weights kept the old chains and the runs whose key no chain had
   shaped to nothing. Each node's weight, style and specified font size go in beside its family.
4. **A covering face that is not loaded** (`text3/cache.rs` `split_text_by_font_coverage`): a chain
   resolved after the layout loaded its faces names faces no one loaded; the run was put on such a
   face and shaped to nothing. It now takes the chain's next loaded face with the glyph (then any
   loaded face, the existing order), and the call counts as short of its font
   (`note_font_shape_deficit`), so it is not cached and a pass with the face loaded shapes again.
5. **One `system-ui`**: `font::loading::browser_generic_families` sets the `system-ui` generic to
   `SystemFontType::Ui`'s chain (css/src/system.rs - ONE list): "System Font" (macOS / iOS),
   "Segoe UI Variable Text" then Segoe UI (Windows; the Windows 11 Settings font), Roboto (Android);
   on Linux a `system-ui` alias of the desktop's fontconfig stays first and the list follows it.
   `prefer_system_ui_font` / `use_system_ui_font` put the desktop's own UI font first; the dll calls
   it on Linux with the detected `SystemStyle::fonts.ui_font` (GNOME / KDE setting) at the first
   layout (`dll/src/desktop/shell2/common/layout.rs`, minimal edit). `build_font_selector_stack`:
   `system:ui` / `system:ui:bold` and, on Apple platforms, `BlinkMacSystemFont` / `-apple-system`
   (`is_apple_system_ui_alias`) build the one `system-ui` selector (bold at 700). `system:title`,
   `menu`, `small`, `monospace`, `serif` keep their named lists.
6. **Style attribute colons** (`core/src/xml_attributes.rs` `style_declarations`, minimal edit):
   `split_once(':')` - the value keeps every later colon (`font-family: system:ui`,
   `url(https://...)` were cut to `system` / `url(https`).
