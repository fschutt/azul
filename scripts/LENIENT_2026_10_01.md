# LENIENT - real-world HTML parses; builtin elements take their arguments; the paste parser

Branch `wt/lenient`, from `16d19442c`. Nothing was compiled (house rule). The new core module
(`core/src/xml_html.rs`) and the hint functions were type-checked with `rustc --emit=metadata`
and `clippy-driver -W clippy::pedantic -W clippy::nursery` on a stub harness (the analogue of
the allowed `clang -fsyntax-only`; nothing linked or run); every Rust file was parse-checked
with `rustfmt --check`. The tree construction's behaviour was checked against Chrome through a
line-by-line Python mirror of the Rust (`scratchpad/lenient/mirror.py`) and headless Chrome
(`scripts/refci/cdp.py`).

## What was built

### 1. LENIENT: HTML as a browser reads it, and ONE tree construction for every loader

**Root cause.** azul had no HTML parser: both XML loaders tokenized with `xmlparser` (an XML
tokenizer that rejects unquoted attributes, `--` in comments, `<` in values, control
characters) and each built its tree with its own rules. AzMail had to turn mail into XHTML in
the app; the paste parser fell back to plain text for Word.

**Where it is fixed: our own layer in azul-core**, not `xmlparser` (RazrFalcon's crates.io
crate; a vendored fork would need a `[patch]`, which the release gate forbids). The brief
allowed both and preferred this.

`core/src/xml_html.rs` = `azul_core::xml::html`:

| Piece | What it does |
|---|---|
| `HtmlTokenizer` | Never fails. Unquoted and bare attributes (`width=150`, `noshade`), a repeated attribute keeps its first value, upper-case names folded, `<` that starts no tag and `&` that starts no reference are text, comments end at `-->` or `--!>` whatever they hold (`<!-- ---- -->`, `<!-->`), doctypes / `<?xml?>` / Word's `<![if !supportLists]>` skipped anywhere, raw text for `style script xmp iframe noembed noframes plaintext`, RCDATA for `title textarea`, CR LF and a lone CR as LF, C0 controls dropped, a tag cut off by the end dropped. |
| `decode_character_references(s, CharRefMode)` | ONE decoder. `Xml` (the strict loaders): `;` required, a number that is not a scalar stays as written. `HtmlText` / `HtmlAttribute`: the HTML Standard's algorithm - legacy names without `;` (`&copy 2026`), the longest legacy prefix (`&notit;` is `¬it;`), the attribute rule (`?a=1&copy=2` keeps its query), the Windows-1252 repair (`&#150;` is an en dash), invalid numbers as U+FFFD. |
| `core/src/xml_entities.rs` | The HTML Standard's whole table: 2231 names (106 legacy, 93 two-character), generated by `scripts/gen_html_entities.py` from Python's `html.entities.html5`. `html_named_entity` (MAILVIEW's 252-name table is gone) and `prepare_string`'s decoder read it too. |
| `TreeBuilder` + `TreeRules` | The tree construction. For every rule set: void elements (the full HTML list incl. `keygen basefont bgsound frame param`), implied end tags (`p` closed by every block, `li`, `dt` / `dd`, `option` / `optgroup`, `tr` / `td` / `th`, `thead` / `tbody` / `tfoot` / `caption` / `colgroup`, headings), an end tag closes up to its element only within the element's scope (a stray `</div>` inside a cell does not close the cell, the row and the table; an unmatched one is ignored), a misnested formatting end tag (`<b><p>x</b>`) closes its element when the block inside it closes (simplified adoption), text runs merged across dropped markup. `TreeRules::Html` adds what a browser repairs: the implied `<html>` / `<head>` / `<body>` (a fragment is a document; head content before the body goes into the head, after it into the body), the implied `<tbody>` / `<tr>`, `</p>` without `<p>` is an empty paragraph, `</br>` is `<br>`, table parts outside a table are ignored, `</body>` / `</html>` are ignored (content after them stays in the body), a second `<html>` / `<body>` is dropped, the formatting elements are reopened in the next block (`<p><b>x<p>y`: y is bold; Noah's Ark: at most 3 equal ones), a link closes an open link, `<x/>` is empty only for void elements and inside `<svg>` / `<math>`, one LF after `<pre>` / `<textarea>` is dropped, the depth limit (512, as Blink) flattens deeper elements. |
| `XmlTreeSink`, `parse_html_into`, `parse_html_nodes` | The `XmlNode` tree (no raw-pointer stack any more). |
| `outline(nodes, with_attributes)` | A tree as one line (`html{head body{p{"Hi " b{"you"}}}}`): the format of the tests and of Chrome's trees. |
| `is_void_element`, `start_tag_closes` | The rules, for others (the builder asks them). |

**Checked against Chrome.** The Python mirror of the Rust builds Chrome's `DOMParser` tree
(head and body, attributes included) for **16 of the 18** corpus mails; the other two
(Postmark invoice / receipt) differ only in foster parenting (template text between table
rows, which Chrome moves in front of the table; their ELEMENTS are Chrome's). Of the 46 rows of
the core test, 39 are Chrome's tree; the 7 others are annotated in the test: comments are nodes
in Chrome (text runs split there, merged here), control characters are dropped on purpose, and
the three simplified-adoption cases.

**The loaders** (`layout/src/xml/mod.rs`):

| Loader | Tokenizer | Rules | Sink |
|---|---|---|---|
| `parse_xml_string` / `parse_xml` (tree, strict) | `xmlparser` via `feed_xml_tokens` | `TreeRules::Xml` (names as written) | `XmlTreeSink`; still `UnclosedRootNode` for an element left open or a tag cut off |
| `parse_xml_to_fast_dom` / `parse_xml_to_styled_dom` (document, strict) | `xmlparser` via `feed_xml_tokens` | `TreeRules::XmlFolded` | `FastDomSink` (the arena; `<head>` hidden, every `<style>` collected and no node, inside `<svg>` what draws nothing hidden) |
| **`parse_html_string` / `parse_html`** (tree, lenient) | `HtmlTokenizer` | `TreeRules::Html` | `XmlTreeSink` |
| **`parse_html_to_styled_dom`** (document, lenient) | `HtmlTokenizer` | `TreeRules::Html` | `FastDomSink` |

`styled_document` is the tail both document loaders share (stylesheet merge, cascade,
`AZ_PROFILE=memory` phases). `decode_xml_entities` is core's decoder in `CharRefMode::Xml`.

### E-XML-3: the two loaders' differences, resolved

| Difference (MAILVIEW) | Now |
|---|---|
| Tag case: the tree loader's DOM builder read `TABLE` with `normalize_casing` (`t_a_b_l_e`, a div); also `linearGradient` -> `linear_gradient`, `transient-window` -> `transient_window` | Both DOM builders (`xml_node_to_dom_fast`, `xml_node_to_fast_dom`, `collect_style_text`) read names ASCII-lower-cased; the strict tree keeps XML's case in `node_type`. |
| Implied end tags: only the tree loader had them (for the top element only) | One rule set (`TreeBuilder`) for both, scope-based. |
| A stray end tag closed EVERY element in the document loader | Ignored by both (scoped search). |
| `</o:p>` closed the enclosing `<p>` in both (they matched the LOCAL name) | Qualified names (`o:p`) on start and end tags. |
| Foreign `o:p`: dropped with its text by the tree loader, a block in the document loader | Both: `element_draws_nothing` applies only inside `<svg>`; elsewhere a foreign-prefixed tag is HTML's unknown element, inline (`tag_to_node_type` -> `Span`, `is_foreign_element`). Outlook's `<o:p>&nbsp;</o:p>` keeps its empty paragraph one line tall. |
| Inside `<svg>`, `<metadata>` and editor elements: dropped by the tree loader, drawn by the document loader | Hidden by both. |
| `<style>` text: the tree loader decoded references, the document loader did not | Both decode (XML). |
| `<transient-window>` configured only by the document loader | Both (`apply_xml_node_attributes` applies `open=` / `anchor=` / ... and `tearoff-zone`). |
| An element left open at the end: the tree loader errors | Kept on purpose: the strict tree loader's contract (pinned by `parse_xml_string_rejects_unclosed_elements`); the document loader and the lenient loaders close. |
| A `<style>` in the body: the tree loader scopes it to its parent, the document loader applies it to the document | The node is gone in both; the scope still differs (see "What is left"). |

The builder's twins of the parser's rules (`layout/src/e2e/builder.rs` `VOID_ELEMENTS`,
`AUTO_CLOSE`) are gone: it asks `is_void_element` / `start_tag_closes` (its copy missed what
closes a `<p>` beyond 25 blocks).

### 2. COMPONENTS: the builtin elements take their arguments

Per the ruling (components take their declared arguments) each attribute below is DECLARED in
the element's builtin data model (`builtin_data_model`), filled by the one filler
(`data_model_with_attributes`) and landed by the element's render side:

| Element | Declared (new in bold) | Landed as |
|---|---|---|
| `ol` | start, type, **reversed** | `list-style-type`; counting up: `counter-reset: list-item <start-1>`; counting down: `reversed` / `start` attributes the layout's numbering reads |
| `ul` | **type** | `list-style-type` (disc / circle / square) |
| `li` | **value**, **type** | `Value` attribute (the item's number; the next ones count on); `list-style-type` |
| `img` | src, alt, width, height, **align, border, hspace, vspace** | `float` (left / right) or `vertical-align` (top / middle / bottom ...), `border: Npx solid`, margins, a percentage `width` / `height` (a number stays the loader's intrinsic size) |
| `font` | **face, size, color** | `font-family`, `font-size` (legacy 1..7, +n, -n: 10 13 16 18 24 32 48 px), `color` (`#rgb`, `rrggbb` without `#`, names) |
| `center` | - | `text-align: center` |
| `div p h1..h6` | **align** | `text-align` |
| `body` | **bgcolor, text** | `background-color`, `color` |

- `builtin_presentational_hints(tag, attributes)` (core/src/xml.rs) returns the CSS (each value
  sanitised: one CSS value or nothing); both DOM builders put it BEFORE the element's `style`
  attribute (`apply_settings`' `intrinsic` slot), so the element's own style wins: core's
  `apply_xml_node_attributes` (the tree loader and the builtin render fn `builtin_dom`) and
  layout's `open_fast_node` (the document loader).
- `apply_builtin_element_args` lands `ol` reversed / start and `li` value as attributes.
- `compute_counters` (layout/src/solver3/cache.rs): an `<ol reversed>` counts down from its
  `start` (else its number of `<li>`), tracked per scope depth so a nested list counting up is
  unaffected; an `<li value>` sets the counter after its increment (HTML's `counter-set`).
- **list-style-position: inside**: the longhand reaches the marker (`fc.rs` reads it per item;
  REFCI's WPT runs paint inside markers inline). What never reached anything was the SHORTHAND:
  the CSS parser had no `list-style`, so `list-style: inside` and every newsletter menu's
  `list-style: none` were dropped. `CombinedCssPropertyType::ListStyle` now expands to type +
  position (omitted parts reset to `disc` / `outside`; `none` is the type). MAILVIEW's
  observation may also come from AzMail's sanitizer, whose style allowlist has
  `list-style-type` but not `list-style-position` (MAIL2's file; for them).
- **Table attributes** (`width height border cellpadding cellspacing bgcolor align valign nowrap
  bordercolor` on table / td / th / tr) are TABLE-A's: not touched here (note for TABLE-A:
  `builtin_presentational_hints` is the place a `td` / `table` hint would go, next to these).

### 3. The paste parser on the lenient loader

`layout/src/paste_html.rs` reads `parse_html_nodes` (also without the `xml` feature). Word's
flavour (unquoted attributes), a web page's open `<p>` and LibreOffice's `<BR>` now paste with
their bold / italic / underline / strike, links, paragraphs, line breaks and lists. `<o:p>` is
inline. Word's list paragraphs (`style='mso-list:lN levelM lfoK'`), one after the other with
the same list id, become one list - ordered when the `mso-list:Ignore` marker is a number or
letters before `.` / `)`, else unordered - and the marker element is dropped.
