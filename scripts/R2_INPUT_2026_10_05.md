## Per item

### I1 - the e2e protocol has no paste op (FIX9-INPUT 3.8)
- **Root cause:** every debug op changes state through a `CallbackChange`, because full.rs only holds a
  `CallbackInfo`. No change could stage clipboard content and run the paste. In the dll, a Ctrl+V reads
  the real OS clipboard, and the runner has no clipboard at all.
- **Fix:**
  - layout/src/callbacks.rs: new `CallbackChange::Paste { content: ClipboardContent }` and the
    test-facing pusher `CallbackInfo::simulate_paste(content)`.
  - layout/src/e2e/full.rs: new `DebugEvent::Paste { text, #[serde(default)] html: Option<String> }`.
    Its arm builds `ClipboardContent { plain_text, html, styled_runs: empty }` and pushes the change.
    Without a focused node it refuses by name, like `text_input`.
  - Both hosts get the same arm: runner.rs `Runner::apply_paste`, and the arm in the dll's
    `apply_user_change` (event.rs, next to `SetSelectAllRange`). It mirrors the dll's deferred
    clipboard block, but the content is handed in:
    1. `clipboard_manager.set_paste_content`;
    2. dispatch `EventType::Paste` at the focus (or the root, like the dll);
    3. unless a callback calls `prevent_default`, run `LayoutWindow::paste_clipboard_content`, then
       `apply_pending_text_and_reveal()`. A plain paste only RECORDS its text, and an op has no pass
       after it to land that text;
    4. `clear_paste()`.
  - `PasteOutcome` maps to a result the way the dll's `PasteFromClipboard` arm does, and a
    RefreshDom from a Paste callback becomes `ShouldRegenerateDomCurrentWindow`.
  - doc/src/gene2e.rs: OP_POLICY row `("paste", None)`.
- **RED tests (layout/src/e2e/runner.rs `tests`):**
  - the existing `a_scenarios_paste_op_pastes_bold_html_into_the_focused_editor` (un-ignored);
  - the new `a_paste_callback_that_prevents_default_keeps_the_scenarios_paste_out_of_the_editor`. It
    has a non-vacuous premise: without the veto, the same scenario lands "pasted".
- **Verify after the build:** both tests pass, and `gene2e every_real_op_is_classified` passes.
  - If the plain-text half of the veto test fails its PREMISE, look at `process_text_input` with the
    focus on a host whose text sits in a child `<p>`. The bold-HTML test covers the
    `paste_inline_formatted` path instead.
  - A live check: `{"op":"paste","text":"x"}` against an AZ_DEBUG app with a focused TextInput.

### I2 - `set_copy_content`'s doc (FIX9-WIDGETS round 2 item 6)
- The old doc said the content applies only "if preventDefault() was not called". The dll's
  `SetCopyContent` arm actually writes it as soon as the callback's changes are applied, regardless.
- What `prevent_default` really decides is whether the engine's DEFAULT copy runs after the
  `On::Copy` callbacks. That default writes the current selection OVER the override when there is a
  selection.
- The doc now says both: the content is written after the callback returns, from any callback. In an
  `On::Copy` callback, also call `prevent_default` to make it stick (like the web's `setData` plus
  `preventDefault`).
- No RED, because this is a doc change. ASCII only.

### I3 - tests drain each other's request completions
- **Root cause:** one static Mutex queue serves the whole process, and every drainer takes everything.
  The drainers are the http.rs and dialogs tests, request.rs's own tests, and the e2e runner's pump
  inside the parallel runner tests.
- **Fix (option a):** under `cfg(test)` (azul-layout's own unit tests only), `queue::with_queue` serves
  a `thread_local!` RefCell queue.
  - Each completion is issued on the calling thread (`complete`) or polled by the pumping thread
    (`defer`; the http worker thread only answers the poll's channel).
  - The dll, the integration tests (layout/tests) and product builds keep the process-wide queue.
  - The module doc says so. So does the http test comment that said "the queue is process-wide".
- **RED:** request.rs `a_tests_completion_is_not_drained_by_a_test_running_beside_it`. Thread A
  completes, thread B drains, and A must still find its entry.
- **Verify:** `cargo test -p azul-layout --features e2e-server --lib` (request, http, dialogs, runner)
  is no longer flaky.
- **Limit:** layout/tests/e2e_json.rs (integration) still pumps the process-wide queue. If a race ever
  shows up there, the next step is a `test-support` feature or an env switch instead of `cfg(test)`.

### D2 - `focus_node` delegates like the engine (user decision 2026-10-05, option b)
- **Root cause:** the op checked the ASKED node with its own `is_focusable`. That was a second answer
  to "who takes the focus", next to the engine's `resolve_focus_target`.
- **Fix (full.rs):** the op now asks `resolve_focus_target(FocusTarget::Id(asked), layout_results,
  None, focus_out_of_scope_doms())`.
  - It pushes the same `set_focus(FocusTarget::Id(asked))` that an app's call pushes.
  - It answers `FocusNodeResponse.node_id` = the node that took the focus.
  - It errors only when the resolver keeps a node that cannot hold focus (nothing focusable inside
    it) or when the node does not exist.
  - The `DebugEvent::FocusNode` doc is updated.
- **RED (runner.rs tests):** `focus_node_on_an_unfocusable_row_focuses_its_first_focusable_descendant`.
  - `.row` (a label plus a contenteditable field): the focus must land on `.field`, and the step's
    response must carry its id.
  - `.label` (nothing focusable inside): the scenario must still fail.
