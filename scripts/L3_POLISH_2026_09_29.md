## 1. The debugger / AzBuilder page has a light and a dark mode

**The page** (`dll/src/desktop/shell2/common/debugger/`):

- Every colour is a token on `:root` in `debugger.css`. The light palette is the default. The
  dark palette is ONE `@media (prefers-color-scheme: dark) { :root { .. } }` block, so the
  page follows the desktop.
- The hard-coded colours became tokens too, in `debugger.css` and in the styles that
  `debugger-dnd.js`, `debugger-project.js` and `debugger-export.js` inject:
  - syntax colours (`--syn-*`) and the type-badge hues (`--hue-*`);
  - the component and dataset badges;
  - the checkerboards behind pictures (`--checker-a/-b`) and the thumbnail backdrop
    (`--thumb-bg`, `--thumb-loading`);
  - text on the accent (`--on-accent`), the strongest text (`--text-strong`), the gutter
    (`--text-faint`) and hover tints (`--tint`).

  Shadows, modal backdrops and the box-model diagram keep their literal colours: they read
  the same in both modes.
- **The toggle.** The menu bar has an Auto / Light / Dark radio group. Its logic is
  `app.mode` in `debugger.js`:
  - `init` runs before `window.onload`, so a pinned mode does not flash;
  - the choice is stored in `localStorage['azul_debugger_mode']`, with every access inside
    try/catch;
  - `set(choice)`, `isDark()` and `onChange(fn)` are the API the other scripts use.

  Pinning a mode rewrites the dark block's media condition through the CSSOM: `all` for dark,
  `not all` for light. Auto puts the query back, and follows the desktop live
  (`matchMedia` change). This keeps ONE dark palette, instead of a second copy under
  `:root[data-mode=dark]`. `<html data-mode>` records the choice.
- **Found while doing it:** ten token names the panels use were never defined:
  - `--bg`, `--bg-alt`, `--bg-darker`, `--bg-secondary`, `--hover`;
  - `--fg`, `--fg-muted`, `--text`;
  - `--font-mono`, `--accent-rgb`.

  So the D5 context menu (`.azd-context-menu`) and the code popup (`.azd-popup`) had
  TRANSPARENT backgrounds in dark mode too. These names are now aliases of the tokens. This
  gives a few `.azd-*` boxes a background they did not have before (`--bg-alt` = the sidebar
  surface).

**The palette thumbnails** are rendered in the page's mode:

- `get_component_thumbnail` takes `dark: bool` (serde default false, so old callers are
  unchanged).
- In `builder.rs`, `BuilderSession::thumbnail(.., dark)` calls the new
  `preview_in_dark_mode` when `dark` is set:
  - it cascades the detached preview under the window's context
    (`LayoutWindow::dynamic_selector_context`), with `mode = Dark` and the dark `system:`
    palette (`SystemStyle::colors_for_theme`);
  - the component CSS is then applied under that context;
  - it renders on the dark content background (`SystemColorRef::Background` resolved for
    dark), where the light render uses white.
- The mode is part of the cache key.
- A light thumbnail renders exactly as before: no context, on white.
- In `debugger-dnd.js`, `loadThumb` sends `dark: app.mode.isDark()`. On a mode change,
  `repaintThumbs` asks for every picture again. `S.thumbGen` drops answers that arrive for
  the old mode.
- `OP_POLICY` (`doc/src/gene2e.rs`) already has the op's row. An added argument needs no
  change there.

## 2. V2 P2: a node restyled to other variables resolves them

In `apply_node_style_change` (`layout/src/window.rs`), "changed" was decided by
`changed_property_types`. That function reads `iter_inline_properties`, which skips `var()` /
`env()` references and `--x` definitions. A style that differed only there was stored,
`Unchanged` came back, and nothing was recascaded.

The fix is in that one place. `changed_property_types` became `changed_declaration_keys`:

- It compares EVERY declaration, keyed by `CssDeclaration::get_type()`: the property type,
  or `None` for the custom-property definitions.
- If a changed key is resolved by the variable pass (a definition, or a property with a
  `Dynamic` declaration on either side), the chokepoint runs `StyledDom::restyle` of the
  retained author sheet. That is the author cascade with its variable pass, and it ends with
  the same UA / inheritance / compact tail. Other changes keep the tail-only
  `recascade_ua_inheritance_and_compact`.
- A changed definition gives the `Relayout` tier, as `CssDeclaration::can_trigger_relayout`
  says for definitions.
- Override clearing matches `Some(ty)`.

## Left / findings

- **`get_component_preview` ignores `override_theme`, `override_os` and `override_lang`.**
  They are deserialized (`full.rs` `DebugEvent::GetComponentPreview`) and never read. The
  Components view's preview mode picker (`app.state.previewTheme`) therefore does nothing.
  `preview_in_dark_mode` could serve `override_theme: "dark"`. That needs its own RED.
- **Icons in a dark thumbnail resolve against the light system style.**
  `crate::xml::style_detached_dom` takes no context. Threading one through
  `styled_dom_resolving_icons_with_context` would fix it.
- **A dark thumbnail evaluates `@media` width rules against the window's viewport.** It uses
  the window's context. A light thumbnail has no context, so no conditional rule applies.
- **Twins (NO DUPLICATION):** four base64 decoders exist:
  - `e2e/project.rs` `decode_base64` (now shared with builder_tests);
  - `e2e/project_tests.rs` `base64_decode`;
  - `e2e/full.rs` `base64_decode_for_shot`;
  - the one in `callbacks.rs` tests.

  They could fold into one next to `callbacks::base64_encode`.
- **`form_controls::targets_the_node_itself` accepts structural pseudos** (`*:first-child`).
  `lower_node_pseudo_states` leaves those in selector form, so such a rule, moved into the
  node's own style, still applies unconditionally. This predates this task. It is C2's
  "near-twin" note.
- The slash-command parser (`debugger.js`) has no boolean parameter type. From the terminal,
  `dark` can only be sent as JSON (`{"op": "get_component_thumbnail", .., "dark": true}`). So
  the slash schema was not extended.
- The B7 screenshots `dnd-*-light-*.png` were taken while the page had no light mode, so they
  are dark. `builder-dnd-indicator-smoke.mjs --shots <tag>` would retake them. They were
  left as B7's record.
- `app.init` reads `localStorage['azul_debugger']` without try/catch. This predates this
  task and was not touched.
