## `<form>` -> `Form`

- A raw `NodeType::Form` (Rust `Dom::create_form*`, XML `<form>`) becomes `Form::create(content)`;
  the Form records its INITIAL values from the still-raw content (= the HTML defaults), then the
  content is resolved INSIDE it at the same tree paths (memory keys unchanged). A node that already
  is a Form (dataset is a `FormStateWrapper`: app-built, or an earlier pass) is left alone, which
  also keeps the pass idempotent.
- It keeps the raw form's BLOCK layout (`container_style: display: block`, not the Form widget's
  flex column + gap), id / class / attributes, inline style; its scoped sheets stay scoped (a bare
  `* {..}` on a form keeps reaching its whole content). The marker is `data-azul-form-control="form"`.
- **Handler mapping (the decision):** every `Hover(Submit)` callback of the raw form is carried into
  the Form's `on_submit`, every `Hover(Reset)` callback into `on_reset` (one trampoline each,
  `run_carried_submit` / `run_carried_reset`, running the carried plain callbacks in attach order
  and returning the strongest `Update`). They now run whenever the Form submits / resets - submit
  button click, Enter in a text field (implicit submission), the engine's own Submit / Reset event -
  EXACTLY once: they are NOT left on the form node as well (the engine dispatches Submit to every
  Submit handler on the node, so they would run twice). They receive the `CallbackInfo` of the
  triggering event (hit node = button, field or form) and read the values with the new
  `widgets::form::collect_form_data(&mut info, info.get_hit_node())`, which finds the enclosing
  form from any node. Every other callback on the raw form is carried to the Form node as before.
- `submit_form` / `reset_form` now clone the app callback OUT of the `FormStateWrapper` before
  invoking it (a handler that reads the form would otherwise find the state borrowed).

## Reset vs memory

- Every replaced control that holds a value carries `data-azul-form-key="<u64>"`
  (`MEMORY_KEY_ATTRIBUTE`) on its root; each build REGISTERS that key in `FormControlMemory`
  (bounded + LRU like the values) with: the entry its user value lives under (its own; a named
  radio's group), how its value is spelled, the value it was built with, and its default.
- `reset_form` walks the form's rendered subtree (the contiguous descendant run - named or not),
  calls `FormControlMemory::reset_control(key)` for every key (forget the user value, roll the
  built value back to the default) through `CallbackInfo::get_layout_window().form_control_memory`,
  BEFORE the app's `on_reset` runs, and adds `Update::RefreshDom` when any held a user value (a
  replaced checkbox / slider / drop-down shows its default only by being rebuilt from the app's
  unchanged DOM). An untouched form's reset still asks for nothing.

## FormData of replaced controls

- `form_controls::default_value(kind, spec)` is now THE default of every value-bearing control
  (build uses it too; `resolved_value` applies the remembered user value when it fits the control -
  a radio group's remembered value becomes each radio's checked flag). `Spelling::spell` turns a
  `FormValue` into HTML's form-data string: checkbox / radio -> their `value` ("on" by default) only
  while checked; select -> the chosen OPTION VALUE; range / number -> the number (`"5"`); colour ->
  hex; date / month / week (ISO) / time / datetime-local -> HTML's formats; file -> the path, `""`
  when nothing is picked (HTML's empty file entry).
- Submit (`current_form_data`): the widget's live state first (TextInput text, now also a
  TextArea's, DatePicker, DateTimeLocal), then `FormControlMemory::submission(key)` by the root's
  key (the user's latest value, else the built one), then the `value` attribute.
- Initial values (`collect_initial`): a RAW child contributes `default_submission(child)` (its HTML
  default in the same spelling) - W1's path took a checkbox's `value` whether checked or not.
- Disabled and empty-named controls are left out of both (HTML's form data set rules).

## `<datalist>`

Every datalist gets `display: none` PREPENDED to its inline style (the app's own display still
wins), is not walked into, and a page with a datalist but no control is walked too (prepass
`has_datalists`). Idempotent (a second pass finds the rule in place).

## What is left / known gaps

- ENGINE GAP (W1's, unchanged): text typed through the engine's uncommitted overlay outranks the
  rebuilt DOM until the app acks it, so after a reset + rebuild a replaced text input can still show
  the typed text. The reset tests type through the widget's change hook (memory), not the overlay.
- The E2E XML mount (`xml::parse_xml_to_styled_dom_resolving_icons`) resolves with a FRESH memory,
  so its replaced checkbox / slider / select registrations are not in the window's memory: FormData
  falls back to the value attribute (none) for them and a reset forgets nothing there. Fix: let that
  helper take the window's `FormControlMemory`.
- A raw `<button type=submit|reset>` element (`NodeType::Button`) is not replaced, so inside a raw
  form it does not submit / reset on click (Enter on a reset `<button>` does, via the engine). A
  `("<button>", ..)` row mapping `type` to `ButtonFormAction` would close it.
- A raw `<form>`'s own dataset is dropped (the Form node's dataset is its `FormStateWrapper`).
- `prevent_default` on the engine's Reset event does not stop W1's reset (the Form resets inside
  that dispatch); carried handlers run after the Form's own reset work, like W1's `on_reset`.
- `type=image`: no image is loaded from `src`; no click coordinates (`name.x` / `name.y`).
- The initial `invalid` list for raw defaults is not computed (valid = true); a submit's validity
  comes from the live TextInput state as before.
- ComboBox: its recorder is `on_select`, so text typed without picking from the list may not reach
  the memory - FormData then shows the built value (unverified).
- Two raw radios of one group both `checked`: both show checked on the first build (W2, pre-existing).
- `<select multiple>`, disabled `<option>`s, file `accept` / `multiple`: unchanged (not supported).
- Parent: compile; run `layout --lib` (form_controls + widgets::form unit tests) and
  `layout --test all` (form_controls_become_widgets); the AzWidgets demo and api.json (autofix for
  `collect_form_data` if it should reach FFI) are untouched.
