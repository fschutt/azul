# PIMDRIVE7 - Calendar / Tasks / Contacts / Drive / Meet (wave 7, 2026-10-03)

Branch `wt/pimdrive7` from `2e55eef06`. Nothing was compiled (house rule): every touched `.rs` file parses
(`rustfmt --emit stdout`), every Python script byte-compiles, `mint-and-join.mjs` passes `node --check`. The LOOK and
the E2E scripts ran against the PREBUILT binaries (the wave-6 integration = this base), capped, one at a time.
Interrupted once by a network drop; resumed from `scripts/PIMDRIVE7.PROGRESS.md`.

## 1. What was built, item by item

### 1. The prefixes (ruling; PIM6 D9)
- `examples/azul-calendar/src/ids.rs`, `examples/azul-tasks/src/ids.rs`, `examples/azul-contacts/src/ids.rs`: every
  DOM id and class once, `__azcal_` / `__aztasks_` / `__azcontacts_` + the old kebab name (AzCalculator's `names!`
  macro, `const AzString` via `AzString::from_const_str`). Names made at run time (a calendar row, a day, an
  occurrence `event-<id>-<yyyymmdd>`, a task row / check box / section / step, a contact form row, an import
  column, a letter's section) come from one function per stem in the same module (AzContacts: an `indexed!`
  macro). Each module has a test that every name carries the prefix.
- All UI files use them; helpers that took an id `&str` take the `AzString`. Gone: `views_ui::occurrence_dom_id`,
  `timegrid::WEEK_SCROLL_ID`, `ui::section_id` (AzContacts). AzCalendar's DOM root `azcalendar` is
  `__azcal_app`; the window ids `azcalendar` / `azcalendar-editor` are window names and stay. AzTasks' key rule
  asks `ids::is_task_row` (the old `starts_with("task-")` also took `task-list` / `task-pane` for a row).
- The scripts: `scripts/azcalendar_e2e.py`, `examples/azul-calendar/scripts/{week_interactions,offline_links}.py`
  (`wi.sel(stem)`), `examples/azul-calendar/scripts/mint-and-join.mjs` (`cal(stem)`), `scripts/aztasks_e2e.py`,
  `scripts/azcontacts_e2e.py`. Each detects an older build's bare names once (`detect_naming`), so the scripts ran
  against the prebuilt binaries. The shell's own ids (`#shell-backstage`, `#shell-ribbon`) and azul-appkit's
  (`#appkit-settings`) carry no app prefix.

### 2. AzTasks: a click on a task title in "All" blanked list and detail
Not reproduced on the wave-6 build: four LOOK runs (dark and light, flat and flora, `--view all` / the
navigation / Cmd+5, 1280x800 and the default size, five tasks) - every click selected its task, the list stayed,
the details showed it. Found on the way, in the SCRIPTS: a key tap sent its `key_up` with the chord's modifiers,
and a debug op's modifiers are the whole modifier state (layout/src/e2e/full.rs) - so after Cmd+2 Cmd stayed held
and every later click was a Cmd+click that ADDED to the selection ("2 tasks selected"). `azlin_e2e.App.key`,
`aztasks_e2e`, `azcalendar_e2e` now release the modifiers with the key. `aztasks_e2e.py` states the behaviour (All:
a click on a row's title - scrolled into the list first; the To-Do bar shows a task due today under the same
text - selects it alone, the list and the details stay); it PASSES on the prebuilt binary.

### 3. AzTasks: planned month, board, tags (azul-apps/planning/core/todo.md 2.3 / 2.4)
- **azul-pim**: `dates::month_grid(day, week_start)` (the 42 days of a month grid - AzCalendar's Month view uses it
  too, `views::month_grid_start` gone); `Task.started` (an open task being worked on: a board's Doing, iCalendar's
  `STATUS:IN-PROCESS`; `"started"` in the task file, left out when not started, older versions ignore it;
  `set_started` keeps the first start; a repeat's next occurrence starts unstarted).
- **Model** (`views.rs`, `state.rs`): `planned_month(tasks, days)` (per day the open tasks due then, by time,
  priority, the manual order); `Column { ToDo, Doing, Done }` + `board(tasks, list)`; `Tasks::move_to_column`
  (complete / reopen / start / stop, `AZTASKS_COLUMN <task> <column>`), `Tasks::reschedule` (the due day moves, the
  time stays, it reminds again, a monthly / yearly repeat follows - `reanchor` moved from detail.rs to state.rs,
  one helper), `Tasks::take_dropped` (nav's `dropped_tasks` moved; the month and the board drop through it too);
  vtodo writes / reads `STATUS:IN-PROCESS`.
- **UI** (`layouts.rs`, new): the list header's Segmented switch - "List | Month" on Scheduled, "List | Board" on a
  list (`AZTASKS_LAYOUT <view> <layout>`). The planned month: six weeks from the settings' week start, today
  ringed, another month's days dim, two tasks a day then "+N more", Previous / Next / Today (`AZTASKS_MONTH`); a
  task dragged onto a day is due then. The board: To do / Doing / Done columns with counts, an azul `Card` per task
  (priority, title, flag, due chip, steps, tags); a card dragged onto a column moves there. Tasks select and drag
  as rows do (list.rs' `row_ref` / `on_row_down` / `on_row_drag_start`, now `pub(crate)`). No `CalendarGrid` /
  `KanbanBoard` widget exists: divs, `Card`, `Chip`.
- **Tags**: no `TokenInput` widget exists (spec for WIDGETS in section 8). The closest pieces stay - the task's tags
  as removable Chips, the "Add a tag" field (Enter adds) - and gain the suggestions a token field shows:
  `views::tag_suggestions` (the open tasks' tags the task does not carry, the most used first, six) as Chips a
  click adds.
- `scripts/aztasks_e2e.py` is on the shared driver now (its own App / find_binary / tail / naming copies gone) and
  has a stage `planned_and_board` (the ferns on tomorrow in the month, Next / Today, a drag onto the day after and
  back; the list's board, the plumber's card dragged onto Doing is started - `"started"` in its file). A build
  without the switch skips the stage ("BLOCKED"); on the prebuilt the whole script PASSES.

### 4. AzCalendar's start through the Drive
`event::load`, `calendars::load`, `settings::read`, `sample::write` take the data folder's `Drive` (a `LocalDrive`
on the data folder at start - the drive the file threads write through); the `std::fs` readers and writers are
gone (`event::load_all / save / remove / event_path`, `calendars::load_all / save / remove / calendar_path`,
`settings::path / read_text / write_line`, `sample::write_sample`, `meeting::read_saved_server / save_server`);
their tests put through the drive. A skipped event file is named by its key. RED tests read through a GRANT of
`calendar/` in a bigger tree (`ScopedDrive`), as a bucket would be.
Coordinator note done with it: the meeting server is AzCalendar's own settings line (`settings::MEETING_SERVER_KEY`,
`meeting_server_line`, `meeting_server`, `MAX_BYTES`); AzMeet's `rooms.rs` drops `encode_settings` /
`decode_settings` / `MAX_SETTINGS_BYTES` (kept only for AzCalendar since AzMeet moved to `meet/settings.json`).
`settings.txt` keeps its format (the scripts read it).

### 5. AzContacts LOOK (first time) and fixes
The prebuilt with `--sample` (300 contacts) grows past 1.5 GB during its first layout and is killed by the capped
runner: an ENGINE bug (section 6), so the LOOK ran on 40 of the sample's contacts plus a vCard 3.0 contact with a
PNG photo and a birthday. Seen working: photo avatars (card, form, list), the birthday picker (text + DatePicker +
"Year unknown" + year), the CSV column mapping, the merge screen, the settings page, flat dark and flora light.
App fixes (RED in `scripts/azcontacts_e2e.py` first): the merge screen's Left / Right pickers stand in one column
(the values share the row: zero basis); the CSV column pickers fit the pane on one line (header 140 px, the
example cut with an ellipsis, the picker keeps its width); the vCard import preview's columns share the pane (no
sideways scroll; 3 / 3 / 2 / 3 shares). The E2E types into the search field after a click (its id names the
search row, which holds no text - engine RED below).

### 6. AzDrive Details, AzMeet chat on rejoin, the E2E scripts on azlin_e2e.py
- **AzMeet: a meeting's chat comes back on rejoin.** When a meeting server's room opens, `store::read_meeting` reads
  the meeting folder's `chat.jsonl` and `meeting.json` on an azul Thread; `on_history_read` lists that chat before
  what was said since (`ChatLog::restore`; read; the newest 500 kept; `AZMEET_CHAT_RESTORED <n>`) and adds the
  people it met to the record. Until the read is in, `flush_files` holds the chat and the record back
  (`reading_history`), so a new message never overwrites the old chat (it did: the prebuilt rejoin rewrote
  `meeting.json` and would have written a one-line `chat.jsonl`). `store::parse_chat` / `record_people` read the
  files (tested).
- **DEDUP D29 done**: `azdrive_e2e.py` and `azmeet_e2e.py` run on `scripts/azlin_e2e.py`. The shared `App` gained
  what they had that others need: `hierarchy`, `classes`, `nodes_with_class`, `exact`, `click_exact`, `count`,
  `after`, `settle`, `has(selector)`, `box(selector)`, `drag`, `alive`, `tail`, the capped-runner option
  (`capped`, `cap_mb`, `cap_seconds`; stops the runner's process group), `until` waits out a `KeyError`. Each app
  keeps a small subclass for its own reading (AzDrive: two frames an op, node texts, has = laid out with a size, the
  ribbon, screenshots after settle; AzMeet: two frames, its ids, a node's id with its rect). Both PASS on the
  prebuilt (AzMeet with `--skip rejoin`; the new rejoin stage is RED there, as it should be: the room is rejoined,
  no chat comes back).
- **AzDrive Details NOT moved onto a widget** (decision D6, section 7): ListView lacks multi-select and column resize
  (DEDUP D30); DATATABLE7's DataTable (`wt/datatable7`, not in this base) has sort / multi-select / resize /
  keyboard / a11y but no icon cell, no row drag-out onto folders and no secondary-click event - moving now would
  lose Details' icons, its drag and drop and its context menus. Spec for the move in section 8.
