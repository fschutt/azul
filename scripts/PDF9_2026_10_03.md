# PDF9 - PDF -> SVG in azul's API, AzPdf, the Chrome probe (wave 9, 2026-10-03)

Branch `wt/pdf9` (base `e537ddbe2`). Nothing was compiled (house rules); every Rust file was parse-checked with
`rustfmt`. The two Python scripts ran: the probe's Chrome and pdftoppm columns work today.

## What was built

1. **`ParsedPdf` - PDF bytes -> page count, page sizes, page N as SVG text** (dll/src/desktop/extra/pdf/parsed.rs,
   wasm stub in dll/src/unified/pdf.rs). printpdf parses the bytes ONCE into its op model; the handle is an
   `Arc` (clones share the parse, `Send + Sync`, like `Db`), so an app parses on a Thread and renders only the pages
   it shows. Also the text of a page (search), the title, the outline (bookmarks in document order - printpdf keys
   them `bookmark_<n>` in a BTreeMap whose string order put `bookmark_10` before `bookmark_2`; sorted by `<n>`,
   pages made 0-based), the parser's warnings. Bytes that are not a PDF give an invalid handle with `get_error`,
   never a null one. `Pdf::to_svg_pages` (every page at once, AzDrive's preview) now goes through the same handle:
   one render path, the engine twin is gone.
2. **azul's CPU SVG renderer draws a PDF page** (engine fixes, root causes, RED first):
   - `rgb(r, g, b)` paints drew NOTHING: `parse_svg_color` knew `#hex` and 8 names. printpdf writes every paint as
     `rgb()`, so every PDF page (AzDrive's preview included) came out blank. It is now the one CSS colour parser
     (`ColorU::parse_css`): rgb/rgba/hsl/#rgba/#rrggbbaa/every keyword.
   - Transforms nested the wrong way: an element's transform was premultiplied by its parent's, so the PARENT's ran
     first (an element moved inside a page scaled to the target size moved by the wrong amount). Now
     `own.multiply(parent)`. `parse_svg_transform` reads a transform LIST right to left (it kept only the first
     function), `rotate(a cx cy)` turns about the centre, `skewX` / `skewY`.
   - `ParsedSvg::render` ignored `SvgRenderOptions::fit`: every render without a `target_size` was 800 x 600 (a
     page letterboxed inside). Now Original / Width / Height / Zoom from the SVG's natural size (sides capped at
     16384 px). AzDrive's PDF preview (`fit = Width(560)`) now gets a 560 px wide page.
3. **AzPdf** (examples/azul-pdf, package `AzPdf`, lib `azpdf`): a PDF viewer on the DocumentShell. Open (file
   dialog, a file on the command line, a dropped file, the recent documents on the start screen), the pages in a
   vertical VirtualView (only the pages in view and one either side exist; each is the picture azul drew, the
   nearest-width one while the sharp one renders, a blank numbered page before), thumbnails in a second VirtualView
   in the navigation pane, the outline tab, zoom (fit width / fit page / 25-800 %, Mod+= / Mod+- / Mod+0, a
   drop-down), page navigation (prev / next, the page field, Page Up / Down, Mod+Home / End), search in the pages'
   text (azul-appkit's one `find` matcher, hits with one-line snippets in the side pane, a click goes to the page),
   the status bar (page N of M, "A4 . 210 x 297 mm", zoom, status). All parsing and drawing runs on azul Threads
   (`jobs.rs`); a 120 ms pump timer plans renders (2 threads x 2 pages, LRU caches of 10 pages / 160 thumbnails),
   performs the scroll after an open or a zoom, and saves the recent list. Data: a PDF stays where it is; the data
   tree holds `pdf/recent.json` (with the page each document was left at, reopened there) and with `--sample` the
   sample `pdf/samples/AzPdf sample.pdf` made by azul's own PDF writer. azul-appkit: switches, settings page, About,
   shortcuts. Both themes x modes through ShellThemeScope (the pages stay paper). `--export-png OUT [--page N]
   [--width W] FILE` / `--export-svg OUT` write one page without a window through the viewer's own render path
   (for the probe and later reftests). No CloseGuard: a viewer has nothing to save.
4. **The Chrome comparison probe** (`scripts/pdf_chrome_probe.py`): page 1 of a few PDFs (its own fixtures - text
   and shapes, a page under a `cm` transform - plus any given, e.g. ~/Development/calc.pdf) by Chrome's PDF viewer
   headless (cropped out of the viewer; the crop agrees with poppler: mean diff 0.2-0.8 / 255), by pdftoppm, the
   page SVG shown by Chrome, and AzPdf; three comparisons (end to end, printpdf's PDF -> SVG, azul's SVG renderer)
   as mean abs diff / % pixels off / ink IoU, into `<out>/report.md`. Finding: **Chrome's headless PDF viewer only
   paints with scripts enabled** - refci's `cdp.py` turns them off, the probe passes
   `--blink-settings=scriptEnabled=true`.
5. **E2E** `scripts/azpdf_e2e.py` (writes a 3-page PDF itself with the probe's PDF writer): open, render, Next /
   Page Down, zoom in widens the page, search "needle" -> 2 hits, recent.json names the file, outline tab, settings,
   flora/dark.

## Seen broken / left
- **azul's SVG renderer has no `<text>` and no `<image>`** (layout/src/cpurender/svg.rs renders g/svg/path/rect/
  circle/ellipse/line/polygon/polyline only). printpdf's page SVG carries text as `<text>` with the fonts as
  `@font-face` data URLs and images as `<image href="data:...">`, so AzPdf shows the vector shapes of a page but
  no text and no pictures yet - the biggest gap, the next engine step: parse the `<style>` @font-face data URLs
  into ParsedFonts (one per family), shape `<text>`/`<tspan dx>` with text3 and fill the glyph outlines through
  the element's full matrix (raster.rs already fills glyph paths); decode `<image>` data URLs (PNG/JPEG) and draw
  them with the matrix. Also: stroke-linecap / linejoin / dasharray are ignored (always round, solid).
- **printpdf's PDF -> SVG** (the user's crate, git dependency: fixed upstream, not here - no `[patch]`):
  (a) cubic curves: the points `[c1, c2, end]` are written `Q c1 c2` + `L end` - should be `C c1 c2 end`
      (render.rs `render_line_to_svg` / `render_polygon_to_svg`): every curve is distorted;
  (b) a path's CTM is written `matrix(a -b -c d e H-f)` (render.rs `get_svg_transform`) although the path's points
      are already flipped to `H - y`: correct is `matrix(a -b -c d e+c*H H-d*H-f)`. Every page drawn under a `cm`
      (LaTeX, Word, Chrome's own PDFs) lands in the wrong place - the probe's `transformed.pdf` fixture shows it;
  (c) colour-space operators are TODO, inline images and shadings are skipped (render.rs 563-567, 881-892);
  (d) `/Rotate` of a page is not applied; only top-level bookmarks are read.
  The probe's `svg_in_chrome vs chrome_pdf` column measures exactly this layer.
- A panicking printpdf parse aborts the app (`panic = "abort"` in release): AzPdf parses on a Thread, but a
  malformed real-world PDF that panics printpdf's parser takes the process down. Fuzzing printpdf's parser is the
  fix (it is the user's crate).
- `svg_render` still renders to PNG and decodes it back (the old TODO in layout/src/xml/svg.rs) - one avoidable
  copy per page render.
- The page view re-renders whole pages per zoom bucket (64 px steps, max 4096 px wide): 400 %+ zoom on a HiDPI
  display is upscaled. Tiles would fix it.
- TODO(WIDGETS9A): the toolbar row becomes the shared `Toolbar`; the thumbnail rail and the start screen's recent
  list can become `IconGrid`s. Not in this base.
- Text selection / a text layer, annotations, forms, print, password-protected PDFs: later (planning/core/pdf.md).
- **SVG -> DOM (the later step the plan asks to note)**: `Pdf::svg_page_to_dom` (Rust-only) already maps a page
  SVG through `azul_layout::widgets::map::svg_string_to_dom` (the map tiles' path). What a real page DOM needs:
  (1) `<text>` as absolutely positioned text nodes with the PDF font registered as an in-memory font resource
      (the @font-face data URL decoded once per document) and the text matrix as a CSS transform - this gives
      selectable, searchable, highlightable text (the text layer the viewer wants anyway);
  (2) filled paths: `SvgNodeData::Path` in the DOM is only a CLIP mask today (cpurender/svg.rs comment), so fills
      need a fill-path node type (or the CPU raster as the background image and only text as DOM);
  (3) images as image nodes with transforms; (4) per-page DOM size: thousands of glyph runs per page - one text
      node per text run (printpdf's TJ items), not per glyph. The cheapest useful hybrid: raster the vector layer
      (what AzPdf does now) and overlay a transparent text DOM for selection and search hits.
- The parent may want to run AzDrive's preview test again: its PDF preview is now 560 px wide (fit honoured) and
  shows the page's shapes instead of a blank page.
