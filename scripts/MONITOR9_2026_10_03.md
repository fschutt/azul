## 1. What was built

A new app crate `examples/azul-monitor` (package `AzMonitor`, lib `azmonitor`, bin `AzMonitor`),
registered in the root `Cargo.toml`, `scripts/workspace_test_members.txt` and the `dll_tests` job of
`.github/workflows/rust.yml`. 4,500 lines, 78 unit tests.

- **The sampling model** (`model.rs`, `history.rs`, pure Rust): a reading (`Snapshot`: counts SINCE
  THE PREVIOUS READING plus its `elapsed_ms`, a process' CPU in percent of one core, the user the
  monitor runs as, notices) and what the window shows of the readings (`Model`): one 60-reading
  `History` ring per measure (whole CPU, each core, memory %, disk read / write, network in / out -
  rates over the elapsed time, so a late tick is no spike), the process rows (CPU as the share of the
  whole machine, Task Manager's rule), sorted by the model (case-folded texts, blanks last, ties by
  PID so a tick never shuffles them), filtered (name / user contain, PID starts with), the selection
  kept as a PID across readings, the history as CSV.
- **Two sources** behind one `Source` trait: `live.rs` (this computer through `sysinfo` 0.38: one
  refresh per reading of CPU usage, memory, processes - Linux threads not listed -, the disks' I/O
  counters with the processes' sum as fallback, the networks without loopback; ending = SIGTERM,
  Kill = SIGKILL, a refusal says administrator rights are needed) and `sample.rs` (`--sample`: the
  planning doc's machine - 8 cores, 16 GB, 45 processes, cargo with 12 rustc children - every
  process on its own slow wave, deterministic, nothing killed; root's processes are refused).
- **The sampler** (`sampler.rs`): an azul `Thread` that makes the source ON the thread, reads every
  interval (0 = paused, never sooner than 250 ms), hands each reading to the window as a write-back,
  and runs the window's commands (`End { pid, force }`, `ReadNow`) from an `Arc<Shared>` queue - an
  end is followed by a reading at once, its outcome rides on that reading's notices. It stops on
  `TerminateThread`, on the stop flag, or when a write-back cannot be delivered.
- **The 1 Hz path never lays the page out** (`ticks.rs`, `lib.rs::on_reading`, `ui.rs`): the
  numbers that change live in three LIVE VIEWS - `VirtualView`s whose callbacks read the model (the
  cards strip, the process table, the performance page). A reading re-renders only the live views of
  the screen shown (`trigger_virtual_view_rerender`, found by marker) and rewrites the status bar's
  marked labels (`StatusBar::update_segment_label`); `layout()` runs only for the first reading (the
  empty state gives way to the page) and for what the user does. Typing in the filter also re-renders
  only the table's live view. Each live view wraps its content in its own `ShellThemeScope` (a
  VirtualView's DOM inherits nothing from the page) at the view's exact px size.
- **The window** on the S6 `RecordsShell` in a `ShellThemeScope::body()` with the Slate accent
  (`ShellThemeAccent`'s doc names the system monitor there), `NoTitle` + appkit's `Titlebar`: the tab
  row (`TabHeader` Processes / Performance, the filter `TextInput`, "End process" - disabled without a
  selection), the cards (CPU / memory / disk / network: the value and an Area / Line `Chart` of the
  last minute), the process `DataTable` (7 columns, frozen Name, read-only, filter row off), the
  performance page (CPU chart beside per-core `ProgressBar`s, memory / disk / network charts, the
  CPU brand, processes, uptime, memory, swap), a status bar of five live labels.
- **The table glue** (`table.rs`): THE APP SORTS, NOT THE WIDGET - the rows change every second, an
  order the widget computed from one reading is stale at the next. A header click's `view.sort`
  becomes the model's keys and the view is handed back "in app order" (`order` empty, `ordered`
  false, `order_serial = query_serial`); the header keeps its arrows. The selection is re-put on the
  selected PID's new row at every reading.
- **End process**: select a row, "End process" or Delete (only when the focus is not in the page's
  own DOM - the filter field keeps its Delete): azul's `MessageBox` (Question) in a `Modal` - End
  process / Kill / Cancel (default) - with "It belongs to root: ending it needs administrator rights"
  for another user's process; Escape closes it.
- **Settings** (appkit's page, own category "Monitor"): the update speed (`Segmented` 0.5 s / 1 s /
  2 s / Paused, kept in `monitor/settings.json`, the sampler follows at once) and "Export the last
  minute" -> `monitor/history/<date>.csv` in the data tree through the drive on a Thread (appkit's
  file jobs). About, shortcuts (F1), appearance as every app.
- **Switches**: `--screen processes|performance|settings`, `--theme`, `--mode`, `--size`, `--shot`,
  `--sample`, `--data-dir` (appkit).
- **E2E** `scripts/azmonitor_e2e.py` (see 5).

## 4. New crate (the parent: Cargo.lock + cargo-vet)

- `sysinfo = { version = "0.38", default-features = false, features = ["system", "disk", "network",
  "user"] }` in examples/azul-monitor/Cargo.toml only. Why: processes, CPUs, memory, disks, networks and
  signals on Linux, macOS, Windows, the BSDs (the brief names it). 0.38.4, not 0.39 (0.39 needs rustc
  1.95; the toolchain is 1.91). It reuses the locked `objc2-core-foundation` 0.3.2, `objc2-io-kit`
  0.3.2, `windows` 0.62.2, `libc`, `memchr`; the only new transitive crate is `ntapi` 0.4 (Windows).
  `chrono` (already locked, AzDashboard's features) names the export file.

## 6. Least sure to compile / to work

1. **A DataTable inside a VirtualView** (`ui.rs::render_live` -> `table::table(..).dom()`): clicks,
   the wheel and the keys of a table whose DOM is a VirtualView's nested DOM. EVENTS7 made pointer
   events bubble across the VirtualView host and RULINGS8 the focus; keyboard events to a focused
   node of a nested DOM were not checked by anyone yet. If keys do not reach the table, that is an
   engine bug to fix (not an app workaround); the E2E's Delete on the selected row would show it.
2. `trigger_virtual_view_rerender` from a THREAD WRITE-BACK (`on_reading`) and from a TextInput
   callback (`on_filter`) returning `Update::DoNothing`: the change is queued in the callback's
   changes (window.rs collects write-back changes - read), but no app has relied on it at 1 Hz yet.
3. The VirtualView content root: a div of the view's exact px size around `ShellThemeScope::dom()`;
   if the scope's FILL_COLUMN_BASE fights it, the content may not fill (cosmetic).
4. sysinfo API spots: `refresh_cpu_list` before the first refresh, `ProcessRefreshKind::without_tasks`,
   `Disks::new_with_refreshed_list_specifics(DiskRefreshKind::nothing().with_io_usage())`,
   `Disk::usage()`, `Process::kill_with(..).or_else(|| Some(process.kill()))`, `Networks` deref
   iteration (`is_loopback(name)` with `&&String`).
5. Generated-API spots: `StatusBar::update_segment_label(info, node, label)` (by value, `CallbackInfo`
   is `Copy`), `NodeId { inner: raw - 1 }` from `node.node.into_raw()`, `n.dom == DomId { inner: 0 }`,
   `VirtualViewReturn::default()`, `Button::with_disabled(reason)`.
6. The E2E's text clicks: "Name" (the header), "Kill" (the question), "pipewire" / "sshd" (a row) - a
   second node with the same text would make a click land elsewhere.
