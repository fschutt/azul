# XML8 - the lenient parser, almost HTML5: the standard's tokenizer states and its tree construction as rule tables

Branch `wt/xml8`, from `45c6bf98b`. Nothing was compiled (house rule). The four core files were
type-checked with `rustc --emit=metadata` (library AND `--test`) and linted with `clippy-driver` using
azul-core's CI lint set (pedantic, nursery, unreachable_pub, let_underscore_drop, ...) on a stub harness
(no codegen, no binary, no target dir - as LENIENT did): no error, no warning in `core/src/xml_html*.rs`.
The tree construction's LOGIC was checked against headless Chrome through a line-by-line Python mirror
of the committed Rust (scratchpad, not committed: a mirror is a twin).

User (2026-10-03): "the xml parser has to be very lenient, almost html5-like + also accept mail. Probably
needs a refactor so all the special-cases don't grow out of control."

## What was built

### The refactor: special cases are rows, the algorithms are the standard's

`azul_core::xml::html` is now four files (every public path stays; `xml_html.rs` re-exports):

| File | What |
|---|---|
| `core/src/xml_html.rs` | module root: character references (the ONE decoder), the ONE encoder (`encode_text` / `encode_attribute` - api.json reads them here), `TreeSink`, `XmlTreeSink`, the driver `parse_html_into`, `parse_html_nodes`, `outline` |
| `core/src/xml_html_rules.rs` | **THE DATA.** Every special case is a row citing the HTML Living Standard section |
| `core/src/xml_html_tokenizer.rs` | `HtmlTokenizer`: the standard's tokenization (13.2.5) as a state machine |
| `core/src/xml_html_tree.rs` | `TreeBuilder`: the tree construction (13.2.6) running the tables |

The rule tables (`xml_html_rules.rs`):

| Table | Rows | Replaces |
|---|---|---|
| `ELEMENTS` | 116 elements, binary-searched: flags VOID, FORMATTING, SPECIAL, HEADING, HEAD, MARKER, SCOPE, TABLE_SCOPE, IMPLIED_END, FOSTER_TARGET, BREAKOUT, INTEGRATION_POINT + content (markup / RCDATA / RAWTEXT / PLAINTEXT) | 12 `matches!` category functions |
| `MODES` | which open element decides the insertion mode (13.2.4.1) | - |
| `START_TAGS` | the body's start tags (13.2.6.4.7) -> steps: CloseP, ClosePUnlessQuirks, PopHeading, PopCurrent, CloseListItem, CloseInTable, CloseInScope, CloseRubyParts, CloseOpenLink, CloseOpenNobr, IgnoreInForm, Ignore, Reconstruct, Insert / InsertVoid / InsertFormatting / InsertMarker / InsertForm / InsertSkippingNewline / InsertForeign | `close_implied_by`, `reopens_formatting_before`, the `a` special case, ... |
| `END_TAGS` | the body's end tags -> (scope, action): CloseInScope, P, Heading, Adoption, CloseToMarker, Br, Form, Ignore, AnyOther | `Scope::of_end_tag` and the html / body / head / p / br code paths |
| `TABLE_START_TAGS` / `TABLE_END_TAGS` | the table modes (13.2.6.4.9 - .15): clear back to a context and insert, imply a wrapper (`tbody` / `tr` / `colgroup`), close and reprocess, insert in place, hidden input, form | `close_in_table` + `open_implied_table_parents` (HTML) |
| `TEMPLATE_CONTENT` | 13.2.6.4.18: the mode a table part right in a `<template>` takes | - |
| `ALIASES` | `image` -> `img` | - |
| `QUIRKS_*` | the doctypes of quirks mode (13.2.6.4.1) | - |

**The strict loaders run the SAME `START_TAGS` / `END_TAGS` rows with the HTML-only steps off** - their XML
conveniences (void elements, implied end tags, end tags within scope, a cell closing a cell in its table)
are not a second rule set. `start_tag_closes` (the e2e builder's question) is read from those rows.

### The tokenizer (13.2.5)

One method per state: data, RCDATA, RAWTEXT (+ script data, its escapes not modelled), PLAINTEXT, tag open,
end tag open, tag name, before / after attribute name, attribute name, before attribute value, quoted /
unquoted value, after quoted value, self-closing start tag, bogus comment, markup declaration open,
comment (`-->` / `--!>` / `<!-->`), doctype (name, public / system identifiers, force-quirks), CDATA
section. As in the standard, the TREE CONSTRUCTION switches the text mode after a start tag
(`TreeBuilder::text_mode_for` -> `HtmlTokenizer::set_text_mode`: an HTML `<style>` is raw text, an SVG one
markup) and allows CDATA only in SVG / MathML (`set_cdata_allowed`). New over the old scanner: an end tag's
attributes are read (`</div title=">">`), `<plaintext>` never ends, CDATA outside foreign content is a bogus
comment up to the first `>`, a raw-text element's end tag must be followed by white space, `/` or `>`.

### The tree construction (13.2.6)

HTML builds into an arena (nodes can still MOVE) and replays it into the sink at `finish`; the strict loaders
stream into the sink exactly as before. New in HTML (each with RED rows, all Chrome's trees):

| Rule | Example (Chrome's tree) |
|---|---|
| **Foster parenting** (13.2.6.1, 13.2.6.4.9/.10) | `<table><tr>{{#each}}<td>a` -> `"{{#each}}" table{..}`; `<table><div>` -> div before the table; hidden input / form / style stay in it |
| **The full adoption agency** (13.2.6.4.7) | `<b>x<p>y</b>z</p>` -> `b{"x"} p{b{"y"} "z"}`; Outlook's `<font><div>a</font>b</div>` keeps "b" out of the font; html5lib's adoption01 cases (outer loop 8, inner loop 3) |
| **Quirks mode** (13.2.6.4.1) | no doctype / HTML 4.01 Transitional without system id / legacy: `<p>a<table>` keeps the table IN the p (most mails) |
| Document phases | the head always exists; white space before the document is nothing; head content after `</head>` goes into the head; `noscript` in the head (scripting off); a second `<html>` / `<body>` adds missing attributes |
| Table modes | `<col>` implies `colgroup`; `<table>` in a table closes it; a row closes the caption; `</tbody>` ends the row group |
| Any other end tag | `</span>` with a div open inside is ignored |
| Body start tags | `nobr`, `button`, nested `form` ignored, ruby, `image` = img |
| Foreign content (13.2.6.5) | `<svg><p>` breaks out; `<svg><font color>` breaks out, `<svg><font>` not; MathML `<mi>` holds HTML |
| Template (13.2.6.4.18) | content stays in the template (also in the head); `<td>` in it needs no table |

## api.json

**No change.** `Xml::create_from_html`, `Xml.encode_text` / `encode_attribute` (fn_body
`azul_core::xml::html::encode_*`, still in `core/src/xml_html.rs`) are untouched. Rust-only API (not in
api.json, unchanged paths): `TreeBuilder` (`new` is no longer `const fn`; new `doctype`, `text_mode_for`,
`in_foreign_content`), `TreeRules`, `TreeSink`, `XmlTreeSink`, `HtmlTokenizer` (new `set_text_mode`,
`set_cdata_allowed`), `HtmlToken` (new variant `Doctype(Doctype)`; bogus comments are now `Comment`
tokens), new `Doctype`, `TextMode`, `is_void_element`, `start_tag_closes`, `parse_html_into`,
`parse_html_nodes`, `outline`. The only external users (`layout/src/xml/mod.rs`, `layout/src/e2e/builder.rs`,
`layout/src/paste_html.rs`) need no edit.

## Behaviour changes to expect (lenient loaders only; the strict ones are unchanged)

- Every HTML document has a `<head>` (empty if nothing goes in it); `Xml::create_from_html("")` is
  `html{head body}`. The DOM builders take the body / hide the head: no DOM change.
- Mails without a doctype are in quirks mode: `<p>..<table>` nests the table in the paragraph (as Chrome
  lays them out). AzMail re-serializes and re-parses strictly, where a table still closes the `<p>`.
- Misnested formatting is adopted: text after `</font>` / `</b>` inside a block is no longer formatted.
- Text / elements misplaced in a table appear in front of it (Postmark templates, `{{#each}}`).
- `<image>` is an `<img>`; `</span>` no longer closes a block opened inside the span.

## What is left

- `<frameset>` (replaces the body) and "in select" (its own end tag rules; Chrome's current parser is the
  customizable-select one, which our body rules already match for `<select><div>`).
- SVG's camel-case names (`linearGradient`) - the DOM builders read names lower-cased anyway.
- Comments are not nodes (text across a comment is one text node; Chrome splits it) - deliberate.
- Script data's escape states; `noscript` with scripting on.
- The strict loaders still tokenize with crates.io's `xmlparser` (not ours: a fork needs `[patch]`, which the
  release gate forbids - LENIENT's decision, kept). The SPECIAL set now also names the MathML / SVG integration
  points (`mi mo mn ms mtext annotation-xml desc`): only a malformed XML document with those around an open
  formatting element or list item could tell.
- Twin found (not mine, not fixed): `layout/src/widgets/rich_text/html.rs` `escape_html` duplicates the one
  encoder `azul_core::xml::html::encode_text` / `encode_attribute` (it escapes `"` in text and keeps C0
  controls); AzMail's three "safe link" rules (DEDUP_EDITORS B21) still stand.
- The Python mirror + Chrome probe (`scratchpad/xml8/`) are not committed; to re-check, regenerate the outlines
  with `scripts/refci/mail_outlines.py` and compare a build's `outline()` output.
