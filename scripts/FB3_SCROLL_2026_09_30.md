# FB3_SCROLL: horizontal scroll damage, viewport leftovers, two renderer bugs (2026-09-30)

Branch `wt/fb3-scroll-damage`, from `5bab5dfa2`. **Nothing was compiled or run as a test** (house
rule); every Rust file was parse-checked with `rustfmt --check`. The prebuilt apps were driven
headless through the capped runner (`run_capped.sh --cap-mb 1500`), one at a time. Every fix has a
RED test commit before it; the expected REDs come from the code and, for items 1 and 3(a), from
the live headless reproductions below.

## 1. Root cause per bug

### Item 1: AzReview's horizontal scroll "stops" - only the scrollbar strip keeps updating

**Reproduced headless** (AzReview 1400x900, `wheel delta_x=-300` + `wait_frame`s, `AZ_PATCH_DEBUG=1`,
`AZ_DUMP_FRAME_DIR`): every scroll frame logs `item_diff=Some([])`, `has_scroll=false`, and the
only damage comes from `vview=true` (the child list "changed", see below) and the thumb's GPU-value
damage. The dumped incremental frames differ from a fresh render by ~20k px over the whole sheet
area, with stale glyph fragments inside the code text.

**Root cause.** The sheet strip is a `VirtualView`. A view has no scroll frame: its scroll is the
`content_offset` of its display-list item (`materialized origin - scroll offset`), and the
lightweight scroll path re-points that field alone (`LayoutWindow::patch_virtual_view_content_offset`,
called from the `ScrollTo` arm in `dll/.../common/event.rs`). Every CPU backend presents the frame
from the display-list diff, and `DisplayListItem::is_visually_equal` compared two `VirtualView`
items by `child_dom_id`, `bounds` and `clip_rect` only - `content_offset` was ignored. A scrolled
view compared EQUAL, the diff produced no damage, `collect_scroll_shifts` finds no frame for it, so
nothing repainted the view; the thumb (GPU-value diff) still repainted its bar. On the Mac the
content moved only while something else happened to damage the view (a re-materialisation at an
edge, a child list that changed); once the materialized window was wide enough it froze: "after a
while only the bottom 8px still update".

Why headless still moved the content: AzReview's sheets carry a `RenderImageCallback` image each;
`prepare_frame_content` gives them a new `ImageRef` every frame, so the child list compares unequal
every frame and `compute_virtual_view_damage` repaints the four image rects (at the NEW offset) -
which is what left the fragments between them.

**Fix** (`layout/src/solver3/display_list.rs`): the `VirtualView` arm of `is_visually_equal` also
compares `content_offset`. The item diff then damages the view's box (old and new, projected through
the enclosing frames), and the presented frame equals a full repaint. This is the same fix for the
GPU path's `is_visually_equal` users and for the e2e CPU twin (`layout/src/e2e/cpu_backend.rs`),
which call the same functions.

### Item 3(a): the first text line of a mounted document is not painted in AzWidgets under ~700px

**Reproduced headless** (`mount` two `<p>` at 760x400 vs 760x800, `AZ_ANIM_DEBUG=1`,
`get_animations`, `get_display_list`): at 400 tall the mounted list (12 items) opens ONE
`PushReferenceFrame`, owned by node 4 (the first `<p>`), and `[shot]` shows ~100 GPU transforms left
from the AzWidgets DOM, several at `tx=-57.17` that never change over 40 frames; at 800 tall the
list opens none. AzWidgets at rest holds `active: 476` FLIP moves (`get_animations`) before any
mount.

**Root cause.** `LayoutWindow::tick_animations` writes a FLIP's transform and opacity into the GPU
value cache under the node's id (`anim_transform_keys` / `anim_current_transform_values` /
`anim_opacity_keys` / `anim_current_opacity_values`). `GpuStateManager::remap_node_ids` (the
rebuild's node-id migration) rewrote the twelve scrollbar / CSS-transform / opacity maps and left
these four behind. After a rebuild the value stayed under the OLD id; the display-list builder emits
a reference frame for any node that has both a key and a value (`display_list.rs`, the
`has_reference_frame` / `child_ref_frame` lookups), so the unrelated node that inherited the id was
painted through a stranger's transform. At 760x400 AzWidgets' node 4 was a widget mid-move (a big
translation); the mounted `<p>` took its id and was painted off-screen. At 760x800 node 4 had no
transform. AzMail's DOM has no such node 4, so it never showed.

**Fix** (`layout/src/managers/gpu_state.rs`): `remap_node_ids` remaps the four `anim_*` maps with
`remap_hashmap` - survivors follow their node, unmounted nodes drop their entries.

### Item 3(b): the CPU renderer clips text on one paint path and not on the others

`render_text_prerendered_lcd` (the pre-tiled LCD path) clips a run to `clip_rect ∩ stack clip`,
as WebRender clips a text item. `render_text` (the LCD batch sweep and the grayscale path) used
that intersection only to SKIP a fully clipped run and then rasterised under the stack clip alone
(`rb.clip_box_i` / the sweep's stripe clip from `clip`), so ink outside a run's `clip_rect` painted
on two paths and not on the third - MAILVIEW's list markers survived on the sweep and vanished on
the tiles.

**Fix** (`layout/src/cpurender/raster.rs`): one `text_run_clip(clip_rect, clip, dpi) -> Option<AzRect>`
(the run's clip_rect in device px cut to the active clip; `None` = nothing to paint). `render_text`
shadows `clip` with it before dispatching, so the sweep and the grayscale path clip exactly as the
tile path does. The text-shadow path goes through `render_text` with its clip_rect shifted by the
shadow offset, as before.

The parent's suite run then showed the tile path had the same gap on its inside: pass 2b (tile
copies) was cut to the combined clip, but pass 2a - the batch sweep for glyphs whose tiles
overlap - got the stack clip alone (`2af1e228d`). It now sweeps under the same integral box the
tile copies use. Stack clip `None` means "the run's clip_rect alone" on all three paths.

## 6. What is left

- **VirtualView scroll blit.** A view's step is a repaint of the whole view box (no memmove: it has
  no scroll frame for `collect_scroll_shifts`). AzReview's strip is 1087x738 px per step. A blit for
  views would need the shift collector to read `content_offset` deltas the way it reads frame
  offsets.
- **FLIP moves never settle.** AzWidgets at rest holds `active: 476` FLIP moves; over 1.7 s of
  frames the count went 476 -> 475 while their values converge (translate 15 -> 0.016) but
  `finished` stays false. `tick_animations` keeps writing those nodes' transforms every frame and
  `needs_animation_frame` stays true (an idle AzWidgets never reaches `FrameDamage::None`).
  `Spring::is_settled` (core/src/animation.rs) or a duration cap is the place; not touched here
  (no RED yet). Keys whose node left the tree are skipped by the tick and now dropped from the cache
  at the remap; they still sit in `animations` forever.
- **AzReview headless never idles.** Its per-sheet `RenderImageCallback` images get a new `ImageRef`
  every frame (`prepare_frame_content`), so the child list compares unequal every frame and the four
  image rects are repainted even at rest. Either the callback should be re-invoked only on a
  size/content change or `Image` equality should compare the image data hash rather than the ref id.
- **Text clip twins.** `render_text_prerendered_lcd` keeps its own i32 intersection of
  `clip_rect` and the stack clip (floor/ceil, then `run_clip` for its sweep); `text_run_clip` is
  the float twin used by the other two paths. Identical for the integral clips damage rects
  produce; folding the tile path onto the helper is a small follow-up once a golden run confirms
  no pixel moves.
- **AzReview binary.** `target/release/AzReview` (20:58) predates `libazul.dylib` (21:31); relink
  before probing it again (it ran and rendered for this report, but the coordinator's note says a
  stale ABI can lock up).
- The `a_virtual_view_...` headless test scrolls through `apply_user_change(ScrollTo)`; the wheel
  physics path (`HeadlessEvent::Scroll` + the momentum timer) ends in the same `ScrollTo` change and
  is covered by `a_stepped_wheel_scrolls_the_box_under_the_pointer`.
