### 2. A bare `object` argument
- The scan: `check_fn_body_receivers` - a function with a `self` argument (and no real argument named `object`, like
  GlContextPtr's `test_object_apple`) whose body uses `object` other than as `object.` (not part of a name, a path
  `Json::object(..)`, a field, a call or a macro) is the new CRITICAL kind `BareObjectInFnBody`, whose FIX names the
  receiver to pass (`raw_image`). Python replica over today's api.json: none.
- The add tool emits only the supported forms: `object.m(..)` for methods, the receiver name for `--fn`. The one
  body it wrote with a bare `object` - `core::mem::drop(object)` for any `destroy*` method (it did not even call the
  method) - is gone: a `destroy*` method is called like any other.
- The codegen (`transmute_helpers.rs`) was left as it is: `object` cannot be rewritten blindly (GlContextPtr), and the
  supported forms cover every body the tool writes.

### 3. The module of a new type; a private module on the path
- ROOT CAUSE of "add picks the module by its own rule": three rules. `autofix add` used the widget rule, else the
  name's keywords; the scan's move check (`get_correct_module_with_path`) used structural names -> exceptions table ->
  widget rule -> path confirms -> confident keyword -> path as tiebreaker; the scan's additions left the module to the
  apply side's keyword guess. So a keyword-less name went to `misc` and the next scan moved it; a widget's `*Error`
  went to `widgets` and the scan moved it to `error`. Now ONE function, `module_map::new_type_module(name, path)`,
  decides in the move check's order, so the scan keeps every placement; the add (type and dependency types), the
  scan's additions and an Add patch without a module all call it. One `is_structural` helper for both.
- Path-first placement ("derive the module from where the type lives") was measured and rejected: 1223 of the 2620
  api.json classes whose path maps to a module sit in another one by concern (Component* at `azul_core::xml` in
  `component`, the error/option/vec families, Font* in `font`, time types in `time`, ...). The path decides when the
  name's keyword does not (the move check's tiebreaker); the exceptions table names the rest.
- `--module` was NOT added: the next scan's move check would move a hand-picked module back unless the exceptions
  table names it - the table IS the persistent choice. `TextRasterStyle -> image` is in the table now (MEDIA6's
  wish), and `azul_layout::cpurender::` maps to `image` (the rasterizer draws into a RawImage).
  -> THE NEXT SCAN MOVES `TextRasterStyle` from `css` to `image`. AzPhoto's one import is already switched
  (`azul::image::TextRasterStyle`, commit 3c1d0d238 - revert that line if the move is not applied), and
  `css/src/codegen/lower_types.rs` (generated, `("TextRasterStyle", "css")`) must be regenerated after the scan.
  Nothing else changes module: the prebuilt `azul-doc autofix modules` reports every type in its right module today,
  and `TextRasterStyle` is the only api.json class under `azul_layout::cpurender::`.
- Private module paths: the index now reads each file's module declarations and `pub use` leaves
  (`ModuleFacts`); a type behind a module declared without `pub` gets the path of the `pub use` that re-exports it (a
  glob or the name of its module, or of a module on the way, followed up the tree; renames not followed); one nothing
  re-exports keeps its path and `TypeIndex::private_module_on` names the private module. azul_dll is left out (the
  generated code lives in that crate). Then:
  - `needs_path_fix(api, workspace, index)`: an api.json path through a private module is fixed to the index's public
    path (root+leaf equivalence alone never corrected it);
  - `check_private_paths`: a class whose path runs through a private module nothing re-exports is the new CRITICAL
    `PrivateExternalPath` (FIX: declare the module pub or re-export the type);
  - `autofix add` refuses such a type with that message.
  Today's api.json: no class behind a private module (python replica over the 150 private `mod x;` declarations).

### 4. AUTOFIX6's list
- A borrowed return added BY NAME is cloned: `&T` -> `.clone()`, a borrowed value that converts `.clone().into()`,
  `Option<&T>` -> `.cloned().into()` (`ReturnConversion::for_borrowed_return`). The wildcard still skips borrowed returns.
- `Option<T>` ARGUMENTS cross as their FFI option (`option_arg_ffi_type`): `Option<X>` -> `OptionX` + `x.into()`,
  `Option<&X>` -> `OptionX` + `x.as_ref()`, `Option<&str>` -> `OptionString` + `x.as_ref().map(|s| s.as_str())`, a std
  `Option<String>` -> `OptionString` + `x.map(|s| s.into_library_owned_string())`. `MethodArg.source_ty` keeps the
  generic arguments as written (`Option<AzString>` vs `Option<String>`). CONSEQUENCE: `Type.*` now exports a method
  with an `Option<&str>` argument (it has an FFI form); the AUTOFIX6 wildcard test states it (`set_link`).
- `&[T]` arguments cross as `{T}VecSlice` + `x.as_slice()` (`slice_arg_type`); u8 / f32 / i32 keep the gl
  `U8VecRef` / `F32VecRef` / `I32VecRef` api.json already uses. (The old `&[` arm never matched - the parser splits the
  `&` off first - and `[T]` became `*const [T]`.) Slices therefore pass the wildcard when the VecSlice type exists.
- Every argument accessor is a `{}` template substituted for WHOLE arguments only; the suffix splice
  (`replace("text)")` also hit `context)`) is gone.
- `ClassPatch::is_empty` counts the `remove_*` lists (`has_removals`): a move patch with removals now applies them
  to the moved class; `removes_only()` - a removal for a class the module does not have creates nothing (a warning);
  `is_path_only` is false with removals. pending.rs drops its own copy of the remove-list check.
- A pending WHOLE-class removal followed by an add of that class in one round: `pending::prepare_add` rewrites the
  pending one-item removal into a removal of every function / constructor api.json has for the class, and the add
  supersedes the ones it re-adds - "remove, then add" replaces the class's entries without an apply in between.
  Both add arms call it.
