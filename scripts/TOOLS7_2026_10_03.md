### 0. One method per new type (found at the wave-6 integration) - ROOT CAUSE: file names
`autofix add T.m` for a type api.json does not have wrote `add_<t>_<i>.patch.json` (the type and its dependencies) and
`add_<t>_functions.patch.json` - the SAME names for every method. Three adds of DateRepeatPicker, then one
`autofix apply`: each add overwrote the files of the one before, so the last add's method survived and every patch
"Successfully applied". The apply-side merge was already right (`add_functions: true` merges; re-adding after the
type existed went through the existing-type path, which names its file per method).
- New module `autofix/add.rs`: `new_type_patch_files` names every file by what it holds -
  `add_<t>.type.<added type>.patch.json` (identical content whichever method of `<t>` is added),
  `add_<t>.impls.patch.json`, and `functions_patch_file_name(t, spec)` = `add_<t>_<spec|all>.patch.json` (the name the
  existing-type path already used - one helper for both). `generate_add_type_patches` now hands its functions patch
  over (`AddTypeResult.functions_patch`) instead of dropping it while main.rs computed it a second time.
- The apply reports a dropped entry: `patch::dropped_entries` - every function / constructor a patch of the round
  writes must be in api.json after the last patch (in any module), unless a later patch of the round removes it or its
  class on purpose; each drop is a patch error naming the file that wrote it (`[DROPPED] ...`, `has_errors()`).

### 1. `autofix add Class.name --fn <path::to::free_fn>`
- `type_index::find_free_fn(root, path, class)`: reads the path's crate (the index's ONE crate list, now the const
  `CRATE_DIRS`, also used by the scan's preflight check); a file a `#[path = ".."]` declaration names gets the declared
  module path (`azul_core::xml::html` = xml_html.rs); the public fn is taken from the named module, else from the one
  child module defining it (`pub use text_raster::*`). The body calls the path AS GIVEN.
  `type_index::free_fn_method` reads an `ItemFn` with the method rules (`Into<T>` generics, constructor-ness).
- `function_diff::free_fn_entry(class, api_name, free_fn)`: the free fn's arguments; a first argument of the class's
  own type (value / `&` / `&mut`) becomes `self` (value / ref / refmut) and is passed as the codegen's receiver name
  `receiver_arg_name(class)` (`raw_image` - the generated C function's parameter, so no fn_body rewrite is needed;
  the Python generator rewrites that name too); a `create*` api name returning the class is a constructor.
  `method_to_function_data` and `free_fn_entry` share ONE core, `function_data_for_call`.
- `&mut CallbackInfo` (and every `*CallbackInfo` handle) crosses BY VALUE and is re-borrowed from a mutable copy:
  `{ let mut info = info; ...(&mut info, ..) }` - the ProgressBar.update_progress / TextInput.set_text_in form. `add`
  wrote `*mut CallbackInfo` before, and the drift check reported the existing entries (the prebuilt
  `autofix list ProgressBar` shows `update_progress: api.json declares CallbackInfo, source takes *mut CallbackInfo`
  today; gone with this rule).
- `add.rs::free_fn_patch_file` + the main.rs arm `["autofix", "add", spec, "--fn", path]` (the class must be in api.json;
  writes `add_<class>_<name>.patch.json`, supersedes a pending removal of the same name).
  What wave 6 wrote by hand now comes from the tool:
  `autofix add Xml.encode_text --fn azul_core::xml::html::encode_text` (arg `s: String`, body
  `azul_core::xml::html::encode_text(s.as_str()).into()` - the arg is named after the source, `s`, not `text`),
  `autofix add RawImage.from_text --fn azul_layout::cpurender::text_image`,
  `autofix add RawImage.draw_text --fn azul_layout::cpurender::draw_text` (body `draw_text(raw_image, text, style, x, y)`),
  `autofix add TextInput.set_text_in` (an associated fn: no `--fn` needed now that CallbackInfo crosses by value).

### 2. A bare `object` argument
- The scan: `check_fn_body_receivers` - a function with a `self` argument (and no real argument named `object`, like
  GlContextPtr's `test_object_apple`) whose body uses `object` other than as `object.` (not part of a name, a path
  `Json::object(..)`, a field, a call or a macro) is the new CRITICAL kind `BareObjectInFnBody`, whose FIX names the
  receiver to pass (`raw_image`). Python replica over today's api.json: none.
- The add tool emits only the supported forms: `object.m(..)` for methods, the receiver name for `--fn`. The one
  body it wrote with a bare `object` - `core::mem::drop(object)` for any `destroy*` method (it did not even call the
  method) - is gone: a `destroy*` method is called like any other.
- The codegen (`transmute_helpers.rs`) was left as it is: `object` cannot be rewritten blindly (GlContextPtr), and the
  supported forms cover every body the tool writes.
