# ANIMFRAME8 - an animation frame must cost ~1-2 ms (wave-8 follow-up, 2026-10-03)

Branch `wt/animframe8` (base 5745afee6: wave 8 integrated, LAYOUTPERF8C included). Nothing compiled (house
rule); the "after" numbers are expectations, measured how below.

User (2026-10-03 evening, after the knob tick measured 20-21 ms): "it should usually only patch the display
list - do we have duplicated paths? accessibility tree should only send update patches and none if nothing
rebuilt? transitions should be lightweight: new display list (patched) or not even that if its a GPU property
(transform)? And why is it re-running every vv callback. I think most of that is useless for animations."

## 2. The path map - every path a frame can take (and which one a tick takes)

From most to least work. Every LAYOUT path ends in the one funnel
`LayoutWindow::layout_and_generate_display_list_impl` (window.rs), which always: clears `layout_results`
(every VirtualView child result too) and resets every view's invocation flags, lays the root out
(`layout_dom_recursive_impl` -> GPU-cache `synchronize` -> `solver3::layout_document`), re-invokes and
re-lays-out every VirtualView, re-applies overlay text, rebuilds the whole a11y tree, registers scroll nodes,
derives `NodeResized`, and re-runs the four DOM lints.

| # | path | entry | reconcile | layout | display list | taken by |
|---|---|---|---|---|---|---|
| P1 | full regenerate | dll `common/layout.rs::regenerate_layout` -> app `layout()` -> cascade -> diff -> `layout_new_generation` | yes | dirty roots | patch if structure-preserved, else full | `RefreshDom` (the switch click: 389 ms in AzWidgets) |
| P1b | pre-cascade skip | same, fingerprints equal -> "layout unchanged" (no pass) or "warm relayout" (`layout_new_generation` on the old DOM) | yes | dirty roots | as P1 | a `RefreshDom` whose DOM did not change |
| P2 | incremental relayout | dll `incremental_relayout` / headless `relayout_only` / e2e runner `relayout_only` / `relayout_root_dom_in_place` -> `layout_and_generate_display_list` | YES (all nodes, 4.4 ms) | css-dirty roots | full when css-dirty (`structure_ok` needs empty css dirt) | **every layout-property tween tick (the knob's margin-left)**, layout-affecting restyles, `set_css_property(margin..)` |
| P3 | resize fast path | dll `incremental_relayout_for_resize` (`resize_only_hint`) -> same funnel | skipped (retained tree) | root (warm caches) | PATCH (moved nodes translate) | window resize |
| P4 | display-list rebuild | `regenerate_display_list_for_dom` (macOS/X11 `display_list_dirty`, headless `repaint_only`, e2e `ShouldUpdateDisplayList`) | no | no | full, from the existing layout | paint-only tween ticks that are not a solid colour (border colours, gradients, box-shadow, transform, opacity), caret blink, hover paint restyles |
| P4b | early exit in `layout_document` (Step 1.5) | P2 with only paint-scope css dirt | yes | none | full | paint-only restyle that went through P2 |
| P5 | DL patch in place | `tick_animations` -> `DisplayList::patch_paint_colors` | no | no | items rewritten in place | solid background / text colour tween ticks (`transition_patched`) |
| P6 | GPU values only | `tick_animations` writes the animation channel (`anim_*` keys) | no | no | none (renderers read values by key) | FLIP slides, keyframe tracks (`animation_tick_is_values_only`) |
| P7 | CPU renderer incremental repaint | headless `paint_cpu_frame` / the desktop CPU backends: damage = DL item diff + GPU-value diff | - | - | - | the tail of every path above |

Which path an animation tick takes is decided THREE times, by three copies of one rule that drifted:

- the shells' CSS driver `PlatformWindow::advance_css_animations_now` (dll event.rs): relayout -> P2; patched OR
  values-only -> repaint; else -> P4;
- the debug server's `CallbackChange::TickAnimations` arm (dll event.rs, the AZ_E2E / debug-server tick):
  relayout -> P2; patched -> repaint; else -> P4 (no values-only test: every FLIP tick rebuilds the list);
- the E2E runner's `TickAnimations` arm (layout `e2e/runner.rs`): the same as the debug arm, plus an idle guard.

Duplications / divergences found (the answer to "do we have duplicated paths?"):

1. **Three copies of the tick decision** (above). Unified into one `LayoutWindow::take_animation_frame_work`.
2. **Headless turns every "repaint" into a relayout.** `HeadlessWindow::service_frame` maps a bare
   `ShouldReRenderCurrentWindow` (what a patched / values-only tick returns) to `relayout_only()` - P2, a full
   incremental relayout (10 ms in AzWidgets) for a frame that owes only pixels; the desktop shells just present.
   The paint-only flag that exists for exactly this (`content_repaint_pending`, used for video frames) was
   never raised by the animation drivers.
3. **P4 never syncs the GPU values P6 and the CSS `transform`/`opacity` channel bind.** `GpuValueCache::synchronize`
   runs only inside the layout pass (P1-P3). A `transform` tween (or a plain `set_css_property(transform)`)
   rebuilt the list through P4 against the OLD matrix: the node did not move until some unrelated layout. So
   the "GPU property" path did not exist for CSS transitions at all - a transform tween was strictly more
   expensive (P4 every tick) than a FLIP slide (P6), and showed nothing.
4. **P4 never consumed the css dirt it painted.** A paint-scope transition tick staged its node in
   `pending_css_dirty` and asked for P4; P4 rebuilt the list but left the entry, so the dirt grew by one entry
   per tick until some layout pass ate it, and `animation_tick_is_values_only` stayed false meanwhile.
5. **Two relayout paths for "the DOM did not change"**: P3 takes the retained tree (latch `resize_only_hint`);
   P2 re-reconciles the same unchanged DOM. An override-only tween tick is P3's case (the DOM is the same object,
   only overrides moved), yet it took P2.
6. **The css-dirty patch gate**: P3's patch arm and P2's structure-preserved arm share `PatchState`, but every
   css-dirty pass falls back to a full emission (`structure_ok` requires empty css dirt) instead of re-emitting
   the dirty nodes and splicing the rest.
7. **VirtualViews**: P2/P3 (relayouts of the SAME DOM) clear every child result and re-invoke every view, exactly
   like P1 (a new DOM). The view lifecycle (`check_reinvoke`: bounds expanded, edge scroll) is never consulted.
8. **css_transition_tick cost**: each non-colour tween called `restyle_user_property` (a whole-DOM compact +
   inheritance rebuild) PER TRANSITION PER TICK; a flat Button's hover fade (background + four border colours,
   ANIM8's `decl::state_fade`) paid four whole-DOM rebuilds plus a P4 rebuild per tick, because a border
   colour was not patchable and one unpatchable tween forces the whole tick off P5.

What the AzWidgets switch knob animated: `margin-left` (a LAYOUT property) -> P2 every tick.

## 3. What changed (each with its RED test first)

**K. The knob slides on the GPU** (RED 29c762631, GREEN 97025b4e2 bde873961 bd7b4f74a e58aded70 dbfb358c5).
- `switch.rs`: the knob declares `transform: translateX(0px)` / `translateX(16px)` (consts
  `KNOB_OFF_TRANSFORM` / `KNOB_ON_TRANSFORM`) instead of `margin-left`, its tween is declared on `transform`,
  and the click handler writes the transform. Both themes build the knob through `build_knob_style`. The off
  state is `translateX(0px)`, not `none`, so the knob's reference frame (a CSS transform key) exists from the
  first layout and the first toggle needs no display-list rebuild either.
- `tick_animations` (window.rs): THE GPU PROPERTY PATH. A `transform` tween on a node that has a reference
  frame writes its override through the lean channel and publishes the matrix under the node's existing key
  (`GpuValueCache::refresh_transform_value_of`, core/src/gpu.rs - one keyed node re-read through the cascade,
  the same `css_transform_of` the sync uses). No restyle, no relayout, no display-list rebuild; the frame
  counts as patched (repaint only). A node with no key yet, or a target that is no transform, changes the key
  population and falls through to the rebuild path.
- Duplication 3 (P4 never synced GPU values): one helper `sync_css_gpu_values` now serves the layout pass
  AND `regenerate_display_list_for_dom`. Duplication 4: P4 consumes the paint-scope css dirt of its DOM.
- Duplications 1 + 2: `LayoutWindow::take_animation_frame_work` is the one tick decision (relayout /
  repaint / display-list rebuild) for the shells' CSS driver, the debug server's `tick_animations` arm and
  the E2E runner. The dll wraps it (`PlatformWindow::take_animation_frame_work`) and raises
  `content_repaint_pending` for a repaint frame, so headless `service_frame` paints it from the layout as it
  stands (`repaint_only`) instead of running `relayout_only` (P2) for a frame that owes only pixels.
- Tests moved with the knob: `layout/tests/switch_animation.rs` keeps pinning a LAYOUT-property tween on a
  switch given an explicit `margin-left` knob style; the dll driver tests (`headless/mod.rs`
  `toggled_switch_window`, `knob_glide_progress`) write / read the knob's transform; switch.rs unit tests
  read the knob offset from the transform (`translate_x_px`, `knob_offset_px`, `pushed_knob_offsets`).

**(3) css_transition_tick lightweight** (RED d332a93fb, GREEN 5c5668705).
- The restyle path is batched: every tween writes its override through the lean channel and the frame
  refreshes the cascade ONCE (`recompute_inheritance_and_compact_cache` + font-size invalidation when a tween
  can move one) instead of one whole-DOM `restyle_user_property` per tween (each bumped the epoch twice).
- `DisplayList::patch_paint_colors` takes a `PaintColorSlot` (text, background, one border side): the four
  `border-*-color`s patch in place, and `patch_compact_border_color` keeps the compact cache's border word
  in step (the display-list builder reads border colours there, not through the override - without it a
  list built for any other reason mid-fade would paint the last full restyle's colour). A flat Button's face
  fade (background + four borders) is now a repaint-only frame with zero cascade work. A text-colour fade
  refreshes the inheritance tables on its LAST frame (descendants inherit through them); a patch that misses
  joins the frame's one refresh.

**(1) No reconcile for a tick that changes no DOM node + (2) the css-dirty patch** (RED a3772c8ba, GREEN
f581d023a).
- `LayoutCache::overrides_only_hint: Option<OverridesOnlyStamp>` (solver3/cache.rs): armed by
  `tick_animations` when the frame owes a relayout, every layout-scope tween keeps the layout tree's shape
  (`tween_keeps_layout_tree_shape`: sizes, paddings, margins, insets, flex grow/shrink/basis, gaps, border
  widths - never display / position / float / overflow, which the reconcile re-derives boxes from), no
  paint-scope tween needed a restyle, and no other diff was pending. Stamped with the DOM's node count,
  cascade epoch and every node's interaction state AFTER the frame's own refresh.
- `layout_document` Step 1 takes the retained tree when the stamp matches (the resize path's branch; layout
  roots = the css dirt, not the root). Voided by `apply_content_change` and by every new generation.
- Duplication 6: on a skipped reconcile the patch arm re-emits the css-dirty boxes and everything below them
  (`css_dirty_reemit_set`) and splices the rest, instead of a full emission.

**(4) VirtualViews kept across a relayout of an unchanged host** (RED 1823dcb68, GREEN 64feec075).
- `VirtualViewManager::record_invoked_node` / `invoked_node`: the host node (callback + dataset INSTANCE)
  a view was last invoked for. On the relayout entry (`new_generation == false`) the funnel keeps every view
  whose host node is still exactly that node, in a kept host DOM (`unchanged_virtual_views`): its child
  result survives the clear and its flags stay (`carry_over_views`). Its first check of the pass trusts
  "nothing to do" only while the child was laid out for the box it has now (`take_carried` + the child's
  viewport size); a box of another size renders it again. A kept view the pass never reaches drops its child
  (and the views in it). A new generation re-renders every view as before.
