## Findings first

- **Transport: the reliable path exists and must be used.** `IrohEndpoint::send_message` is reliable and ordered
  (dll `desktop/extra/iroh/engine.rs`: one uni stream per direction, `set_priority(1)`, an unbounded mpsc queue,
  delivered as `Message` events before any frame). The frame path cannot carry H.264, and not only because it is
  latest-wins (a newer frame replaces an unsent one, the receiver keeps only the newest): every frame is its own
  QUIC stream, so a large keyframe and the small P-frame after it race, the P-frame arrives first, and the receiver
  then discards the keyframe as older (`offer_frame`: `newest >= sequence` -> dropped). PLI would loop forever.
  So H.264 packets are messages; JPEG keeps the latest-wins frames (a stale JPEG is worthless).
- **The codec handles lie about working.** `VideoEncoder::open` returns an OPEN handle (`is_open() == true`) that
  never yields a packet on Linux / Windows (gpu-video encode is not wired in any build), Android (MediaCodec not
  implemented), and on Apple when VideoToolbox fails to load or H.265 is asked for. `VideoDecoder::open` likewise
  (Vulkan decode only x86_64 + `video-native`). `VideoEncodeCheck::run()` reports *hardware* capability (always
  "ready" on Apple; Vulkan encode ext on Linux), not whether this build's `VideoEncoder` encodes, so AzMeet does not
  use it. `PlatformCapability::video_codec()` is the same for decode. AzMeet therefore **probes**: at start it
  encodes one test-pattern frame and decodes the result; only a keyframe that comes back as a picture enables H.264.
- **VideoToolbox** (`videotoolbox.rs`): realtime session, no B-frames, Main/AutoLevel, `MaxKeyFrameInterval` 60;
  `encode` is synchronous (`VTCompressionSessionCompleteFrames`), one Annex-B chunk per frame with SPS+PPS in-band
  ahead of every IDR; `force_keyframe` is honoured (`kVTEncodeFrameOptionKey_ForceKeyFrame`). Decode is synchronous
  too, session built lazily from the in-band SPS/PPS.
- **Headless**: the camera and screen backends are registered regardless of `AZ_BACKEND=headless`
  (`ensure_camera_backend` in the layout pass), so a mounted `CameraWidget` would open the real camera. AzMeet never
  mounts one headless (see below).

## What was built

### 1. `examples/azul-meet/src/video_wire.rs` (pure, 25 unit tests, no azul types)
- **Packet** `[2][version 1][codec 1 JPEG / 2 H.264][flags bit0 keyframe][track u32][seq u32][frame_no u32]` +
  payload (JPEG file or Annex B). Kind 1 stays M2's audio state message.
- **Controls** `[3][track]` keyframe request (PLI), `[4][track][seq]` received-through (ack), `[5][flags]` caps
  (bit 0: decodes H.264). Unknown kinds are "not video" and fall through to the audio control decoder; trailing bytes
  allowed.
- **Gap detection is on `seq`, not `frame_no`** (deviation from the prompt's wording, on purpose): `seq` counts one
  codec's packets on one track and is consecutive, so a gap is a missing packet; `frame_no` counts frames captured
  while someone listened and legitimately jumps (a frame the encoder emitted nothing for, a frame that went as JPEG to
  others). Both are in the header.
- `h264_is_keyframe`: an IDR slice (NAL type 5) after a 3- or 4-byte start code.
- `ReceiveTrack` (per peer, per track): decode in order; a gap -> drop everything until the next keyframe and ask for
  one (again at most once per second while waiting); a stream that starts without a keyframe waits likewise; a
  keyframe right after a gap decodes without a request; H.264 acked every 5 packets and at every keyframe; JPEG never
  acked and never waits; JPEG and H.264 are separate streams (the last JPEG frames arriving after a switch disturb
  nothing); a packet <= 1000 behind is late (dropped), further behind restarts the stream; `decoder_is_inert` after 30
  packets from a keyframe with no picture back.
- `KeyframePolicy` (per local track): a fresh encoder's frames are forced until a keyframe comes out; requests (PLI,
  new peer, resync) coalesce to one forced keyframe per 500 ms; a floor of one every 3 s; a forced frame answered by a
  P-frame -> reopen the encoder (a new one starts with a keyframe); 3 reopens in a row without a keyframe -> broken.
- `SendWindow` (per peer, per local track, H.264): nothing before a keyframe (new peer); at 24 unacked packets the
  peer is paused, and once acks bring it to 12 it wants a keyframe and resumes there. This bounds the reliable queue a
  slow link would otherwise grow without end.
- `EncoderHealth` (8 frames in, no packet out = inert), `test_pattern` (8 colour bars moving 4 px/frame) +
  `PatternClock` (15 fps by wall time, skips after a stall), `codec_line` / `video_line` / `send_line`.

### 2. Glue in `examples/azul-meet/src/lib.rs`
- **Start**: `probe_video()` (encode + decode one pattern frame; `AZMEET_VIDEO_CODEC=jpeg` forces JPEG);
  `configure_video` next to `configure_audio`. Log: `[azmeet] Ada: Video: H.264 (VideoToolbox); decodes H.264: yes`.
- **Send** (`send_video`, from the camera/screen consumer hook or the pattern pump): per frame, peers whose caps say
  H.264 get H.264 (`send_h264`: one encoder per local track, reopened on size change / must_reopen; each packet
  offered to each peer's `SendWindow`, sent with `send_message`); the others get JPEG (`send_jpeg`: header + JPEG,
  `send_frame` per peer, latest-wins). An encoder that does not open, gives nothing back, or is broken sets
  `Video: JPEG (<why>)` and the frame goes as JPEG.
- **Receive**: in `pump_link`, frames on tracks 1/2 and messages of kinds 2-5 go to `video_wire::decode_message`;
  packets -> `receive_video` (rules, ack / keyframe request, lazy `VideoDecoder` per peer track, drain
  `recv_frame`, newest picture per (peer, track) shown via `change_node_image` after the drain); controls ->
  `apply_video_control` (request -> force; ack -> window; caps -> switch codec, reset windows). A decoder found inert
  makes this side send caps(false) to everyone (it then gets JPEG).
- **Connect**: caps sent with the state message on every `PeerConnected`; a peer gets JPEG until its caps arrive.
- **UI**: devices panel column "Video": `Video: H.264 (VideoToolbox)` / `Video: JPEG (no encoder)` (plus
  `; JPEG to Ben (no H.264 decoder)`), the link line, `Sending camera: 450 H.264 packets, 0 JPEG frames, 8 keyframes,
  2 on request, 5 periodic, 0 reopens, 1 dropped on purpose`, and per peer track `Video from Ben (camera): H.264,
  decoded 300, keyframes 12, gaps 1, dropped 3, keyframe requests 1`. The 2 s stats log adds these plus per-peer
  window / late counts.
- **Test pattern**: `AZMEET_TEST_PATTERN=1` -> camera (and screen share) are the pattern, camera on from the start,
  toolbar button **Drop a video packet** (drops the next non-key H.264 packet, or the next JPEG frame, before it is
  sent). Headless -> patterns always (off until switched on); no `CameraWidget` / `ScreenCaptureWidget` is mounted.
  stderr: `no camera or screen is opened: both are test patterns`.
- **ALPN** `azmeet/mjpeg/1` -> `azmeet/2` (M2 clients cannot connect to M3 ones: the wire changed).
- Shared helper: `send_message_to` / `all_peers` now serve both the audio state and the caps message (was a
  per-message loop); `audio_devices_allowed` -> `devices_allowed` (now also gates camera/screen).

### 3. `examples/azul-meet/scripts/two-clients.mjs`
Both clients run with `AZMEET_TEST_PATTERN=1`. After the audio checks: each window's codec line (H.264 or JPEG;
`--require-h264` fails a JPEG run); each decodes >= 30 frames (2 s) of the other's camera in that codec with >= 1
keyframe; both say no camera/screen is opened. Then Ben clicks **Drop a video packet**: Ada counts a gap; with
H.264 her keyframe requests rise, she dropped the P-frames after the gap, then decodes 15 more frames after one more
keyframe; Ben's "on request" count rises and his stderr shows `Ada asked for a keyframe`. A keyframe right after the
dropped packet needs no request, so the drop is repeated (up to 3 times). With JPEG: a gap, no request, decoding goes
on. Then M2's Mute and Leave checks.

Dry run (no Rust app; a Node stand-in in the scratchpad, `m3/fake-azmeet.mjs`, against the real meet dev server of
azul-apps-m1): M2's stand-in (no video) **FAILS** at "Ada's window to show its video codec" (RED); the M3 stand-in
**PASSES** in H.264 mode, in JPEG mode, and with the keyframe-after-drop retry; `--require-h264` **FAILS** its JPEG
mode as intended.

## api.json

**No change.** Existing API used: `VideoEncoder::open / backend_name / is_open / encode / recv_packet / close`,
`VideoDecoder::open / is_open / decode / recv_frame / close`, `VideoFrame` (struct literal),
`OptionU8Vec::into_option`, `OptionVideoFrame::into_option`, `PlatformCapability::video_codec`,
`IrohEndpoint::send_frame / send_message`, `RawImage::encode_jpeg / decode_image_bytes_any`.

Recommended library follow-ups (not done, outside this task's files), in api.json terms:
1. `VideoEncoder::open` / `VideoDecoder::open` should return an invalid handle (`is_open()` false) where no engine is
   compiled in, or a new `VideoEncoder::is_functional(&self) -> bool`; and `VideoEncodeCheck` should reflect the
   compiled engine, not just the hardware. Then apps need no probe frame.
2. Stream priority / a reliable track in `IrohEndpoint`: e.g. `send_message_on(peer: u64, track: u32, data: U8Vec)`
   with `IrohConfig::with_track_priority(track: u32, priority: i32)`. Today H.264 rides the message stream at
   priority 1, ABOVE audio frames (priority 0): under congestion video can starve audio (the design wants
   audio > screen > camera), and a large keyframe head-of-line-blocks PLIs, acks and mute messages on the one ordered
   stream.
3. `IrohPeerStats.messages_queued: u64` (outbound message backlog), which would replace AzMeet's ack-based window.
4. Headless gating of camera / screen backends (like biometric / keyring): under `AZ_BACKEND=headless` or `AZ_E2E`,
   `CameraWidget` / `ScreenCaptureWidget` fall back to `capture_common`'s own test pattern. AzMeet could then drop its
   pattern generator and just mount the widgets.
5. `VideoEncoder::set_bitrate(&self, kbps: u32)` (VT `AverageBitRate` at runtime) for rate adaptation.

NO DUPLICATION notes: AzMeet's `test_pattern` is app-side because the library's generators are not public API; the
library itself already has two twins: `layout/src/widgets/video.rs::video_test_worker` (SMPTE bars) and
`layout/src/widgets/capture_common.rs` `TestPattern::{ColourCycle, MovingBand}`. The JPEG `RawImage` construction
that `send_feed_frame` had inline is now the one `rgba_image` helper (also used for decoded H.264 pictures).

## Least sure to compile / run

Nothing here was compiled with cargo. `video_wire.rs` (with its tests) type-checks alone
(`rustc --edition 2021 --crate-type lib --test --emit=metadata`, no warnings) and is rustfmt-clean with the repo
config. `lib.rs` was type-checked in a harness (scratchpad `m3/harness_head.rs` + `m3/make_harness.py`): stubs with
the generated signatures from `target/codegen/dll_api_external.rs` plus **99 items copied verbatim** from lib.rs
(every struct and function M3 touched, including `call_layout`, `pump_link`, `apply_link_event`, the whole video
section, the M2 audio glue it calls): no errors, no warnings; rooted like `start()`, no dead code in `video_wire.rs`
or `audio.rs`. Remaining risks:
1. Signatures the harness took from the generated external bindings: `VideoEncoder::encode<I0: Into<VideoFrame>>`,
   `recv_packet(&mut self) -> OptionU8Vec`, `VideoDecoder::decode<I0: Into<U8Vec>>`,
   `recv_frame(&mut self) -> OptionVideoFrame`, `VideoEncoder::backend_name() -> AzString`,
   `PlatformCapability::video_codec().available`. The link-static (iOS / Android) bindings were not checked.
2. `rgba_image(frame.width, frame.height, frame.bytes)`: a partial move out of `VideoFrame` (fine: `AzVideoFrame`
   has no `Drop` impl in the generated code; `azul_core::video::VideoFrame` has none either).
3. `use video_wire::{Codec, Control, Message}` next to `azul::prelude::*`: explicit imports win over the glob if the
   prelude has a `Message`.
4. Runtime: the debug server's `click` op on "Drop a video packet" (same mechanism as M2's "Mute"); the 2 s stats
   refresh is what updates the panel lines the test reads; VideoToolbox in a headless process (the dll's own
   `videotoolbox_roundtrip` test runs windowless, so it should work).

## What is left

1. **Simulcast ladder + `IrohLoadBalancer`** (next task): every sender encodes one 320x180 stream and sends it to
   every peer (full mesh). Renditions per tile size (`IrohTileRole::rendition_height`), backbone selection, forwarding;
   a new keyframe per rendition switch (with the design's hysteresis).
2. **HEVC** (`open(h265 = true)` is a stub on every backend today) and AV1.
3. **Hardware encode/decode off Apple**: gpu-video (Vulkan Video) encode is not wired on Linux/Windows, decode only
   x86_64 + `video-native`; Media Foundation, VAAPI, MediaCodec not implemented. Until then those platforms send JPEG
   (and receive H.264 only where Vulkan decode works; otherwise their inert decoder asks for JPEG).
4. **Bitrate adaptation**: the VT bitrate is fixed at open (400 kbps); the only congestion response is the send
   window pausing a peer (which then resumes at a keyframe, i.e. it degrades to keyframes). Needs `set_bitrate`, a
   rate controller from RTT / acks, and fps / resolution shedding (camera first).
5. **QoS**: video on the message stream outranks audio frames (see follow-up 2); LTR frames from the design doc.
6. Smaller: the picture decoded before a track's tile exists is not shown (the tile is laid out after the first
   packet); no local preview of the test pattern (the self tile says "You · test pattern"); `frame_no` is carried but
   unused by the receiver.
