### a_text_field_takes_the_font_size_its_app_gives_it - 2e7f99692
- Root cause: FIX9 4.1 (4abc009bc) moved `font-size: 11px` from the value `<p>` to the container's INLINE props.
  An app's `.dom().with_css("font-size: 24px")` is `Dom::with_css`: a node-only SCOPED SHEET (INLINE rule
  priority, but selector-matched), and the cascade puts a node's own inline declarations above every
  selector-matched rule (prop_cache `get_property` PRIORITY 1, `apply_cascade_properties` step 4 after step 3).
  So the container kept 11 px, the `<p>` inherited it, the field stayed 22 px.
- CODE wrong (Chrome: the UA's input font is the lowest origin; `<input style="font-size: 24px">` is 24 px).
  The 11 px is now `text_input::field_font_default()`: a component sheet
  `.__azul-native-text-input-container { font-size: 11px }` at `rule_priority::UA`, attached in
  `TextInput::dom_in` (both themes; NumberInput / ColorInput / flora's number input build through `dom()`).
  The class selector keeps it on the container (a `*` rule would pin the `<p>` too). The three
  TEXT_INPUT_CONTAINER_PROPS variants lose their inline font-size.
- Note: an app that styles the field with `with_container_style` WITHOUT a font size gets 11 px again (as before
  4.1), not the inherited size FIX9's note 7 described - Chrome's model (UA default unless the author sets one).
- Broader finding (not changed): every widget default declared inline beats an app's `.dom().with_css(..)` for
  that property. Apps can only override through `with_*_style`. Worth a design decision (fold `Dom::with_css`
  bare declarations into the node's inline style after the widget's, or move widget defaults to UA sheets).
- Confidence: medium-high. Least sure: the cascade ranking of a UA-priority component rule vs the INLINE-priority
  `with_css` rule on the same node (should be priority order, `sort_rules_in_cascade_order`).
- Files: layout/src/widgets/text_input.rs.

### an_inline_date_picker_fits_its_pane - NOT FIXED
- CODE wrong, in the ENGINE (the widget is right: Chrome shrinks `width: 32px` flex items whose content is
  narrower - automatic minimum size = min(32, content min-content ~15) - to 26 px each in a 200 px pane).
- Root cause: a row flex item's automatic minimum size comes from taffy's `SizingMode::ContentSize` min-content
  query, and the bridge answers it with the item's own width:
  1. `taffy_bridge::compute_non_flex_layout` injects `own_definite_width` into `known_dimensions` for EVERY query
     (239134683); taffy's own leaf algorithm ignores the style size under `ContentSize`.
  2. Even without that, its MinContent answer is `warm.intrinsic_sizes.min_content_width`, which sizing.rs
     overwrites with the definite `width` (css-sizing 5.2.1 contribution) - the content's own min-content is lost.
  So min = 32 and the seven columns never shrink (224 of 200).
- Proposed fix: in compute_non_flex_layout, skip the injection when `inputs.sizing_mode == ContentSize`, and for a
  ContentSize MinContent query of a node with an own definite width answer the content's min-content (the
  layout's `content_width` at `available_width_type: MinContent`, or a stored pre-clamp intrinsic); keep the
  `measured_content_sizes` pure-measure slot for InherentSize queries only. Cross-cutting (every row-flex item
  with a definite width), cannot be validated without a suite run; a widget-side `min-width: 0` would be the app
  workaround the house rules forbid.

### a_short_list_in_a_shell_pane_fills_its_pane_from_the_top - NOT FIXED
- AZ_TAFFY_DEBUG on the prebuilt binary: taffy is handed INFINITE sizes - `n3 kd=(None,Some(inf))
  avail=(Definite(1100),Definite(inf))`, the same for the shell (n4), C (n5) and the split halves; the final pass
  even HITs `n3 kd=(None,Some(inf)) avail=(..,Definite(720))`. Two engine leaks:
  1. `fc::translate_taffy_size` maps an INFINITE containing-block size to `Some(inf)` in taffy's `parent_size`, so
     taffy resolves `height: 100%` to `Some(inf)`;
  2. `fc::resolve_explicit_dimension_height` resolves a percentage against `constraints.available_size.height`
     even when it is INFINITY (CSS 2.2 10.5: it computes to `auto`), so the body's `height: 100%` becomes a known
     height of INF. (`layout_flex_grid` already guards the AVAILABLE space against `Definite(inf)` with the
     comment "must NOT reach taffy"; the known / parent sizes are not guarded.)
- But fixing both makes the chain CSS-correct, i.e. content-sized: the test's DOM is `html (height auto) > body
  { height: 100% }`, which Chrome (standards mode) also lays out content-sized - the row would still end at 383.
  The test's 720 needs the root `html` to fill the viewport, which azul intends (core/src/ua_css.rs: the
  `(Html, Height) => HEIGHT_100_PERCENT` rule, commented out as a "DIAG (2026-06-02, REVERT)" for a wasm-lift
  mis-dispatch), or a body root as the real window has (an Html root is only injected around the user's DOM by
  csd.rs / the titlebar / the Linux software menubar - the latter sets `height: 100%` on it explicitly).
- Decision wanted: re-enable the UA `html { height: 100% }` (and check the wasm lift), or make the injected Html
  roots `height: 100%` and the test's html too; then fix the two INF leaks. Not a widget fix.
