## 1. What was built

### The field (`core/src/resources.rs`)

* `pub app_id: AzString` in `AppConfig`, right after `theme` and before the 4-aligned `mode`,
  with the other 8-aligned fields. An `AzString` is 8-aligned and a multiple of 8 in size, so
  there is still no padding. `app_config_has_no_padding_between_its_fields` destructures and sums
  the new field too.
* Default empty = not declared (`AppConfig::create`).
* `with_app_id(AzString) -> Self` and `set_app_id(&mut self, AzString)`, shaped like
  `with_theme` / `set_theme`.

### The precedence rule: one pure function (`layout/src/managers/notification.rs`, `wire`)

* `PlatformAppId { AppleBundle(String), AndroidPackage(String), Flatpak(String) }` is what the
  platform declared. `id()` returns the id and `origin()` a readable source for the log.
* `ResolvedAppIdentity { identity: AppIdentity, warning: Option<String> }`.
* `AppIdentity::resolve(app_id, platform: Option<&PlatformAppId>, exe_path)` is a pure function
  of its inputs, so it is tested without an OS:
  1. A non-blank platform declaration wins. If the app's `app_id` names another app, the result
     carries a warning that names both ids. A bundle id equal to the app_id's Apple form
     (`org.example.my_app` -> `org.example.my-app`) counts as the same app.
  2. Otherwise a non-blank `app_id` wins (`AppIdSource::Declared`).
  3. Otherwise the id comes from the executable (`from_executable`), which is today's behaviour.

| OS | what `desktop::app_identity` passes | effect |
|---|---|---|
| macOS / iOS | `AppleBundle(CFBundleIdentifier)`, only when the process runs from a `.app` | the bundle wins; a different app_id is logged as a warning. An unbundled binary passes nothing, so there the app_id wins (it feeds WM_CLASS under XQuartz). |
| Android | `AndroidPackage` read from `/proc/self/cmdline` | the package wins; a different app_id is logged as a warning |
| Windows | nothing (an unpackaged exe) | app_id is the AUMID; `toast_activator_clsid` and the registry values follow it |
| Linux | `Flatpak(FLATPAK_ID)` inside a sandbox, else nothing | FLATPAK_ID wins inside Flatpak. Outside it, app_id is the `desktop-entry` hint, the Wayland `app_id` default (a window's `wayland_app_id` still overrides it) and the X11 `WM_CLASS` default. All three already read `current().desktop_entry()` (N1), so nothing changed in the shells. |

### Runtime (`dll/src/desktop/app_identity.rs`, `dll/src/desktop/app.rs`)

* `declare(app_id: &str)` is called once, from **`App::create`**, right after the logger is
  installed. `App::create` is the one place the AppConfig is in hand before every run path:
  * `App::run` covers the three `run.rs` platform `run()`s, the headless path and the crash
    reporter;
  * `App::run_tray_only` covers `run.rs::run_tray_only`;
  * iOS's `UIApplicationMain` (`ios/mod.rs` `install_launch_hooks` in `didFinishLaunching`) is
    reached through `App::run`.

  So there is one call instead of four. `App` has no API that replaces its config after
  `create`, and the other app-level globals (`set_app_mode`, `set_app_theme`) are installed at
  the same place.
* `declare` resolves at once, so a conflict with the bundle, package or Flatpak id is logged at
  startup. A process keeps ONE identity, because its registry keys, activator and window classes
  are already out. Two cases are logged and ignored:
  * a second, different declaration (a second `App`);
  * a declaration after `current()` was already read.
* `current()` feeds `DECLARED`, `platform_app_id()` (the per-OS reader, formerly `declared_id()`)
  and `current_exe` to `AppIdentity::resolve`. It logs the warning with `plog_warn!`.

### Build tools (`doc/src/bundle.rs`, `doc/src/mobile/run.rs`): done, small

* `bundle_metadata(cargo_toml, key)` is now THE `[package.metadata.bundle]` line scan. It is the
  old `configured_icons` body with the key as a parameter, and `configured_icons` delegates to it,
  so the scan is not duplicated.
* `configured_identifier(cargo_toml) -> Option<String>` reads `identifier`; a blank value counts
  as none.
* `default_bundle_id(cargo_toml, binary)` returns the configured identifier's Apple form, else
  `bundle_id_for(binary)`. `azul-doc bundle macos` uses it when `--bundle-id` is not given. Module
  docs and usage text are updated.
* `mobile::run::Target::resolve` resolves `--package`, then `configured_identifier`, then the old
  `com.azul.<crate lowercase, '-' -> '_'>`. The id is used verbatim for both iOS and Android.

### Docs

* **Where the guide documented notifications and app identity: nowhere.** A grep of
  `doc/guide/en` for AUMID, desktop-entry, AppUserModel, CFBundleIdentifier and app identity
  finds nothing, and there is no notifications page. The closest existing section was
  `system/windowing.md` "Platform-specific options", which covers `wayland_app_id` and
  `x11_wm_classes`.
* Added `## App identity` to `doc/guide/en/system/windowing.md`, right after that section. It
  covers:
  * the field and a Rust snippet;
  * the per-OS precedence table;
  * the empty default;
  * `[package.metadata.bundle] identifier` and how the tools use it;
  * the Linux `<app_id>.desktop` requirement;
  * the Windows Settings-entry migration note.
* Added a paragraph "The app's id" to `doc/guide/en/deploying/mobile.md`, after the pipeline
  table. It links to `../system/windowing.md#app-identity`.

### Manual checks (for a person)

* **Windows:** `AppConfig::create().with_app_id("org.example.Widgets".into())`, then post once.
  * `reg query "HKCU\Software\Classes\AppUserModelId\org.example.Widgets"` shows `DisplayName`
    and `CustomActivator`.
  * Settings > Notifications shows a new entry.
  * Quit, then click the Action Center entry: the app starts (the activator follows the AUMID).
* **Linux (Wayland):**
  * `WAYLAND_DEBUG=1 ./app 2>&1 | grep set_app_id` shows `org.example.Widgets`;
  * `dbus-monitor "interface='org.freedesktop.Notifications'"` shows
    `"desktop-entry": <"org.example.Widgets">`;
  * on X11, `xprop WM_CLASS` shows `"org.example.Widgets", "Org.example.Widgets"`.
* **Linux (Flatpak) with a different app_id:** `FLATPAK_ID` stays the id, and the log shows the
  warning.
* **macOS:** bundle with `--bundle-id com.other.id` while the app sets
  `app_id = "org.example.Widgets"`. The log shows `AppConfig::app_id is "org.example.Widgets",
  but the app bundle's CFBundleIdentifier is "com.other.id" ...`, and notifications still work
  under `com.other.id`.
* **Build tool:** add `[package.metadata.bundle] identifier = "org.example.Widgets"`, then run
  `azul-doc bundle macos <crate> --dry-run`. It prints `CFBundleIdentifier org.example.Widgets`.
  `azul-doc mobile build android <crate>` prints the same id as the package.

## 6. Twins found (NO DUPLICATION rule), left alone

* `layout/src/icon_remap.rs::current_app_name()` computes `current_exe().file_stem()`. That is a
  second copy of "the executable's name" (`wire::AppIdentity::exe_name`). It keys the user's icon
  rules (`~/.azul/icons/...`), and it lives in `azul-layout`, which cannot call the dll's
  `current()`. Whether an app_id should also key those rules is a product question.
* `mobile::run::Target::resolve`'s derived bundle id (reported by N1) is still there. The
  configured identifier is now used verbatim for both iOS and Android. The user's own string is
  not projected: an identifier with `-` is not a valid Android package, and one with `_` is not a
  valid `CFBundleIdentifier`. The fix is still the one N1 named: an Android projection of
  `AppIdentity` next to `apple_bundle_id()`, used by both mobile targets.

## 7. What is left

* **Validation / projection for Android:** the Android package form, per section 6.
  `PlatformAppId::names` compares an Android package with the app_id exactly, so
  `org.example.my-app` vs `org.example.my_app` warns.
* **Windows migration:** the old AUMID keys (`com.azul.<exe>` and the pre-N1 `azul.<exe>`) stay
  in HKCU after an app starts setting `app_id`. A one-time `RegDeleteTreeW` was not built; the
  guide says so.
* **MSIX package identity** (a packaged Windows app) is not read. It would be a fourth
  `PlatformAppId` variant (`GetCurrentPackageFullName`).
* **A build-time mismatch warning** (bundle id vs `app_id`) is impossible without running the
  app. The runtime warning covers it.
* **A notifications guide page** does not exist. App identity lives in `system/windowing.md`
  for now.
* **Debug-only check:** N1 suggested "a debug build could warn when the bundle's id and app_id
  disagree". The warning is logged in every build.
