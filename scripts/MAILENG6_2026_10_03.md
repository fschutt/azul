## What was built, item by item

1. **The font bug (TABLES' ignored tests), root-caused.** `getters.rs::collect_font_stacks_from_styled_dom`
   turned a plain 0-based arena index into a node with `NodeId::from_usize(i)`, the 1-based FFI
   decoder (0 = None, n = node n - 1). Phase 1 (the dedup key) and Phase 2 (the representative's
   cascade) therefore read the weight and style of the node BEFORE each text node: " tail" in
   `<p><b>bold</b> tail</p>` asked for the bold face, its own regular chain was never collected,
   never loaded, and the run shaped to nothing. Fixed: `NodeId::new(i)`, and the key is the text
   node's own resolved (fontconfig weight, style) in ONE encoding. TABLES' three tests are
   un-ignored; new font-independent unit tests in getters.rs.
3. **Chrome's rounded font metrics.** Measured in headless Chrome 154 (11 Mac families x 13 sizes,
   143 cases): `line-height: normal` = round(A) + round(D) + round(G) at the font size (Blink
   `AscentDescentWithHacks` / `SimpleFontData::PlatformInit`); my model reproduced all 143. ONE
   helper, `LayoutFontMetrics::line_metrics_px`, now turns a face's vertical metrics into pixels,
   used by `LineHeight::resolve*`, the glyph boxes (`inline_box_px`, both `get_item_vertical_metrics`
   twins), the dense view (`resolved_run_ascent`, 4 copies -> 1) and the strut (fc.rs). The leading
   is shared by `split_leading` (floor above, rest below: LayoutNG `CalculateLeadingSpace`), the
   same for glyphs and the strut. The root's `normal` is `Px(A + D + G)` of its first available face.
4. **`line-height: 20px` pitch / unset lines.** Verified on the prebuilt wave-5 AzPaint: 3 lines of
   `font: 15px Arial; line-height: 20px` are 60px (Chrome 60), an unset `<p>` after it is `normal`.
   TEXTENG's wave-5 fixes hold; nothing changed.
5. **Tables.** A cell of only inline-level boxes (no loose text) is an inline formatting context, so
   its `text-align` places them (Postmark's button, the receipt's prices); a guarded exception keeps
   block-in-inline cells on the block branch. Collapsed borders in an rtl table meet a column line
   by the table's direction (`CollapsedBorders.rtl`; cell and table half-borders on the right side).
   `<td style="display:block">` and the receipt's -8px are TABLES' wave-5 fixes (TABLES 3.1 / 3.3);
   I did not re-measure them - the parent's corpus run confirms.
6. **Atomic inlines in spans + strut metrics.** `collect_inline_span_recursive` measures
   inline-flex / inline-grid / inline-table as atomic inlines (they were "inlinified"), and an
   `<img>` in a span or link goes through the root's image path, now ONE helper `push_inline_image`
   (it was an empty inline span). `ParsedFont` reads OS/2 `sxHeight` / `sCapHeight`; the strut's
   x-height / cap height are the face's (0.5em / 0.7em only without them).
7. **The Times / Helvetica / Courier "+15% ascent".** Checked against Blink: it IS a name list in
   both engines (not a stand-in for USE_TYPO_METRICS - Apple's three faces do not set it), but Blink
   matches the name table's FAMILY exactly, only on Apple platforms, and adds
   floor((A + D) * 0.15 + 0.5) to the ROUNDED pixel ascent. `browser_compat_ascent` (PostScript
   prefix, font units, every platform) is replaced by `font::parsed::browser_ascent_boost(family)`
   + the flag `LayoutFontMetrics::browser_ascent_boost`, applied in `line_metrics_px`.
2. **Percentage heights in auto-height parents** (CSS 2.2 10.5): see the section below.
8. **(Added by the coordinator, from SMALL6) An overflowing line lost its start.** CSS Text 3 7.1:
   a line too long for its box is START-aligned whatever `text-align` says. Measured in Chrome 154
   (a 100px box; an unbreakable 205px word, a 191px `nowrap` line, the overflowing 2nd line of a
   paragraph; left / right / center / justify / start / end / -webkit-right; ltr and rtl): every
   overflowing LTR line starts at x 0, every overflowing RTL line ends at x 100; fitting lines keep
   their alignment. `position_one_line` applied the negative remaining space of right / center
   lines (AzCalculator's long results cut off at their start); the Knuth-Plass path used offset 0
   in RTL too. Now ONE rule for both, `text3::cache::line_alignment_offset`, and ONE start/end
   mapping, `physical_text_align` (it was written out twice); the unused twin
   `calculate_alignment_offset` is deleted.

## Item 2 in detail

CSS 2.2 10.5: a percentage `height` whose containing block's height depends on its content
computes to `auto`. Azul forwarded every auto-height box's own containing-block height to its
children (`cache::prepare_layout_context`, read back by `fc::layout_bfc`), so `height: 100%`
chained up to the window and a mail's paper (`body { height: 100% }`, mapped by AzMail onto the
paper div) ended one window down. Now ONE decision, `cache::forwards_containing_block_height`:
an in-flow `display: block` (list-item, flow-root) box of a DOM node, in horizontal writing, not
the root, whose parent is a block container (not flex / grid) passes an INDEFINITE height, as in
Chrome's standards mode. The root (the window), flex / grid items, anonymous boxes, abspos boxes,
floats, table boxes, inline-blocks and vertical writing keep forwarding. And a percentage height
against an indefinite containing block is now sized by its content like `auto`
(`cache::is_percentage_height` in `calculate_layout_for_subtree_fragment`) - sizing alone could
only give it a pre-layout estimate.

What changes for the apps (static audit; I did not run them before/after: the "after" needs a
build, which the house rules leave to the parent):
- All 48 `height: N%` in examples/ (Rust; C / C++ / Python mirror them), dll/src and
  layout/src/widgets, plus the code-built `PANE_BASE` / `FILL_COLUMN_BASE` / split pane: NONE has a
  content-sized block parent - each sits on the root, in a flex container, or under an abspos or
  px-height box. Nothing visible changes.
- The ~36 test files with percentage heights or vertical scrollers: none affected either (roots,
  flex items, definite parents; the paged harness gives the root a definite block).
- Caveat 1 (Chrome does the same): with client-side decorations the user's `<body>` becomes the
  child of an injected auto-height `<html>` (dll/src/desktop/csd.rs); a `height: 100%` child of a
  body that declares NO height then sizes to its content. No in-repo app does this (the NoTitle
  apps declare `height: 100%` on the body itself, which still resolves against the root);
  `examples/rust/{anim,tray,transitions}.rs` would, if they turned decorations on.
- Caveat 2: an auto-height `overflow: auto|scroll` box inside a content-sized block now grows to
  its content (it kept sizing's placeholder before), as in Chrome - mail `pre { overflow: auto }`.
- Caveat 3: the VideoWidget's VirtualView inherits the height its caller gives the widget's div;
  a third-party caller leaving it auto inside nested plain blocks gets a content-sized video.

## Seen broken, not fixed (other owners or too big for this wave)

- **Block-in-inline is not implemented** (CSS 2.2 9.2.1.1): `<div><a><span style="display:block;
  height:40px"></span></a></div>` lays out 19.2px tall and the span gets no box (Chrome: 40px). The
  reconciler and `layout_ifc` do not split an inline around a block; `<a><img style="display:block">`
  in mail hits it. The cell IFC change keeps such cells on the block branch.
- A shaping result with a font deficit is cached in `per_item_shaped` (text3/cache.rs ~9230): text
  stays invisible after its font loads, until the item is reshaped.
- `bolder` / `lighter` map statically to 900 / 300; CSS Fonts 4 makes them relative to the parent
  weight (`<b>` in normal text should be 700).
- `dll/src/desktop/shell2/common/layout.rs:1555` pairs GeolocationProbe nodes with
  `NodeId::from_usize(i)` of an `enumerate` index - the same off-by-one as item 1.
- `UnifiedLayout::first_baseline` / `last_baseline` report a cluster's raw ascent (`baseline_scaled`,
  no line offset, no leading) as the IFC's baseline (fc.rs 4551 / 4800, read by inline-block
  baseline alignment).
- `editing_host_strut_height` (an empty contenteditable) still resolves `normal` as 1.2em.
