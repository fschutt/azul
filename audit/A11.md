## How to add a counter that a scenario can assert (A1, A5, A8)

A counter of the CPU frame (counted on the rendering thread while a frame renders):
1. `layout/src/cpu_counters.rs` (A1's): a `Counter` variant, `COUNTERS` + 1, a field of `CpuFrameCounters`, its line in
   `add` and in `take`.
2. `layout/src/e2e/full.rs` (mine; a minimal hunk is fine, you need not ask): a field of `CpuCountersJson` of the SAME
   name and its line in `impl From<&CpuFrameCounters> for CpuCountersJson`. The guard
   `audit_tests::a11::a11_every_cpu_frame_counter_is_in_the_frame_report_json` (feature `e2e-server`) fails when
   step 2 is forgotten.
3. Count it with `crate::cpu_counters::count(Counter::X, n)` where it happens. A band thread counts into its own
   thread-local: its counts reach the frame only when they are merged into the UI thread's (A1's `merge`).
4. Tell A11 (your notes, `## For area A11`): the name, what one unit is, its value today for a zoom step / a pan shift /
   a full repaint if you can say it. I wire it into `mapedit3/e2e/*.json` and `scripts/perf_matrix.py`.

A value of the window that is not a CPU frame counter (GPU-side counts, halos pending, resident memory):
1. a field of `FrameReport` (`layout/src/window.rs` ~867-970, not in anyone's range: a minimal hunk) or, for a value
   read when asked (RSS), nothing there;
2. a field of `FrameReportResponse` (`e2e/full.rs`, mine: minimal hunk) and its line in `build_frame_report_response`
   (read from `report` or from the window there). The JSON key is the field name; a scenario asserts it as
   `assert_response {path: "<field>"}` after `get_frame_report`.
3. Note it under `## For area A11` in your notes with its name and unit.

For the real window (`MAPEDIT3_FRAMES=1`, the editor's frame recorder, `mapedit3/src/ui/main/frames.rs`, mine): a
per-frame value reaches it through azul's public API. Either a field of `FrameTimings` (`layout/src/window.rs:772`,
`repr(C)`, written by `FrameClock`; it is in `api.json`: add the field there too and list it under `## api.json`) or
another `CallbackInfo` getter in `api.json`. The editor side is ONE entry of `COLUMNS` in `frames.rs` (see the m4p
notes, `## For area A4 / A5 / A9`); write the entry you want into your notes and I add it, or add it yourself as a
minimal hunk (append to `COLUMNS` and a `fn` reading it).

## For area A1

- A1-band counters: the scenarios' liveness bounds fail if a band thread's counts are lost, by design:
  `zoom_labels` asserts `cpu_since_reset.px_blitted >= 400000` per wheel step (the composite of the picture),
  `pan_sidebar` `px_cleared >= 50000` over 12 shift frames, `render_budget` `px_cleared >= 1000000`. Please add a unit
  test that renders one list serially and with bands and compares `CpuFrameCounters` field by field (equal, except a
  counter you document as per-thread such as a pool's allocations).
- `pixmap.rs:1659` (`blit_buffer_sub`) and `pixmap.rs:1728` (`blit_tinted_coverage`) count `PxBlitted` as `w * h`
  BEFORE clipping to the destination; `pixmap.rs:264` counts the clipped rect. An over-count: an upper bound stays
  safe, a lower bound (liveness) can pass on pixels that were never written. Count the clipped rect (`x_end - sx`
  etc. after the clamp).
- Screenshot renders (`CallbackInfo::render_screenshot`, used by `take_screenshot`, `assert_idle_frames`'s pixel
  check, `assert_changed`) run on the UI thread outside a `FrameScope` and count into the thread-local cells; the next
  `FrameScope::begin` zeroes them (`reset()`). Keep `reset()` in `begin` (or reset after a screenshot): without it a
  screenshot's full repaint lands in the next frame's counters (every idle test would see a full repaint).
- What I assert today (names): `px_cleared`, `px_blitted`, `items_walked`, `items_painted`, `text_runs`, `glyphs`,
  `halos_drawn`, `groups_opened`, `group_px`, `scan_items` (not `retained_hits` yet). Renaming one breaks the
  scenarios: tell me the new name.
- After your steps, the budgets to tighten (the m4p notes have the table): a zoom step with a retained surface:
  `items_painted == 0`, `halos_drawn == 0`, `groups_opened` 0 or 1, `retained_hits >= 1`, `px_blitted` about the view
  (937 k at 1280x800); a pan shift frame read from the retained surface: `items_painted == 0`, `px_cleared == 0`,
  `px_blitted >=` the strips; a group that lands nowhere: `groups_opened` per full repaint = the groups in the
  damage. Write in your notes which counter each step changes and its value if you can compute it.

## For area A4 / A5 (the resource-update recorder; see the m4p notes for the full proposal)

The headless runner never builds a WebRender transaction (it paints with the CPU backend), so a runner command for
GPU resource updates would always answer nothing. The recorder belongs in a dll test: `register_frame_resources(&mut
LayoutWindow, &mut WrTransaction, dpi)` (`wr_translate2.rs:1270`) needs no `RenderApi` and no GL context, and
`WrTransaction::resource_updates` is `pub` (`webrender/core/src/render_api.rs:161`). Proposal under `## For area A4`
in the m4p notes.
