# A9: memory and allocation (audit of 2026-11-21)

Area: per-frame allocations and clones, the bounds of every retained cache on an 8 GB machine, leaks, a way to see
memory growth (RSS). Cuts across every other area; owns no big file. Model: Opus. Blind: nothing here was compiled
or run; every number below is read from the types and the code (file:line of `audit/base`, `f48bcc7b4`) or from the
samples (`municipal-city-12k.mapjson` = Tuebingen, counted with `python3 -I`), and is marked *est.* where a size could
not be read off a type (sizes of structs nobody can `size_of` without a compiler).

## Claims

A9 restructures nothing. Minimal patches only (RULES.md section 4), never inside a function another area claims, in A1's
three big files only on top of `audit-A1-structure`. Touched (few lines each, function not claimed by its owner):

- `layout/src/window.rs` `FrameReport::merge_into` (A9-01), `LayoutWindow::remap_node_ids` dropped-child loop (A9-04);
- `layout/src/e2e/full.rs` `e2e_set_presented_frame` (A9-02), `FrameReportResponse` + `build_frame_report_response`
  (A9-07, two fields: resident memory now / peak);
- `layout/src/cpurender/raster.rs` `WindowGpuValues::of_doms` (A9-03, after the A1 tag or `[pre-structure]`);
- m4p `mapedit3/src/ui/main/frames.rs` (A11's file: minimal hunks): resident memory in the recorder (A9-05), the
  recorder's JSON written off the UI thread (A9-06);
- tests in `layout/src/audit_tests/a9.rs`, `dll/src/desktop/audit_tests/a9.rs`, and next to private items.

## Sizes used throughout

Window 2560x1440 logical. DPI 1: 2560x1440 = 3,686,400 px, RGBA = **14,745,600 B (14.7 MB)**. DPI 2: 5120x2880 =
14,745,600 px, RGBA = **58,982,400 B (59.0 MB)**. The view's isolated group (CPU_RENDERING 1.2): (2510+512)x(1402+512)
= 3,022x1,914 = 5,784,108 px = **23.1 MB** at DPI 1; at DPI 2 6,044x3,828 = 23,136,432 px = **92.5 MB**.
Tuebingen view: 1,567 texts, 617 images, 2,118 reference frames (= 2,118 CSS `transform`s, each a `TransformKey` in the
view DOM's `GpuValueCache::css_transform_keys`, `core/src/gpu.rs:54`; + 1 for the picture root), 17,495 items.
`HashMap<usize, ComputedTransform3D>`: entry 8 + 64 = 72 B; 2,119 entries need 4,096 buckets (2,048 x 7/8 = 1,792 <
2,119) = 4,096 x 73 + 16 = **~299 KB** per map. `LogicalRect` = 16 B. `CellAa` (agg) = 16 B. A tile = 512x512x4 =
1,048,576 B.

## Leaks and growth

- A9-01 (`FrameReport` accumulated damage on the GPU path): fixed.
- A9-04 (`child_dom_fingerprints`, `child_layout_caches` of a VirtualView child whose host unmounted): fixed.
- E8 (recorder frames): 32 B per frame for the life of the process; deliberate (the JSON has every frame); with A9-06
  the cost per write no longer lands on the UI thread. Left.
- `GLYPHS` (#30): the halo glyph cache never runs `gc()`; bounded by rotation (2 generations), so not a leak: its
  bound (up to ~56 MB at DPI 2) is held for the life of the thread. For A5: call `gc()` where the frame's halos are done.
- Caches keyed by a scale that takes a new value at each zoom settle: glyph cells (#6: ppem / `scale_fixed` in the key),
  CPU halos (#7: scale in the key), GPU halos (#29), shaped text (#19: font size in the style hash). All bounded by
  their LRU / generations (checked); none is keyed by the per-step transform (the zoom step composites, the settle
  re-renders at one new scale).
- Checked, no growth: `FrameIndex` is stored in its list and dropped with it (#13); `ContentJournal` (#23); patch
  damage log (#24); `VirtualViewManager::states` (#25); a dropped child's GPU value cache (`window.rs:30351`); the
  editor's tile cache (E1-E4 bounded), undo (E7).
- Not read: `core/src/resources.rs` image/font key lifetimes on the GPU side (A4's notes), WebRender's caches (A4),

### A9-01
- file: `layout/src/window.rs:1067` (`FrameReport::merge_into`), recorded at `dll/src/desktop/shell2/macos/mod.rs:9948`
- class: leak
- evidence: `accumulated_paint_damage` / `accumulated_present_damage` are `extend`ed by every recorded frame's rects
  and only cleared by `reset_counters` (e2e `reset_frame_counters`). A CPU frame report becomes `Full` on the first
  frame (`Full` absorbs), but the macOS GPU path records `FrameDamage::Rects(self.gpu_damage_rects.clone())` for every
  frame and never `Full`: 2 x 16 B x rects per frame, 60 fps -> 1.9 KB/s per rect, ~7-14 MB per hour of animation (Vec
  doubling), for the life of the window; and every `frame_report_synced()` clones the whole report.
- fix: a rect already covered by one of the last 8 accumulated rects is not appended (the union is unchanged: exact);
  past 4,096 rects the list is replaced by its bounding box (a superset; only an e2e step with > 4,096 distinct rects
  between two resets sees it).
