# A9: memory and allocation (audit of 2026-11-21)

Area: per-frame allocations and clones, the bounds of every retained cache on an 8 GB machine, leaks, a way to see
memory growth (RSS). Cuts across every other area; owns no big file. Model: Opus. Blind: nothing here was compiled
or run; every number below is read from the types and the code (file:line of `audit/base`, `f48bcc7b4`) or from the
samples (`municipal-city-12k.mapjson` = Tuebingen, counted with `python3 -I`), and is marked *est.* where a size could
not be read off a type (sizes of structs nobody can `size_of` without a compiler).

## Claims

A9 restructures nothing. Minimal patches only (RULES.md section 4), never inside a function another area claims, in A1's
three big files only on top of `audit-A1-structure`. Touched (few lines each, function not claimed by its owner):

- `layout/src/window.rs` `FrameReport::merge_into` (A9-01), `LayoutWindow::remap_node_ids` dropped-child loop (A9-04);
- `layout/src/e2e/full.rs` `e2e_set_presented_frame` (A9-02), `FrameReportResponse` + `build_frame_report_response`
  (A9-07, two fields: resident memory now / peak);
- `layout/src/cpurender/raster.rs` `WindowGpuValues::of_doms` (A9-03, after the A1 tag or `[pre-structure]`);
- m4p `mapedit3/src/ui/main/frames.rs` (A11's file: minimal hunks): resident memory in the recorder (A9-05), the
  recorder's JSON written off the UI thread (A9-06);
- tests in `layout/src/audit_tests/a9.rs`, `dll/src/desktop/audit_tests/a9.rs`, and next to private items.

## Sizes used throughout

Window 2560x1440 logical. DPI 1: 2560x1440 = 3,686,400 px, RGBA = **14,745,600 B (14.7 MB)**. DPI 2: 5120x2880 =
14,745,600 px, RGBA = **58,982,400 B (59.0 MB)**. The view's isolated group (CPU_RENDERING 1.2): (2510+512)x(1402+512)
= 3,022x1,914 = 5,784,108 px = **23.1 MB** at DPI 1; at DPI 2 6,044x3,828 = 23,136,432 px = **92.5 MB**.
Tuebingen view: 1,567 texts, 617 images, 2,118 reference frames (= 2,118 CSS `transform`s, each a `TransformKey` in the
view DOM's `GpuValueCache::css_transform_keys`, `core/src/gpu.rs:54`; + 1 for the picture root), 17,495 items.
`HashMap<usize, ComputedTransform3D>`: entry 8 + 64 = 72 B; 2,119 entries need 4,096 buckets (2,048 x 7/8 = 1,792 <
2,119) = 4,096 x 73 + 16 = **~299 KB** per map. `LogicalRect` = 16 B. `CellAa` (agg) = 16 B. A tile = 512x512x4 =
1,048,576 B.

## Leaks and growth

- A9-01 (`FrameReport` accumulated damage on the GPU path): fixed.
- A9-04 (`child_dom_fingerprints`, `child_layout_caches` of a VirtualView child whose host unmounted): fixed.
- E8 (recorder frames): 32 B per frame for the life of the process; deliberate (the JSON has every frame); with A9-06
  the cost per write no longer lands on the UI thread. Left.
- `GLYPHS` (#30): the halo glyph cache never runs `gc()`; bounded by rotation (2 generations), so not a leak: its
  bound (up to ~56 MB at DPI 2) is held for the life of the thread. For A5: call `gc()` where the frame's halos are done.
- Caches keyed by a scale that takes a new value at each zoom settle: glyph cells (#6: ppem / `scale_fixed` in the key),
  CPU halos (#7: scale in the key), GPU halos (#29), shaped text (#19: font size in the style hash). All bounded by
  their LRU / generations (checked); none is keyed by the per-step transform (the zoom step composites, the settle
  re-renders at one new scale).
- Checked, no growth: `FrameIndex` is stored in its list and dropped with it (#13); `ContentJournal` (#23); patch
  damage log (#24); `VirtualViewManager::states` (#25); a dropped child's GPU value cache (`window.rs:30351`); the
  editor's tile cache (E1-E4 bounded), undo (E7).
- Not read: `core/src/resources.rs` image/font key lifetimes on the GPU side (A4's notes), WebRender's caches (A4),

### Judgement

**What the editor may hold.** The machine has 8 GB; macOS with WindowServer and the usual background holds ~3 GB, a
browser and a mail client another 2-3 GB; the swap-in risk starts when the editor plus those pass ~6.5 GB. Proposed
budget: **at rest 600 MB, at a peak 1.0 GB** at the user's display (D2), 25 % more at D3. Today: D2 rest ~0.8 GB
(t = 256) to 1.1 GB (low zoom), peaks to ~1.4 GB; D3 rest ~1.0-1.5 GB. Over by ~200-500 MB at rest. The rows that close
the gap (each with its owner below): E1 -64 to -270, E2 -31, S4 -23, C1-C4 -1 to -2 F (-22 to -118), C6 -44 (D2),
S2 -12, C9 -18, G1 at low zoom (follows E1).

**Over-generous or duplicated rows** (the change, its arithmetic, and that one view's working set still fits):
1. E1 tiles (A7-editor): 512 px rasters at DPI 1 are 2-4 x the pixels a tile shown at 129-256 pt needs; and "128
   besides the view" is a count, not bytes. Change: `RASTER_PX = 256 x dpi` (256 at DPI 1, 512 at DPI 2: the view at
   DPI 1 = 117 x 256 KiB = 29 MiB, was 117); "besides" as bytes: 64 MiB (64 tiles at DPI 2, 256 at DPI 1). D2 saves 64
   MiB at rest, D1 ~200 MiB; at t = 129 on D1 (425 tiles) 425 -> 106 MiB. The view's own tiles stay unevicted (A7-editor-06).
2. E2 base64 fonts (A7-types: `FontFileBase64`): 31.0 MB of base64 text held for the session only to be saved again.
   Change: decode once at open into `Arc<[u8]>` (the same allocation `PrintPdfFont::bytes` and the registration use),
   encode at save (on the save worker). -31 MB; save +31 MB transient on the worker.
3. S4 fonts in azul (A8, blocked (b) on rust-fontconfig): `FcFont.bytes: Vec<u8>` copies every in-memory face once
   more (23 MB). Change: `Arc<[u8]>` in rust-fontconfig (patch file in `audit/patches/`, A8 writes it) and
   `register_font` storing the `Arc<Vec<u8>>` it is given without the `Arc<[u8]>::from` copy. -23 MB (+ -23 MB transient).
4. C1-C4 the same picture 4-5 times (CPU, macOS): framebuffer, `cached_bitmap` (rows copied from the framebuffer),
   AppKit backing store, compositor root layer. Changes: (A10) make the `NSBitmapImageRep` over the framebuffer's
   own bytes (`initWithBitmapDataPlanes:` with the framebuffer pointer, no copy; drawn on the main thread only, which
   is the thread that writes the framebuffer) -1 F; (A1) the full repaint renders the root layer's range straight
   into the target and composites only the child layers over it, so `CompositorState` keeps no root pixbuf -1 F.
   D2 -45 MB, D3 -118 MB. A9-09 already drops the root layer while minimised.
5. C6 kept surfaces (A1): 2 surfaces / 96 MB keeps TWO view pictures at D2 (88 MB) while the editor needs one. Change:
   `max_bytes = min(96 MB, 2 x F)`: D1 29.5 (one 23.1 surface), D2 45 (one 44.2), D3 96 (one 92.5). -44 MB at D2.
6. C9 band glyph caches (A1/A8): three more caches of the same glyph cells. Change: `MAX_BAND_CACHE_ENTRIES` 4,096 ->
   1,024 (a band's labels: Tuebingen 1,567 labels x ~10 cells / 8 bands = ~2k lookups, a few hundred distinct), or
   bands look up the window's cache read-only first (a `get_cells(&self)` probe before the band's own `get_or_build`).
   -9 MB D1, -18 MB D2/D3.
7. S2 shaping cache floor (A8-06): 16,384 keeps ~10 old zoom levels of a 1.5k-label view that a zoom back hits only at
   the exact old scale. Change: clamp `sweep_at` to 4,096..32,768 (2 x kept still holds Berlin's 12.5k). -12 MB T.
8. G1 and E1 together on the GPU path: every visible tile is in the editor's cache AND in WebRender's atlas. Not
   avoidable with raw images (WebRender needs the template to re-upload after an eviction); halved by change 1 at DPI 1.
9. C10 / G3 CPU and GPU halo stores: only the one of the running backend is filled (both thread-locals start empty;
   `text_halos` runs on the GPU path only, `kept_cpu_halo` on the CPU path only): checked, not a duplicate.
10. E6 `LAID_OUT` (A7-types): since A7-types-21 the analysis fills `RUNS` (a quarter of an entry), not `LAID_OUT`;
    `LAID_OUT` keeps 2 x 16,384 layouts for its remaining callers. Change: `LAID_OUT_GENERATION` 16,384 -> 4,096 unless a
    remaining caller has a working set above it (then say which). -12 to -48 MB worst case per thread.
11. G6 / G7: WebRender's own bytes are unmeasured: `RenderApi::report_memory` into the frame recorder (A4 / A11).
