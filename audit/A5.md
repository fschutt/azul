# A5: the label flicker on the GPU path ("labels flicker one by one")

Blind audit, nothing compiled or run. Base: `audit/base` (`e02646d9a` + scaffolding). Line numbers are the base
commit's unless a commit is named. Numbers marked *est.* are computed from the code's formulas, not measured.

**Root cause (A5-01, confirmed by reading, event sequence below): the kept halo pictures were an LRU smaller than one
frame's labels, and a label whose halo is not kept is painted without one.** On the user's 2x display the byte bound
(32 MB), not the entry bound (1,024), is what a Tuebingen-style view exceeds. Second cause of the same symptom
(A5-02): every zoom that settles makes every halo a new picture, a frame draws a bounded number, the rest of the labels
are painted without halo until their turn. Both are fixed; the rest of H1-H7 is refuted or is a trigger of these two.

The GPU halo path is byte-identical in the three revisions involved: `git log 7b9625951..e02646d9a` is empty for
`dll/src/desktop/wr_translate2.rs`, `compositor2.rs`, `layout/src/managers/gpu_state.rs`, `layout/src/image_memo.rs`;
`text_halo.rs` changed once (`03bd2e761`), which only ADDS the CPU renderer's own cache (`CPU_HALOS`, a second
`ImageMemo`; the GPU's `HALOS`, key, budget and constants are untouched). So what was read is what the user ran, in
both binaries (`mapedit3-a74d11c`, `mapedit3-azul03bd2e7`).

### The event sequence of A5-01 (old code)

Inputs: a view of N distinct halos L0..L(N-1) in list order, a cache of C < N (entries or bytes), a frame budget that
draws b halos (`HALOS_DRAWN_ANYWAY` 2, then 12 ms: `wr_translate2.rs:674-676`; *est.* 12-40 at 2x for the editor's
spreads, from `dilate_disk`'s ink x taps).
Each frame runs two scans in list order: `text_halos(.., Some(fonts))` in `register_image_resources`
(`wr_translate2.rs:768-782`: kept -> used; missing -> drawn while the budget lasts, `text_halo.rs:228-234`, else
deferred) and `text_halos(.., None)` in the translation (`compositor2.rs:315`: kept ones only). `ImageMemo::get` ticks
the clock per lookup (`image_memo.rs:50-57`); `insert` at a bound removes the entry with the smallest `last_used`
(`:67-79`).

1. Frames 1..C/b: fill. Frame F: the cache holds L0..L(C-1), each touched in list order by the last translation.
2. Frame F+1, scan 1: L0..L(C-1) found (touched in order, so L0 is now the oldest). L(C) missing: drawn, inserted,
   `insert` drops the oldest: **L0, which this same scan used**. ..., L(C+b-1) drops L(b-1). Budget spent; the rest
   deferred, `halos_left > 0` -> `halos_owed` (`:1359`) -> the platform loop asks for another frame
   (`macos/mod.rs:9567`, `:9981-9988`).
   Scan 2 (translation): L0..L(b-1) are not kept -> `halos.get(&item_index)` is `None` -> `builder.push_shadow` with
   `blur_radius` only (`compositor2.rs:2248-2275`). WebRender's shadow has no spread, and a blur of 0 is "a copy of
   the primitive" added straight to the draw list (`scene_building.rs:2748-2797`, `blur_is_noop`): for the editor's
   `text-shadow: 0px 0px 0px <w>px` (`map.rs:1122`) a copy of the text in the halo's colour UNDER the text.
   **Drawn: L0..L(b-1) without their outline; L(C)..L(C+b-1) with it.**
3. Frame F+2, scan 1: L0 missing -> drawn, drops the oldest, now L(b) (the first entry the last translation touched
   and this scan has not reached). ... **Drawn: L0..L(b-1) have their halo back, L(b)..L(2b-1) lost theirs.**
4. And so on: a hole of b labels walks through the list one hole-width per frame and wraps; each kept label is
   without halo for one frame in every (C+b)/b; the N-C-b labels at the end never get one. Each frame also adds b
   images and deletes b (3 epochs later), translates every list again and rebuilds the scene (A4, For area A5, 1).
5. After `HALO_FOLLOW_UPS_MAX` = 900 follow-ups the chain stops (`:1358-1359`), with the hole where it is and the
   tail without halo, until the next frame that scans (any rebuilt list: a hover over a label, a tile without a
   node, a settle) starts 900 more. So yes, it also cost frames at rest: up to 15 s of them after each trigger.

Which bound, at which scale (the picture was the whole box the glyphs can reach, `text_halo.rs:467-476` with
`visual_bounds` `display_list.rs:3345-3382`: W = (pen span + 2 em) x dpi + 2r, H = 2.25 em x dpi + 2r, r = ceil(spread x
dpi), 4 bytes a pixel). A street name of a municipal sample (2.3 mm type, 0.35 mm outline, 12 glyphs) at 6 px/mm, *est.*:

| | box, DPI 1 | box, DPI 2 | Tuebingen view, 1,567 texts | the user's full screen (1470 x 956 pt; *est.* 640 texts in the picture) | Berlin, 12k texts (if its style had outlines) |
|---|---|---|---|---|---|
| bytes per halo | 112 x 37 px = 16.6 KB | 223 x 73 px = 65 KB | | | |
| old: 1,024 entries | | | DPI 1 and 2: over by 543 | under | over by 11k |
| old: 32 MB | holds 2,020 | **holds 500** | DPI 1: 26 MB, under; **DPI 2: 102 MB, over 3x** | DPI 1: 11 MB; **DPI 2: 42 MB, over** | 199 MB / 780 MB |
| new: picture cut to its ink (A5-04) | *est.* 7 KB | *est.* 28 KB | 11 MB / 44 MB | 4.5 MB / 18 MB | 84 MB / 336 MB |
| new: 96 MB, 16,384 entries | | | fits, twice over at DPI 1, once and a settle's overlap at DPI 2 | fits 5x | DPI 2: about 2,700 sharp, the rest on small stand-ins (2 KB each), stable |

Other estimates of the same box: A8 8.7 KB / 32 KB (it takes the run's clip as the unpadded line box, 90 x 18 px at
DPI 1; the clip and the ink box a halo is drawn in are padded by an em and more, `display_list.rs:9515-9560`,
`:3370-3381`), A9 6 KB / 24 KB. With those the 32 MB hold about 1,000 pictures at DPI 2, the same count as the entry
bound; with mine about 500. Either way: at DPI 2 the Tuebingen view is over the old cache by bytes AND by entries,
and `frame_box_bytes` of the new counters is the measured value of the "box" rows. Every headless number so far is
DPI 1, where only the entry bound binds and only above 1,024 texts; on the user's Retina display the thrash starts
somewhere between 500 and 1,000 labels in the picture.

A8's reading ("every label is asked for every frame in the same order, an LRU smaller than the cycle hits 0 %: each
frame evicts exactly the entries the next frame needs first") is the mechanism above with one correction: the hit
rate is not 0 % because a frame DRAWS only b halos (the budget), so it also drops only b. With no budget every miss
would drop the next entry the scan needs, all N would be drawn every frame, and nothing would flicker (every label
would have a fresh halo in every frame, at N halo rasters per frame: the 5 s frames `943d03e0c` cured). The budget
turned that cost into the flicker: the b halos drawn per frame are paid for with b labels that go without.

### The event sequence of A5-02 (old code)

A zoom settles (`tiles.rs:546`, 140 ms after the last step): `render_map_view` builds every label at the new scale;
`font_px = layer.font_size * s` and the spread `text_outline_width * s` (`map.rs:1105`, `:1122`), both part of the key
(`text_halo.rs:389-394`). Settle frame: scan 1 finds no key, draws b, defers N-b; the translation paints N-b labels
with WebRender's spread-less shadow: **every halo but b is gone in one frame**, then b more labels per follow-up frame
get theirs, in list order: N/b frames (*est.* 0.5-2 s for the user's 640, each frame a full re-translation and
scene build). During the gesture itself nothing changes (the picture root's transform is a value; the kept
pictures are scaled by the GPU).

### A5-03, the key (old code)

`Scope::key` hashed `round((glyph.x - first.x) * 64)` and the same for the clip and ink rects
(`text_halo.rs:395-406`). The positions are window positions in f32: the difference depends on where the label stands.
Example: advance 4.6953125 px. Pen at 20.0: 24.6953125 - 20.0 = 4.6953125 -> 300.5 steps -> 301. Pen at 2047.9 (f32
2047.9000244140625): 2052.59521484375 - 2047.9000244140625 = 4.6951904296875 -> 300.49 steps -> 300. Simulated (f32
emulation, 200k random advances and origins up to 3,000 px): 0.3 % of the values differ between two places; with
about 14 position-dependent values per label one label in 25 gets a new key at every pan that re-renders the view
(`OVERSCAN_PX` 256, `map.rs:289`), is drawn again and is without halo meanwhile.

## Findings

### A5-01 a frame's halos are dropped by the frame itself (the flicker)
- file:line: `layout/src/cpurender/text_halo.rs:41-43`, `:222-234`, `:270-271`; `layout/src/image_memo.rs:61-91`;
  `dll/src/desktop/compositor2.rs:2220-2275`; `dll/src/desktop/wr_translate2.rs:1351-1359`.
- class: wrong-output (and waste: follow-up frames for ever).
- evidence: the sequence and the table above.
- fix: `HaloCache` (text_halo.rs). A scan (`within_halo_budget` = one frame's look at its lists) drops no entry that
  it or the scan before it has used, as a shadow's own picture or as a stand-in; entries used by neither go, oldest
  first; when the pictures in use fill the cache a new one is not drawn (`unkept`), keeps its stand-in, and no frame
  is owed for it (`admit` counts it apart from `pending`). Bounds 96 MB / 16,384 (1.2 % of 8 GB; the renderer holds
  the pictures a frame paints once more as textures). `HALO_FOLLOW_UPS_MAX` stays as a backstop only.
- test: `text_halo.rs` `audit_a5_tests::a_view_of_more_halos_than_the_cache_holds_keeps_the_halos_it_has` (1,567
  labels against 1,024: the set with a halo never shrinks, comes to rest with nothing drawn or dropped),
  `pictures_of_earlier_frames_make_room_oldest_first`, `the_bytes_of_the_pictures_in_use_are_not_given_up`; dll
  `audit_tests::a5::a5_a_view_that_does_not_fit_keeps_its_halos_and_comes_to_rest_at_{1x,2x}` (the recorder).
- status: fixed `175b52e85` + `816b3bb25` (the two-scan rule and the stand-in's replacement).

### A5-02 a halo whose picture is not drawn yet was no halo (the wave after every zoom settle)
- file:line: `text_halo.rs:226-230` (deferred -> `None`), `compositor2.rs:2248-2275` (fallback without spread).
- class: wrong-output.
- fix: a SPREAD shadow without its own picture is painted (same image item, same place in the list) with a stand-in:
  (1) the newest kept picture of the same SHAPE - fonts and glyphs, blur and spread as 32nds of the type size, not the
  size - stretched about the first glyph's pen by new size / old size, at most 8x (`HaloCache::stand_in`,
  `placed`); at a zoom settle that is the label's own old picture, as the zoom's transform showed it; (2) else a
  small picture drawn now at a quarter of the size (half under 20 px/em, none under 10): 1/16 of the pixels, 1/4 of
  the spread, *est.* 1/250 of the dilation; 64 per frame, then 6 ms (`Scope::preview`, `PREVIEWS_ANYWAY`,
  `PREVIEW_TIME`); kept as the halo of that text at that scale, found as the stand-in of its shape. Blur-only
  shadows are unchanged (WebRender's own blur is right for them). A stand-in is held like an own picture and gives
  way to the picture it stands for (`make_room(.., replacing)`).
  Decision recorded: a ring of text copies as the stand-in was rejected - a dilation by r needs O(r^2 / stroke^2)
  copies (*est.* 32-64 per label at the editor's 4-8 px spreads on a 2x display).
- test: `a_stand_in_is_stretched_about_the_first_glyphs_pen` (100 x 30 px at 24 px/em, corner (-6,-22) from the pen;
  at 36 px/em, pen (300,200): painted from (291,167), 150 x 45), `a_stand_in_is_kept_while_it_is_painted_and_gives_way_to_what_it_stands_for`;
  dll `a5_a_zoom_that_settles_keeps_every_halo_at_{1x,2x}`.
- status: fixed `175b52e85`, `816b3bb25`. Kill switches (one line each, in `text_halos`): the `scope.preview(..)?` arm
  (no small pictures), `None if scope.spread <= 0.0` -> `None` (no stand-ins at all).

### Checked: fine
- A5-10 image-key lifecycle of a dropped halo: its `ImageRef` leaves the cache and the live set; the key is deleted 3
  epochs later (`wr_translate2.rs:1778-1797`); no list names it by then (every list is translated again when a halo
  was drawn). `ImageRef` ids are never reused (`core/src/resources.rs:2349-2353`). The recorder asserts it per frame.
- A5-11 the scale of the picture root (the zoom's transform) is not in the key (`dpi` is): a zoom gesture draws no

- A5-12 the CPU path since `03bd2e761` uses its OWN cache (`CPU_HALOS`, 4,096 / 32 MB of 1 byte a pixel, key
  `raster::kept_shadow_key`): no interaction with the GPU's. It draws a missing halo at once, so it cannot flicker;
  over its bound it draws every halo every frame (cost only). See For area A1.
- A5-13 does a pending halo keep the window awake? Old: yes, see sequence step 5. New: `pending` falls by at least
  `HALOS_DRAWN_ANYWAY` per follow-up frame and nothing in use is dropped, so the chain ends after at most
  pending / 2 frames; `unkept` owes nothing.
- A5-14 two windows on one thread share the cache: with the two-scan rule two windows that scan in turn do not drop
  each other's halos (three would). The editor has one.

## How the user sees it (three lines)

1. Old binary (`mapedit3-azul03bd2e7`), Tuebingen-type sample, window as usual: zoom once and wait: the outlines
   of the labels keep going off and on here and there for about 15 s, stop, and start again when the pointer crosses
   a label. Make the window a quarter of its size (under about 500 labels in the picture): it does not happen. That
   is A5-01 and nothing else on the list behaves so.
2. New binary with `MAPEDIT3_FRAMES=1` (or `AZ_HALO_STATS=1` for a line per frame on stderr): F12 after the view
   came to rest. **`h used` over 1,024 or `h box MB` over 32 proves the old cache could not hold this view**; under
   both refutes A5-01 for it (then it was A5-02 alone: look at `h wait` in the "zoom settle" row).
