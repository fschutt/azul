## Spaces

A2-cpu's `## Spaces` did not exist when this was written (its notes file held the heading only); these are the names used
here. The first four are the renderer's, the rest the shells'.

| space | origin, direction | unit | where |
|---|---|---|---|
| logical px | window top-left, y down | CSS px = AppKit points = Wayland surface units | display lists, `FrameDamage::Rects`, `LogicalRect` |
| buffer px | frame top-left, y down, row 0 = top row | device pixels | `AzulPixmap`, every CPU frame, `to_rects_physical` (`PxRect`) |
| DPI factor | `size.dpi / 96` (u32 dpi) | buffer px per logical px | 1 or 2 on macOS, n/96 elsewhere |
| frame size | `ceil(logical * dpi)` in f32 | buffer px | `CpuBackend::render_frame`, `present_geometry::frame_size_px` |
| AppKit view points | view BOTTOM-left, y UP (`isFlipped` is not overridden in `CPUView` or `GLView`: checked) | points | `setNeedsDisplayInRect:`, the rect `drawRect:` gets, `bounds` |
| AppKit backing px | view bottom-left, y up | device pixels (`convertRectToBacking:` = points x backing scale) | `dirty_rows_to_copy`'s input |
| bitmap rep space | bitmap bottom-left, y up; BYTES are stored top row first | pixels (the rep's `size` equals its pixel size) | source rect of `drawInRect:fromRect:` |
| AppKit window base | window bottom-left, y up | points | `NSEvent.locationInWindow` (mouse) |
| X11 window px | window top-left, y down | device pixels | `XPutImage` / `XShmPutImage` dest, ConfigureNotify, pointer events |
| Wayland surface units | surface top-left, y down | logical | pointer events, `wl_surface.damage`, viewport destination |
| Wayland buffer px | buffer top-left, y down | device pixels | shm slots, `wl_surface.damage_buffer` |
| Win32 client px | client top-left, y down | device pixels | `BitBlt` / `StretchDIBits` dest, `WM_SIZE`, mouse lparam; DIBs are made top-down (`biHeight < 0`) |
| Android buffer rows | buffer top-left, y down | device pixels | `ANativeWindow_lock` lines |

Conversions (all in `layout/src/window.rs`, tested in `layout/src/audit_tests/a10.rs`):

- logical -> buffer px (`to_rects_physical`): `x0 = floor(x * d)`, `x1 = ceil((x + w) * d)`, same for y, clamped to the buffer,
  empty rects dropped. Outward. Same formula as `cpurender::logical_rects_to_buffer` (checked).
- buffer px <-> bottom-left px (`flip_rect_y`): `y' = H - (y + h)`; involution for rects inside the buffer.
- bottom-left px (fractional) -> rows / columns (`rows_of_bottom_left_rect`): `y0 = floor(H - (y + h))`, `y1 = ceil(H - y)`,
  `x0 = floor(x)`, `x1 = ceil(x + w)`, clamped. Inverse of the flip.
- buffer px -> AppKit points (`present_rect_in_view_points`, macOS): flip, then divide by the backing scale.
- device px -> logical that renders back to the same px (`logical_len_for_px`), fractional surface size (`surface_len_px`).

The one worked example, used in commits and tests: the strip of a pan step, logical (1267, 20) 13 x 1402 in a 1280 x 1440 pt view.

| | scale 1 | scale 2 |
|---|---|---|
| buffer | 1280 x 1440 px | 2560 x 2880 px |
| present rect (buffer px) | (1267, 20, 13, 1402) | (2534, 40, 26, 2804) |
| `setNeedsDisplayInRect:` (points, y up) | (1267, 18, 13, 1402) | (1267, 18, 13, 1402) |
| `drawRect:` dirty rect in backing px | (1267, 18, 13, 1402) | (2534, 36, 26, 2804) |
| rows / columns copied (top-down) | rows 20..1422, columns 1267..1280 | rows 40..2844, columns 2534..2560 |
| bytes copied into the bitmap | 1402 x 52 = 72,904 | 2804 x 104 = 291,616 |
| source rect in the bitmap (y up, px) | (1267, 18, 13, 1402) | (2534, 36, 26, 2804) |
| destination rect (points) | (1267, 18, 13, 1402) | (1267, 18, 13, 1402) |

## Findings

Severity = ms x frequency where a cost is known; `wrong` = wrong pixels on screen.

### A10-01 macOS present: rect conversions
- file: `dll/src/desktop/shell2/macos/mod.rs` (`dirty_rows_to_copy`, `update_framebuffer`, `invalidate_present_rects`, `drawRect:`)
- class: sign/offset
- evidence: algebra and table above. Both invalidation paths computed `x / (fb_w / bounds_w)`, `bounds_h - (y + h) / (fb_h / bounds_h)`;
  for whole pixel sizes that equals `flip / scale`. `drawRect:` flips back with the framebuffer's height and draws the bitmap's
  `(x0, H - y1, x1 - x0, y1 - y0)`. All four steps agree; the view is not flipped; the bitmap's bytes are top row first.
- fix: none needed for whole sizes; the arithmetic is now `present_rect_in_view_points`, `bitmap_source_rect` (macOS) and
  `flip_rect_y`, `rows_of_bottom_left_rect` (layout), and the invalidation uses the backing scale `drawRect:` sized the buffer with
  (exact inverse of `convertRectToBacking:`) instead of the framebuffer / bounds ratio.
- test: `a_present_rect_is_invalidated_flipped_and_in_points`, `the_rows_drawn_are_the_rows_invalidated`,
  `a_dirty_rect_rounded_outward_by_appkit_still_covers_the_damage`, `appkit_shows_the_copied_rows_where_the_frame_has_them`
  (draws through AppKit into an offscreen bitmap and reads the rows back: runs without a window), layout:
  `a_rect_is_flipped_by_its_bottom_edge`, `the_flip_round_trips_for_every_rect_in_a_buffer`, `rows_of_a_fractional_bottom_left_rect`.
- status: checked: fine; restructured 8a40ffa87 (+ 45f75aeb7)

### A10-02 macOS: the view's framebuffer was truncated, the frame is `ceil`
- file: `macos/mod.rs` `drawRect:` (`backing.size.width as usize`) vs `layout/src/cpu_backend.rs:358` (`(width * dpi).ceil()`)

- fix: `cpu_view_framebuffer_size` = `present_geometry::frame_size_px` on `bounds as f32` (the numbers `handle_resize` stores).

  The other half: the STATE the frame is sized from followed the view only beyond a 0.5 pt tolerance

  also follows whenever `frame_size_px(state) != frame_size_px(bounds)`.
- test: `the_views_framebuffer_is_the_size_of_the_renderers_frame`, `the_macos_state_follows_the_view_when_their_frames_differ`
- status: fixed 8a40ffa87, 1f481839f. If the error line of `note_cpu_frame_size` still shows on a real window, the render
  view and the content view have different bounds (the state is synced from `window.contentView`, the framebuffer from the

### A10-10 Wayland: a preferred scale that is not a multiple of 1/24 does not fit `size.dpi`
- file: `linux/wayland/events.rs` `wp_fractional_scale_preferred_scale_handler` (`new_dpi = (scale_120 * 96 + 60) / 120`)
- class: wrong-output (whole-window resampling)
- evidence: `size.dpi` is u32 with 96 per 1.0, the compositor's scale is n/120. Exact only when n is a multiple of 5 (125, 150,
  175, 200 %). 110 % (n = 132) -> 105.6 -> DPI 106 = 1.1042: 1000 units -> buffer 1104 px, surface 1100 px.
- fix (proposed, not applied: it changes which factor every Wayland conversion uses): keep `size.dpi` as the rounded value
  for the app, but size buffers and frame from `preferred_scale_120`: `d = scale_120 as f32 / 120.0` in `cpu_buffer_spec`,
  in the head of the CPU arm (`dpi` handed to `render_frame` and to `to_present_rects_physical`), and in the GPU path's
  `physical_size`. Wayland pointer coordinates are surface units, so input does not depend on it.
- status: fixed 3d12d951f (CPU path: `WaylandWindow::frame_factor`, `present_geometry::wayland_frame_scale`, the layout
  window is told through `LayoutWindow::set_frame_scale`; a scale change inside one whole DPI remakes the buffers).
  Tests: `a_wayland_frame_is_sized_with_the_compositors_scale_not_with_the_rounded_dpi`,
  `wayland_sizes_and_renders_with_the_compositors_preferred_scale`. Open rest: the GPU path's EGL surface (For area A4, item 3).

### A10-12 Win32: an unchanged frame is presented in full on every WM_PAINT
- file: `windows/mod.rs` CPU block (`.unwrap_or_else(|| vec![(0, 0, w, h)])` on both the DIB and the StretchDIBits path)

### A10-13 macOS: on the path without a display link every frame is presented twice
- file: `macos/mod.rs` (`deliver_invalidation_now` -> `setNeedsDisplay(true)` -> `drawRect:` renders inside)
- class: waste
- evidence: `drawRect:` gets the whole bounds, renders, and the render's `invalidate_present_rects` /

- fix (proposed): skip the invalidation for rects the running `drawRect:` covers; needs `getRectsBeingDrawn:count:` to be exact

- status: open: needs a run. Whether the second pass can be skipped depends on two things AppKit does not document for

  already satisfied, and whether `getRectsBeingDrawn:count:` reports the region the layer really keeps (a `CALayer`
  coalesces to one rect). A wrong skip leaves stale pixels on screen; the waste is one redundant blit on a path that is
  not the default (display link off) and in live resize. The run: `Vsync` off, `AZ_PROFILE=cpu`, hover a button: two
  `draw_rect_cpu` spans per `draw_rect_render_present` confirm the finding; then try the skip with

## Part 1. macOS, line by line

Path of a frame (CPU backend, display link running, the default):

1. `request_redraw` raises `redraw_requested`; the pacer starts the CVDisplayLink or leaves the flag for its next tick.
2. Tick: CVDisplayLink thread -> `vsync_ticks::deliver` -> MAIN thread `mark_views_dirty_on_main` -> `TickAction::Render` ->
   `render_and_present_in_draw_rect` (outside `drawRect:`).
3. CPU arm: `native_target_ptr(w, h)` hands the view's `framebuffer: RefCell<Vec<u8>>` to the renderer as an external pixmap
   (`AzulPixmap::from_external`), `render_frame` paints the damage into it, `native_target = None` after the call.
4. `invalidate_present_rects(to_present_rects_physical(...))`: one `setNeedsDisplayInRect:` per rect.
5. End of the run-loop turn: AppKit calls `drawRect:(dirty)` once with the bounding box of the invalid region; no flag is
   set any more, so nothing renders; the dirty rows are copied into the cached `NSBitmapImageRep` and that span is drawn.

Proofs, step by step:

- **Buffer geometry.** `width x height` = `cpu_view_framebuffer_size(bounds, scale)` (A10-02); stride `width * 4`, tight;
  RGBA8 premultiplied, bytes in memory order R, G, B, A (the renderer's order: `AzulPixmap`); row 0 = top. The bitmap
  (`color_space::cpu_frame_bitmap`): 8 bits, 4 samples, alpha, not planar, `bytesPerRow` asked `width * 4` but READ BACK
  (`draw_framebuffer_span`), `bitmapFormat` checked to be neither alpha-first, non-premultiplied, float nor little-endian
  32-bit (`holds_premultiplied_rgba8`), tagged sRGB; a rep that does not come back that way falls back to the generic one.
  Its `size` is its pixel size (made from pixel dims at 72 dpi), so the source rect of the draw is in pixels.
- **Ownership.** The framebuffer is the view's `Vec`; only `drawRect:` (resize), `update_framebuffer` and `native_target_ptr`
  touch its length, all on the main thread. The raw pointer handed to the renderer lives from `native_target_ptr` to the end
  of `render_frame`; nothing in between calls AppKit or runs the run loop (`prepare_frame_cpu`, the layout callbacks and the
  thread writebacks all run BEFORE the pointer is taken). The dangle guard clears it after the call. The bitmap is cached,
  made anew when the size differs, `bitmapData` is asked on every draw (which is also AppKit's signal that the bytes changed).
- **Rects.** A10-01. The view is not flipped; every conversion flips exactly once.
- **Rounding.** Present rects are outward and clamped (A10-04). Odd pixel rects at 2x are half-point rects; if AppKit rounds
  them to whole points the rows are a superset (`a_dirty_rect_rounded_outward_by_appkit_still_covers_the_damage`).
  `draw_framebuffer_span` refuses anything outside either buffer (A10-03).
- **Resize / live resize.** `windowDidResize:` -> `handle_resize` (state := bounds, exactly) -> during a live resize
  `contentView.display()` runs `drawRect:` now: the framebuffer is resized keeping the top-left (rows are top-down and the
  content is top-left anchored, whichever edge is dragged), `redraw_requested` is raised, the render goes into it natively:
  `render_frame` sees the compositor's old size, computes the L-shaped strips (`compute_resize_damage`), repaints them and
  the relayout's damage. The bitmap is new, so the whole frame is copied and drawn. Outside a live resize the tick may
  render first: that is A10-07.
- **First frame.** Either order works: `drawRect:` first (blank buffer, render inside, owned pixmap, full copy), or tick
  first (the view adopts the pixmap's size, full copy, `drawRect:` finds the same size).
- **`FrameDamage::None`.** Nothing copied, nothing invalidated; unless the view shows the blank fill (A10-07).
- **Second display, full screen.** Size and / or scale change: A10-07 (kept pixels only at the same scale), A10-08 (full
  repaint at the new factor), the display link is made anew for the new display (`handle_dpi_change`). In one of the two
  possible orders (AppKit draws at the new scale before `windowDidChangeBackingProperties:` reaches us) ONE stretched frame
  is shown: the state still has the old factor, the frame has the old size, `update_framebuffer` rescales it. The next
  frame is right. Removing it needs the DPI sync inside `sync_window_size_from_content_view` (it only syncs the DPI when the
  size changed); not done, it would run a layout regeneration from inside `drawRect:` on a path that cannot be tried here.
- **Threads, re-entrancy.** Everything is on the main thread; `CPUView` is `MainThreadOnly`, `canDrawConcurrently` is not
  set. `drawRect:` cannot run while a frame is rendered into the buffer: the renderer does not return to the run loop.
  A1's row bands will write the buffer from worker threads while the main thread is blocked in `thread::scope`: fine for
  AppKit (nothing else touches the view), provided the scope joins before `render_frame` returns (For area A1 item 5).
  Nested `drawRect:` (a callback that resizes the window during a live resize -> `display()`): the outer call holds no
  `RefCell` borrow while it renders, and holds no renderer pointer outside `render_frame`: checked.

### macOS: the states of the view's framebuffer (A10-07)

State = (`fb_content_valid`, `fb_blank`, size). `V` = holds the last frame pixel for pixel (may be a render target, may take
partial copies), `S` = shows the last frame stretched, `B` = blank fill.

| event | from | to |
|---|---|---|
| `drawRect:` same size | any | same |
| `drawRect:` new size, same scale | V | V (top-left kept, strips blank: the renderer's own resize damage covers exactly them) |
| `drawRect:` new size from S or B, or another scale | any | B, and a render is forced |
| `update_framebuffer`, frame of the view's size, whole | any | V |
| `update_framebuffer`, rects | V | V; from S or B it becomes the whole copy -> V |
| `update_framebuffer`, frame of another size | any | S |
| native render (`native_target_ptr`) | V only | V |
| present of an owned frame with damage `None` | B | whole copy -> V; from V or S: nothing |

Sequences (old result / new result):

- Zoom button, tick before `drawRect:`: tick renders at the new size -> owned, full -> rescaled into the old-size buffer (old:
  V, new: S) -> `drawRect:` resizes (old: keeps the squeezed picture as V; new: B) -> render (old: native, damage `None`,
  squeezed picture stays; new: owned, damage `None`, whole copy because B) -> right.
- Move 1x -> 2x, notification first: full repaint at 2x (A10-08) -> owned -> rescaled into the 1x buffer (S) -> `drawRect:`
  at 2x: B -> owned, `None` -> whole copy -> V.
- Move 1x -> 2x, `drawRect:` first: B (scale changed) -> render at the stale factor -> owned 1x frame -> rescaled to 2x (S,
  one stretched frame on screen) -> notification -> full repaint at 2x -> native refused (S) -> owned -> whole copy -> V.
- A size mismatch that never ends (A10-02's case): every frame owned + rescale, the view stays S, an error line after 3 frames.

- renderer: memmove of the clip (1 pass) + the strip;
- macOS: 1 pass (rows) + AppKit draw (>= 1 pass) + CA upload: at least 3 passes of 14 MB = 42 MB of traffic, 170 MB at
  Retina. At 10-20 GB/s for buffers that do not fit a cache that is 2-4 ms at DPI 1 and **8-17 ms at Retina**, before the
  unknown CGImage copy. The paint of that frame is 2.9 ms (ledger): **at Retina the present, not the paint, is the pan's cost.**
- Wayland: memmove + catch-up copy of the clip + compositor upload. X11 SHM: memmove + swizzle of the clip + server copy.

### Design: a present that moves pixels (not implemented)

Decision: **not implementable safely blind.** What "a pan costs the strip only" needs, and why each piece cannot be proven here:

1. The renderer must report the MOVE, not only the rects: `present_moves: Vec<(clip_px, dx, dy)>` next to the paint rects
   (today `ScrollShiftOutcome.present_extra` says "this clip changed", which is true and loses the information). A1's file.
2. A shell primitive that moves window pixels without an upload:
   - X11: `XCopyArea(window -> window)` of the clip by (dx, dy), then SHM-put the strip. Exists, cheap (server side), but
     `GraphicsExpose` for obscured sources must be handled (repaint those rects), and the order of the copy and the puts
     matters with a compositing manager.
   - Win32: `ScrollDC` / `BitBlt` window-to-window, then blit the strip from the DIB. Under DWM the redirection surface is
     the source, so it is exact; `ScrollWindowEx` must NOT be used (it invalidates and scrolls child windows).
   - Wayland: none in core protocol (a buffer attach always carries damage for what changed on screen); the equivalent is
     a second `wl_subsurface` whose position moves, i.e. option 3.
   - macOS: `-[NSView scrollRect:by:]` copies bits only in a view that owns a backing store of its own and is documented
     as a no-op-or-redraw for layer-backed views (all views since 10.14): not usable.
3. So on macOS (and Wayland) the only real version is a **layer per retained surface**: the map view's picture (A1's
   retained group surface, with the editor's 256 px overscan) becomes the `contents` of its own `CALayer` (an `IOSurface`,
   BGRA, double-buffered like the Wayland slots, or a `CGImage` over the surface's memory); a pan is
   `layer.position` / `bounds.origin` inside a `CATransaction` with actions disabled, a zoom is `layer.transform`, and the
   window server composites on the GPU: zero bytes per pan or zoom frame, the strip is not even needed while the overscan
   lasts. Everything painted ABOVE the map (panels, tooltips, selection chrome) must then live in a layer above it with a
   transparent hole: the window's single framebuffer becomes "below", "promoted", "above". That is WebRender's compositor
   surface model on the CPU path; it needs A1's retained surfaces to exist, an export API (surface, extent, matrix, clip,
   opacity, z order), hit-testing unchanged (it is layout-based: fine), and it is useless before a real window shows that
   the present is what a gesture pays.

Open risks: z-order splitting when UI overlaps the map; tearing between the layer move and the framebuffer's strip (two
commits must land in one `CATransaction`); `IOSurface` pixel format (BGRA: the renderer's pool-order mode exists for
Wayland, plus an in-place swizzle of damage); colour management of layer contents (the window is tagged sRGB, an IOSurface
needs its own tag); memory (one overscanned surface = 92 MB at Retina).

Cheaper intermediates on macOS, in the order to try AFTER the measurement:
- **B: render into the bitmap** (no separate framebuffer): `native_target_ptr` returns the rep's `bitmapData`, rows padded
  via `CpuBackend::native_target_row_padding_px` (exists for Wayland). Removes the row copy (`draw_rect_cpu_rows`) and one
  frame-sized buffer. Worth it only if that span is a large part of `draw_rect_cpu`.
- **C: `CGImage` over the framebuffer + `CGContextDrawImage`** (no `NSBitmapImageRep`): removes AppKit's possible whole-bitmap
  copy. The FFI declarations exist in `ios/mod.rs` (`CGDataProviderCreateWithData`, `CGImageCreate`). Worth it only if
  `draw_rect_cpu_appkit` does not shrink with the dirty rect.
- **D: `layer.contents = CGImage` (softbuffer's way)**: Core Animation copies the whole image at every commit: no dirty
  rects at all. Worse than today for small damage; not recommended.

The measurement that decides (one run, real window, CPU backend): `AZ_BACKEND=cpu AZ_PROFILE=cpu`, pan over labels for a
few seconds, then hover a button. Read the spans `draw_rect_cpu` (a whole `drawRect:`), `draw_rect_cpu_rows` (our copy),
`draw_rect_cpu_appkit` (AppKit's draw), `present_view_blit` (legacy copy; should not appear), `draw_rect_render_present`
(a frame's render). If `draw_rect_cpu_appkit` for a hover (a button-sized rect) is as large as for a pan, AppKit copies
the whole bitmap per draw (do C); if `draw_rect_cpu_rows + draw_rect_cpu_appkit` of a pan frame is above ~4 ms, the pan
needs option 3 (and A1's moves); below that, leave the present alone.

### A10-17 two DPI factors: the frame's (`dpi / 96`) and `get_hidpi_factor()`'s (three decimals, cut)
- file: `core/src/window.rs` `WindowSize::get_physical_size`, `linux/x11/mod.rs` `hidpi()`, every shell's `render_frame` call
- class: sign/offset (rounding)
- evidence (A2-cpu-13 / -24, its item for A10): a 1280 x 720 logical window: 150 % and 125 %: both factors are 1.5 / 1.25,
  1920 x 1080 and 1600 x 900 either way. DPI 128 (4/3): 1.3333334 against 1.333: width 1706.67 -> 1707 px against 1706.24
  -> 1706 px. DPI 110: 1467 x 825 against 1466 x 824. *sim*: px -> logical -> px with the cut factor is wrong for 381,189
  of 1,183,744 (DPI 96..384 x 1..4096 px), with `dpi / 96` for none. X11 derived its logical sizes with the cut factor and
  rendered with the exact one (1920 px at DPI 128: 1440.36 logical, content 1920.48 px, frame 1921 px);
  `get_physical_size()` made 2099 px of a 2100 px window (and my own A10-05 code used it: the frame would have been one
  pixel SMALLER than the window above about 2000 px at such DPIs).
- fix: `present_geometry::frame_dpi_factor(dpi)`; `LayoutWindow::frame_scale()` (that, or what the shell said with
  `set_frame_scale`); macOS / X11 / Win32 / Wayland render at `layout_window.frame_scale()`, iOS / Android at

### The contract of `present_moves` (for A1's producer; the consumer is written after the user's numbers)

Space: **device pixels of the frame** (A2-cpu's D), whole numbers, origin top-left, y down.

```
pub struct PresentMove {
    /// The pixels the move WRITES, in the new frame: (x, y, w, h).
    pub dst: (u32, u32, u32, u32),
    /// Displacement of the content: new[p] = old[p - (dx, dy)] for every p in dst. Positive = right / down.
    /// (A2-cpu's `px_dx` / `px_dy` are scroll deltas: dx = -px_dx, dy = -px_dy.)
    pub dx: i32,
    pub dy: i32,
}
CpuBackend::last_present_moves: Vec<PresentMove>   // in the order the renderer applied them; empty for a Full frame
CpuBackend::last_painted: FrameDamage              // the rects WRITTEN after the moves (what `render_frame` returns)
CpuBackend::last_present_damage                    // unchanged: painted + moved clips, for a consumer that cannot move
```

1. `dst` and its source `dst - (dx, dy)` both lie inside the moved clip and inside the buffer: `dst = clip ∩ (clip + (dx, dy))`.
   Only whole-pixel moves are reported (the renderer's own gate); a clip that was repainted instead is in `last_painted`.
2. The invariant the producer guarantees and tests: take the PREVIOUS frame, apply the moves in order (each reads the
   result of the ones before it, overlapping source and destination handled as `memmove`), then copy `last_painted` from
   the new frame: the result equals the new frame, every pixel. (Test: random scroll / pan / edit sequences, 0 px differ.)
3. The consumer: (a) moves the WINDOW's pixels, in list order; (b) then presents `last_painted` from the frame. Never
   the other way round: a painted rect may overlap `dst` (the strip that came in, a fixed overlay or scrollbar repainted
   over the moved area) and has to win. Rects outside every `dst` are independent of the moves.
4. The consumer may use the moves only when the window shows the previous frame completely: no OS re-present pending
   (`os_present_requested`, Expose, `WM_PAINT` from the OS), the previous present was not skipped (Wayland: buffers held),
   the buffer size is the same, the frame is not `Full`. Otherwise it presents `last_present_damage` as today.
5. A source the window system cannot read (X11: obscured or off-screen, reported as `GraphicsExpose`): the consumer
   presents that rect from the frame; the frame always holds the whole new picture.
6. Per shell: X11 `XCopyArea(win, win, gc, dst.x - dx, dst.y - dy, w, h, dst.x, dst.y)`; Win32 `BitBlt(hdc, dst.x,
   dst.y, w, h, hdc, dst.x - dx, dst.y - dy, SRCCOPY)`; Wayland and macOS have no such primitive (Part 2).
7. Example (A2-cpu's shift table, dpi 1, view box (48, 40) 304 x 200, content moves LEFT by 12: `px_dx = +12`):
   `dst = (48, 40, 292, 200)`, `dx = -12`, `dy = 0` (source (60, 40, 292, 200)); `last_painted` = the strip
   (339, 40, 13, 200), which overlaps the last column of `dst` and is presented after the move. Presented bytes:
   13 x 200 px instead of 304 x 200.
