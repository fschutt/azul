## Spaces

A2-cpu's `## Spaces` did not exist when this was written (its notes file held the heading only); these are the names used
here. The first four are the renderer's, the rest the shells'.

| space | origin, direction | unit | where |
|---|---|---|---|
| logical px | window top-left, y down | CSS px = AppKit points = Wayland surface units | display lists, `FrameDamage::Rects`, `LogicalRect` |
| buffer px | frame top-left, y down, row 0 = top row | device pixels | `AzulPixmap`, every CPU frame, `to_rects_physical` (`PxRect`) |
| DPI factor | `size.dpi / 96` (u32 dpi) | buffer px per logical px | 1 or 2 on macOS, n/96 elsewhere |
| frame size | `ceil(logical * dpi)` in f32 | buffer px | `CpuBackend::render_frame`, `present_geometry::frame_size_px` |
| AppKit view points | view BOTTOM-left, y UP (`isFlipped` is not overridden in `CPUView` or `GLView`: checked) | points | `setNeedsDisplayInRect:`, the rect `drawRect:` gets, `bounds` |
| AppKit backing px | view bottom-left, y up | device pixels (`convertRectToBacking:` = points x backing scale) | `dirty_rows_to_copy`'s input |
| bitmap rep space | bitmap bottom-left, y up; BYTES are stored top row first | pixels (the rep's `size` equals its pixel size) | source rect of `drawInRect:fromRect:` |
| AppKit window base | window bottom-left, y up | points | `NSEvent.locationInWindow` (mouse) |
| X11 window px | window top-left, y down | device pixels | `XPutImage` / `XShmPutImage` dest, ConfigureNotify, pointer events |
| Wayland surface units | surface top-left, y down | logical | pointer events, `wl_surface.damage`, viewport destination |
| Wayland buffer px | buffer top-left, y down | device pixels | shm slots, `wl_surface.damage_buffer` |
| Win32 client px | client top-left, y down | device pixels | `BitBlt` / `StretchDIBits` dest, `WM_SIZE`, mouse lparam; DIBs are made top-down (`biHeight < 0`) |
| Android buffer rows | buffer top-left, y down | device pixels | `ANativeWindow_lock` lines |

Conversions (all in `layout/src/window.rs`, tested in `layout/src/audit_tests/a10.rs`):

- logical -> buffer px (`to_rects_physical`): `x0 = floor(x * d)`, `x1 = ceil((x + w) * d)`, same for y, clamped to the buffer,
  empty rects dropped. Outward. Same formula as `cpurender::logical_rects_to_buffer` (checked).
- buffer px <-> bottom-left px (`flip_rect_y`): `y' = H - (y + h)`; involution for rects inside the buffer.
- bottom-left px (fractional) -> rows / columns (`rows_of_bottom_left_rect`): `y0 = floor(H - (y + h))`, `y1 = ceil(H - y)`,
  `x0 = floor(x)`, `x1 = ceil(x + w)`, clamped. Inverse of the flip.
- buffer px -> AppKit points (`present_rect_in_view_points`, macOS): flip, then divide by the backing scale.
- device px -> logical that renders back to the same px (`logical_len_for_px`), fractional surface size (`surface_len_px`).

The one worked example, used in commits and tests: the strip of a pan step, logical (1267, 20) 13 x 1402 in a 1280 x 1440 pt view.

| | scale 1 | scale 2 |
|---|---|---|
| buffer | 1280 x 1440 px | 2560 x 2880 px |
| present rect (buffer px) | (1267, 20, 13, 1402) | (2534, 40, 26, 2804) |
| `setNeedsDisplayInRect:` (points, y up) | (1267, 18, 13, 1402) | (1267, 18, 13, 1402) |
| `drawRect:` dirty rect in backing px | (1267, 18, 13, 1402) | (2534, 36, 26, 2804) |
| rows / columns copied (top-down) | rows 20..1422, columns 1267..1280 | rows 40..2844, columns 2534..2560 |
| bytes copied into the bitmap | 1402 x 52 = 72,904 | 2804 x 104 = 291,616 |
| source rect in the bitmap (y up, px) | (1267, 18, 13, 1402) | (2534, 36, 26, 2804) |
| destination rect (points) | (1267, 18, 13, 1402) | (1267, 18, 13, 1402) |

## Findings

Severity = ms x frequency where a cost is known; `wrong` = wrong pixels on screen.

### A10-01 macOS present: rect conversions
- file: `dll/src/desktop/shell2/macos/mod.rs` (`dirty_rows_to_copy`, `update_framebuffer`, `invalidate_present_rects`, `drawRect:`)
- class: sign/offset
- evidence: algebra and table above. Both invalidation paths computed `x / (fb_w / bounds_w)`, `bounds_h - (y + h) / (fb_h / bounds_h)`;
  for whole pixel sizes that equals `flip / scale`. `drawRect:` flips back with the framebuffer's height and draws the bitmap's
  `(x0, H - y1, x1 - x0, y1 - y0)`. All four steps agree; the view is not flipped; the bitmap's bytes are top row first.
- fix: none needed for whole sizes; the arithmetic is now `present_rect_in_view_points`, `bitmap_source_rect` (macOS) and
  `flip_rect_y`, `rows_of_bottom_left_rect` (layout), and the invalidation uses the backing scale `drawRect:` sized the buffer with
  (exact inverse of `convertRectToBacking:`) instead of the framebuffer / bounds ratio.
- test: `a_present_rect_is_invalidated_flipped_and_in_points`, `the_rows_drawn_are_the_rows_invalidated`,
  `a_dirty_rect_rounded_outward_by_appkit_still_covers_the_damage`, `appkit_shows_the_copied_rows_where_the_frame_has_them`
  (draws through AppKit into an offscreen bitmap and reads the rows back: runs without a window), layout:
  `a_rect_is_flipped_by_its_bottom_edge`, `the_flip_round_trips_for_every_rect_in_a_buffer`, `rows_of_a_fractional_bottom_left_rect`.
- severity: low
- status: checked: fine
- note: the old arithmetic was right for whole pixel sizes; it is now pure functions (8a40ffa87, 45f75aeb7).

### A10-02 macOS: the view's framebuffer was truncated, the frame is `ceil`
- file: `macos/mod.rs` `drawRect:` (`backing.size.width as usize`) vs `layout/src/cpu_backend.rs:358` (`(width * dpi).ceil()`)
- class: sign/offset (rounding)
- evidence: bounds 1280.3 pt at 2x: backing 2560.6; view 2560, frame 2561. `native_target_ptr` refuses (sizes differ), the
  frame is rendered into an owned pixmap and `update_framebuffer` takes the nearest-neighbour rescale path: a per-pixel loop
  with bounds checks over the whole frame, every present (14.7 MB at 2560 x 1440), and a soft picture. Whole sizes agree.
  Needs fractional bounds, which AppKit rarely gives a window; severity low, but permanent when it happens.
- fix: `cpu_view_framebuffer_size` = `present_geometry::frame_size_px` on `bounds as f32` (the numbers `handle_resize` stores).
  A mismatch that lasts 3 frames is logged at the error level (`note_cpu_frame_size`).
  The other half: the STATE the frame is sized from followed the view only beyond a 0.5 pt tolerance
  (`sync_window_size_from_content_view`): state 800.2 pt, view 800 pt, 2x -> frame 1601 px, view 1600 px, for good. It now
  also follows whenever `frame_size_px(state) != frame_size_px(bounds)`.
- test: `the_views_framebuffer_is_the_size_of_the_renderers_frame`, `the_macos_state_follows_the_view_when_their_frames_differ`
- severity: low
- status: fixed 1f481839f
- note: view size 8a40ffa87, state sync 1f481839f. If the error line of `note_cpu_frame_size` still shows on a real window, the render view and the content view have different bounds.

- test: `a_span_outside_the_frame_is_not_presented`

## Part 1. macOS, line by line

Path of a frame (CPU backend, display link running, the default):

1. `request_redraw` raises `redraw_requested`; the pacer starts the CVDisplayLink or leaves the flag for its next tick.
2. Tick: CVDisplayLink thread -> `vsync_ticks::deliver` -> MAIN thread `mark_views_dirty_on_main` -> `TickAction::Render` ->
   `render_and_present_in_draw_rect` (outside `drawRect:`).
3. CPU arm: `native_target_ptr(w, h)` hands the view's `framebuffer: RefCell<Vec<u8>>` to the renderer as an external pixmap
   (`AzulPixmap::from_external`), `render_frame` paints the damage into it, `native_target = None` after the call.
4. `invalidate_present_rects(to_present_rects_physical(...))`: one `setNeedsDisplayInRect:` per rect.
5. End of the run-loop turn: AppKit calls `drawRect:(dirty)` once with the bounding box of the invalid region; no flag is
   set any more, so nothing renders; the dirty rows are copied into the cached `NSBitmapImageRep` and that span is drawn.

Proofs, step by step:

- **Buffer geometry.** `width x height` = `cpu_view_framebuffer_size(bounds, scale)` (A10-02); stride `width * 4`, tight;
  RGBA8 premultiplied, bytes in memory order R, G, B, A (the renderer's order: `AzulPixmap`); row 0 = top. The bitmap
  (`color_space::cpu_frame_bitmap`): 8 bits, 4 samples, alpha, not planar, `bytesPerRow` asked `width * 4` but READ BACK
  (`draw_framebuffer_span`), `bitmapFormat` checked to be neither alpha-first, non-premultiplied, float nor little-endian
  32-bit (`holds_premultiplied_rgba8`), tagged sRGB; a rep that does not come back that way falls back to the generic one.
  Its `size` is its pixel size (made from pixel dims at 72 dpi), so the source rect of the draw is in pixels.
- **Ownership.** The framebuffer is the view's `Vec`; only `drawRect:` (resize), `update_framebuffer` and `native_target_ptr`
  touch its length, all on the main thread. The raw pointer handed to the renderer lives from `native_target_ptr` to the end
  of `render_frame`; nothing in between calls AppKit or runs the run loop (`prepare_frame_cpu`, the layout callbacks and the
  thread writebacks all run BEFORE the pointer is taken). The dangle guard clears it after the call. The bitmap is cached,
  made anew when the size differs, `bitmapData` is asked on every draw (which is also AppKit's signal that the bytes changed).
- **Rects.** A10-01. The view is not flipped; every conversion flips exactly once.
- **Rounding.** Present rects are outward and clamped (A10-04). Odd pixel rects at 2x are half-point rects; if AppKit rounds
  them to whole points the rows are a superset (`a_dirty_rect_rounded_outward_by_appkit_still_covers_the_damage`).
  `draw_framebuffer_span` refuses anything outside either buffer (A10-03).
- **Resize / live resize.** `windowDidResize:` -> `handle_resize` (state := bounds, exactly) -> during a live resize
  `contentView.display()` runs `drawRect:` now: the framebuffer is resized keeping the top-left (rows are top-down and the
  content is top-left anchored, whichever edge is dragged), `redraw_requested` is raised, the render goes into it natively:
  `render_frame` sees the compositor's old size, computes the L-shaped strips (`compute_resize_damage`), repaints them and
  the relayout's damage. The bitmap is new, so the whole frame is copied and drawn. Outside a live resize the tick may
  render first: that is A10-07.
- **First frame.** Either order works: `drawRect:` first (blank buffer, render inside, owned pixmap, full copy), or tick
  first (the view adopts the pixmap's size, full copy, `drawRect:` finds the same size).
- **`FrameDamage::None`.** Nothing copied, nothing invalidated; unless the view shows the blank fill (A10-07).
- **Second display, full screen.** Size and / or scale change: A10-07 (kept pixels only at the same scale), A10-08 (full
  repaint at the new factor), the display link is made anew for the new display (`handle_dpi_change`). In one of the two
  possible orders (AppKit draws at the new scale before `windowDidChangeBackingProperties:` reaches us) ONE stretched frame
  is shown: the state still has the old factor, the frame has the old size, `update_framebuffer` rescales it. The next
  frame is right. Removing it needs the DPI sync inside `sync_window_size_from_content_view` (it only syncs the DPI when the
  size changed); not done, it would run a layout regeneration from inside `drawRect:` on a path that cannot be tried here.
- **Threads, re-entrancy.** Everything is on the main thread; `CPUView` is `MainThreadOnly`, `canDrawConcurrently` is not
  set. `drawRect:` cannot run while a frame is rendered into the buffer: the renderer does not return to the run loop.
  A1's row bands will write the buffer from worker threads while the main thread is blocked in `thread::scope`: fine for
  AppKit (nothing else touches the view), provided the scope joins before `render_frame` returns (For area A1 item 5).
  Nested `drawRect:` (a callback that resizes the window during a live resize -> `display()`): the outer call holds no
  `RefCell` borrow while it renders, and holds no renderer pointer outside `render_frame`: checked.
### macOS: the states of the view's framebuffer (A10-07)

State = (`fb_content_valid`, `fb_blank`, size). `V` = holds the last frame pixel for pixel (may be a render target, may take
partial copies), `S` = shows the last frame stretched, `B` = blank fill.

| event | from | to |
|---|---|---|
| `drawRect:` same size | any | same |
| `drawRect:` new size, same scale | V | V (top-left kept, strips blank: the renderer's own resize damage covers exactly them) |
| `drawRect:` new size from S or B, or another scale | any | B, and a render is forced |
| `update_framebuffer`, frame of the view's size, whole | any | V |
| `update_framebuffer`, rects | V | V; from S or B it becomes the whole copy -> V |
| `update_framebuffer`, frame of another size | any | S |
| native render (`native_target_ptr`) | V only | V |
| present of an owned frame with damage `None` | B | whole copy -> V; from V or S: nothing |

Sequences (old result / new result):

- Zoom button, tick before `drawRect:`: tick renders at the new size -> owned, full -> rescaled into the old-size buffer (old:
  V, new: S) -> `drawRect:` resizes (old: keeps the squeezed picture as V; new: B) -> render (old: native, damage `None`,
  squeezed picture stays; new: owned, damage `None`, whole copy because B) -> right.
- Move 1x -> 2x, notification first: full repaint at 2x (A10-08) -> owned -> rescaled into the 1x buffer (S) -> `drawRect:`
  at 2x: B -> owned, `None` -> whole copy -> V.
- Move 1x -> 2x, `drawRect:` first: B (scale changed) -> render at the stale factor -> owned 1x frame -> rescaled to 2x (S,
  one stretched frame on screen) -> notification -> full repaint at 2x -> native refused (S) -> owned -> whole copy -> V.
- A size mismatch that never ends (A10-02's case): every frame owned + rescale, the view stays S, an error line after 3 frames.

A pan step at 2560 x 1440 (clip 2510 x 1402 = 14.1 MB; x4 at DPI 2 = 56 MB), per frame:
- renderer: memmove of the clip (1 pass) + the strip;
- macOS: 1 pass (rows) + AppKit draw (>= 1 pass) + CA upload: at least 3 passes of 14 MB = 42 MB of traffic, 170 MB at
  Retina. At 10-20 GB/s for buffers that do not fit a cache that is 2-4 ms at DPI 1 and **8-17 ms at Retina**, before the
  unknown CGImage copy. The paint of that frame is 2.9 ms (ledger): **at Retina the present, not the paint, is the pan's cost.**
- Wayland: memmove + catch-up copy of the clip + compositor upload. X11 SHM: memmove + swizzle of the clip + server copy.
  Win32: memmove + BitBlt of the clip.

### Design: a present that moves pixels (not implemented)

Decision: **not implementable safely blind.** What "a pan costs the strip only" needs, and why each piece cannot be proven here:

1. The renderer must report the MOVE, not only the rects: `present_moves: Vec<(clip_px, dx, dy)>` next to the paint rects
   (today `ScrollShiftOutcome.present_extra` says "this clip changed", which is true and loses the information). A1's file.
2. A shell primitive that moves window pixels without an upload:
   - X11: `XCopyArea(window -> window)` of the clip by (dx, dy), then SHM-put the strip. Exists, cheap (server side), but
     `GraphicsExpose` for obscured sources must be handled (repaint those rects), and the order of the copy and the puts
     matters with a compositing manager.
   - Win32: `ScrollDC` / `BitBlt` window-to-window, then blit the strip from the DIB. Under DWM the redirection surface is
     the source, so it is exact; `ScrollWindowEx` must NOT be used (it invalidates and scrolls child windows).
   - Wayland: none in core protocol (a buffer attach always carries damage for what changed on screen); the equivalent is
     a second `wl_subsurface` whose position moves, i.e. option 3.
   - macOS: `-[NSView scrollRect:by:]` copies bits only in a view that owns a backing store of its own and is documented
     as a no-op-or-redraw for layer-backed views (all views since 10.14): not usable.
3. So on macOS (and Wayland) the only real version is a **layer per retained surface**: the map view's picture (A1's
   retained group surface, with the editor's 256 px overscan) becomes the `contents` of its own `CALayer` (an `IOSurface`,
   BGRA, double-buffered like the Wayland slots, or a `CGImage` over the surface's memory); a pan is
   `layer.position` / `bounds.origin` inside a `CATransaction` with actions disabled, a zoom is `layer.transform`, and the
   window server composites on the GPU: zero bytes per pan or zoom frame, the strip is not even needed while the overscan
   lasts. Everything painted ABOVE the map (panels, tooltips, selection chrome) must then live in a layer above it with a
   transparent hole: the window's single framebuffer becomes "below", "promoted", "above". That is WebRender's compositor
   surface model on the CPU path; it needs A1's retained surfaces to exist, an export API (surface, extent, matrix, clip,
   opacity, z order), hit-testing unchanged (it is layout-based: fine), and it is useless before a real window shows that
   the present is what a gesture pays.

Open risks: z-order splitting when UI overlaps the map; tearing between the layer move and the framebuffer's strip (two
commits must land in one `CATransaction`); `IOSurface` pixel format (BGRA: the renderer's pool-order mode exists for
Wayland, plus an in-place swizzle of damage); colour management of layer contents (the window is tagged sRGB, an IOSurface
needs its own tag); memory (one overscanned surface = 92 MB at Retina).

Cheaper intermediates on macOS, in the order to try AFTER the measurement:
- **B: render into the bitmap** (no separate framebuffer): `native_target_ptr` returns the rep's `bitmapData`, rows padded
  via `CpuBackend::native_target_row_padding_px` (exists for Wayland). Removes the row copy (`draw_rect_cpu_rows`) and one
  frame-sized buffer. Worth it only if that span is a large part of `draw_rect_cpu`.
- **C: `CGImage` over the framebuffer + `CGContextDrawImage`** (no `NSBitmapImageRep`): removes AppKit's possible whole-bitmap
  copy. The FFI declarations exist in `ios/mod.rs` (`CGDataProviderCreateWithData`, `CGImageCreate`). Worth it only if
  `draw_rect_cpu_appkit` does not shrink with the dirty rect.
- **D: `layer.contents = CGImage` (softbuffer's way)**: Core Animation copies the whole image at every commit: no dirty
  rects at all. Worse than today for small damage; not recommended.

The measurement that decides (one run, real window, CPU backend): `AZ_BACKEND=cpu AZ_PROFILE=cpu`, pan over labels for a
few seconds, then hover a button. Read the spans `draw_rect_cpu` (a whole `drawRect:`), `draw_rect_cpu_rows` (our copy),
`draw_rect_cpu_appkit` (AppKit's draw), `present_view_blit` (legacy copy; should not appear), `draw_rect_render_present`
(a frame's render). If `draw_rect_cpu_appkit` for a hover (a button-sized rect) is as large as for a pan, AppKit copies
the whole bitmap per draw (do C); if `draw_rect_cpu_rows + draw_rect_cpu_appkit` of a pan frame is above ~4 ms, the pan
needs option 3 (and A1's moves); below that, leave the present alone.

## What to look at on the real window

All with `AZ_BACKEND=cpu` (the CPU backend), on the Retina display, and where it says so with `AZ_PROFILE=cpu`.

1. **Plain use**: open a sample, hover, type, pan, zoom. Any garbage, shear (rows offset sideways), upside-down or mirrored
   regions, or text that looks squashed and doubled means a present bug: run again with `AZ_NATIVE_BACKBUFFER=0`; if that
   fixes it the native arm is wrong, if not the blit is (the test `appkit_shows_the_copied_rows_where_the_frame_has_them`
   should then already have failed in the verification pass).
2. **Small damage far apart** (a blinking caret in the sidebar while a tile arrives in the map): nothing between them may
   flicker or go stale.
3. **Zoom button / double-click on the title bar / Split View tile** (a resize that is not a live drag): the window must
   show the new layout at once, sharp. A squeezed or stretched picture, or a blank window that fills only where the mouse
   hovers, is A10-07 not holding.
4. **Live resize by an edge, slowly and fast, growing and shrinking**: no blank strips that stay, no shear.
5. **Drag the window to a display with another scale** (external 1x monitor) and back: at most one soft frame on arrival,
   then sharp everywhere. A top-left quarter at the wrong size, or doubled / cropped content, is A10-08 or A10-07.
6. **Full screen and back.** As 3.
7. **stderr**: a line `[CPUView] the frame is WxH px and the view's framebuffer WxH px, N frames in a row` means the two
   sizes disagree permanently (A10-02): every frame is slow and soft; send the line. A line `[CPUView] not presenting rows`

### The contract of `present_moves` (for A1's producer; the consumer is written after the user's numbers)

Space: **device pixels of the frame** (A2-cpu's D), whole numbers, origin top-left, y down.

```
pub struct PresentMove {
    /// The pixels the move WRITES, in the new frame: (x, y, w, h).
    pub dst: (u32, u32, u32, u32),
    /// Displacement of the content: new[p] = old[p - (dx, dy)] for every p in dst. Positive = right / down.
    /// (A2-cpu's `px_dx` / `px_dy` are scroll deltas: dx = -px_dx, dy = -px_dy.)
    pub dx: i32,
    pub dy: i32,
}
CpuBackend::last_present_moves: Vec<PresentMove>   // in the order the renderer applied them; empty for a Full frame
CpuBackend::last_painted: FrameDamage              // the rects WRITTEN after the moves (what `render_frame` returns)
CpuBackend::last_present_damage                    // unchanged: painted + moved clips, for a consumer that cannot move
```

1. `dst` and its source `dst - (dx, dy)` both lie inside the moved clip and inside the buffer: `dst = clip ∩ (clip + (dx, dy))`.
   Only whole-pixel moves are reported (the renderer's own gate); a clip that was repainted instead is in `last_painted`.
2. The invariant the producer guarantees and tests: take the PREVIOUS frame, apply the moves in order (each reads the
   result of the ones before it, overlapping source and destination handled as `memmove`), then copy `last_painted` from
   the new frame: the result equals the new frame, every pixel. (Test: random scroll / pan / edit sequences, 0 px differ.)
3. The consumer: (a) moves the WINDOW's pixels, in list order; (b) then presents `last_painted` from the frame. Never
   the other way round: a painted rect may overlap `dst` (the strip that came in, a fixed overlay or scrollbar repainted
   over the moved area) and has to win. Rects outside every `dst` are independent of the moves.
4. The consumer may use the moves only when the window shows the previous frame completely: no OS re-present pending
   (`os_present_requested`, Expose, `WM_PAINT` from the OS), the previous present was not skipped (Wayland: buffers held),
   the buffer size is the same, the frame is not `Full`. Otherwise it presents `last_present_damage` as today.
5. A source the window system cannot read (X11: obscured or off-screen, reported as `GraphicsExpose`): the consumer
   presents that rect from the frame; the frame always holds the whole new picture.
6. Per shell: X11 `XCopyArea(win, win, gc, dst.x - dx, dst.y - dy, w, h, dst.x, dst.y)`; Win32 `BitBlt(hdc, dst.x,
   dst.y, w, h, hdc, dst.x - dx, dst.y - dy, SRCCOPY)`; Wayland and macOS have no such primitive (Part 2).
7. Example (A2-cpu's shift table, dpi 1, view box (48, 40) 304 x 200, content moves LEFT by 12: `px_dx = +12`):
   `dst = (48, 40, 292, 200)`, `dx = -12`, `dy = 0` (source (60, 40, 292, 200)); `last_painted` = the strip
   (339, 40, 13, 200), which overlaps the last column of `dst` and is presented after the move. Presented bytes:
   13 x 200 px instead of 304 x 200.

### The layer-backed present: implementation plan (A10-06, `blocked (a)`)

Goal: a pan or a zoom of a promoted view writes no pixel: the window server moves or scales a layer.

1. **What the renderer exports** (A1's retained group surface, per promoted frame; `CpuBackend::last_layers: Vec<PresentLayer>`):
   `PresentLayer { id: u64 /* frame key, stable across frames */, surface: *const u8 + (w, h, stride) /* device px,
   RGBA8 premultiplied, top row first, valid until the next render */, placement: [f32; 6] /* affine: surface px ->
   window device px (the frame's matrix x dpi; a pan is a translation, a zoom a scale) */, clip: PxRect /* window
   device px */, opacity: f32, z: Below | Promoted(order), surface_damage: Vec<PxRect> /* surface px repainted this
   frame; empty for a pan inside the overscan */ }`, and the window framebuffer split in two targets: BELOW (everything
   painted before the first promoted frame) and ABOVE (everything after it, transparent where nothing is painted).
   A frame is promoted when A1's retained surface exists for it (value-only transform, extent >= 256 x 256), at most 2.
2. **The view's layer tree** (the CPU view becomes layer-hosting: `setLayer:` a root `CALayer`, then `setWantsLayer:`):
   root (geometry flipped, `contentsScale` = backing scale) -> `below` (contents = the BELOW target) -> one layer per
   `PresentLayer` (anchorPoint (0, 0), `masksToBounds` on a clip sublayer of `clip` size) -> `above`.
3. **Per frame**, inside ONE `CATransaction` with `setDisableActions:YES`: for each promoted layer set
   `affineTransform` from `placement` and the clip layer's frame from `clip`; if `surface_damage` is non-empty,
   refresh its contents; refresh `below` / `above` contents only where their damage is (they change when UI changes,
   not on a pan). One transaction = the move and the strip land in the same window-server frame (no tearing).
4. **Contents**: an `IOSurface` per target (BGRA; the renderer's pool-order mode exists for Wayland's ARGB slots, with
   the in-place swizzle of damage), two per layer, used alternately with the cross-slot catch-up the Wayland shell
   has (`slots[..].stale`), `layer.contents = surface` + `setContentsChanged`. First version, simpler: a `CGImage`
   over a copy of the damaged target (what iOS does): correct, one copy per changed target, none for a pan.
5. **Colour**: each `IOSurface` tagged sRGB (`IOSurfaceSetValue(kIOSurfaceColorSpace)`), or `layer.colorspace`; the
   test `a_css_colour_drawn_from_the_cpu_frame_into_an_srgb_surface_keeps_its_bytes` gets a layer twin.
6. **Input and hit-testing**: unchanged (layout-based). **Resize / scale change**: drop every layer's contents and go
   through one full frame. **Fallback**: no promoted frame -> today's single backing store path, unchanged.
7. **Tests**: the renderer's invariant (compose BELOW, promoted surfaces through `placement` and `clip`, ABOVE =
   the single-target frame, every pixel, within the resample tolerance of the affine blit); the placement arithmetic
   (flip, scale) as pure functions; offscreen `CALayer.renderInContext:` for the tree.
8. **What decides whether to build it**: `draw_rect_cpu_cgimage` (or rows + appkit) of a pan frame on the real window.
   Under about 2 ms on the user's display the single backing store is enough.

Why a single backing store cannot use `last_present_moves`: the layer's backing store has no "move" (the one AppKit
call, `scrollRect:by:`, is deprecated and does not copy bits in layer-backed views); moving the rows inside the staging
bitmap costs the bytes that copying them from the framebuffer costs (a `memmove` of the clip for a `memcpy` of the
clip), and AppKit still has to draw the clip into the backing store. With `cgimage` the renderer's own `memmove` in the
framebuffer IS the move, and nothing else is copied by the view. So per pan frame on macOS: renderer `memmove` of the
clip (1 pass) + AppKit's draw of the clip into the backing store (>= 1 pass) + Core Animation's flush; bitmap mode adds
the row copy (1 pass: 20.4 MB for a 2840 x 1800 clip on the user's display).

### What the merged renderer already has (read in `layout/src/cpurender/retained.rs`, 643 lines, and by grep)

- A reference frame whose matrix is NOT a translation is painted into a surface of its own (`raster::TransformGroup`,
  `raster.rs` ~1375) and composited through the matrix (`GroupGeometry::finish`, ~1645: the affine blit). A1 keeps that
  surface from frame to frame: `RetainedFrames` (`CpuBackend::retained_frames`, `cpu_backend.rs:310`), keyed by
  `SurfaceKey` (list allocation, push index, size, dpi bits, sub-pixel phase, live values inside, text settings);
  `Entry { surface: Arc<AzulPixmap>, valid: Vec<[i32; 4]>, placement }`. A hit is `retained.lookup(&candidate.key,
  candidate.needed)` at `raster.rs` ~2975; a miss paints and `retained.offer(..)` at ~2873.
- Consequence 1: **a zoom step** (matrix = scale + translate) with a kept surface costs the affine composite of the
  view and nothing else. That composite is what a layer transform replaces.
- Consequence 2: **a pan at scale 1 has no kept surface**: its matrix is a translation, which the walk folds into its
  offset (`ReferenceFrameGroup::begin`: `acc -= t`), and the pixels are moved in the window target
  (`execute_virtual_view_shift`, a `memmove`) with a strip painted next to them; the frame reports
  `CpuBackend::last_present_moves` (`PresentMove { dst, dx, dy }`, `compositor.rs:1893`) and
  `last_present_damage_after_moves`. A pan of a SCALED view composites the kept picture (rule 4 of `retained.rs`:
  same phase at whole-pixel offsets).
- So "a pan inside the overscan is a layer move" needs one thing the renderer does not have: a kept surface for the
  view's picture ALSO when its matrix is the identity or a translation. That is the first renderer change (R1 below).

### The design, reduced to what must be built

Three layers, in this order, inside the CPU view (which becomes layer-hosting when the switch is on):

1. **below**: the view's existing layer, drawn by `drawRect:` from the framebuffer as today, with ONE difference: the
   promoted frame's picture is not composited into the framebuffer; the pixels under it hold what is painted BEFORE the
   frame (the view's background), opaque.
2. **promoted**: one `CALayer` whose contents are the kept surface (an sRGB `CGImage` over a copy of it, or an
   `IOSurface`), inside a clip layer (`masksToBounds`) of the frame's clip, with `affineTransform` = the group's matrix.
3. **above**: one `CALayer` of the clip's size, transparent, holding ONLY what the window list paints after the frame's
   pop inside the clip (`overlay_rects_after_frame`, `compositor.rs:3913`, already finds those items for the shift
   path). Empty (no layer, no surface) when nothing is painted over the frame: the common case for the editor's map.

Promotion rule (pure, to be tested): promote the frame F of a frame's render when ALL hold: the switch is on; F has a
kept surface this frame (hit or freshly offered); F is the largest such frame (at most one); F's surface is at least
256 x 256 px; no opacity / filter / mask group and no non-rectangular clip is open around F (the layer tree cannot
express them: fallback); the window is not transparent (`cpu_backend.transparent`). Otherwise nothing is promoted and
the frame is presented as today. When promotion starts or stops, ONE frame is presented in full through the old path
(the GPU's bilinear and the CPU's fixed-point composite differ by a level or two: the switch-over frame must come from
one of them only).

### What the plan of the fifth pass got wrong (found while reading the walk)

1. **The walk cannot report the layer.** The plan had the hit and the pop push a `PresentLayer` with the group's matrix
   and clip. A pass paints under the DAMAGE rect (a band's rows): its clip is the pass's, not the frame's, and a frame
   whose only change is the promoted frame's own move reaches the frame with no pass at all once that move is no damage.
   So the layer is PLANNED before the frame is painted (`present_layer::plan`: a scan of the lists that keeps the clip and
   the offset a walk without a damage rect has, and paints nothing), and the walk only does two things: isolate the frame
   (R1) and not composite it (R2).
2. **"Filter the frame's value damage" skips the frame as idle.** With the promoted matrix's change removed from the
   damage, a zoom step is a frame in which nothing else changed: `FrameChanges::is_idle`, early return, the layer keeps
   its old matrix. `promoted_frame_moved` keeps it a frame (it paints nothing and reports the new matrix).
3. **A pan at scale 1 is not a matrix.** The editor pans by the view's content offset (`update_virtual_view`), which the
   backend executes as a pixel move of the view's clip (`execute_virtual_view_shift`). In layer mode that move is skipped
   for the view that shows the promoted frame alone (`LayerPlan::alone`: its list paints nothing else), and is a repaint
   of the view's box for one that shows more.
4. **`affineTransform` is not needed.** The promoted frame's matrix is a scale and a move (anything else is not
   promoted: `LayerMatrix::is_upright`), and a layer's contents are stretched to its frame: a pan or a zoom step is
   `setFrame:` of the picture layer. No `CGAffineTransform` crosses the FFI (the dll does not depend on
   objc2-quartz-core or objc2-core-foundation's CG types directly, and gets no new dependency).
5. **The clip layer's y.** The plan's example put the clip layer at (50, 38): that is the clip's top in the frame's
   y-down terms. A sublayer of a view that is not flipped is placed from the BOTTOM: (50, 18) for a 1912 px frame. Every
   rect is flipped once against the height of what it is in (`layer_geometry`); no layer is `geometryFlipped`.
6. **Holding the surface's `Arc` in the image's provider** (the plan's zero-copy version) breaks the renderer: `commit`
   merges a painted part into a kept surface only when nobody else holds it, and replaces the surface otherwise, which
   forgets everything painted before. The shell copies (46.6 MB per change of the surface on the user's display).
7. **Not in the plan:** what shows of the surface and is not painted has to become damage (`damage_for_missing`), or a
   pan past the 64 px a pass paints ahead shows transparent columns; the surface's pixels need a stamp (`painted_at`),
   because a repair of a replaced list (a tile arriving) changes pixels under the same key; `release_caches` has to force
   a full frame, because the picture is in no other buffer.

### The design as built

Renderer (`layout/src/cpurender/present_layer.rs`, `raster.rs`, `retained.rs`, `cpu_backend.rs`):

- **Plan** (`plan`, each frame that is not idle, when `promote_for_present`): scan the window's list and its views' lists
  (`Scan::scan`); every frame whose picture the walk can keep (`retained_candidate` with any matrix: self-contained, no
  view inside, at least 256 x 256 px, under the cache's bound, not text alone) and that is in no opacity / filter / mask
  group, rounded clip or text shadow is a candidate; whatever paints after a candidate inside its clip marks it painted
  over. Promoted: the largest candidate, if nothing is painted over it and its surface lands upright (`choose`).
  Not promoted at all: a transparent window, a frame of another size or scale factor than the one before, a list with a
  filter the layered compositor paints, `AZ_CPU_FULL=layers`, 60 frames after a failure.
- **Paint**: `CpuRenderState::promote = PromoteFrame { transform_key, composite: false, paint_margin }`. The walk
  paints the frame as an isolated group, keeps its surface, composites nothing: the window's frame holds, under the
  layer's clip, what is painted BEFORE the promoted frame.
- **Damage** of an incremental frame: minus the promoted frame's own matrix change; minus the pixel move of the lone
  view; plus what the layer needs of its surface and is not painted (`RetainedFrames::missing` -> `damage_for_missing`:
  the passes over those rects miss the kept surface there and paint it); plus the layer's clip when the promotion
  starts, stops or the clip changes.
- **Report**: `CpuBackend::last_present_layer` = `PresentLayer { surface_id, surface_size, matrix, clip, generation }`,
  the surface's bytes through `with_present_layer_surface`. `last_present_damage` is what it was: the rects of the
  window's frame that changed (nothing for a move of the layer).
- The spaces: everything is device px of the frame, origin top left, y down (A2-cpu's D). `LayerMatrix` takes a surface
  pixel there: `x' = xx x + tx`, `y' = yy y + ty` (upright).

macOS (`dll/src/desktop/shell2/macos/layer_present.rs`, `mod.rs`):

- the tree, the geometry and the transaction: the module's head, and fdf0ba6dc's message (with both worked examples);
- per frame, in the CPU arm of `render_and_present_in_draw_rect`: `promote_for_present = switch && the view's

  changes it inside one `CATransaction` with actions disabled. Both land in the same run loop turn, so Core Animation
  commits the layer's move with the view's redraw;
- fallbacks, each through the window's frame alone and ONE repaint of the clip by the renderer: a frame that promotes

### What to look at on the real window: the layer mode (`AZ_BACKEND=cpu AZ_CPU_PRESENT=layer`)

Run everything once without `layer` first (the default path must be unchanged by all of this), then with it. With
`AZ_PROFILE=cpu` the spans `layer_present_transaction` (every frame that changes a layer) and `layer_present_contents`
(a copy of the surface handed over) appear; `draw_rect_cpu_cgimage` should NOT appear for a pan inside the overscan or
for a zoom step.

16. **At rest**: the map looks as without the switch: same place, same size, sharp, same colours as the UI around it.
    The map shifted, mirrored or upside down inside its box = the flip or the division by the scale in
    `layer_geometry` / AppKit's sublayer space. Soft at rest = the picture layer's frame is not the surface's size / 2.
    Colours of the map differ from the rest (a saturated swatch) = the image is not taken as sRGB. Labels in the map are
    antialiased in grey in this mode (they are painted into a surface): expected.
17. **Pan** (drag, slowly and fast, in every direction): the map follows the pointer, the UI around it does not move, no
    tear between map and UI (a tear = the layer's move and the frame's redraw are not in one commit). A strip at the
    edge that stays empty or shows old pixels for longer than a frame = the missing part was not painted
    (`damage_for_missing`) or its pixels not handed over (the stamp). A seam between what was there and the strip (a
    line, a shift by a pixel) = the phase rule. A hitch every ten frames or so is the 46.6 MB copy (A10-27): say how
    bad it feels; `layer_present_contents` says how long it takes.
18. **Zoom** (pinch or wheel) and **pan during a zoom**: the picture scales smoothly, soft while scaled, and snaps
    sharp when the view renders again at the settle. A jump at the settle (the map moves by a few pixels) = the
    surface of the new render lands elsewhere than the scaled one did. A one-frame blink of brightness or sharpness
    when a gesture starts or ends = a switch-over frame (the picture was composited by the CPU in one frame and by the
    GPU in the next); it should only happen when a panel or popup over the map comes or goes.
19. **A popup, menu, tooltip or panel over part of the map**: it must stay visible (A10-28: the layer mode switches
    off while something is painted over the map, with ONE repaint; the map must not jump). The thing hidden behind the
    map = the planner did not see it paint over the frame. Native menus and tooltips are windows of their own and do
    not count.
20. **A panel opening beside the map** (the view's box changes): the map's box follows at once; no strip of map left
    where the panel is.
21. **Live resize** (every edge, grow and shrink) and the **zoom button / full screen**: the map resizes with the
    window as without the switch (the layers are hidden while the size changes); after the drag ends the next
    interaction puts the layer back, possibly with one slower frame. A map that stays at its old size or place, or a
    second map behind the first = a layer left visible after a resize.
22. **The window dragged to a display of another scale** and back: at most the one soft frame of the default path, then
    sharp, map included. A map at half or double size = the layer placed with the old scale.
23. **Minimise and restore, Cmd-H and back**: the map is there at once after the restore. A blank map until the first
    click = no frame was owed after the release (`redraw_requested` at `set_display_link_paused`).
24. **Memory pressure** (`sudo memory_pressure -S -l warn`, then `critical`): the map may be blank for one frame, then
    is back. Blank until something changes = as 23.
25. **stderr**: `[CPUView] layer present: the layers could not be made` = the view has no layer: the old path from
    then on, say so. `[CpuBackend] layer present: the surface of the promoted frame is not complete` = a part of the
    surface no pass painted; the frame is repaired and the layer mode pauses for 60 frames: send the line and what
    you did.
26. **Does it promote at all?** If nothing differs from the default and `layer_present_transaction` never appears,
    something is painted over the map at rest, or the map's root is in a group (opacity, filter, rounded clip): A10-28.
27. **Screenshots and frame dumps** (`AZ_DUMP_FRAME_DIR`, the debug server) show the window's frame WITHOUT the map
    in this mode: the map is in the layer.
