### A8-01 `dilate_disk` O(ink x pi r^2) per halo
- file: `layout/src/cpurender/raster.rs` `dilate_disk` (base 5841)
- class: quadratic (in r), waste
- evidence: every ink pixel walked every tap of the disk, 4 channels, plus a source copy and a u32 x 4 accumulator.
  Runs for every halo the kept-halo cache does not hold: every label at a settle repaint (the key holds
  `font_size_px`, which a zoom changes; 1,567 labels Tuebingen), per frame for halos beyond the cache's bounds. Editor
  radius = 0.2 mm x scale: 1.2 px at scale 6 (9 taps), 2.4 at DPI 2 (21-37), 4-8 zoomed in (69-225 taps).
  The brief's dense "sliding max over every pixel" would be SLOWER at these radii: a label's buffer is ~20-30 % ink,
  the dense form costs ~3 (2R+1) + 2 pi r per buffer pixel (r = 1.2: 23 vs 0.3 x 9 = 2.7 for the sparse scatter;
  r = 8: 107 vs 68). So: keep the sparse scatter and merge runs of equal pixels instead.
- fix: disk by rows; a run of equal pixels in one source row writes its row span `L + 2 b` once per disk row
  (`grow_run`), u16 accumulator, no source copy, `first` channel parameter. Proof and offset sets r = 1, 2, 3 in the
  commit message. Solid 64 x 16 block r = 2 -> 8: 5,376 -> 20,736 writes (old 21,504 -> 230,400).
- test: `raster::audit_a8_dilate_tests::{a_disk_grown_by_runs_is_the_disk_grown_by_pixels, growing_the_alpha_alone_
  grows_the_alpha_the_whole_pixels_grow, the_dilation_work_grows_with_the_radius_not_with_the_disk_area}`; existing
  `dilate_disk_tests` (vs the original gather) stay. Pure-python model of both: 348 random cases equal
  (scratchpad `a8py/dilate_equiv.py`).
- correction to the commit message: the mutation "`wt <= 0` -> `wt < 0`" is EQUIVALENT (it only appends zero
  weights). A real one: `for dx in 0..=reach` -> `1..=reach` in `dilate_disk_channels`.
- status: fixed 34f151893

### A8-06 the text caches swept on every call past 4,096 entries (A9 H15, A3-solver 38)
- file: `text3/cache/shaping_cache.rs` `shape_content` (base 952-962)
- class: quadratic-ish / waste (a thrash)
- evidence: past 4,096 entries every `shape_content` called `begin_generation`, which keeps only what was touched
  since the previous sweep = little more than the previous call. The solver calls `shape_content` twice per IFC per

  the sidebar alone would evict the map's labels.
- memory (for A9): up to ~32k paragraphs, ~40 MB at an estimated 1.2 KB per short paragraph over the three caches
  (was ~4k, ~5 MB); a Berlin view needs ~12.5k (~15 MB).
- test: `text3::cache::shaping_cache::audit_a8_tests::*` (4 tests; the last shapes 5,000 paragraphs twice per pass

## For area A5

- **Halo sizes** (from `draw_kept_text_shadow` / `text_halo.rs` `Scope::draw`): box = the run's clip rect (device px)
  + `reach` = blur radius + ceil(spread) on every side, +1 px right and below on the CPU path. Typical editor label at
  DPI 1, scale 6: 15 px font, ~10 glyphs, clip ~90 x 18 px, spread 1.2 -> reach 2: (90 + 5) x (18 + 5) = 2,185 px.
  CPU kept halo (`CpuHalo.coverage`): 1 byte/px = ~2.2 KB + ~80 B (Arc, struct, ImageMemo entry). GPU halo
  (`Kept.image`, RGBA premultiplied): 4 bytes/px = ~8.7 KB (the `AzulPixmap` is copied into the `ImageRef`:
  `pixels.data().to_vec()`, so ~17 KB transiently). DPI 2: font 30 px, clip ~180 x 36, reach 3: 187 x 43 = 8.0 KB CPU /
  32 KB GPU. Zoomed in (scale 20, 50 px font): ~300 x 60 -> ~20 KB CPU / 80 KB GPU.
  Consequence: `MAX_CPU_HALOS` 4,096 x 2.2 KB = 9 MB < 32 MB (count binds); Tuebingen 1,567 fits. GPU `MAX_HALOS`
  1,024 x 8.7 KB = 8.9 MB < 32 MB: the COUNT binds, and 1,567 labels > 1,024: with an LRU and every label drawn each
  frame in the same order, the GPU halo cache hits 0 % at steady state (cyclic access larger than the capacity) and
  the per-frame budget re-draws a bounded few per frame: consistent with H1 "labels flicker one by one". 2,048-4,096
  GPU entries at 8.7 KB = 18-36 MB.
- **`ImageMemo::insert` is O(entries) per insert once full**: `min_by_key` over all entries to find the oldest, per
  insert (`image_memo.rs` 60-89). A settle that draws 1,567 new halos into a full CPU memo (4,096) visits
  1,567 x 4,096 = 6.4 M entries (~6-20 ms, inferred); the GPU memo (1,024) the same pattern every frame while it
  thrashes. Fix: an LRU list (index-linked `Vec` + `HashMap<K, slot>`), or evict in batches (when full, drop the
  oldest 1/8 found by one `select_nth_unstable_by_key` pass: O(n) per n/8 inserts = O(1) amortised).
- Every halo key holds `font_size_px` (and quarter-pixel glyph positions): every zoom settle misses every halo, by
  design (new size = new pixels). A8-01/A8-04 make those misses cheaper; the count is A5's.

### A8-11 LCD blend per pixel (`render_glyphs_lcd`, 82 % of Berlin's text time at 7b9625951) - open
- file: agg-rust-azul 1.1.4 `pixfmt_lcd.rs` `PixfmtRgba32LcdLinear::{new, blend_solid_hspan, composite_pixel}`
  (a crates.io dependency: not changed here)
- class: waste (per pixel), serial contention (per run)
- evidence: per run `new` locks a GLOBAL `Mutex` (`coverage_tone_lut`, copies 256 B) and allocates `c3`
  (`Vec::with_capacity(256)`); per pixel `composite_pixel` computes, per stripe, `boost(c)` (LUT load, `k*c*(255-c)`,
  a division by 65,025, `min`) and `* a_fg / 255`, then six sRGB->linear loads (three of them the run's constant fg),
  three blends and three linear->sRGB loads: ~70 ops a pixel, of which ~30 depend only on (cov, a_fg, params) and 3
  loads only on the run. Under A1's band threads every LCD run of every band takes the one mutex.
- fix (proposed, exact): either upstream in agg-rust-azul (a version bump: the coordinator's / user's call): cache the
  tone LUT per thread (`thread_local!` `[Option<(u8, [u8; 256])>; 4]`), hold `c3` in a thread-local, precompute per
  pixfmt a 256-entry `cov -> boost(cov) * a_fg / 255` table lazily on the first span (or per thread keyed by
  (gamma, contrast, a_fg)), and fg_lin once; or an azul-side `PixelFormat` replica in `text_raster.rs` used by
  `render_glyphs_lcd`, its LUTs built by the identical f64 expressions (`SrgbLuts::build`, `coverage_tone_lut`: same
  `f64::powf`, same rounding), tested byte-for-byte against `PixfmtRgba32LcdLinear` on random spans, backgrounds,
  colours, stripe clips and both subpixel orders. Expected: ~40 % of the composite (inferred); the composite's share
  of `render_glyphs_lcd` is unmeasured (sort + sweep + cell copies are the rest) - measure with `AZ_PROFILE=cpu`
  spans `glyph_lcd_outline` / `glyph_lcd_sweep` first.
- status: open (not done blind: a 200-line replica whose gain is unmeasured)
