## How a hit test maps a point (after A6-01 .. A6-04)

Space names as in `audit/A2-cpu.md` `## Spaces` (L = list space of a dom, P = painted space; the window is the root
list's P). One hit tester for every backend: `CommonWindowState::perform_hit_test` -> `CpuHitTester` (`layout/src/headless.rs`).
WebRender's hit tester is not asked on any backend (see `## For area A4`).

The tester keeps, per dom, one entry per laid-out box in **static space**: `S = L + placement`, where `placement` is zero
for the root dom and `view.bounds.origin + host placement + content_offset_at_build` for a `VirtualView` child (so a
child's static space is its L moved to where its view put it when the tester was built). Each entry has a **chain**:
the frames it is painted in, outermost first. A link is one map from the space inside it to the space around it:

| link | forward (inside -> around), what the renderers paint | inverse (around -> inside), the hit test |
|---|---|---|
| `Scroll(dom, node)` | `q - s`, `s` = `ScrollManager::get_current_offset` | `q + s` |
| `Transform(dom, node, o)` | `o + M (q - o)`; `M` = `GpuStateManager::painted_transform_of` (the DRAWN value: CSS channel, else animation, else sticky), as the plane homography `[m00 m10 m30; m01 m11 m31; m03 m13 m33]`; `o` = the frame's box corner in S (`PushReferenceFrame::bounds.origin + placement`) | `o + M^-1 (q - o)`; nothing when `|det| < 1e-12` or the point is behind a perspective's eye (`w <= 1e-9`) |
| `View(child dom)` | `q + (content_offset_now - content_offset_at_build)` | `q - (...)`; the difference is read off the view's item by `sync_view_placements` before every query of `perform_hit_test` |

A chain = `[host links open at the view's item ..., View(child), the child's own links ...]`; the own links of a box are
the reference frames of its transformed layout ancestors and of ITSELF, and the scroll frames of its `ScrollChain`,
merged by the depth of each frame's box (of one box: its reference frame around its scroll frame).

window point `w` -> for each chain asked for: `p_chain = L_n^-1( ... L_2^-1( L_1^-1(w)))` (outermost link first; a chain's
point is its parent chain's point through one more link, kept for the query). An entry is hit iff `p_chain` is in its
static rect (and clip path) and, for every clip of the entry (the viewports of the enclosing views in the HOST's chain
at the view's item, the boxes of its clipping ancestors in the ancestor's own chain), the point in THAT chain is in the
clip rect: the clips as drawn. Front to back: reverse paint order within a dom, a child dom spliced in where its view's
item paints.

The forward direction (`node_rect_to_screen`, `content_rect_to_screen`, `nested_dom_window_origin`, `painted_webviews`)
applies the same links innermost first.

What callbacks are handed, and what it means under a transform:
- `CallbackInfo::get_cursor_relative_to_node()` = the hit test's `point_relative_to_item`: the pointer in the node's own
  content box, UNTRANSFORMED (the point mapped through the inverse chain, minus the box's static origin and its
  padding + border). Under a zoom a label 80 px wide still reports x in 0..80. For a node that is not under the pointer
  (a bubbling ancestor is under it, so it is fine; a captured pointer outside the node): the same mapping, outside 0..size.
- `get_node_position` / `get_node_size` / `get_node_rect` / `get_hit_node_rect`: LAYOUT values in the node's own dom (L),
  no scroll, no transform, no view placement. They do not change during a zoom.
- `get_node_hit_test_bounds`, `LayoutWindow::get_node_painted_bounds`, the a11y bounds, spatial navigation: the bounding
  box of the box's four corners painted through the frames of its OWN dom (P of that dom); for a child dom add
  `window_space_offset_of_dom` (exact while the host's frames at the view only translate; a host that scales or turns
  the view also scales the child's rect about that origin, which these callers leave out: A6-07, open).
- the hit depth, the hovered chain, `:hover`, the cursor type, tooltips: all from the same `FullHitTest`, so they
  follow the drawn picture during and after a zoom or a pan.

Hand-computed examples: in the commit message of `1f910ffbc` (four of them) and encoded in the tests named there.

## Findings

### A6-01 a reference frame's matrix was inverted about the window's corner, not about the frame's own box corner
- file:line `layout/src/headless.rs:349-382` (base: `resolve_chain`), `:321-346` (`ResolvedChain`)
- class: sign/offset (wrong-output: presses and hover land on the wrong node)
- evidence: the renderers paint `o + M (p - o)` (`raster.rs:1225-1250`, `compositor2.rs:1531-1568`), `M` from
  `ComputedTransform3D::from_style_transform_vec` = `T(-origin) M T(origin)` in BOX-LOCAL px (`core/src/transform.rs:395`).
  The chain composed the raw `M`s and applied the inverse to the window point. Right for translations (the only case the
  existing tests had: `a_transformed_box_is_hit_where_it_is_painted.rs`, `a_node_mid_slide_...`), wrong for every scale /
  rotation whose box is not at (0, 0) of the window. In the Tuebingen view: 2,118 frames, 923 turned labels: none of them
  hit where drawn (the label is hit somewhere on an arc about the window's corner). Under the editor's zoom (picture root
  `translate scale`, corner at the view's origin + content offset): every box of the view off by
  `(k - 1) x (view origin + content offset)`: 25 px at k = 1.5 and a view at x = 50. The editor's `zoom_in_progress`
  workaround (a press during a zoom does nothing) exists because of this.
- fix: `HitChainLink::Transform` carries the frame's corner; `frame_to_local` / `frame_to_screen`. Independently found by
  A2-cpu (A2-cpu-03): the two derivations agree.
- test: `a_frame_is_painted_and_hit_about_its_own_corner`, `a_turned_label_in_a_zoomed_and_panned_view_is_hit_where_it_is_drawn`,
  `a_frame_that_cannot_be_inverted_is_hit_nowhere` (headless.rs); `drawn_is_hit::*` (audit_tests/a6.rs: the CPU rasteriser
  against the tester, pixel by pixel)
- status: fixed `1f910ffbc`

### A6-05 a query still inverts one link per distinct chain of a shown dom (one per turned label)
- file:line `layout/src/headless.rs` `dom_hits` (the loop over `index.groups`)
- class: waste (O(turned labels) per query, about 60 - 80 ns each: 2,118 x 70 ns = 0.15 ms in the Tuebingen view)
- evidence: a chain group's boxes can only be skipped once the point is in the group's space, which needs the frame's
  LIVE matrix (one `painted_transform_of` look-up). An index of the groups in their PARENT's space (the label frames in
  the picture root's space) would make it O(log n), but it depends on every label's matrix and must know when one
  changed. `GpuValueCache`'s value maps are public fields written from about ten places (`window.rs`, `gpu.rs`,
  `solver3/mod.rs`); there is no change stamp. A stamp bumped by hand at every writer is the kind of fix one missed call
  turns into a wrong hit, so it is not done blind.
- fix (proposed, for a session that can run the tests): make the three value maps private behind setters that bump a
  per-cache epoch; the tester caches each group's bounds in its parent's space with the epoch.
- status: open: needs a change stamp on the GPU values (A2-gpu owns `gpu_state.rs`; `core/src/gpu.rs` is A3-core's)
