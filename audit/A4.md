## The frame, per trigger

Threads: UI thread (callbacks, layout, translation, transaction, then `renderer.update` + `renderer.render` + swap);
scene builder thread; render backend thread (RB); 8 `WRWorker#` rayon threads (glyph raster only; `init.rs:511`);
low-priority scene builder (unused). On every shell the UI thread sends the transaction and then waits in
`flush_scene_builder` until the scene builder AND the render backend have processed it (see Stalls 1): a frame is
strictly sequential, UI -> scene builder -> RB (+ workers) -> UI. One frame per vsync at most on macOS (`request_frame`
+ frame pacer + display link tick, `macos/mod.rs:10503`, `:5851`), not one per event.

n: I = items of the view's list (17,495), F = reference frames (2,118 then; about 924 after the editor's `placed`
change: one per turned label, two spatial nodes each), K = bound values of all DOMs (one per CSS `transform` node:
about F), N = layout nodes (12.5k Berlin), P = primitives in view, T = overlay images.

## Findings

### A4-01 the dynamic properties pile up in WebRender (leak, and per-frame work that grows with every frame)
- file:line: `dll/src/desktop/wr_translate2.rs:2257` (`synchronize_gpu_values`), `webrender/core/src/scene.rs:55-110`.
- class: leak + quadratic (in the number of changed frames). The same finding as A2-gpu-02; verified independently.
- evidence: azul sends the FULL set with `append_dynamic_properties` whenever one value changed; the fork's
  `SceneProperties::add_properties` extends `pending_properties`, which only `reset_properties` empties, and azul
  never sent `ResetDynamicProperties` (no caller of `reset_dynamic_properties` in the repository).
  `flush_pending_updates` then compares pending with current, clears three hash maps, inserts every pending value
  (later duplicates win, so the picture was right) and clones the list. K values of 72 bytes: zoom step f leaves f x K
  values. After 10 s of zooming at 60 Hz with K = 2,000: 1.2 M values, 173 MB in two copies, 1.2 M hash inserts +
  86 MB copy per frame on the RB while the UI thread waits. Never freed. Also grows on every scrollbar fade frame and
  on every full transaction (`invalidate_submitted_digests` makes the set "changed").
- fix: `txn.reset_dynamic_properties()` before the append.
- test: webrender `scene::audit_a4_tests::appended_properties_pile_up_unless_the_host_resets_them_first`, dll
  `audit_tests::a4::a4_01_changed_gpu_values_replace_the_set_webrender_holds`.
- status: fixed `85d19c71a`.

### A4-02 every zoom step rasterises every visible glyph again; every turned label has glyphs of its own
- file:line: `webrender/core/src/prim_store/text_run.rs:260-270` (`update_font_instance`), `:340-350`,
  `webrender/core/src/prepare.rs:461-507`, `webrender/core/src/resource_cache.rs:1126-1159`,
  `webrender/glyph/src/font.rs:119-248` (the rasteriser), `rasterizer.rs:479-482`, `core/src/renderer/shade.rs:537`,
  `core/src/batch.rs:1192`, `:1234-1300`.
- class: waste (the largest term of a GPU zoom step by reading), and wrong bounds in the batcher.
- evidence: a run whose prim-to-raster transform is more than a translation asked for glyphs rasterised under the
  transform (`transform_glyphs`); the glyph cache keeps a glyph by the font instance WITH that transform. The fork's
  rasteriser never reads the transform: it draws at the font's size, returns `GlyphFormat::Alpha`, and the shader
  variant is chosen by the glyph's format (no `GLYPH_TRANSFORM`), i.e. the upright bitmap is drawn through the
  matrix. So: a new scale of the picture root = a new font instance for every run = every glyph on screen rasterised
  on the workers (`resolve_glyphs` blocks the RB) and uploaded again, bit for bit the same (est. 10k per step on
  Tuebingen, 15-40 ms inside `gpu wait`; several times that on Berlin); 923 turned labels = 923 glyph sets; and
  `batch.rs` computed a `TRANSFORM_GLYPHS` run's bounds as if its bitmaps stood upright in device space, which is not
  where the shader draws them (the bounds decide which batches may be merged: a draw-order hazard for turned and for
  zoomed labels against their halos; not proven to have misordered anything).
- fix: `glyph_raster_mode` (the decision as a function) never asks for transformed glyphs: one font instance and one
  glyph set for a run under any 2D transform. Offsets stay unsnapped where they were (`drawn_through_transform`), glyph
  keys are the same (azul sets no subpixel positioning): no pixel changes by reading.
- test: webrender `prim_store::text_run::audit_a4_tests::no_2d_transform_asks_for_glyphs_rasterised_under_it`.
- status: fixed `56bb92351`. History: a first fix (`e921c2d65`: mark the moving transform with the fork's pinch-zoom
  switch, a settle timer, a forced tile invalidation) treated the symptom and was reverted (`fdb45f0a6`) when the
  rasteriser turned out to ignore the transform.

### A4-03 WebRender's hit tester is fed and rebuilt, and nobody asks it
- file:line: `compositor2.rs:545`, `:675`, `:826`, `:1116`, `:1202`; `webrender/core/src/render_backend.rs:573-580`,
  `:1563`, `:909`; `hit_test.rs:273-307`; the one hit tester: `shell2/common/event.rs:4107`.
- class: waste, per frame O(spatial nodes) and per translation O(hit areas).
- evidence: 3,703 of the view's 17,495 items are `HitTestArea`; each was serialised, put into the scene's
  `HitTestingScene`, and after every scroll offset or property change the RB ran one more `update_tree` and copied two
  world transforms per spatial node into a hash map (`read_spatial_tree`). `common.hit_tester` is only ever assigned.
- fix: the translation pushes hit-test items only with `AZ_WR_HIT_TEST=1`; a hit tester of a scene without items reads
  nothing; `rebuild_hit_tester` does not update the tree for it.
- test: dll `compositor2::audit_a4_tests::a4_03_hit_test_areas_are_not_sent_to_webrender`, webrender
  `hit_test::audit_a4_tests::a_scene_without_hit_test_items_reads_no_spatial_node`.
- status: fixed `af69be285`. Left: `request_hit_tester(..).resolve()` at window creation (`macos/mod.rs:6638`) blocks
  the UI thread once on the RB (Stalls 5); the field and `AsyncHitTester` are A6's to remove.

### A4-04 the frame clock counts a frame twice: the recorder's "interval" is the renderer's time, its work 0
- file:line: `layout/src/window.rs:824-841` (`note_present`), `:2964`, `:2992`; callers `wr_translate2.rs:1989`,
  `:3005`, `:3162`, `layout/src/cpu_backend.rs:334`; `macos/mod.rs:9693`, `:9948`, `headless/mod.rs:1799`,
  `e2e/runner.rs:4076`.
- class: wrong-output (of the measurement: `get_frame_timings`, `MAPEDIT3_FRAMES`).
- evidence: `note_frame_presented` (frame handed over) and `record_frame` (frame drawn) both ticked the clock. On
  macOS, both backends, per frame: `frame_count` +2, `frame_interval_us` = time between the two calls of the same
  frame (flush + draw on the GPU path, the paint on the CPU path), `frame_work_us` = 0. The table of the binaries
  `mapedit3-a74d11c` / `mapedit3-azul03bd2e7` therefore shows the renderer's time per frame in its mean / p50 / p95
  columns, not the frame rate, and `missed` = frames. X11 / Wayland / Win32 GPU were right (no `record_frame`).
- fix: `FrameClock::note_rendered` (called by `record_frame`): same frame, not counted again, work extended to the draw.
- test: layout `audit_tests::a4::a4_04_a_frame_noted_and_then_recorded_is_one_frame`,
  `a4_04_a_window_counts_a_noted_and_recorded_frame_once`.
- status: fixed `c54650199`. IMPORTANT for the user's pending run: a table taken with a binary before this fix must be
  read as "mean = flush + draw per frame" (still useful: it is `gpu wait` + `gpu draw`).

### A4-07 `synchronize_gpu_values` copied and sorted every bound value on every frame
- file:line: `wr_translate2.rs:2127-2239`, `gpu_state.rs:209-251`. A9 H7.
- class: waste, per frame O(K) with 6 allocations (320 KB at K = 2,000) and a byte-wise FNV.
- fix: first walk sums one hash per (kind, key, value) and counts, no allocation; only a changed set is collected.
  Contract with the fork stays "the whole set, reset then append" (decided with A4-01: a delta message would need a
  second code path in `SceneProperties` that keeps its two lists in step; the reset makes WebRender's side O(K) per
  CHANGED frame only).
- test: dll `audit_tests::a4::a4_07_the_digest_of_the_bound_values_sees_a_swap_and_not_the_order`.
- status: fixed `39a77728b`. Still O(K) per frame for the walk: see For area A2-gpu / A3-core (write generation).

### A4-08 pan and zoom draw every tile of the map again (the picture cache does not serve them)
- file:line: `wr_translate2.rs:2072-2096` (the view scrolls on `ExternalScrollId(0, child pipeline)`),
  `compositor2.rs:1545-1556` (`is_2d_scale_translation: false`), fork `spatial_tree.rs` `find_scroll_root`
  (a `PipelineRoot` frame is never a scroll root; a non-2D reference frame forgets the roots below it),
  `picture.rs:7040-7100` (a slice keeps its tiles through a zoom only when the SLICE is under the zoomed node).
- class: waste (architecture). Per pan frame and per zoom step: P prims prepared and batched on the RB (est. 3-8 ms for
  17.5k items) and all map tiles rasterised on the GPU, where a slice of its own would be composited at an offset
  (pan) or kept and scaled (zoom with `low_quality_pinch_zoom`).
- fix (designed, not done): the view's child list gets an explicit scroll frame of its own (a real `define_scroll_frame`
  with the view's extent, scrolled by `scroll_all_nodes` instead of the pipeline root), and a frame whose transform is
  only ever a translation + scale is declared `is_2d_scale_translation: true` (needs the engine to know that: the
  matrix must be checked on every value, and the list re-translated when it stops being true). Then WebRender gives
  the map its own slice: pan = tile reuse + the exposed strip, zoom = `ReferenceFrameKind::Zoom` semantics.
- test: `gpu draw` and `fbuild` per pan frame before / after; a scene test in the fork (slice count, tiles valid after
  a scroll of the view).
- status: open: needs a measurement first (the counters), then a design pass with A2-gpu (matrix promises) and the
  editor (the picture root). The cost it leaves is visible as `fbuild` + `gpu draw` on pan frames with `scenes` = 0.

### A4-09 a tile arriving in place re-translates the view's list and rebuilds the scene
- file:line (base): `layout/src/window.rs:11518` (`patch_display_list` -> `Arc::make_mut`), `gpu_state.rs:401-418`,
  `wr_translate2.rs:3082-3091`, `:1494-1500` (new slot -> `force_all`); editor `tiles.rs:294-300`, `map.rs:718`.
- class: waste. severity: high (est. 15-40 ms per arriving tile, up to 25 a second while tiles come in).
- evidence: two mechanisms. (1) A slot gets its stable key with the FIRST picture that replaces the node's image
  (`plan_overlay_image_uploads`: `new_slot`), and a new key must be named by the list: `force_all`, every list of the
  window translated (I = 17,495 + the host) and the scene built. In the editor EVERY arrival is a first one: a tile
  that is being drawn is a node with a shared transparent 512 px picture, and its tile arrives once per view. (2) For
  a later picture of the same node the patch moves the list to a new allocation (`Arc::make_mut` against the
  renderer's `Weak`), `display_lists_unsubmitted` sees another allocation, and the list goes again although the
  renderer's copy says the same (same key, same rect).
- fix, three parts:
  - GPU side (`93aeb0a41`, done): a node that shows a NULL image (`ImageRef::null_image`: a size, no pixels) is given
    the key of its slot in the scan, showing one clear pixel (`reserve_image_places`, `ImageRefHash::PLACE`), and the
    translation paints it from that key. The first picture is then `update_image` like every later one. New
    `RendererResources::node_image_is_replaced_in_place` and `GpuStateManager::display_list_moved` for the layout side.
  - layout side: A3-window calls the two (the exact lines are in the section For area A3-window). Until then the
    patched list is still sent (correct, as before; mechanism 2 stays).
  - editor: a tile being drawn shows a null image (the exact line is in the section For area A7-editor). Until then
    mechanism 1 stays for the editor (a transparent picture is no place).
- test: dll `audit_tests::a4::a4_09_a_tile_that_arrives_is_new_pixels_under_the_key_its_place_has` (calls the two
  functions the way A3-window's lines do: 0 lists, 0 items, 1 update, 0 adds per arrival).
- status: fixed `93aeb0a41`

### A4-11 the image key of a GL texture slot can collide with an image's key
- file:line: `gl_texture_cache.rs:58-66` (`(dom << 32) | node`), `wr_translate2.rs:3272-3275` (`ImageKey { key:

- evidence: the texture of node n of DOM 0 gets key n; the n-th `ImageRef` ever created gets key n too. Both in one

### A4-23 what a hover (a patch of one node) costs on the GPU path, and what it would have to be sent as
- asked by A3-window after its node patch (`25cf3821f`). Read, nothing fixed here beyond A4-22.
- the path: the patch moves the view's list to a new allocation; the event result is
  `ShouldUpdateDisplayListCurrentWindow`, which macOS turns into `display_list_dirty` (`macos/mod.rs:404`): `drawRect:`
  regenerates the ROOT list (`:9476`) and takes the FULL transaction: three scans of every list for resources
  (est. 1 ms together at 17.5k items: small), translation of the patched list (O(I), est. 3-8 ms), the root list
  again, a scene build of every pipeline (est. 10-30 ms) and a frame build, with the UI thread waiting.
- already there: a list is its own pipeline and only lists that are not held are translated and sent
  (`display_list_is_held`: `Arc` identity); a patched list sent alone is what the LIGHTWEIGHT transaction does
  (`display_lists_unsubmitted`, `wr_translate2.rs:3082`), without the scans and without the root regeneration.
- not possible in WebRender: an item-level update of a list, or a scene build of one pipeline (any `SetDisplayList`
  rebuilds the scene of the document: `scene_builder_thread.rs:579`, `:603`). So a patch that changes a LIST costs
  O(I) translation + O(all items) scene build whatever azul does; the scans are the small part.
- what removes the cost: the hover must not change a list. The editor's rule is a background colour

## Stalls: where the UI thread waits for the GPU side (ranked by ms x frequency, est.)

1. `flush_scene_builder` after EVERY transaction (`macos/mod.rs:9857`, `common/layout.rs:2109`, x11 / wayland / windows
   the same): `rx.recv()` returns when the scene builder has built the scene AND the render backend has built the frame
   (the flush travels scene builder -> RB's queue behind the transaction: `scene_builder_thread.rs:314`,
   `render_backend.rs:1196`). The UI thread is idle for the whole scene build + frame build + glyph raster of every
   frame: `gpu wait`. It is what makes the frame drawn in the same `drawRect:`; the price is that nothing overlaps.
   The alternative exists in the code (`Notifier::wake` -> `drain_loop_work` -> `frame_waiting` -> a pass that only
   draws the published frame, `macos/mod.rs:10187-10209`): send, do not flush, draw when woken. Not changed blind:
   the GL texture and epoch bookkeeping after `render` assumes the frame of this pass, and a value transaction could
   then overtake a scene transaction (resource order no longer depends on the flush: A4-24).
2. `renderer.update()` + `renderer.render()` on the UI thread (`macos/mod.rs:9872-9885`): texture uploads of every new
   image and glyph (`update_texture_cache`), shader compiles at first use, all draw calls: `gpu draw`.
3. Text halos drawn on the UI thread inside the transaction (up to 2 + 12 ms per frame, `wr_translate2.rs:674-676`),
   for as many frames as it takes: `res ms`. A5.
4. `gl_context.flushBuffer()` (`macos/mod.rs:9957`): the swap; with the context's default swap interval it should not
   wait for vsync (`configure_vsync` is a no-op, `:5677`), the window server may still throttle it. Not in any column
   of mine: `interval - work`-style arithmetic does not isolate it; A10.
5. `request_hit_tester(..).resolve()` once per window creation (`macos/mod.rs:6638-6640`): a `recv` on the RB.
6. A scene builder panic (A4-06) would turn stall 1 into a crash: `recv().unwrap()`.

## For area A5 (the flicker): what the GPU path does with halos and with image keys

Read, not run. The sequence below fits "labels flicker one by one" on a view with more labels than `MAX_HALOS`.

1. **Every halo drawn re-translates every display list and rebuilds the whole scene.**
   `translation_env` (`wr_translate2.rs:2827`) is `(scale << 32) ^ halos_drawn()`, a process-wide count
   (`text_halo.rs:115`, thread-local, all windows). `display_list_is_held` (`gpu_state.rs:382`) compares it for every
   DOM. So a scan that drew ONE halo makes `submit_display_lists` translate and send the host list and the view's
   17.5k items again (`wr_translate2.rs:2888`), WebRender rebuilds the scene of every pipeline
   (`scene_builder_thread.rs:549-604`: any `SetDisplayList` sets `rebuild_scene`), and the UI thread waits for it
   (Stalls 1). A follow-up frame (`halos_owed`) therefore costs: scan of all lists for images
   (`images_in_display_lists`) + `text_halos` over all lists TWICE (once with fonts in
   `collect_image_resource_updates_and_halos_left:772`, once per translated list in `compositor2.rs:315`) + up to
   12 ms of halo raster + full translation + full scene build + frame build. That is the price of each "one more
   label got its halo".
2. **A view with more shadowed texts than `MAX_HALOS` (1,024) never converges.** `ImageMemo` is an LRU
   (`image_memo.rs:60-90`). A scan asks for the halos in list order. With 1,567 texts and 1,024 kept: the first miss
   draws a halo and evicts the least recently used entry, which is the next kept halo further down the list (it was
   touched last in the previous scan, everything before the miss was touched in this one). When the scan reaches that
   one it is a miss again, and so on: a cascade down the list until the budget (2 free + 12 ms) is used up; the rest
   is deferred, `halos_owed` stays true, the next frame continues. Net: every frame D halos appear and D others
   disappear, the hole of 543 labels walks through the list, for `HALO_FOLLOW_UPS_MAX` = 900 frames (15 s at 60 Hz)
   after every scan that starts the chain, and then it stops with about a third of the labels without a halo until
   the next rebuild starts it again.
3. **What a label without its kept halo looks like**: the translation falls back to `builder.push_shadow`
   (`compositor2.rs:2248-2275`) with `blur_radius` only: WebRender's shadow has no spread (the comment at
   `text_halo.rs:299-301` says so). A spread-only halo (`blur 0, spread > 0`, an outline) becomes a plain copy of the
   text under the text: the label loses its outline for as long as its halo is not kept. That is the visible
   flicker: outline there / not there, label by label, D per frame.
4. **Image keys of evicted halos**: an evicted halo's `ImageRef` leaves the memo, so it is no longer in the live set
   of `register_image_resources`; `collect_stale_image_deletes` deletes its key 3 epochs later (`now - last > 2`).
   Epochs advance once per transaction that sends lists, i.e. once per follow-up frame here. When the cascade draws
   the same label again it is a NEW `ImageRef` (new id, new key, new upload). So the thrash is also one `AddImage`
   (upload) and one `DeleteImage` per halo per frame: the columns `res add`, `res del`, `uploads`.
5. **Delete / add ordering (H3)**: checked, fine. All resource updates of a transaction are applied by the render
   backend in push order, after the scene of the same transaction is swapped in and before its frame is built
   (`render_backend.rs:1375`, `process_transaction` -> `update_document`). The order azul pushes: overlay texture
   add/update (`register_overlay_textures`), font deletes, font adds, overlay raw add/update
   (`upload_overlay_images`), image GC deletes, image adds (`wr_translate2.rs:1276-1418`). A delete only names a hash
   that no current list names (the live set is recomputed from the current lists in the same call), and every list
   that changed its halos is re-translated in the same transaction (item 1), so no list WebRender holds names a
   deleted key. Tiles replaced in place keep their key (`update_image`): no delete at all.
   One hole, not on the editor's path: the halo memo is per thread, not per window. Window A's scan can evict a halo
   that window B's held list names; B's key is deleted only by B's own scan, which re-translates first, so still no
   dangling key, but B shows the fallback until its next transaction.
6. **Keys**: `Scope::key` hashes glyph positions relative to the first glyph in 1/64 px and the clip / ink rects, the
   blur, the spread and the dpi (`text_halo.rs:384-409`): stable under a pan and under a re-render at the same scale.
   A re-render at another scale (every zoom settle) changes the font size, so every halo is a new key: 1,567 draws
   after every settle, at D per frame.
7. **H2 (glyphs under a transform)**: real, but it is a cost, not a flicker: the RB waits for the glyphs inside the
   frame build (`resolve_glyphs`), no frame is shown without them. A4-02 (fixed). One thing of it could have drawn
